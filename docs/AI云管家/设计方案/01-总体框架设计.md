# 01 总体框架设计

> AI云管家 = 平台底座（现有安巡云资产）+ 业务模块（巡检/工单/设备/收费/智控…）
> 核心原则：**模块化单体、按可拆标准写、不拆微服务**。

## 1. 为什么不拆微服务

| 维度 | 现状判断 |
|---|---|
| 部署形态 | 甲方私有化部署（单台服务器 docker-compose），微服务运维成本甲方接不住 |
| 团队规模 | 开发团队小，微服务的联调/分布式事务成本是净亏损 |
| 业务阶段 | 功能探索期，模块边界还在快速变化，过早固化服务边界会被反复打脸 |
| 性能 | 继续模块化单体；容量需按 09 §5 的负载预算实测，不以小区数量直接承诺性能 |

**但按"将来可拆"的标准约束现在**——具体规则见 §1.1（领域地图 + R1~R7 + 拆分预案），一句话：一域一包、跨域只走公开接口与事件、表只归一个 owner、跨域只存 ID 不加 FK。

### 1.1 领域地图与边界纪律（目标，需逐步改造）

现有模块存在跨域 model import、直接读表和 mp 业务规则，不宣称已解耦。下表是 owner 目标；“新建”不代表代码已有。输出分组由 report 拥有，采集分组属于 inspection，两者独立映射。

| 域 | owner 与状态 | 公开契约目标 |
|---|---|---|
| inspection | 已有点位/模板项/采集分组/绑定/计划/任务/正式记录/草稿，需改 | 批量候选模板查询、计划选用集合校验、任务上下文、已审核事实分页读取；同类型多套与计划显式选择本期完成 |
| equipment | 已有设备/维保流水/L2 资产字段方案，需改 | 类型规则/台账摘要/已确认维保事实；维保确认事务才更新有效日期 |
| workorder | 新建事项/工单/关联（04） | 幂等接收已审核异常，抢单/分派/审核命令，状态批量查询 |
| acceptance | 新建批次/矩阵记录/清单 schema 与记录（05） | 批次与已确认问题/交接事实读取；清单归本域，不借用 equipment schema |
| report | 已有报告/计划；新建 doc_template、输出分组、report_file、生成任务 | 创建任务/冻结待审件/签字归档/文件查询；有持久状态，不是无状态域 |
| stats | 已建 `stats_task/stats_checkin/stats_config_alert` 投影（00110），任务变更同事务同步、支持全量重建 | 本域投影/汇总表，只读公开 DTO，不写源域表；记录来源/水位/延迟，可重建 |
| system/auth/community | 已有账号/角色/菜单/字典/配置/小区楼栋，审计需补 | 认证授权/数据范围、租户与字典批量查询；底座也经契约而非任意读表 |
| file | 已有 upload_file（当前 model 位于 system），需收口 owner | 租户+用途授权的上传/读写/派生文件引用；物理迁移前清点引用 |
| ai | 已有 pkg/ai 和 mp 中 Redis job，需抽象 | Provider 与识别任务接口；识别任务不等于可靠领域事件 |
| mp | 已有 App 通道层，需移出业务规则 | 只做协议/DTO/认证上下文适配，调用业务公开命令/查询 |

| # | 可执行规则与核验 |
|---|---|
| R1 | 公开接口集中 `service/api.go` 或域专用 contract 包，输入显式 `context + TenantScope + actor/data scope`，批量 DTO、分页、错误码、锁定/一致性语义明确；不暴露 GORM/model/任意 map |
| R2 | 禁止跨域读表/Join/Preload/import model；report 装配调用已审核事实读接口，stats 走自有投影。存量违例逐条登记与移除，不靠改包名证明解耦 |
| R3 | 跨域仅存 ID，不加新跨域 FK；域内可用 FK。入口校验引用归属与状态，删除限制/作废/失联对账由 owner 契约处理，不假设事件自动保全引用 |
| R4 | 展示冗余标来源 ID、事实时间和同步水位；同域事务强一致，跨域投影最终一致。报告冻结时记录读取边界/事实清单，检测源数据变化后拒绝冻结或重装配，禁止拼接不同审核状态 |
| R5 | 跨域状态联动按 §4.1 的生效点组织：**当前阶段同事务 + 业务唯一键**，不经队列；真异步的外部副作用（通知/AI/渲染）走 §4.3 的任务队列。同步查询/校验调公开接口。事实入参/payload 自包含业务必需信息（文件存受权 ID 非公网 URL）；补充查询仅经接口，不能用当前状态替代历史事实 |
| R6 | 共享内核限基础类型/时间/错误/基础设施；业务 DTO 由提供域 contract 拥有，消费方可映射自己的视图，不复制业务规则；Provider 是基础设施边界而非允许裸读的共享业务层 |
| R7 | 表唯一 owner，迁移注释标 `-- owner: <域>`；跨域投影用不同表名并标来源。CI 计划检查 import/SQL/table owner 清单与契约测试，不以表名前缀猜 owner |

未来是否拆服务由运行成本决定：可先评估 report **渲染 worker** 和 IoT，再评估工单/巡检；report 主记录、文件、签字、任务均有状态，需要单独迁移方案。传输切换必须重新设计超时、认证、序列化、重试、契约版本与部署事务，不能承诺换适配器业务零改动。自检看边界违规清单、契约/租户负例、批量查询与投影重建测试，不用"拷包零编译错误"衡量耦合。

**三类依赖要分开治，代价差很多**

1. **底座常量与字典**（占 system 那 43 个类型的大头）：`AIGatePass`/`FlowCheckinReview`/`StatusEnabled`/`DefaultTenantCode` 这类枚举常量被 7 个域引用。这**不是领域耦合**，是共享内核缺位——按 R6 应下沉到 `pkg/types` 或各域自有常量，不需要建契约包。**先做这一类，能一次性消掉大部分 import 计数**，且几乎零风险。
2. **真业务读取**：report/stats/mp 读 inspection 的打卡事实、report 读 equipment 的维保流水。这才是 R1/R2 要的契约包，也是 08 §1 要求"report 通过公开 API 取数"的那部分。
3. **底座表直读**：各域直接查 `SysUser`/`SysRole`/`Tenant`/`UploadFile`/`SysDictData`。这类走 system/file 的查询接口即可，但面广（7 个域），建议随 1.10 安全补齐一起做——因为租户校验本来就要在这些入口统一。

**施工顺序建议**（与 06 期次对齐）

| 步骤 | 范围 | 风险 |
|---|---|---|
| ① 常量下沉 | 第 1 类，`pkg/types` + 各域自有常量 | 低，纯移动 |
| ② `inspection` 契约包 | 暴露已审核事实的分页读取、任务上下文、模板候选查询；改掉 report/stats/mp/equipment/community 共 13 处读表 | 中，report 取数逻辑需重写 |
| ③ `equipment` 契约包 | 暴露台账摘要、已确认维保事实；改掉 report 1 处 | 低 |
| ④ `system`/`file` 查询接口 | 账号/角色/租户/字典/文件，随 1.10 一起 | 中，面广但逻辑简单 |
| ⑤ `mp` 退回通道层 | 19 处跨域依赖降到只依赖各域契约；业务规则迁回 inspection/equipment | **高**，`checkin_service.go` 1300+ 行，且 03 §5 列的旧行为（pending AI 放行、空流程直通、围栏缺坐标跳过）都在这里 |

⑤ 是单项最大的一块，但也是收益最大的：mp 按定位只应做"协议/DTO/认证上下文适配"，现在却是业务规则的实际所在地。建议它**单独成项**，不要混在契约层改造里一起评估工期。

### 3.2 模块注册机制（解耦的关键）

目标是新建模块显式注册机制：业务模块在两端描述菜单/权限/入口，平台壳按注册信息装配。现有菜单配置可复用，但注册与待办契约仍需实施和回归，不承诺新模块壳零改动：

**后端**：模块注册表（代码内显式注册，非动态插件）
```
模块 = {
  code: 'workorder',
  name: '工单',
  权限点: ['workorder:list', 'workorder:claim', 'workorder:assign', 'workorder:finish', 'workorder:review'],
  菜单(PC): [{ path, title, icon, perm }],
  入口(App): [{ key, title, icon, area, perm, badge: () => 待办数, surface }],  // area=业务分区（巡查维保/工单整改/品质管理/管理中心），决定图标配色；surface=workbench 分区宫格 | home 待办 | home 常用
}
```
- 权限点随模块注册进角色管理；PC 菜单、App 主页分区宫格与更多页宫格、待办角标全部由注册表驱动。**图标配色由 `area` 统一派生**，同一功能在主页与更多页同色，颜色不承担"是否可用/是否危险"的含义（02 §7）
- 新模块至少增加注册项、路由实现、权限/菜单迁移和契约回归；超出既有入口能力时仍需修改壳并评审

**前端 PC**：复用现有配置化菜单，改为与显式注册表的路由/权限一致校验，工作量以实施盘点为准。

**App**：首页分区宫格、全部功能目录页宫格均从注册表 + 权限过滤渲染，配色由 `area` 派生（02 文档 §2/§3/§7）。

## 4. 跨域事实联动（事实边界本期必做；事件设施按部署形态演进）

> **本节已按"过度设计"复盘修订。** 原稿要求本期手写 outbox + 逐订阅者 delivery + 租约 + fencing token + 去重表 + 死信 + 授权重放，并作为上线门禁。复盘结论：8 个联动点的生产方与消费方**在同一个进程、同一个 PostgreSQL**，用"同事务 + 唯一键"即可拿到"不丢、不重"的同等保证，不需要自建消息中间件。
>
> 修订把原 §4 拆成两件事：**§4.1 事实边界与生效点**（契约，本期必做、零额外设施）和 **§4.3 真异步任务**（用现成库）。原 §4.2 的完整持久协议降级为 §4.4「拆分时的目标协议」，不再是期1 门禁。

### 4.1 事实边界与生效点（本期必做）

名称统一 `域.对象.已发生动作`，不得在别处缩写或另起同义名。**这张表是本期的业务约束**：它规定"哪个事务里才算事实已发生、谁该跟着写什么"。当前阶段这些联动以**同事务 + 唯一键**实现，不经任何队列；名称保留，便于将来真拆分时逐条对应。

| 生效点 | 事务边界与联动动作 | 当前实现 |
|---|---|---|
| `inspection.checkin.submitted` | 正式提交事实，仅用于待审/通知；**不能入工单池** | 不产生跨域写；通知走 §4.3 异步任务 |
| `inspection.checkin.abnormal_approved` | 巡检异常审核最终通过事务；workorder 幂等创建 issue 与绑定它的待接单工单。提交、AI 初判、审核驳回不触发 | **同事务**调 `workorder` 公开契约建事项及单事项工单，唯一键 `(tenant_id, source_type, source_item_id)` 兜重复，无手工打包环节 |
| `workorder.item.finished` | 整改提交完成，进入待审核 | 同事务，workorder 域内；不是闭环 |
| `workorder.item.review_passed` | 主管审核通过并更新工单闭环投影；维保类按设备规则回写有效日期，不改巡检原始事实 | 同事务，workorder 域内；承接查验问题不进入本链路 |
| `equipment.maintenance.confirmed` | 维保流水审核/确认通过，在 equipment 事务内更新有效日期/状态并记已生效；待审/驳回不生效，重复确认不重复改台账 | **本就是同事务**（原稿也要求在 equipment 事务内生效），唯一键 `(tenant_id, batch_registration_id, batch_item_id, maintenance_action)` |
| `report.archived` | 最终签字文件与归档事务完成后广播；不是预览生成通知 | **保留异步**：渲染/转换本就是 §4.3 的任务，归档后的下游（通知、统计投影）由任务触发 |
| `iot.alert.created` | 未来期4 经规则确认的告警，按配置派单 | **保留异步**：外部输入，天然在事务之外（期4） |

巡检异常联动的入参必含租户/小区、记录与项稳定 ID/code、已审核异常事实/标签/说明、点位设备及人员展示快照、受权照片 ID、审核人和时间。维保联动携带流水 ID、设备 ID、生效日期和动作事实。文件仍须经 file 域授权，不携带长期公共 URL 或密钥。**这些要求与是否走队列无关** —— 同事务调用时它们是契约入参，异步化后它们是 payload。

### 4.2 为什么不本期自建事件设施

| 原稿理由 | 复盘 |
|---|---|
| "按将来可拆的标准约束现在" | 让未来可拆的是**契约**（§1.1 R1~R3、R7：一表一 owner、禁跨域读表、只存 ID、公开接口），不是事件总线。契约当前完成度 **0%**（无任何 `service/api.go`），而 `report` 仍直接 `db.Model(&insmodel.CheckinRecord{})`、全仓约 50 处跨域 model import。**这些不改，有总线也拆不动** |
| "拆分后换传输即可" | §1.1 结尾自己写明"传输切换必须重新设计超时、认证、序列化、重试、契约版本与部署事务，不能承诺换适配器业务零改动"。既然那天要重做，现在预建省不下工 |
| "先拆 report 渲染 worker 和 IoT" | 这两个恰好都不需要域间事件总线：渲染 worker 要的是**任务队列**，IoT 要的是**边缘队列**。见 §4.3 |

同事务写入不堵死拆分：调用点形态不变（`workorder.CreateIssue(ctx, scope, fact)`），拆分那天变的是它背后从同事务改成异步投递，而事务边界重设计本就是上面那条已承认要做的工作。

**本期的硬约束仍在**：生效点不得前移（提交、AI 初判、驳回一律不触发下游写）、跨域写必须走 owner 域公开契约而非直接改表、每个联动必须有业务唯一键、并发与重复提交须有测试。这些是正确性要求，和实现方式无关。

### 4.3 真异步任务（用现成库，不自建）

确实进不了 DB 事务的只有**外部副作用**：通知推送、AI 识别、LibreOffice 渲染/转换、文件写入与派生。这类需要的是**任务队列**，不是领域事件总线。

选型结论：**引入 `riverqueue/river`**（PostgreSQL 原生任务队列）。理由是原 §4.2 列出的需求基本就是它的既有能力，没有自写的价值：

| 原稿要求 | River 对应能力 |
|---|---|
| 业务事实与投递意图同一事务提交 | `InsertTx(ctx, tx, args, opts)` —— 与业务写入同一 pgx 事务，回滚即不入队 |
| 稳定幂等键、重复不重复执行 | `InsertOpts.UniqueOpts{ByArgs, ByPeriod, ByQueue, ByState}`，重复入队返回 `UniqueSkippedAsDuplicate` |
| 退避重试、上限后死信 | `MaxAttempts` + 内置退避；超限转 `discarded` |
| 租约、崩溃接管 | 内置（任务领取与超时接管由库负责） |
| 死信排查与重放 | River UI |

落地要求：跑在同一个 PG 实例上，与业务共用事务；队列按用途分（`notify` / `ai` / `render`），各自设并发上限；**渲染队列全局并发受 09 §4.3 的 LO 隔离约束**。现有 Redis AI 队列在期1 一并迁到 River，减少一套需要自己维护恢复语义的队列（Redis 继续用于会话/黑名单）。

**不引入 Watermill**：它提供的是路由与中间件抽象，SQL adapter 给 pub/sub，但 outbox 与消费端去重事务仍需自写 —— 加一层抽象而不消掉难的部分。也不引入 Kafka/NATS/RabbitMQ。

### 4.4 拆分时的目标协议（当前不实施）

真出现第二个进程（最可能是 report 渲染 worker 或期4 IoT）时，跨进程的那条边才需要下列协议。**本节是那天的设计输入，不是期1 门禁**：

- **Envelope**：`event_id`（全局唯一、重试不变）、`event_type`、`schema_version`、`tenant_id`、`aggregate_type/id`、`aggregate_seq`、`occurred_at`、`producer`、`correlation_id`、`causation_id`、`payload`。业务事件租户必填，平台事件显式 `scope=platform` 并白名单，不以空租户推断超管。
- **生产事务**：源业务事实和 outbox 同一事务提交；回滚不留事件。以聚合序号/业务唯一键防重复事实，不只依赖随机 event_id。
- **投递与持久消费**：至少一次。每个稳定 subscriber 的 delivery 持久登记，唯一键 `(tenant_id, subscriber, event_id)`。
- **ACK 边界**：收到消息/调用 handler 不算成功。消费者在持久事务中同时完成去重登记、业务写入、delivery completed，commit 后才 ACK。
- **重试/死信/并发**：退避加抖动；永久错误与未知 schema 直接死信并告警；人工修复后按租户与订阅者授权重放，保留 event_id 与审计。租约可续期、超时接管，完成更新带 owner + fencing_token。
- **留存**：去重与死信重放窗口协调，窗口内不删去重标记；禁止清表治积压。

届时优先评估能否直接用 River 的跨进程能力承载，而不是先自写 relay。

## 5. 多租户与品牌

- 保留现有租户与权限能力，按 09 §4 补齐隔离缺口并验收；AI云管家品牌（名称/logo/启动页/推送文案）走租户级品牌配置 + 平台默认值，不写死
- "使用层级过多"整改：用户登录云管家后直接使用各模块，无二级账号体系（现状已满足，重点是 App 壳整合，见 02 文档）

## 6. 数据互通原则（对齐纪要"统一管理"）

- 同一域内强一致（事务）
- **跨域联动当前也在同一事务内完成**（单进程单库，§4.1）；真正最终一致的只有外部副作用（通知/AI/渲染，§4.3）与 stats 投影
- 拆分出第二个进程后，那条边才转为最终一致（§4.4）
- 无法/无需互通的模块（如未来的智宣素材库）独立运行，但**租户、账号、权限、消息、文件必须走统一底座**——这是"纳入整个系统统一管理"的落点
