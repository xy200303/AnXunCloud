# 02 App 框架与 UI 布局

> 状态：改造评审设计，不代表当前 App 已实现。业务状态以 03/04/05/07 为准，输出状态以 08 为准。
> App 以 `../APP原型/预览/v2/` 最新画板为视觉基线；本文同步已经确认的新交互原则与业务分工，旧文档、旧画板中的冲突描述不再作为施工依据。
> 保留现有 uni-app / uni-ui 和 PC Vue / Element Plus 技术栈，不为换皮引入第二套组件库，不为旧 UI 留兼容实现。

## 1. 产品壳与入口

- 五 Tab 固定为 **AI助手 / 主页 / 卷宗库 / 社区 / 我的**，无中央加号。
- AI助手：对话区域，可命令 AI 完成工作（agent 调用封装为工具的系统增删查改能力）；主页：项目范围、通知、看板与分区功能卡；卷宗库：所有台账与报告的统一归档入口（最近查看 + 八大分类）；社区：后续业主端的四个板块——**物料资源**（物业材料采购与采购招商）、**智慧产品**（公司产品宣传）、**便民集市**（小区周边商业与便民服务信息平台）、**邻里交互**（业主交流信息发布）；发布内容同步业主端展示，规划中随业主端开放；我的：个人记录、设置与账号操作。**通知不占 Tab**：通知公告以主页滚动通知条呈现，通知列表页保留、从滚动条进入。主页不再放 AI 输入入口，AI 入口就是 AI助手 Tab。
- 扫一扫固定在**主页顶栏右侧**，与消息入口并列；不在首页宫格重复，不占系统安全区。二级页左上保留返回，不重复堆放扫码。打卡、工单核验、设备查询复用同一个扫码页，由入口参数区分用途。
- 不展示大号品牌字与 slogan。应用名、图标可体现品牌，内容区不重复宣传。
- 主页按平台门户排版（**白底卡片式驾驶舱**）：顶部项目行（定位图标 + 项目名 + 等 N 个项目 + 下拉）；浅蓝滚动通知条（喇叭图标 + 公告，整条可点）；指标卡只展示已有真实数据源的内容；**最近使用**、**智管/智控/智创**分组卡均为「圆形语义色浅底图标 + 必要角标 + 更多 ›」；规划中功能收进每组「更多 ›」页，不与已可用功能混淆。名称对齐甲方（如岗勤管理含用户管理/岗位设置/人员分配，项目经理在 App 可办）。原工作台功能目录并入首页分区，不再占 Tab，也不在“我的”重复一套管理中心。
- 功能入口、数据和操作均按权限过滤；前端隐藏不是授权，接口仍检查租户、项目和操作权限。

## 2. 首页

从上到下（布局参考甲方原平台首页，用本系统样式）：

1. **顶栏**：项目范围标识（如"戎安华府 等 3 个项目"）+ 扫一扫、消息。项目行可打开项目选择底部上滑 sheet，选择范围只看本人任职/授权项目；看板、待办和通知按所选范围过滤，执行类动作仍以任务与对象权限为准。右侧扫一扫固定，可用能力才显示。
2. **滚动通知条**：展示最新公告，整条进入通知列表；通知详情由列表项进入，不在一条通知条上设置两个容易误触的去向。
3. **移动看板**：只展示有真实数据来源的指标，标明统计周期、单位与权限范围；查看详情进入 `62 看板详情`。收费、报事等未上线指标不以演示数值冒充生产数据；加载失败显示重试，不显示假零。
4. **最近使用**：按本人权限和实际使用显示任务、巡检、工单、台账等入口；待办数量以必要角标承载，不铺成长列表。
5. **中台入口组**：按甲方规划分**智管 / 智控 / 智创**三组，四列图标宫格；组内放已有的常用功能并对齐甲方名称——智管：巡检督查（含我的任务/巡查打卡/打卡审核/巡检记录）、工单管理（工单池）、承接查验、品质报告、岗勤管理（含用户管理/岗位设置/人员分配，项目经理在 App 可办）；智控：设备台账；其余（收费/入伙服务/装修/报销/资产、智慧通行/智慧消防/各监测、智创全部）为规划中功能，收进每组右上角「更多 ›」页。每个入口采用统一图标槽与语义浅底，不用颜色表示是否可用。
6. **每组右上角「更多 ›」**：首页分区卡只显示常用功能，点击进入该板块全部内容；管理功能已经包含在首页及其分组更多页中，不再另建一个与首页重复的管理中心。无权限入口直接不展示，规划中入口明确标状态，不做“看着能点、点了没反应”的假按钮。

待办数量靠常用宫格角标承载，不单设待办列表区。基层执行入口只有「我的任务」：里面是派给我的巡检任务和工单任务（含维保执行工单）；有权限的临时维保登记从设备台账、扫码或管理入口直接进入，提交后从「我的维保登记」追溯。

宫格优先四列；窄屏或大字号时允许降为两列，不能为了凑齐一行把最后一个入口拉长。模块间用卡片留白和细分割线，避免反复增加标题。我的任务不再在更多页重复展示为另一套流程。

首页优先保证项目、通知、核心指标和高频任务在首屏可见；内容超出时自然纵向滚动，**不把 844px 当固定高度或强行压缩全部内容**。原型画板高度按实际内容确定，固定底栏不得遮住最后一项。

看板指标必须标明口径：现场已提交与审核通过分别统计，不能把待审核写成合格完成；逾期任务与设备到期分开。设备到期仅在设备/维保任务中提示，不在到场签到前弹红色遮罩。

`blocked_by_config` 点位（坐标缺失、围栏半径非法、凭证配置与点位能力不符等**管理端配置缺陷**）从完成率分母剔除并单列展示，不计巡检员未完成、不混进逾期任务（03 §6）。该状态面向管理端：巡检员侧只显示"该点位配置有误，已通知管理员"，不给自助解除入口，也不能用"无法检查"顶替——"无法检查"记现场客观情况，配置缺陷记系统问题，两者统计口径分开。

## 3. AI助手、卷宗库、社区、通知、我的

### 社区（Tab）：生态接入枢纽与服务集市

社区是 AI云管家的**生态接入枢纽与服务集市**（"云启三方、共筑美好"服务体系的核心落地载体）：平台提供标准化开发接口，支持自研产品、第三方 SaaS 与硬件服务快速接入；串联物业供方、小区外包服务商、本地便民商家、社区居民等多方主体，搭建分层的社区服务生态。四个板块：

- **物料资源**：项目经理遴选对接园区运维物资与硬件工具（垃圾桶、工装、门禁门机、疏通机等）；统一管理外包第三方服务商档案（电梯维保、水箱清洗、绿化养护等），实现供方筛选、比价、履约跟踪。
- **智慧产品**：依托平台开放能力陆续上线自研产品、第三方标准化 SaaS 及硬件配套服务，各项目按需开通调用、即开即用。
- **便民集市**：物业经理引入周边合规商家，上架家政、家电维修、空调加氟、餐饮、陪诊等本地化便民服务，**物业审核后统一推送给业主**，在物业监管下搭建可信便民服务市场。
- **邻里交互**：业主提交寻人、寻物招领、旧物置换等邻里信息，**经物业审核后对外展示**，激活小区自治氛围。

核心价值：不只是信息发布区——通过统一接入规范沉淀可复用的产品与服务商资源，降低项目落地新能力的成本；依托物业公信力运营服务生态，形成稳定的商业化增长空间，支撑党建引领下的社区共治。本端默认混合推荐内容流，点板块图标切换专属内容；便民/邻里类信息均须物业审核后对外。

### 卷宗库（Tab）：所有台账与报告的统一归档

顶部**最近查看**，下方**八大分类**按钮（各配独立图标色）：红色物业类（党建学习/三会一课/主题党日/志愿便民/三方联动/红色物业创建/宣传台账/共建函件）、合同协议类（物业服务合同、外包分包、维保合同、工程协议、补充协议、承诺书、履约函件）、台账计划类（月度计划与复盘、承接查验、分户查验、报修投诉、收费、巡检、隐患销项、考勤、资产台账、日常通知、往来函件）、服务报告类（月/季/年服务总结、品质自查、满意度调研、专项汇报、项目复盘、查验总结）、政策法规类（物业条例、消防法规、维修资金文件、红头文件、行业通知）、内部制度类（管理制度、作业 SOP、岗位职责、考核方案、作业指引、案例判例）、管理规约类（管理规约、议事规则、表决资料、装修约定、业委会文书）、安全应急类（消防/防汛/治安/电梯应急预案、培训记录、演练影像、隐患整改闭环）。归档件只读；纠错走作废/重出流程，不覆盖原件。**分类归属**：系统生成的台账按母版直接归类（巡检/维保/计划类入台账计划类，承接查验与服务总结入服务报告类），不需要识别；上传的存量/外来文件按标题内容自动预分类——规则优先（标题关键词匹配），匹配不了的走 AI 分类建议，**预分类只进"待确认"，人工确认（可批量）后才正式入架**；分类只打标签，不改文件名、不动原件。

### 助手（Tab）：对话 + 工具调用

对话区域（微信式：无输入时左侧切换语音/文字、右侧加号传附件；输入文字后左侧隐藏、右侧为加号 + 发送按钮；语音状态中间为"按住 说话"，长按录音、松开发送），可直接命令 AI 完成工作（"生成本周品质周报""查 1 栋灭火器逾期""把 2 栋换粉派给老王"等）。实现上走 agent：系统的增删查改按业务域封装为**工具**（入参/权限/返回结构显式声明），agent 在权限内调用工具取数与操作；工具调用沿用接口鉴权，AI 不绕过租户/项目/操作权限。回答基于 response 流（SSE）**Markdown 流式渲染**，思考过程与工具调用轨迹可展开查看；写操作先生成待确认计划，App 用**居中确认弹窗**写清对象、动作与条数，确认后才执行并留痕。只生成文字材料的场景不触碰正式报告链。

### 全部功能（并入首页分区卡）

| 分区 | 入口示例 |
|---|---|
| 任务执行（跨域，不归属单一业务域） | 我的任务、巡查打卡、附近点位、手动补巡（需授权） |
| 工单整改 | 工单池、派单管理、审核 |
| 品质管理 | 巡检记录、数据看板、品质报告、设备台账、承接查验、统计报表 |
| 管理中心 | 点位、人员、巡检计划、抽查计划、审核确认、维保确认、检查项模板、公告 |
| 系统设置 | 组织权限、审批流程、签章、输出模板等有权限的设置 |

同一能力允许首页常用快捷入口，但只有一个目标页面，不复制另一套流程。输出模板属于系统设置，**检查项模板不展示输出表型/Word 母版入口**。

**检查项模板与输出模板两项在 App 上只读**：按 08 §5，这两个配置界面以 PC 为主，App 侧只提供只读查看入口，无权限者直接不展示，编辑、发布启用、批量录入与 layout 块编辑一律在 PC 完成。目录页不放"看得见点不动"的编辑按钮。

### 通知（页面，不占 Tab）

主页滚动通知条进入。分类入口 + 消息列表。消息显示对象、事件、时间、未读状态；点击直达具体记录/工单/报告。通知只负责“发生了什么变化”，不再做第二套待办宫格；待办数量由主页承担。对象已删除或无权访问时解释原因并允许返回，不进入空白页。通知失败不回滚已成功的业务提交，后台补发与去重。

### 我的

用户与当前组织卡片 + 个人记录列表：我的任务、巡检记录、我的维保登记、我的签名；设置列表：账号与安全、关于云管家（内含可单独点击的「检查更新」列表项）。页面底部保留独立的「切换账号」「退出登录」列表行，点击后用**居中确认弹窗**，不使用底部上滑确认层。切换账号进入账号列表，不直接弹窗代替账号管理。签名录入仅保存个人签名素材，不能等同于同意某份报告；不再放一个与首页分区重复的管理中心。

## 4. 巡检主流程

我的任务/扫码 → 对象详情和到场确认 → 一页检查表 → 提交 → 审核结果。

- 先展示点位和设备身份；凭证方式与围栏是独立配置。可选围栏必须在管理端表单可配置，不能后端支持而前端无入口。
- 到场确认后直接检查，不再展示需要再点击展开的逾期横幅；到期设备按顺序进入检查项或维保任务。
- 巡检负责找出问题，并解决能够现场解决的问题：现场可处理的轻微问题选“异常已现场处理”，在该检查项内附处理前后证据，页面下方不重复设置同一组照片；不进入工单。现场解决不了、需要别人/备件/资质/隔天的，才提交异常并等待审核入工单。
- 检查项使用严格分层的独立卡片，不用左右缩略行、不用点击后才展开：第一层为名称 + “拍什么 / 怎么判”小字；第二层为图像组；第三层为结论分段按钮；仅选择异常时才在卡片内展开观察点多选与备注。参照 `../APP原型/预览/v2/13 巡检打卡.png`。
- 检查项之间用卡片留白与细分割线，不重复无意义的小标题。结论需要符合 03 的完整性校验，不以页面默认选中代替已检查。
- 同一表单支持人工与 AI。AI 启用项拍照后自动填建议，用户可改判并留原因。
- AI 识别中：提交按钮禁用，附近写明“还有 N 项正在识别”，可继续填其他项；无阻塞识别弹窗。
- AI 失败：该项提供重试与人工核查入口；填写原因并按强审规则处理，不把失败伪装成正常。重拍后旧识别结果不得覆盖新照片。
- 导航栏问号是“无法检查”入口；仅个别标签不可读等情况在相应项显示局部入口。说明范围、原因和所需证据，不能一键把未检查全部判正常。
- 提交成功展示记录详情及审核状态；“我的巡检记录”可再次找到。驳回记录展示原因与修改重提按钮，审核中不可直接改写已提交内容。
- 异常先随记录审核，**审核通过后自动形成待接单工单**；创建 issue 与工单和审核结论在同一事务内，失败整体回滚，不让巡检员重复提交。

## 5. 维保执行、生效与确认

**有权限的执行人员可以使用独立「维保登记」入口。** 首页管理入口、设备台账多选/设备详情、扫码与我的任务都可进入相应登记或执行流程；直接进入登记页时先选择设备或恢复本机草稿，不能落到没有对象、没有下一步的空提交页。派给我的维保执行工单出现在「我的任务」里，执行完成后提交证据，进入维保生效确认。管理侧仍可看设备台账、维保确认和维保流水。

- **单台/批量执行**：维保工单来自计划到期、巡检异常或厂家施工安排；执行页按设备带出类型、到期日、来源问题、已有证据和需补证据。换粉/水压试验可多张设备共用一张作业后合影；单台维修/更换新瓶采个体证据。
- **工单转维保**：纯维保与混合工单都只由主管审核一次，通过即完成闭环；涉及有效期的设备在同一审核生效点按设备规则回写日期，维修/清理类只记维修记录。主管可自行现场或电话核查，不另派复查任务。
- **维保谁去做**：维保生效确认单不进工单池，但维保执行任务必须有人负责。计划/到期维保按计划配置的 `assign_lead_days` 提前生成 `work_type=maintenance` 工单；已逾期由每日扫描即生成。聚合粒度与批量登记一致：同小区、同设备类型、同动作、同到期周期/施工批次一张工单，逐台为 item；可抢单、派单、批量派单。厂家整批施工也应有任务单或交接记录，不能只在台账里写日期。
- **AI 在维保只是辅助**：读标签/日期可预选，但 pending/failed 不阻塞登记提交；允许人工填写或改判日期并留痕，主管确认页必须同时看到 AI 结果、人工值和证据。巡检结论的 AI pending 禁提交规则不照搬到维保登记。
- 全选全部结果必须明确范围，不把当前加载的几十条冒充全部。筛选变化清空旧选择并说明。
- 后台作业显示已处理/成功/失败/跳过；提供失败明细、导出与仅重试失败。不因部分失败把成功设备重做，也不把处理完成写成全部成功。
- **提交成功进入「我的维保登记」对应记录**，也可随时从我的或首页记录入口再次找到。记录可查对象清单、引用证据、共享照片、状态、确认记录；驳回后修改重提，确认通过才写正式维保流水与台账日期。
- 审核/确认保持同一交互：确认列表不放单个通过/驳回按钮，整卡进入详情后在底部选择「驳回 / 通过」；同批次、同动作、同证据的登记可用底部操作条批量确认。通过、驳回都用居中弹窗，不把主操作藏在点击卡片展开后。

## 6. 承接查验与报告

- 承接从批次进入，册名/表名来源于甲方母版与独立查验清单配置。清单、矩阵、设备检查适配不同录入方式，不强行把非设备资料变成设备。
- 普通查验路径只显示：选对象 → 逐项查验 → 问题拍照/说明 → 提交审核。不在查验卡片上选择责任方；交接前问题按甲方口径默认属移交方需处理事项，确有争议由负责人在报告/签署阶段处理。
- 问题页可查看来源、事实证据与风险措施；问题只进入承接查验报告，不转工单、不进工单池、不做整改跟踪。
- 报告列表每张卡只显示一个下一步动作：生成中看进度/重试失败册，待审核去审核，待我签去签字，已归档查看/下载；完整状态机收进详情时间线。巡检五册全部 PDF 就绪后才可提交审核；单册失败可重试，缺转换服务是发布阻塞，不以 Word 下载代替 PDF 交付成功。
- 生成报告支持三种明细范围：全部明细、仅异常明细、正常代表样本 + 全部异常。第三种用于设备很多的项目：每个点位/设备只保留本周期最早一条审核通过的正常记录作代表样本，异常记录全量保留；汇总表仍按全量已审核事实统计，封面和明细页眉必须标明“正常项为代表样本”，不能让读者误以为只巡了这些。
- 审核的是冻结的预览内容；签署后形成归档件。重出生成新报告，旧文件不覆盖；签字后修改内容必须走新报告/重新签署，不可沿用旧签名。

## 7. 组件与可用性规范

| 项 | 规范 |
|---|---|
| 基础组件 | uni-grid、uni-list、uni-card、uni-icons、uni-easyinput、uni-popup、uni-segmented-control 等；按钮优先原生 button，与官方组件统一样式，不手绘可交互控件 |
| 横向分类 | uni-segmented-control 可置于 scroll-view 中横滑；切换后保持选中项可见，不再自绘一套选项卡 |
| **严格分层** | 同类列表项必须使用同一种卡片骨架：标题/提示层 → 媒体或关键字段层 → 主操作层 → 条件详情层。条件详情只在对应状态下展开；已完成项不折叠成只剩状态的摘要行。巡检检查项参照 `../APP原型/预览/v2/13 巡检打卡.png`，禁止退回左右缩略行或点击后才看到检查内容 |
| **列表与审核** | 多选卡片 + 全选行 + 底部「已选 N 条」操作条 + 可退出多选；整卡进详情。打卡审核等审核列表不放单个通过/驳回按钮，单条进详情后在底部决策，批量动作固定放列表底部 |
| **弹层分型** | 项目、人员、筛选等**选项类**使用底部上滑 sheet；通过、驳回、退出、修改密码等**确认/取消类**使用居中弹窗，不能用上滑弹层代替确认，也不能把主操作藏在卡片展开里 |
| **结论选择** | 巡检/查验的「正常 / 有异常」用**分段控件**（两个等宽、至少 48px 高的按钮，选中态填充：正常=绿、异常=红），**不用小圆点单选**——这是一线每天点几百次的最关键操作，视觉权重必须与重要性匹配。AI 未出结果时该项置灰禁用，不能“看着能点、点了没反应” |
| **默认值** | **决策性选项一律不预设默认值**：维保方式、本次涉及设备、待接单合并均为空选。这几处都有不可逆的外部后果（算错到期日、未核对就合并），“最可能的选项”不等于“默认选项”。到期设备只是筛选结果，不等于授权作业（07 §3）；承接查验不在查验卡片上选择责任方 |
| **阻塞提示** | 按钮只说动作（“提交本点位”），**阻塞原因不写进按钮文案**：缺什么、在等什么分行列在按钮上方，并能定位到具体那张卡——“要等”和“要做”是两件事，不能混成一个灰按钮。提交待确认的动作要写明去向（“提交，待主管确认”），不能只写“提交” |
| PC | 沿用现有侧栏、顶栏、标签页与 Element Plus 筛选/表格/抽屉，不重画成另一套产品架构。新增/编辑默认用弹窗或抽屉，不随便新开整页；只有多列表格 + 批量错误预览这类复杂编辑器才用整页。抽屉遮罩要淡（抽屉式编辑的价值就是保留上下文，重遮罩会把价值抵消）；同一对象名不在面包屑、标签页、页内标题里重复三遍 |
| 交互目标 | 可点击区域至少 **48×48px**；图标有可访问名称；问号须有说明，不能用颜色作为唯一状态 |
| 字号与对比度 | 采用 **26 / 22 / 17 / 16 / 15 / 14 / 13 / 12** 八档（底栏 11、角标/水印 10 为限定例外）；正文 15，14 只给时间戳/单号/单位；次要正文 `#6B7385`，正文对比度 ≥4.5:1，图形与控件边界 ≥3:1；大字模式不截断关键操作 |
| 图标与配色 | 宫格图标底板按业务分区使用语义浅底，同一功能在主页与更多页一致；颜色不承担“是否可用”或“是否危险”的唯一含义，状态同时给文字/图标。同一屏内图标不重复，统一 22×24 图标槽 |
| 间距与高度 | 4/8px 节奏；同层元素间距一致，卡片间细线/留白，保留底部安全区，固定栏不遮最后一项。画板高度按内容确定，长页自然滚动，不设 844px 固定下限 |
| 表单 | 标签常显、必填清楚、错误邻近字段；提交失败保留数据，重复点击由前后端共同防重 |
| 加载与空态 | 首屏加载、分页、无数据、筛选无结果、请求失败、无权限分别表达；不用“暂无数据”通吃，不用假零代替失败 |
| 反馈 | 成功跳详情或可追溯列表；错误说明下一步，不只弹“失败”；高风险操作明确对象与后果。错误信息只讲发生了什么和下一步，**不混入制度说明** |
| 主题 | 品牌蓝 #2B5AED，实际代码统一令牌；禁 emoji 当结构图标，禁页内任意新增硬编码颜色 |

## 9. 角色减负与信任设计（评审新增硬规则）

系统设计不能只满足管控，还要让各角色少干活。以下规则进入验收，不是口号。

### 9.1 项目负责人/甲方管理人：只看管辖范围，不被系统当审批节点

- 没有“老板”这个系统角色。项目管理员只看自己管辖的项目；租户管理员才看全租户。看板默认按当前数据范围过滤，不让项目经理看到无关项目，也不让租户管理员误以为自己只有单项目。
- 常规月报、日常签署按流程授权给对应负责人；管理人只收**一页摘要**：管辖项目数、异常数、风险项、逾期项、经手人、需升级的少数事项。只有交接、重大遗留、超授权风险才升级给更高权限。
- 必须提供**管辖项目横向对比**：完成率垫底、整改最慢、报告拖延、逾期设备最多的项目自动排前，不让管理人逐个切项目。
- 迁移/停写必须给甲方成本口径：预计影响多少巡检员/多少任务、通知谁、失败回滚时当天记录怎么处理。没有这份说明，不上线。

### 9.2 巡检员：系统出错不能让一线背锅

- AI 慢/失败是系统状态，不在按钮区写成“你差什么”。识别中只在项卡显示，提交按钮给明确可做的下一步：继续填其他项、稍后自动好、或转人工核查；不让巡检员站着等。
- 点位配置缺陷（缺坐标/围栏非法/凭证不配）不记巡检员未完成，允许“先拍照留痕 + 上报配置异常”，任务不计逾期；后台通知管理员修配置。
- “无法检查”要低代价但可审计：一次选择原因 + 必要佐证，不默认强制复杂审批；只有涉及免照片、设备不存在、标签磨损等高风险原因才进人工审核。界面不得写“这不是快捷键”这类不信任文案。
- 手套/地库/弱网：主操作触区按 48px 设计，关键结论按钮支持放大模式；断网时本地草稿、照片队列和恢复进度可见，能明确看到“已存本地/待上传/已上传”，不承诺未上传材料换机恢复，但同机恢复必须可靠。

### 9.3 项目主管：审核是判断，不是体力活

- 审核列表默认按风险排序：安全相关、逾期、AI 异常、改判、无法检查优先；同类问题（同楼栋/同设备/同异常标签）可合并处理，不强迫逐张看相同照片。
- 派单页显示候选人负载：当前在手单数、今日已完成、预计可用时段、是否请假/代理；只知道“有资格”不够。
- 支持排班与代理审核：夜班/周末/请假时可配置代理人；代理范围、时间和操作留痕，不允许长期把账号借给别人。

### 9.4 系统管理员：新项目不能从零配

- 提供行业预置包：消防/供水/供电/电梯等标准点位类型、检查项模板、台账字段、审批流程、输出模板一键导入；管理员只改差异。
- 初始化必须有可承诺路径：预置包导入 → 小区/楼栋/点位/设备 Excel 导入 → 二维码/NFC 批量生成与打印 → 试点点位验收。说明书要给“新项目上线清单”，不只给功能说明。

### 9.5 共性：管控藏在后台，信任放在前台

防作弊、防自审、防越权照做，但不在每个按钮旁边写威胁性提示。界面只告诉用户下一步能做什么；限制、审计、风控在后台执行。每个角色减少的 clicks 要可度量：老板少翻页、主管少点重复审核、巡检员少等 AI、管理员少从零配置。
