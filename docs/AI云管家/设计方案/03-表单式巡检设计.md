# 03 表单式巡检设计

> 替代被甲方否决的"一照片一界面"向导（pages/checkin/quick）。
> 核心：进入点位 = 一页表单，全部检查项一页内拍完提交；AI 项级并行识别，不阻塞填其他卡，但提交前必须全部完成。

## 1. 交互流程对比

**已否决的旧向导**：凭证核验 → 逐项（引导语→拍照→等 AI→判定→下一项，每项一屏）→ gate 提交 → 下一点位。切换验收后删除旧路由与实现，不保留兼容入口。
痛点：步骤多、跳转多、老年巡检员易迷失；拍照必须当场等 AI 结果。

**表单式（新）**：

```
点位列表 → 进入点位 → [凭证核验（如需）] → 表单页（一页）→ 提交 → 下一点位
```

## 2. 表单页布局

```
┌───────────────────────────────┐
│ ← 1栋3楼通道消火栓             │  标题=点位名（项不再与点位名混淆）
│ 消防设施 · 1栋                │
│───────────────────────────────│
│ ✓ 已核验 NFC · 距点位 12m      │  只写核验事实；未核验时同位置给「去核验」
│───────────────────────────────│
│ 消火栓箱整体检查               │  ┐ 检查项卡（无采集分组标题）
│ 拍消火栓箱整体照片，打开箱门让  │  │
│ 水带、枪头都在画面里           │  │ 检查项卡（每个检查项一张 uni-card）
│ ┌─────────┐ ┌─────────┐      │  │
│ │  相机    │ │ +       │      │  │ 照片槽（photo_required：必拍项 1 张起，可多张）
│ │ 点击拍摄 │ │         │      │  │ 图标使用统一矢量图标，不用 emoji
│ └─────────┘ └─────────┘      │  │
│ AI：识别中…                   │  │ AI 后台识别，可继续填其他卡
│ [   正常   ] [  有异常   ]    │  │ 等宽分段按钮；AI 预选也须人工确认
│ ├─ 有异常时展开 ─              │  │
│ │ 观察点：[水带破损][枪头缺失] │  │ 异常观察点 chip（写入 abnormal_tags）
│ │ 备注：[输入框，可不填]       │  │ 异常备注
│───────────────────────────────│
│ 下一场所项 / 下一台设备检查项    │  ┘ 到期设备按顺序成为普通检查项，不设逾期横幅
│───────────────────────────────│
│ 还差 1 项照片                  │  阻断原因独立于按钮，并可定位到检查项
│ ┌───────────────────────────┐ │
│ │        提交本点位          │ │  底部固定主按钮；不在按钮中堆完成度和规则
│ └───────────────────────────┘ │
└───────────────────────────────┘
```

**消火栓与灭火器点位分开（甲方口径）**：两者物理上不一定在同一位置，必须按实际安装位置分别建点位、分别打卡拍照，不得合并成"通道消火栓+灭火器"复合点位一次打卡；前期建点工作量大不作为合并理由。**一设施一打卡**：每个消火栓/灭火器设施各自一个点位、各自一张 NFC（或二维码）凭证，不多个设施共用一个点位凭证。专项抽查（如灭火器压力/日期 2% 抽检）本就按设备逐台拍照，不与栓箱点位合并，无需额外拆分。

**卡片控件由检查项 `value_type` 决定**（录入侧永远同构：同一张"检查项卡片"，差异只通过 `value_type` 换控件、`standard` 换说明文字、`photo_required`/`note_required` 换必填项体现，绝不按模板定制卡片布局——08 文档 §3.3/§6.3）：

| `value_type` | 控件线框 | 判定（唯一依据，08 §3.2.3） |
|---|---|---|
| `ok`（√×） | `[ 正常 ] [ 有异常 ]` 等宽分段按钮，高 ≥48px；AI 预选标明来源，异常才展开观察点+备注 | AI verdict + 人工确认/改判 |
| `number` | `[数字输入框] 单位`（MPa / V / m³ / ℃）；越界即时高亮 | 前端按 `value_min`/`value_max` 越界高亮提示；服务端按同一对列判 abnormal；AI 读数仅作交叉校验，不替代服务端判定 |
| `date` | 日期选择器（生产日期由 AI 读标签预填） | **不判定，仅记录**；台账日期比对由 `builtin_kind=equipment_date_spot` 的内置合成项负责，用户自配 date 项无需判定配置 |
| `text` | 单行输入（水表读数/位置说明） | 不判定，仅记录 |
| `enum` | 选项按钮组（`enum_options`，如 正常/异常） | 按 `enum_options` 判 |

值落库分列：`number` → `value_num`、`date` → `value_date`、`text`/`enum` → `value_text`、`ok` → `result`。`enum_options` 每项为 `{value,label,result}`，提交 `value_text=选项.value`；`result` 只能是 `normal|abnormal`，服务端按该归类判定，不能由客户端直接指定枚举结论。

卡片通用展示规则：`standard`（单项标准原文）在项名下以次要文字展示；`unit` 跟在数值输入框后；`value_min`/`value_max` 越界前端高亮；`note_required` 的项必须填备注；照片槽是独立属性（`photo_required`），不与 `value_type` 绑定。`ai_enabled=false` 的项（噪音/气味等感官项）不显示 AI 角标、不计入 AI pending 判断，但仍须人工显式给结论。

**适老减负规则**：
- `ok` 类项不默认选中，不用小圆点单选；拍照或 AI 预选后只需确认/改判，异常才展开观察点+备注。数值/文本/日期/枚举项必须显式填值（填不了走「无法检查」）；未完成确认或无必填证据不得提交
- place/object 两层出项（08 文档 §3.1）：`level=place` 点位（如进水泵房）= 先出场所检查项，再按设备清单逐台出设备项（一个点位可挂 0~N 台设备）；`level=object` 点位直接出项
- 必拍项未拍照时提交按钮置灰，"还差 N 项照片"独立放在按钮上方并可定位到对应卡片，不塞进按钮文案
- 凭证未核验（扫码/NFC/围栏按点位配置）时表单只读，凭证位置直接给「去核验」；不额外弹逾期遮罩或要求先点进红色横幅
- 现场处置照片只出现一次：有现场处理时在该检查项内补处理前/后证据，不在页面下方再设一组重复上传位

## 3. 统一交互：AI 预选 + 人工确认/改判（人工/AI 巡检同页）

人工巡检与 AI 巡检**统一为同一页表单**，模式差异只体现在"结果谁来填"：

```
同一页表单，每项一张卡：
├─ AI 启用（租户/点位级开关）：拍照 → 后台识别（不阻塞，可继续填其他卡）
│   → 结果出来自动预选（正常✓ / 异常⚠，带蓝色「AI」角标）
│   → 巡检员扫一眼：对就确认，不对点改（改判留痕，角标变「人工改判」）
├─ AI 未启用：同一张卡，拍照 → 手选 正常/异常（无 AI 角标）
└─ 异常时（两模式相同）：展开观察点 chip + 备注
```

规则细节（目标契约，不代表当前服务已满足）：
1. **识别中**：卡片显示“AI 识别中…”，不阻塞其他卡；任一当前请求 `pending/running` 时，前后端均禁止提交，不得把识别中当故障逃生。下文 AI pending 统指排队及运行中的未终结请求。
2. **AI 预选可改**：保留 AI 原判、人工结果、改判人/原因；异常、存疑、人工改判、无法检查及 AI 故障均强制人工审核，流程配置不得直通。
3. **AI 失败**：超时/失败由服务端落 `error` 终态（不是无限 pending）。允许重试；或逐项显式填人工结论/必填值和故障说明后提交待人工审核，不得以“默认正常”代填。`done` 表示识别终结，不等于审核通过。**`error` 不阻塞提交**——只有 `pending/running`（识别中）禁提交（§3.1），AI 只是辅助，失败时人工给结论即可，但必走人工审核。
   > **与空名单叠加的放行路径（期1 必堵）**：现 `checkin_ai_gate.go:94-100` 把 AI 失败路由到 `AIGateReview` 转人工，这步正确（`FlowStep.OnReview` 也只有 `next/reject/goto:N`、不含 `finish`）；但若该人工环节名单为空，`WalkFlowSkipEmpty` 会跳过并走到链尾 `walk.Finish` → `AuditAutoPass`。**「AI 失败 + 空名单」= 静默自动通过**，必须随空名单修复一并堵死（14 §4.6）。另 `seed.go:508/514` 的注释写"超时/失败默认通过/放行"，与代码实际行为不符，属陈旧注释，须订正。
4. **重拍防串结果**：每个项实例保存 `request_id + retake_seq + photo_set_hash`；重拍/删换照片递增 `retake_seq` 并废弃旧判定。回调只可条件更新当前 `retake_seq`、照片集合且仍 pending 的草稿；旧回调即使晚到也不得覆盖新照片或人工结果。提交按服务端当前请求校验，不信客户端 AI 状态。
5. **无法检查**：一级入口为导航栏问号图标，位置避开小程序右上胶囊安全区；仅个别标签不可读等情况在相应项显示局部入口。按受影响项登记原因，整点位逃生也逐项留痕；不可拍摄/相机故障按明确配置免照片，设备不存在/标签磨损须现场佐证，不能顺手跳过凭证或围栏。无法检查不算正常或问题项，现场覆盖与有效检查数分别统计，强制人工审核。
6. **手动填法同页**：`ai_enabled=false` 的项（原 `judge_type=manual`，如噪音/气味等照片判不了的项）本就不调 AI，按配置人工填写；租户/点位级 AI 开关与项级 `ai_enabled` 是 AND 关系。已发起识别的项不得切手动来绕过 pending。所有照片、数值、备注必填与服务端规则一致。

> 原"AI 识别异步化（提交后出结果）"方案否决，理由：现场纠错成本远高于当场确认。

## 4. 点位-模板关系（bug2 整改）

按 `point_type` 与 `purpose` 筛候选启用模板，同类型允许多套；**本期**由计划 `template_ids` 显式选择，任务固化集合。

> **现状差距（真缺口，非已实现）**：`template_ids` 目前挂在**点位**上（`points/index.vue:199`、`api/point.ts:75`），计划表单里没有这个字段（`plans/index.vue`）。本条要求的"由计划显式选择、任务固化集合"尚未落地——按点位取模板会让同一点位的不同计划拿到同一套模板，无法表达"月度全检 vs 专项抽查用不同模板"。
点位例外绑定用于有权限的补充配置，不能隐式取任意一套或默认并集全部模板；任务未明确选定时提示配置，不静默猜测。

**卡片标题自带对象名；App 不显示采集分组标题**。检查项卡片按固定分层呈现：名称与“拍什么/怎么判”提示 → 图像组 → 结论分段按钮 → 仅异常时展开的观察点/备注；不折叠已完成项，不用左右缩略摘要行。卡间 hairline 分隔。L1 采集分组与 report 输出两级表头独立，报告章节/分组由输出配置映射，不反向绑死采集布局（08）。

## 5. 数据与提交状态（目标）

01～09 是重构目标，不是现状验收单。当前 `mp/service/checkin_service.go`、`checkin_ai_gate.go` 已有草稿/审批链，但仍有 pending AI 故障放行、空流程直通、围栏缺坐标跳过等旧行为，均须替换；不能把本方案描述为已实现。不保留新旧业务双轨。

- 模板按 08 的稳定 `template_id` + `item_code` 匹配；同一项在多台设备重复出现时用 `equipment_id` 区分，**场所自身的项 `equipment_id` 为 NULL**（场所就是 `record_id → point_id`，不另编码成 `place:<point_id>`）。草稿和记录项不能以名称为键。
- 点位检查逻辑记录以 `(tenant_id, task_id, point_id, round_seq)` 唯一；`round_seq`（第几轮）由服务端确定，补巡必须显式关联原记录。项实例唯一键为 `(tenant_id, record_id, template_id, item_code, equipment_id)`；Postgres 下用两个部分唯一索引解决 `equipment_id IS NULL` 不去重的问题，不依赖 PG 15+ 的 `NULLS NOT DISTINCT`（08 §3.4.2）。
- **项实例身份就是记录项自己的 `id`（UUIDv7）**，记录项上不再另存 `source_item_instance_id`——04 的 `work_order_issue.source_item_id` 存的就是这个 `id` 值，一行里不立两个号称"不可变项实例 ID"的字段。修订号不进入 issue 唯一键。
- 提交事务校验后写记录、逐项事实、照片归属、流程快照和幂等回执，状态统一 `pending`；草稿提交成功才清。客户端 UUIDv7 同键同载荷返回原结果，同键不同载荷冲突。

| 转移 | 操作者与前置条件 | 结果 |
|---|---|---|
| draft → pending | 任务执行人，有小区/点位权限，当前项完整且 AI 无 pending | 现场提交成功；记录尚未审核生效 |
| pending → approved | 当前审核节点授权人，非提交人；普通正常记录由 agent 批量预审、审核人一次确认（12 §4），不再有按配置的自动系统审核 | 审核统计生效；异常必须人工通过 |
| pending → rejected | 当前人工节点授权人，非提交人，必填原因 | 不发布 issue，不计审核完成 |
| rejected → pending | 原执行人或经授权接替人修订重提，revision 条件更新 | 同一逻辑记录/项实例，保留旧修订和驳回日志 |
| approved → locked | 归档权限与归档流程 | 禁止修改；纠错走作废/重新审核，保留归档件 |

异常、存疑、人工改判、AI error、无法检查必须有人工节点；空流程/空审核名单不能自动通过，挂待配置并通知管理人。**节点无人等同空名单**：审批链节点绑的角色在该对象范围内无在职人员时，现有 `flow_service.go:139` `WalkFlowSkipEmpty` 的自动跳过实现与本条冲突，期1 必须改为挂起+告警+修复入口，不得保留跳过语义。配套前置两道：创建小区必带默认审批链、完整度未过不得启用且不生成巡检任务；**前置只减少触发，不取代运行期挂起**（14 §4.6.2）。审核与重提均用状态+revision 条件更新，防重复审核覆盖新修订；无审核人时不得让提交人自审——**按自然人去重**，同一人的多个账号不得互审（14 §2.1）。

**审核链节点类型含 agent 预审节点**（默认链的 AI 审核位改为 agent 审核）：agent 节点用工具做复杂分析——对照识别结论、证据完整性、数值区间、历史记录、台账日期、同类问题分布——产出"建议通过/建议驳回/须人工"结论与依据，**不直接置 approved**；其后人工节点看到的是 agent 分析结论而非裸记录。低风险正常记录的批量预审即该节点能力在审核列表的呈现（12 §4）。agent 不可用/超时等同节点断链：挂起+告警，不得跳过或默认通过。

## 6. 提交拦截与任务完成口径

- 凭证 `credential=none/qrcode/nfc/any` 与 `require_fence` 独立配置，两者启用则均需通过；`any` 仅在已配置二维码/NFC 中任选其一。定位失败、缺点位坐标或半径非法均阻断要求围栏的点位，并提示管理人修配置；不得自动放宽为免围栏。手动补巡/无法检查不豁免到场规则，例外需独立授权、原因及审计。
- **配置错误阻塞态 `blocked_by_config`**：缺点位坐标、围栏半径非法、凭证配置与点位实际能力不符（如配了 NFC 却没有 NFC ID）等，属于**管理端配置缺陷，不是现场操作问题**。此类点位由服务端判定并置 `blocked_by_config`，App 直接显示"该点位配置有误，已通知管理员"，不让巡检员反复试、也不停在一个永远提交不了的表单上。该点位**不计入现场完成分母、不计巡检员未完成**，同时触发管理端告警与待办。巡检员**无权自助解除**，也不能用"无法检查"绕过（§3.5 已禁止跳过凭证与围栏）——"无法检查"记的是现场客观情况，配置缺陷记的是系统问题，两者统计口径必须分开。管理员修正配置后点位恢复可执行，阻塞起止时间留痕。
- 必拍项、必填值/备注、文件租户/上传归属、设备范围、当前 AI 请求均由服务端复核；前端置灰不替代鉴权。
- **现场完成**：任务所有应检点位已成功提交（`blocked_by_config` 点位从分母剔除并单列展示、归因管理端），巡检员可收工；驳回后显示”需补正”，原提交时间保留。**审核统计完成**：所有应检记录最终审核通过（无法检查单列覆盖/有效数），被驳回/待审不算通过。首页不得混用两个百分比。
- 审核通过即入池，两者在同一事务内完成：异常项要么连同审核结论一起提交成功，要么整体回滚重审，**不存在"已审核通过但待入池"的中间态**。不以工单闭环阻挡下次巡检。

## 8. 与工单/审核的衔接

`提交 pending → 异常人工审核通过 approved → inspection.checkin.abnormal_approved → 异常项 issue 入池`。生效点名称与边界统一按 01 §4.1；正常记录审核通过不触发异常入池。

审核通过事务内**直接调 workorder 的公开契约建事项**，与审核结论同一事务提交：入参含租户/小区、记录 ID 与项实例 ID（即 `checkin_record_item.id`）、revision、对象与问题照片快照，工单域据此落库，不回查巡检域表。防重靠工单域唯一键 `(tenant_id, source_type, source_item_id)`（04），重复审核/并发提交只产生一份事项。未通过的修订绝不建事项；驳回重提只修订同一记录。**不得用提交后 goroutine 代表入池成功** —— 跨域写必须在同一事务内完成，失败即整体回滚、审核结论一并不生效。已通过记录需纠错时走明确撤销/重审，不能静默删已执行 issue。
