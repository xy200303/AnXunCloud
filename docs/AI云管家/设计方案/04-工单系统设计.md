# 04 工单系统设计

> 主链路：巡检异常在人工审核通过的同一事务内自动形成待接单工单，执行人抢单或主管分派，整改提交后由主管一次审核，审核通过即闭环。
> **不再设置工单复查、复查任务或整改后需要复查开关。** 主管可以现场核查、电话核查或直接依据整改证据审核；通过只代表主管已确认，不再派一张复查单重复确认。

## 1. 概念模型与边界

本方案是 workorder 域的建设目标。工单是整改事项的执行载体，一套引擎服务多个异常来源；承接查验问题除外。

- `issue` 是一个来源异常/任务项实例；`work_order` 是 1..N 个 issue 的执行载体。`work_type` 可为 `inspection_fix`（巡检异常整改）、`maintenance`（计划/到期维保执行）、`repair`（报事报修，期3）、`iot`（期4 告警）。
- 巡检异常只有在人工审核通过后才入池。来源域与 workorder 域在同一事务内创建 issue 及绑定它的单事项 `pending` 工单，**没有待入池或手工打包中间态**。
- 主管可合并同小区、同专业且未接单的工单，可改派；不得合并已接单或跨小区工单。
- 计划/到期维保按维保计划触发，同小区、同设备类型、同动作、同施工批次聚合为一单，设备作为工单项。维保“生效确认单”不是独立第二套流程，其审核行为与工单审核一致：主管一次确认即完成并回写台账。
- 承接查验问题只形成 acceptance 域的问题清单与报告，不直接转工单；确需维修时另行立项。
- 主状态为 `pending / in_progress / pending_review / done / closed`。`pending_review` 是整改已提交、等待主管审核，不叫待复查。

## 2. 权限与派工候选人

授权模型以 14 为准：角色决定可执行动作和可抢工单类型，任职行决定数据范围。

- 正式候选人 = 本小区有有效任职 + 角色含该工单类型；临时与流动人员可先抢单，系统再生成该小区、该工单生命周期的临时任职。
- 分派候选人 = 同租户、启用账号、该小区有效任职、具有执行权限且符合专业要求。提交分派时再次校验，防止离职或撤权竞态。
- 消防、电梯、配电、计划/到期维保等涉及资质或期限的工单默认派单/指定厂家；清理、普通维修可配置允许抢单。
- 审核人由当前审批节点候选人确定，**不得审核本人整改**。候选人身份自带该工单读取权限；名单为空或只剩本人时挂起并告警，不自动通过。

| 动作 | 权限与数据范围 | 附加校验 |
|---|---|---|
| 查看池/工单 | `workorder:list` + 租户/授权小区 | 执行人仅看授权可抢池及本人单 |
| 合并工单 | `workorder:merge` + 管理小区 | 同小区同专业且全部待接单 |
| 抢单 | `workorder:claim` + 本小区执行资格 | 原子认领，条件更新防抢占 |
| 分派/改派 | `workorder:assign` + 管理小区 | 改派必填原因并保留原执行痕迹 |
| 整改提交 | `workorder:finish` + 当前执行人 | 所有事项证据与说明齐全，不可代交他人单 |
| 工单审核 | `workorder:review` + 当前节点候选人 + 小区 | 本人不可审核本人整改；一次通过即闭环 |
| 关闭无效/重复 | `workorder:close` + 管理小区 | 仅非终态，必填原因；有执行记录不得删除 |

## 3. 状态与并发契约

| 转移 | 条件 | 同事务变更 |
|---|---|---|
| 巡检异常审核通过 → issue + pending 工单 | 来源审核最终通过且范围有效 | 创建 issue、绑定 order_id、写待接单工单与事件日志 |
| 待接单工单合并 | 同小区同专业且全部待接单 | 原子调整绑定，保留来源与审计 |
| 维保计划/到期 → maintenance 工单 pending | 按计划触发与聚合键生成 | 写聚合工单与逐台 item，幂等防重复 |
| pending → in_progress | 合格执行人抢单或主管分派 | 条件更新并绑定执行人 |
| in_progress → in_progress | 主管改派 | 更新执行人/revision，保留历任执行人 |
| in_progress → pending_review | 当前执行人完整提交全部整改项 | 固化整改证据和审核链，issue 同步进入待审核 |
| pending_review → done | 当前节点候选人审核通过 | 工单及 issue 同时完成，写闭环事件 |
| pending_review → in_progress | 主管驳回并填写原因 | 仅被驳回事项回整改，其他已通过事项保持完成 |
| 任意非终态 → closed | 主管关闭无效/重复单并说明原因 | 写关闭留痕；关闭不等于整改完成 |

**一次审核即闭环。** 主管可以补充现场或电话核查，但这些是主管审核前的自主行为，不生成额外地复查任务，不改变工单状态，也不要求同一主管对同一证据再点一次“通过”。多事项工单可以逐项审核，已通过项不因其他项驳回而回滚。

纯维保事项同样只审核一次：审核通过完成工单，并在同一事务中按设备规则回写维保有效日期。混合工单中的其他事项与维保事项共用一套工单审核，不再区分“工单复查”和“维保生效确认”两条流程。

所有转移均校验 tenant/community、原状态及 revision；抢单、分派、审核使用条件更新。重复点击以 operation_id 返回原回执，done/closed 不允许任意改事实，纠错须授权作废或补充处理留痕。

## 4. 页面设计

**基层执行人员只看「我的任务」**：巡检任务和派给自己的工单在同一列表，按期限排序，显示类型、对象、位置、当前状态和下一步动作。

**工单池（主管/可抢单人员）**：待接单 / 整改中 / 待审核 / 已完成四个 Tab；支持抢单、合并、分派和导出，不提供工单设置或复查入口。

**工单详情与审核**：问题照片与整改照片对照，展示整改说明、轮次和时间线。待审核时底部提供 `驳回整改 / 审核通过`；驳回必填原因。审核通过后页面只读。

主管可依据证据直接审核，也可自行现场或电话核查。系统不强制记录核查方式，不把核查方式变成新的配置项。

## 5. 与巡检完成的边界

巡检提交统一待审核，现场完成与审核统计完成分开。异常人工审核通过即入池，事务失败则来源结论也不生效。工单未闭环不阻断现场完成或下次任务，超期工单置顶提醒并升级管理人。

## 6. 数据与幂等契约

| 表 | 关键字段/约束 |
|---|---|
| work_order | tenant_id/community_id/order_no、status、assignee_id、revision、review_flow 快照、deadline/priority、closed_at/close_reason |
| work_order_issue | tenant_id/community_id、order_id 必填、source_type/source_record_id/source_item_id、来源 revision、对象/问题/照片/责任快照、状态 |
| work_order_fix_attempt | order_id/issue_id/整改轮次、执行人、说明/照片、提交时间；重做不覆盖前轮 |
| work_order_event | tenant_id/order_id/issue_id、事件/operation_id、操作者、前后状态/revision、原因及时间 |

issue 唯一约束为 `(tenant_id, source_type, source_item_id)`。巡检来源存 `checkin_record_item.id`；重复审核、并发提交、来源重试均返回已有 issue 及其工单。承接查验没有 issue 来源。

不建 `workorder_event_inbox`：入池是同事务直调，没有消息和 event_id，去重由 issue 业务唯一键承担。

## 7. 联动

- `inspection.checkin.abnormal_approved`：来源域在异常审核通过的同一事务内调用 workorder 域公开契约创建 issue 与待接单工单，幂等由 issue 唯一键保证。
- `workorder.item.finished`：整改已提交，进入待审核，不是闭环。
- `workorder.item.review_passed`：主管审核通过，在该 issue 置 done 的同一事务内生效；全部 issue done 后工单闭环。字段名保留为内部契约，但界面统一叫“工单审核”，不再使用“复查”。
- 维保域在同一审核生效点按设备规则回写有效日期，不另设第二次确认流程。
- 报告处理情况使用闭环结论只读快照；每日 job 对逾期工单提醒并升级负责人。

## 8. 配置归属

- 审批链只在 `82 审批流程配置` 维护，支持平台默认、租户默认与小区覆盖，复用同一设计器。
- 小区覆盖在 `83 流程与签字` 维护，只改绑定岗位、签署方式和候选名单。
- 承接查验报告签署状态在 `84b` 查看，配置仍回 `82 / 83`，不在报告页重复配置。
- 业务模块保留执行配置（如计划、点位、模板、人员），共享审批配置不复制到各业务页。
- 计划管理是一级菜单，巡检计划、报告计划及后续其他计划统一展示；具体生成规则仍归各业务域。
- AI 失败或不可用时直接转人工填写/确认，按 App 当前实现执行，不设巡检规则配置页。
