# 05 承接查验设计

> 新物业接管小区时的全面检查：资料采集 + 房屋/公区查验 → 查验报告，
> 用于交接留痕与报告产出。
> 定位：复用基础设施（拍照/AI/审核链、以及 01 §4.3 的异步任务队列），**记录与流程、判定语义独立**——承接查验不是点位打卡，独立建域（acceptance）。问题只归集到本域问题清单与报告，**不进工单池，也不做整改跟踪**。口径以 08 文档 §2.2/§7 为准。

## 1. 范围与流程（目标）

01～09 是重构目标；当前未建立独立 acceptance 域，不能称“一个枚举+一张表即可接入”。期2 并行，依赖独立记录、清单配置、审核/签署和 L3 输出，不复用打卡业务、不留兼容双轨。

`建批次/对象清单 → 随机或按规则分派任务 → 资料核对与现场查验 → 发现问题拍照 → 人工选择问题类别 → AI 辅助识别问题点 → 人工确认 → 审核 → 报告签署交接`。普通查验页只暴露这条主路径；带遗留交接、签署例外都属于负责人「特殊处理」，不在普通查验卡片上长期占位。

**执行口径（甲方确认）**：现场查验**逐项查看但不逐项拍照**——承接查验很多内容平时巡检不查（如房屋本体按楼栋整体查门窗、外墙等），查验人一项项看过，**只登记有问题的项**；正常项不拍照、不留逐条记录。发现问题的项才拍照、选择问题类别、记录事实。报告仍按母版出 √/× 结果：已确认覆盖的无问题项默认为 √，问题项为 × 并汇入问题照片表；覆盖确认按对象（楼栋/册）由查验人显式完成，不凭空生成"全部正常"记录。承接查验检查项独立于日常巡检（`purpose=verify`），不复用 patrol 模板。

承接查验是**集中性交接动作**，不需要点位打卡、不套巡检任务/频次/到场凭证，也不按固定巡检员排班。查验人员可不固定：可为项目内部员工，也可为外聘临时人员；由物业项目经理按批次统一分派任务。分工分两大类：**资料核查**与**现场查验**；现场查验既可按楼栋/单元逐栋划分，也可按类型划分（园林绿化、康乐器材、供水供电设施设备等）。项目经理可手派，也可选**随机分派**：系统按批次成员、分工范围和对象数量自动分配，结果可预览调整，不外聘人员写入长期编制。外聘临时人员使用批次级临时授权，不写入长期项目编制；所有记录按操作人留痕。**任务分工是负责人配置信息，普通查验页不展示全量分工，只显示当前人的查验范围**。只复用表单、拍照、AI 能力服务、审核基础组件，不继承巡检状态或异常自动入池逻辑。普通查验员只需要理解：接任务、按分工逐项查内容、拍照、提交；签署条件和遗留处理由负责人/管理人集中处理。

## 2. 配置与记录实例

- 矩阵检查项来自 `check_template.purpose=verify`，不复用 patrol；清单走 acceptance 域独立 `acceptance_list_schema` / `acceptance_list_row`，表型标记由本域自持，**不塞入设备台账 L2 `equipment_type_schema`**。08 §7/§8 原先那套「清单型走 `equipment_type_schema` 的 `table_mode=list`」已在 08 中删除，口径以本文与 08 §0.1/§3.7 为准，不再按旧段落实现。
- 清单配置含稳定 `table_code`、行 `code`、名称/规格/单位/排序/必填规则及启用状态；录入/导出不以行号或名称识别。模板改名不换 code；动态增行由服务端分配稳定 code，禁止删除后复用旧 code。
- 批次先确定查验对象 `target_id`（资料集合、楼栋/单元/楼层/房屋/区域/设备等）；同物理对象在不同查验位置须显式建成两行 `acceptance_target`，不能用 nullable target_ref_id 或名称当唯一身份。批次内需记录任务分工：`work_scope=docs|site`，site 可再按 `building_scope` 或 `category_scope` 分配；外聘临时人员用批次级临时授权，不进入长期 `project_staff` 编制。
- `acceptance_record` 唯一键：**`(tenant_id,batch_id,target_id,table_code,item_code)`**。矩阵 item_code 是稳定项 code，清单 item_code 是稳定行 code；行内多个值存事实字段，不另造同键多行。项实例身份就是 `acceptance_record.id`（04 的 `work_order_issue.source_item_id` 存的就是这个值），不在记录表上再立一个同义字段；revision 不进唯一键。
- 缺项/待补和现场异常自动归集本域问题清单；资料缺项只形成问题事实，不由 AI 或查验人认定责任。现场查验**只有问题项落 `acceptance_record`**（照片/类别/事实），正常项不建逐条记录；覆盖确认按 target 级显式记录（"本栋/本册已逐项查验"），不用空记录凑数。问题项按对象一页录入；AI pending/error/重拍代次（`retake_seq`）采用 03 同样硬约束，仅约束问题项照片。
- **AI 复用走 09 §2.2 能力服务，不在 acceptance 里直接接模型**：现场查验用 `image_inspection` 辅助识别问题点（瑕疵/异常位置建议）；资料扫描用 `doc_scan_extract/doc_page_check` 做名称、编号、日期、页数、签章、缺页、数量的预提取。**类别不由 AI 判定**：AI 做不到专项识别，拍照后由查验人人工选择所属类别——类别就是各册/台账下的专项，如室外场地的园林植物、硬质景观、康乐设施、排水设施、环卫设施、标识标牌、室外照明、灌溉系统 8 项，或分户台账的入户门/土建/室内门窗/厨卫/水电表/强弱电 6 项；AI 只在已选类别内给问题点建议。AI 结果只生成待确认清单行/查验草稿和问题建议，必须人工确认后提交；缺页、无签章、编号/日期不一致、数量不符自动进入人工审核，不能扫描完就算已移交，也不能把 AI 建议当最终问题事实。

## 3. 问题事实与签字主体

承接查验**不让查验人员选择责任方，也不填整改期限**。现场只记录事实：缺项、异常、位置、照片与说明。按甲方口径，交接前的问题默认属于移交方/上一家需处理的事项；如确有争议，由项目负责人在报告与签署阶段处理，不在普通查验卡片上长期占位。

签字主体独立配置：查验人、审核人（原件通用签章页）；移交方、接收方（资料清单原件）；确需业委会/社区见证时另设明确身份和授权，不假称原件固定“三方签字”。每个主体记录组织/代表人、授权凭据、签署时间/报告摘要；流程审核通过不等于代替外部主体签字。

## 4. 状态/权限矩阵与交接条件

角色沿用四档；下列权限均叠加租户/小区、批次成员和对象范围，不以“主管”标签替代后端鉴权。

**新建批次权限**：项目经理/项目管理员可为自己管辖的小区/项目新建批次；租户管理员可查看本租户全部小区并为任一小区建批次；超管只能走显式租户管理流程，不默认替业务建批次。批次列表、编辑、送审、签署同样按该数据范围过滤，不靠前端隐藏。

| 转移/动作 | 权限与条件 |
|---|---|
| draft → inspecting | `acceptance:manage` 的批次负责人；确定配置、对象与抽查范围及查验成员 |
| inspecting → reviewing | `acceptance:submit` 的查验成员在负责范围完成；全部必填/证据齐，AI 无 pending；批次统一送审 |
| reviewing → inspecting | `acceptance:review` 当前节点非提交/查验人驳回，必填原因；原记录 revision 修订，不复制问题 |
| reviewing → handover | 当前非本人审核链全部通过；冻结审核事实和问题清单，生成待签报告 |
| handover → done | `acceptance:sign` 绑定主体本人签署，且所有必需主体签齐、遗留条件满足、报告文件已固化 |
| handover → inspecting | 未完成签署需补正：负责人有撤回权限及原因，已签草稿标失效，保留签署证据，再审再签 |
| done 后纠错 | 仅有 `acceptance:reopen` 的负责人申请、非原申请人批准；原件不改，补充修订重新审核/生成文件/全体重签 |
| 问题归集/报告输出 | 批次成员与授权管理人；问题只进本域清单与报告，不转工单、不做整改跟踪 |

转移采用状态+revision 条件更新，审核/签署不得本人审批本人查验成果；节点无人或只有本人时挂起升级，不能空链通过。签署校验全部冻结文件按 `volume_code + format + sha256` 排序形成的集合摘要，任一册或 DOCX/PDF 内容变化必须使旧签署失效。撤回走 `acceptance:manage`，已归档重开申请与批准均走 `acceptance:reopen`；重开申请存于 `acceptance_reopen_request`，批准人按自然人标识与申请人去重。

**遗留问题不必全部整改完成才交接**，但每项必须事实与证据完整、风险/安全措施明确、接收方明确接受且附在签署文件中；重大安全风险未有获批处置措施则阻断交接。系统只保留报告与签署事实，不提供整改跟踪；后续怎么处理由甲方线下或报事流程自行安排。

签后 `locked_at` 锁定记录与签署文件。报告归档后不重写事实；纠错须授权申请、非原申请人批准、重新审核并全体重签，不引模板版本系统。

## 5. 原件册号与报告边界（核验结果）

按甲方口径，承接查验台账分三类：**物业机构更迭承接查验、新建物业承接查验、物业分户验收**。现有母版覆盖第 1 类（机构更迭六册）与第 3 类（分户验收台账）；**新建物业承接查验母版甲方尚未提供，列为待确认输入**，未提供前不臆造其册号与表型。

依据实际 `docs/模板/承接查验/` 七个 docx 的 `word/document.xml` 封面及 `backend/.tmp/template_dump.md` 明细，不按摘要补齐缺号：

|---|---|---|
| 物业资料（第1册）1008 | 文件名第1册；封面实际留空 | 资料清单/照片、移交接收签字 |
| 房屋本体20261015 | 封面第2册 | 外墙屋面/楼道公区矩阵及照片 |
| 设施设备（第4册）20261013 | 文件名与封面第4册 | 矩阵/清单及设备编码（GB-01…） |
| 室外场地 | 封面“第   册”，未知 | 8 个专项各配记录/清单表+照片表：园林植物、硬质景观、康乐设施、排水设施、环卫设施、标识标牌、室外照明、灌溉系统 |
| 物业用房 20261015 | 封面“第   册”，未知 | 权属/实体/配套设施；100㎡/20㎡提示 |
| 地下车库（第6-册）20261016 | 文件名与封面第6册 | 权属及土建/排水/消防等专项 |
| 物业分户验收台账20261021 | 封面“第   册”，留空未定 | 户内分户查验，**一户一档**：6 类别（入户门/土建工程/室内门窗/厨房卫生间/水电表/强弱电）逐项 √×+问题数量；按区/栋分户验收记录表+问题照片表（一问题一行）；分户验收汇总表（楼栋×6 类别）；表计底数明细（水表/电表抄表底数） |

dump 的概览（约第569行）写“室外场地第5册”，但原始展开第3437行与原件均为空，故**撤销第5册断言，也不把物业用房臆定第3册**。物业资料 dump 摘要有第1册称呼，但实际封面也为空，来源标为文件名。六册报告模板≠已确认连续1～6编号；分户台账封面册号同样留空，册号由甲方确认后配置，未确认输出使用类别名并明示未定，正式编号签署前须确认。

分户台账与六册报告的口径差异：查验对象是**户（房号）**，target 落到房屋级 `acceptance_target`；每户一张记录表（一户一档），汇总表按楼栋聚合；表计底数（水/电表读数）作为事实数值记录进 `acceptance_record`，不回写设备台账。原件说明中"建立整改销项台账、督促责任主体闭环整改"是**母版原文**；本方案系统口径不变——分户查验问题同样只进问题清单与台账报告，不做整改跟踪（§3/§7）。台账一式叁份的执件主体按新建/机构更迭不同（建设单位/施工单位/物业企业，或业委会/原物业/现物业），沿用 §3 签字主体独立配置，不硬编码固定三方。

dump 旧汇总"118表"对应原六份承接模板，新增分户台账后明细各文件总数为 17/20/36/20/10/15/20；这些数字含封面/目录/签章/照片，不能当业务检查表数量；矩阵35/清单23等摘要不是配置导入验收数量，须逐表建 table_code 清单后验收。

L3 `doc_kind=acceptance` 按六个类别加分户台账配置输出模板，直接使用甲方原始 DOCX 母版，封面/目录/说明/签章/业务表+照片表保持原结构，仅按槽位写入真实事实与图片，不使用 Sections+Rows 自绘报告；不硬编码“6条租户行=册号1～6”。分户台账按区/栋装订：每户一张分户验收记录表（一户一档），栋级配问题照片表，册首为分户验收汇总表与表计底数明细。通用签章原件是“查验人员签章/审核人签章”（dump 第1936行），非固定三方。无 LibreOffice 时只能临时提供明确标注的 docx；要求 PDF 的正式部署不算验收通过，不假装成功。

输出槽位登记在 `acceptance/service/mother_slots.go`，以稳定 `table_code` 为唯一映射入口，禁止把任意记录写进固定“第一张表/第一行”。资料册使用 `documents_project/engineering/owner/operation/title/keys`；室外场地使用 `outdoor_garden/hardscape/recreation/drainage/sanitation/signage/lighting/irrigation`；物业用房使用 `premises_documents/building/assets`；地下车库使用 `garage_documents/structure/drainage/traffic/lighting/fire/ventilation/camera/access/civil_defense`。房屋本体按母版四个楼栋段登记 `building_{1..4}_exterior/common`，设施设备按 `facilities_*` 登记各专项。分户使用 `unit_door/building/windows/kitchen/meter/electric`，按实际户数复制完整“记录表＋照片表”段，不按母版示例房号写死。冻结项名称只用于在已登记表格内定位真实表头/清单行；找不到槽位必须渲染失败，不得降级为自绘或错写。

`acceptance_target.building_id` 是分户归属楼栋；`acceptance_record.value_map` 保存结构化事实，表计键固定为 `water_meter_number/water_reading/electric_meter_number/electric_reading`，数量使用 `quantity`。冻结和归档阶段均分别登记 DOCX 与 PDF 两种 `acceptance_report_file`，下载按登记格式返回，不以改扩展名代替转换。

`acceptance_target.table_codes` 是对象—专项分配关系，批次内同一 `table_code` 只能分配给一个对象；问题登记、资料核验、覆盖确认与渲染共用该关系。对象确认覆盖后，其矩阵专项中未登记问题的冻结项输出 √，已有问题事实仍输出 ×，不能因后填默认合格覆盖问题。`acceptance_problem` 另存 `risk_level/safety_measure/measure_approved/accepted/accepted_by/accepted_at/acceptance_file_id`；最终签署前逐项检查措施、接收人和接收文件，重大风险措施未获批即阻断。接收事实变更提升批次 revision、使本修订签署失效并重新生成冻结文件；River 任务唯一键包含 revision，不能复用旧任务或旧产物。

## 6. 数据模型（acceptance 域，目标）

| 表 | 关键内容 |
|---|---|
| acceptance_batch | tenant/community、批次、对象/抽样范围、status/revision、负责人/成员、审核链、locked_at |
| acceptance_target | `target_id`（本表主键，查验对象身份）、batch_id、对象类型/引用 ID、位置/名称快照 |
| acceptance_list_schema/row | table_code、稳定行 code、显示/必填规则；独立于设备 L2 |
| acceptance_record | §2 唯一键（`target_id` 为指向 acceptance_target 的普通外键，域内可用 FK）、verify/list、结果/值/缺项/证据、revision；仅最小展示快照，不复制模板树 |
| acceptance_problem | record_id 唯一、事实/位置/证据、风险与接受记录 |
| acceptance_signature | 批次/修订/报告摘要、签署主体及代表授权、签署证据/时间、失效原因 |
| acceptance_handover_log | 审核、签署与重签；签后增补不覆盖已签事实 |

历史修订仅保留事实/操作证据；不引入模板版本机制。跨域对象仅存 ID 和来源快照，不跨域 FK/join。

## 7. 问题归集与报告边界

- reviewing 通过进入 handover 后，已审核异常/缺项进入本域问题清单，并随报告输出。草稿、已驳回或普通查验人不能直接发布问题。
- 问题唯一键沿用 `(tenant_id,batch_id,target_id,table_code,item_code)`；重复提交、并发修订不重复生成问题。来源记录修订只追加审核/签署日志，不覆盖已审核问题事实。
- 问题不生成工单、不产生 `acceptance.issue.*` 生效点，也不做整改跟踪。报告只呈现问题事实、照片、风险说明与遗留接受情况；后续是否维修不由本模块闭环。
- 报告“处理情况”默认来自签署时的遗留接受文件快照；不开放手填，不能把“已写入报告”冒充“对方已接受遗留”。

App 目标页：批次 list/detail；资料 docs（独立清单配置）；对象 form；问题 issues（事实/遗留接受）；报告 report（审核、真实主体签署、下载与重签）。权限入口按 02 模块注册表过滤，服务端仍独立鉴权。
