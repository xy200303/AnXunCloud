## 破坏性迁移与上线门禁

**不双写、不留兼容接口。停写迁移与备份恢复不是兼容层。** 迁移前逐租户记录行数、主键、文件摘要、审核与签字关联、待处理任务，负责人签核清理范围。

**上线前必须给甲方一份“停业务成本单”**，不是只给技术门禁：预计影响的项目/巡检员/任务数、停写窗口时长与备选时段、通知责任人与通知文案、失败回滚时当天已提交记录/照片/审核结论如何恢复或封存、恢复演练实测耗时。甲方负责人需要拿它向业主交代；没有这份成本单和恢复演练记录，不得进入正式切换。

### 为什么期1 拆成 1A / 1B 两次切换

原计划把 6 件事压在一次停写切换里（表单式巡检、工单新域、可靠事件设施、模板 code 回填、安全补齐、维保生效），风险集中且回滚代价极高：按本文禁止兼容层的纪律，回滚 = 恢复备份 + 丢弃新版本已写入的事实。

关键区别是**有没有存量数据**：

| | 切换 1A（停写） | 切换 1B（不停写） |
|---|---|---|
| 范围 | 1.1 / 1.2 / 1.3 / 1.5 / 1.6 / 1.7 / 1.8 / 1.10 / **1.11** / **1.12** | 1.4 工单域 / 1.9 的 River 任务队列部分 |
| 性质 | 改既有表结构、回填 code、精简快照、租户归属回填、改既有维保确认语义 | **全新表，零存量数据** |
| 为什么这样分 | 存量打卡事实/草稿/模板/任务/待确认维保流水必须在停写窗口内一次性转换或排空，歧义映射须人工确认 | 新域没有要迁的数据，停写对它毫无意义；可灰度、可观察、出问题只停新功能不动既有事实 |
| 失败处置 | 保持停写、中止上线、按下方切换顺序恢复 | 关闭新模块入口即可，巡检主链路不受影响 |

**判据是"有没有存量数据要改"，不是"表是不是新建的"**：1.11 维保生效虽然新增批量登记单表，但它同事务改写既有 `equipment_maintenance` 的确认语义与存量台账日期，还要处置存量 pending 流水，所以归 1A；反过来，工单域和事件设施完全没有存量数据要迁，放进停写窗口只是白白延长停机。

1B 内部不再有"事件设施先于工单上线"的顺序要求 —— 跨域联动已改为同事务函数调用，没有需要先行观察的投递设施（01 §4.2）。1.11 维保生效在 1A 即在 equipment 事务内完成，不依赖任何队列。

期2 的 L3 输出与归档闭环仍是一次切换（见期2 表与 2.6），不因本节拆分而放宽 LO 环境门禁。

切换顺序（1A 与期2 各执行一次完整流程；1B 只需第 4 步的回归与监控，不停写、不备份窗口）：

1. 在隔离恢复环境演练 DB + uploads/对象文件 + 必要 Redis 状态/配置引用的同一恢复点，记录恢复耗时与校验；密钥仅引用现有保管系统，不进方案包。
2. 发布最小 App 版本门槛并启用旧版**服务端停写**（含草稿/照片关联/离线补传/审核），通知并排空客户端离线任务；前端弹强更不是唯一屏障。停止定时任务、worker 与 relay，排空/取消外部 AI、LO 工作并核验无在途回写。
3. 停写后最终备份并验证可恢复；执行一次性转换与 Goose。现有 Goose 有 PG 会话锁和迁移失败中止启动，但不能代替发布停写/备份，也不保证非事务步骤自动回滚。
4. 校验行数/关联/租户/文件摘要/任务集合，跑构建、回归、安全负例、事件崩溃验收、LO 隔离与真实多册签字归档，再开新版本写入口、worker 和调度，监控积压/死信/失败率。
5. 任一步失败即保持停写，中止上线，禁止部分新结构对外。仅在确认恢复点和全部写入口关闭后协调恢复 DB/文件/队列及旧服务版本；验证一致性后恢复旧写入。新版本若已开放写入，先封存新增事实并评估恢复损失，不可直接回滚覆盖；恢复不是长期兼容双写。

容量、耗时和恢复目标按 09 §5 的**待压测预算**与现场演练修订。每期保存验收证据，未过门禁的项仍标待实施/待验收，不以“方案定稿”替代交付。
