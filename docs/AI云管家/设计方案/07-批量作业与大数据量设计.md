# 07 批量作业与大数据量设计

> 甲方小区量级：设备数千台、巡检点位数百至数千、承接查验房屋数千户。
> 本文是 01～09 重构目标的统一批量/性能契约，不是现状验收单。现有维保有单台登记、批量确认及台账回写基础，但筛选快照、批量登记单、严格并发与错误分类仍须实施；`../APP原型/预览/v2/` 中的画板不等于已落地。

## 1. 统一原则（所有列表与批量操作共用）

| 原则 | 口径 |
|---|---|
| 列表 | 服务端稳定排序/游标分页 + 客户端增量渲染，默认20/屏；筛选按类型/楼栋/状态缩圈 |
| 多选 | 增量加载时保留已选；**筛选/选项卡变化立即清空旧选择并提示**，不混入旧筛选的隐藏选择；可通过「清空选择」和已选清单逐条取消退出多选 |
| 全选 | “全选筛出的 N 项”不是当前页；先请求服务端预览，显示数量、业务摘要/冲突及权限范围 |
| 载荷 | 手选 `ids[]` 或全选 `filter + excluded_ids[]` 二选一，均带 `selection_token + operation_id + payload_hash` |
| 快照 | selection_token 绑定用户/租户/动作/规范化筛选/排除项/截止时间及候选集合摘要；服务端暂存候选ID/版本或等效可重现快照，token 有效期明确 |
| 落库重查 | 只在预览集合内与**当前权限/状态**求交，不加入预览后新匹配项；不能把快照当授权。权限改变须拒绝/重预览，状态漂移按 §7 分类 |
| 排除项 | 去重并验证属于快照且有权限；篡改 token、额外 ID、越权 ID 均拒绝，不静默吞掉 |
| 事务 | 打包/分派/批量维保单为一个原子业务单元；**跨域联动在同一事务内完成**（01 §4.1），外部副作用（通知/AI/渲染）用 `InsertTx` 与业务写入同事务入 River 队列（01 §4.3）；部分成功模式须按 §7 明示 |
| 防呆上限 | 维保单批500台 / 派单单批200项 / 任务生成单次2000点位；预览和落库双重校验，超出要求拆批 |
| 幂等 | `(tenant_id,actor_id,action,operation_id)` 唯一，同键同载荷返回原回执，不同载荷409；另有领域唯一键，不以“一台同日一条”误杀合法不同维保 |

令牌过期、候选/规则实质变化、权限失效时返回明确错误并重预览。数据库读取失败不能伪装成“无匹配项”；最终回执区分入库成功与异步任务（通知/AI/渲染）是否已入队。

## 2. 巡检侧

现有代码已有两类能力，方案只收口口径，不重新发明：

- **任务点位列表**：分页 + 增量渲染；按楼栋/类型/完成状态筛（小区管理 → 小区点位页已有筛选雏形，统一口径）
- **计划批量生成**：按楼栋/类型批量生成任务（现有），单次任务点位上限 2000，超出提示拆任务
- **抽查计划**：现有 `inspection_plan.plan_kind=spotcheck`、`spotcheck_config` 支持 `ratio_percent` 抽查比例 / `fixed_count` 固定数量（二选一，固定数量优先）、`strategy=random|longest_unseen`、`no_repeat` 连中保护、`due_day` 完成期限日；抽查计划当前仅支持 monthly，任务用 `inspection_task.due_date` 判定逾期。计划编辑与巡检/报告计划采用同一类表单，明确展示周期、范围、模板、比例/数量与执行人，不只暴露一个比例。灭火器压力、日期专项按 2% 配置；防火门、应急灯、安全出口指示牌、手报、喷淋头、烟感等按月抽查，比例未确认时不内置默认值。设备日期标签抽查另有确定性哈希：类型 `spot_ratio` 优先于全局 `equipment.spotcheck_ratio`，长期未验证（超 6 个月）翻倍且 cap 100。新 UI 只把这些已有配置暴露清楚，不按名称前缀另造规则。
- **打卡审核列表**：列表卡片只承担选择与进入详情，**不放单个通过/驳回按钮**；批量动作固定在底部「已选 N 条」操作条，单条进入审核详情后在底部选择通过或驳回。低风险正常记录可批量通过；异常、改判、无法检查和 AI 失败记录必须逐条看证据。
- 巡检表单页一次一个点位，两类连续录入场景：`level=place` 点位（泵房）下逐台设备连续出项（先场所项、再按设备清单逐台）；模板/检查项批量录入（145 项，见下）
- **模板批量录入（期1）**：Excel 粘贴生成模板与检查项，先预览行级错误/冲突。code 冲突必须显式选择覆盖并校验权限/revision，不静默覆盖；独立模板可选部分成功，同模板项/发布必须原子，按 §7 返回分类结果。

## 3. 维保侧（批量登记与确认目标）

换粉/水压试验允许同小区、同设备类型、同动作/施工日期批量单；维修/更换新瓶可单台。路径必须是：列表/扫码选设备 → 系统带出对象、到期规则与已有巡检/工单证据 → 只补缺失证据 → 动作由人显式选择（不默认）→ **提交待确认**，不是立即生效。批量登记不得把已选设备清空后要求重新勾选；不满足同批的组合在预览阶段提示拆分。AI 读取标签/日期只作辅助预选，pending/failed 不阻塞维保登记提交；人工日期可填可改并留痕，主管确认时兜底核对。

**计划/到期维保的工单生成与批量登记同粒度**：触发时间为 `next_due_date - assign_lead_days`（按设备类型/小区配置，缺省 7 天；已逾期由每日到期扫描即生成）。聚合键为 `(tenant_id, community_id, equipment_type, maintenance_action, due_period/施工批次)`，一张维保工单带逐台 item；工单项幂等键 `(tenant_id, order_id, equipment_id, maintenance_action)`。已有未关闭或已确认的同键项不重复生成。巡检异常引出的单台维修仍按来源项实例成单，不与计划维保聚合。聚合维度由维保计划配置，不允许现场人员临时把不同批次拼成一单。

| 状态转移 | 权限/校验 | 生效边界 |
|---|---|---|
| draft → pending | `maintenance:register` + 本小区设备执行范围；校验日期/动作/文件与快照，冻结成员清单 | 仅登记单/明细，不产生已生效流水，不改台账日期 |
| pending → rejected | 当前确认节点 `maintenance:confirm`，非登记人；必填原因 | 单与明细保持未生效 |
| rejected → pending | 原登记人或授权接替人修订重提，revision 条件更新 | 保留原单/明细身份与旧证据；不重复生流水 |
| pending → pending | 当前非本人节点通过，但仍有后续节点 | 只推进环节，不能提前回写 |
| pending → confirmed | 当前非本人末节点确认，重新锁定/核对成员及设备权限状态 | **同事务**最终确认整单 + 逐台生效流水 + 回写日期/计算到期日，并在同一事务内完成 01 §4.1 的 `equipment.maintenance.confirmed` 生效点 |

- 默认人工确认；批量单强制至少一名合格非登记人确认，空流程/空名单不自动生效，挂待配置并升级。不得照搬现有单台服务空流程直通。
- 唯一有效流水键 `(tenant_id,batch_registration_id,batch_item_id,maintenance_action)`；相同设备同日不同合法动作可共存，重试/驳回重提不能复制流水。已确认单不原地修改，纠错须授权冲正/补录且保留审计。`equipment_maintenance` 现状只有 `tenant_id + equipment_id`，按项目过滤要 join equipment；改为冗余 `community_id` 并在确认事务内一并写入，与巡检/工单域"每条数据带项目 ID、按 `identity.ProjectIDs` 集合过滤"的口径一致。
- 确认按稳定设备ID顺序加锁，状态+revision 条件更新，只一个确认胜出；设备已报废、被移出范围、动作冲突、台账日期较新时返回具体冲突。不能盲目用旧日期覆盖新日期；确有较早历史施工须独立授权补录，生效流水与“不推进最近日期”结论一并留痕。
- 批量单是原子确认单位，任何成员确认冲突整单保持 pending 并提示重预览/修订，不允许显示“整批已确认”但部分设备未生效。若需拆批，先显式形成新单关联原单，重新预览/审核；不能后台静默剔除成员。
- **纯维保与混合工单都只审核一次**：主管通过即完成工单，并在同一事务中按设备规则回写有效日期；维修/清理类只记维修记录。主管可自主现场或电话核查，不产生额外地复查任务。导出仅取 confirmed 流水，走 `engine=xlsx_template`，不把 pending 当完成。
- 确认列表卡片不放单个通过/驳回按钮：整卡进入确认详情，在详情底部选择「驳回 / 通过」；同批次、同动作、同证据集合的批量确认固定放在列表底部操作条。所有确认均用居中弹窗，不把主操作藏在点击卡片展开后；跨批次或成员有冲突时必须拆单重预览。
- 当前 `equipment/service/maintenance_service.go` 已有 Register/Confirm/ApplyLedgerWriteback，但不等于上述批量单契约完成；尤其注册权限仅租户放行、空链直通、数据库错误混同 NotFound 等旧路径须替换，不保留双轨。

**`pending → confirmed` 是本方案最长的单事务，必须单列压测场景。** 一次确认在同一事务里写整单确认 + 最多 500 台生效流水 + 500 行台账日期回写，并按稳定设备 ID 顺序逐行加锁。09 §5.2 的负载表目前只覆盖在线混合、AI、报告，**没有这个场景**，而它恰恰是锁持有时间最长、最容易在真实数据量下暴雷的一处。验收须包含：

| 维度 | 要测什么 |
|---|---|
| 规模 | 按 §1 防呆上限满额 500 台确认，另测 50/200 台对照，记录事务时长分布 |
| 锁 | 行锁持有时长、锁等待队列、与同小区并发巡检写入的相互阻塞；确认是否需要分批提交或缩短锁窗口 |
| 超时与重试 | 事务超时阈值、死锁重试次数与退避、重试耗尽后的回执语义（整单保持 pending，不得出现部分生效） |
| 并发 | 两名合格确认人同时确认同一单：只一人胜出，败者得明确 conflict 与最新 revision；不得双写流水 |
| 冲突回滚 | 单内任一设备已报废/被移出范围/台账日期较新时整单回滚，核验无残留流水与无半写回的台账日期 |

压测结论要同步补进 09 §5.2 的负载表（本文不代改）；若 500 台满额确认达不到可接受的事务时长与锁等待，先收敛 §1 的防呆上限或改为显式拆批（拆批必须形成新单关联原单，不得后台静默剔除成员），不得以"实际不会有人一次确认 500 台"略过该场景。

## 4. 工单/派单侧

- **工单池**：分页 + 筛选（类型/楼栋/来源/状态），数据为自动生成的待接单工单；巡检异常不再停留在等待手工打包的散件池。「全选筛出的 N 单」仍使用统一快照口径。
- **合并与批量分派**：仅同小区、同专业且未接单的工单可合并或批量派一人，操作人及候选执行资格均在落库前重查（04），不只查编制；并发已占用返回冲突，不抢覆盖。批量催办是独立通知任务。
- **我的任务**：统一承载派给我的巡检、整改和维保执行任务，仍分页，个人量小不能成为无界返回理由；不再另设「我的工单」。
- issue 防重键 `(tenant_id,source_type,source_item_id)`，不是一条打卡记录一个事项。一个记录多个异常/同项多设备必须分别建 issue 及对应待接单工单，驳回修订与并发重复调用不重复建。

## 5. 承接查验侧

- 对象清单按楼栋分页；抽样比例由批次配置并固化对象范围，不把5%当甲方定值，也不因数千户自动免查必查公共/安全对象。
- 问题批量归集先快照预览，再按 05 的审核状态/批次权限重查；每项按 `(tenant_id,batch_id,target_id,table_code,item_code)` 唯一。遗留接受状态在报告中展示，不转工单、不做整改跟踪。

## 6. 报告/统计侧

- 月报按 tenant+小区+月份建索引，审核生效记录与现场提交量分列；不实时扫明细大表。
- 版式按 `doc_template`，不得为压页数裁明细。5本巡检报告逐册独立任务、失败可单册重试，zip 只含真实成功产物并明示失败册，不伪报整套成功；空册完整输出骨架。
- 照片并发预压缩、LibreOffice 转换串行；无服务只给 docx 并明示。承接查验六份类别与未知册号按 05 原件核验，不硬补3/5册。

## 7. 错误分类与原子边界

不能用“一台出错都跳过”覆盖安全与系统错误，也不能将所有数据库错误当 NotFound。

| 分类 | 处理与回执 |
|---|---|
| 同 operation_id 已成功、同领域键已处理 | 幂等返回原成功结果，或明确 already_processed；不是第二次成功写入 |
| 可预期状态漂移/并发占用 | 明确 conflict + 当前版本；原子单整体无变更，要求重预览；仅允许独立项模式跳过 |
| 参数/模板/证据错误 | 预览列出行级校验错误；未经确认不落库。原子单任一错误即拒绝 |
| 越权/跨租户/令牌篡改 | 整请求拒绝且审计，不暴露外租户对象存在性；不得当成功跳过 |
| 数据库断连/超时/死锁重试耗尽、非预期异常 | 当前原子单回滚，返回明确可重试系统错误和 request_id；不得吞掉继续 |
| 业务已提交但异步任务（通知/AI/渲染）未完成 | 回执业务已提交 + 任务已入队，队列按 01 §4.3 自行重试，不让用户再次提交事实 |

**部分成功仅适用于相互独立的单元**（如多模板导入、多个单册报告、已显式声明的多工单催办/逐单操作）。预览必须显示模式，逐单事务各记幂等回执；禁止将一个批量维保单、一个打包单、一次最终签署偷偷拆为部分成功。批量正常巡检审核还须排除异常、存疑、改判、AI error、无法检查及本人提交记录，逐记录核验当前审核节点。

返回 `operation_id/status/committed/succeeded/already_processed/conflicts/validation_errors/failed/retryable` 及逐项原因/回执，计数须能对账。外层系统错误必须同时标明是否已有独立单元提交，不能只报“跳过N”或“一切失败”；重试只处理未成功单元。异步任务（通知/AI/渲染）另列入队与执行状态。
