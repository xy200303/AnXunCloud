## 0. 结论与范围
### 0.1 三层配置与本期硬边界
甲方材料是 **13 份 docx（5 本巡检、6 册承接查验、1 本分户查验台账、1 本换粉维修）+ 1 份 xlsx 设备档案**，见 `backend/.tmp/template_dump.md`。原件是输出样式和业务口径的输入，不等于 13 套执行模板；xlsx 设备档案也不等于换粉维修流水报告。

| 层 | 回答什么问题 | 载体 | 边界 |
|---|---|---|---|
| L1 检查项模板 | 查什么、怎么判、拍什么 | `check_template` / `check_template_item` | 类型、用途、频次建议、值类型、标准、稳定 code、录入顺序；**不存输出分组、列宽、列序、合并跨度** |
| L2 设备档案字段方案 | 设备档案显示、录入、导入导出哪些字段 | `equipment_type_schema` | **仅设备档案**；非设备的资料、钥匙、园林清单不进入这里。**动态列已是现有实现、非待建**（`equipment/index.vue:89-99、455` 按 `config.list_columns` 渲染，无方案时回落默认列集）；唯一索引用**两个部分唯一索引**（`00052:18-19`）而非 `COALESCE` 补丁，随 06 的 1.0b 改 scope 两列的成本低于另三张表 |
| L3 输出模板 | 哪些表装订成哪本、怎么排版和绑定 | `doc_template` + `template_output`（owner=report） | StylePack + 块 DSL；输出分组、列序、行模式、照片区都归 report |

本期 L1 必须同时完成：`point_type` 必填及 19 类字典、`purpose=patrol|spot|verify`、两态 `draft|enabled`、稳定项 code、值类型/标准/值区间、计划明确选择模板及任务保留选择结果。**同类型多套不是二期能力**：控制室两张执行表当期就必须区分，禁止把点位所有模板无条件并集成一张表单。

**不做版本机制**：L1、L3 均无版本表、`version`、`published_version` 或历史重建接口。逐项事实及最小展示快照保留；重出按最新配置生成新编号、新审核的新报告，旧归档永不覆盖。稳定 code 负责身份对齐，不负责还原旧结构、旧标准规则或重算历史结论。

`check_template_group` 不建；若试验库已建，其输出属性迁入 report 后删除。`template_output` 按 **租户 + doc_template + check_template** 绑定，不做模板级 1:1；同一套执行项可在不同册子有不同表头、列序和宽度。

承接查验矩阵可消费 `purpose=verify`，但配置选择、对象、记录和流程属于 acceptance；清单型由 acceptance 自有配置及稳定行 code 管理（§7）。维保是确认后生效的批次/流水，不是检查项模板；如需逐项作业检查，另选 `purpose=spot`，不把维保字段塞入 L1。

**命名约定（全文及 01~10 一致）**：`check_template.purpose` 是检查用途（patrol/spot/verify），`doc_template.doc_kind` 是输出文档类别（monthly_report/acceptance/maintenance_ledger），两者不是一回事，不再共用 `kind` 一个词。被检对象一律用具体实体名（`equipment_id`，NULL=场所自身），不使用 `target_instance_id`/`subject_key`/`occurrence_id` 这类抽象键名；跨域来源引用统一 `source_type`/`source_record_id`/`source_item_id`。

可按需延后的是 L1 复制母版（blueprint）、词库与片段；**不包含本期计划模板选择，也不包含 L3 必需的 StylePack 输出母版**。本篇是待实施方案，不把原件解析结果、源码阅读或保真目标当作真实渲染已验收。

### 0.2 术语与数据流
- `point_type` 是检查点/场所类型，决定模板候选和报告归章；`equipment_type` 是资产类型，决定设备档案、生命周期规则。唯一连接是 `equipment_type.attrs.point_type`，不另建硬编码映射。
- L1 模板是执行检查定义；blueprint 仅是复制起点，不做运行时继承。StylePack 是输出样式母版，不是检查项母版。
- DocModel 是经过绑定、宽度和安全校验的输出块模型；装配器通过各域公开 API 取得 DTO，渲染器只消费 DTO/DocModel，不查库、不跨域 join。

```text
L1 类型/用途候选 → 计划明确 template_ids → 任务保留选择结果
  → 场所/设备/重复实例逐项事实 + 最小展示快照
inspection / equipment（档案、confirmed维保）/ acceptance 各域公开 API
  → report 装配器 → doc_template + template_output + StylePack
  → OOXML DOCX → soffice PDF → PNG → 冻结预览 → 审核 → 独立签字归档任务
```

### 2.2 六册承接查验
原件约118张表，含矩阵、对象行清单和统计，封面/册目录/说明/签章/对象表/照片表成组。范围包括物业资料（资料、权属、钥匙门卡）、房屋本体、设施设备、室外场地（园林植物等）、物业用房、地下车库。表数含照片配对，不能当作118套 L1。矩阵消费 verify，非设备对象行清单由 acceptance 自有配置和稳定行 code 管理，详见 §7，不借设备 L2。

另有**物业分户查验台账**（20261021，20 张表）是六册之外的独立交付件：户内专项核验，**一户一档**。封面册号留空；说明明确一式叁份且新建/机构更迭执件主体不同；结构为分户验收汇总表（楼栋 × 入户门/土建工程/室内门窗/厨房卫生间/水电表/强弱电 6 类别）→ 按区/栋的分户验收记录表（每户一表，√/× + 问题数量，附查验标准）+ 栋级问题照片表（一问题一行）→ 分户验收照片（按类别问题明细）→ 表计底数明细（水表/电表抄表底数）。分户记录表矩阵消费 verify，表计底数作事实数值记录；说明中"整改销项台账"系母版原文，系统侧仍只进问题清单与报告，不做整改跟踪（05 §3/§7）。

### 2.3 换粉维修与设备档案是两份业务
- docx 换粉维修台账：封面/说明/签字 → 第一批明细与照片 → 第二批明细与照片。八列是序号、灭火器编号、位置、数量、生产日期、最近换粉日期、下次换粉日期、状态；批次四字段为维修人、维修单位、批次、验收人；资料含收集、送检、归位照片和票据证照。
- 生命周期原件规则区分：**首次换粉5年、之后2年；首次维修3年、之后2年；10年报废**。参数按设备类型和作业类型配置，不把换粉/维修混为同一 first_months。
- xlsx 唯一 sheet“设备档案”只有项目名称、所属设备系统、设备分类、点位信息、换粉日期五列，是 L2 档案导入样本，不是完整批次维修台账。完整 L3 输出必须从批次+confirmed流水装配，不可只读 equipment 当前日期逆推历史。

### 2.4 差异承载位置
L1 负责项数、值类型、单位、标准/值区间、必拍/备注要求和录入顺序。以下全部在 report：`template_output.columns` 的输出列序/宽度、`header_groups` 的两级表头及引用项、row_mode（date/point/grid/equipment）、row_axis、header_fields、issue_columns、photo_inline、standard_prefix。跨度由引用列推导，不建 `check_template_group`。

日期级按一次实际检查实例输出，点位级一行一点位、设备级一行一设备，grid按楼层/区域展开；同日多轮不能取最后一条吞记录，应保留实例或明确经甲方确认的聚合口径。表尾标准由当前 item.standard 按 standard_no 归并，standard_no是标准引用编号，不是列序。问题表列与照片墙因原件而异（器材有处理情况、系统可为照片墙+备注），不写死所有问题表五列。固定骨架可以复用，但签字角色、汇总列和问题区仍需配置及验收。

## 3. L1 检查项模板（本期执行契约）
### 3.1 归属与选择
一个模板只归属一个非空 `point_type`，无“全设备通用模板”。字典 `attrs.level=place|object` 决定先场所项、再逐台设备项，场所点位允许挂0~N设备。类型只产生候选，**计划选择才决定本次查哪套**；设备档案仍按 equipment_type，不把泵房与水泵合成同一字典。**消火栓（栓箱）与灭火器按实际安装位置分别建点位、分别打卡拍照，不得合并成复合点位一次打卡，且一设施一点位一凭证（NFC/二维码），不共用**——两者物理上不一定在同一位置，前期建点工作量大不作为合并理由（甲方口径）；专项抽查（如灭火器压力/日期抽检）按设备逐台拍照，本就独立，无需再拆。

### 3.2 字段与唯一性
以下是目标结构约束，不是可直接执行的完整迁移 SQL；新增非空约束必须在 §1 回填完成后施加。

#### 3.2.3 判定权威只有一条线

`judge_type`/`judge_config` 当前一列同时承载**三个正交维度**（证据：`internal/pkg/ai/client.go:338` 的 `judgeInstruction`、`template_service.go:223` 的 `rejectBuiltinJudgeType`、`ai_item_jobs.go:112/596` 的 manual 分支），必须拆开：

| 原 `judge_type` 取值 | 去向 | 说明 |
|---|---|---|
| `metric` + `judge_config{metric,unit,min,max}` | `value_type=number` + `unit` + `value_min`/`value_max` | 判定参数只剩一个来源 |
| `state` / `indicator` + `judge_config{expected}` | `value_type=enum` + `enum_options`（提示语仍留 `ai_prompt_kind`） | 期望值不再存两处 |
| `general`/`presence`/`damage`/`label`/`passage`/`leak`/`tidiness`/`baseline`，以及上面两项的提示语部分 | `ai_prompt_kind` | **只生成 prompt 文本，不判 abnormal** |
| `manual` | `ai_enabled=false` | 这不是判定类型，是"要不要调 AI" |
| `equipment_validity` / `equipment_date_spot` | `builtin_kind` | 系统内置合成项标记 |

落地后 `judgeInstruction()` 签名由 `(judge_type, judge_config)` 改为 `(ai_prompt_kind, value_type, unit, value_min, value_max, enum_options)`；输出的 prompt 文本基本不变（`metric` 仍生成"读取表计数值填入 reading"），但**参数只有一个来源**，不会出现 `judge_config` 与 `value_min/value_max` 两套区间打架。

`builtin_kind` 同时取代 §1 要收口的 `strings.HasPrefix(name, "设备维保·")` 名称前缀判断；**不再另加 `synthetic` 列**，否则合成项会出现名称前缀、`judge_type`、`synthetic` 三套识别方式。

判定归属：`number` 看 `value_min/value_max`；`enum` 看 `enum_options`；`ok` 看 AI verdict + 人工确认/改判；`text` 不判定；**`date` 不判定、仅记录** —— 台账日期比对由 `builtin_kind=equipment_date_spot` 的内置合成项负责，用户自配 date 项不需要任何判定配置列。

`models.go:182` 现有注释只列了 11 个取值，漏了 `manual` 与两个 `equipment_*`（`NormalizeJudgeType` 实际接受 14 个），迁移时一并修正。

#### 3.2.4 code 与 id 的分工

两者回答不同问题，都要保留：

| | `id`（uuid） | `code`（varchar） |
|---|---|---|
| 回答什么 | 这一**行**是哪一行 | 这个**业务概念**是哪个 |
| 唯一范围 | 全局 | `(tenant_id, template_id)`；整模板复制后可重名 |
| 跨库/跨副本搬运后 | 变 | 不变 |
| 谁引用它 | `work_order_issue.source_item_id` → `checkin_record_item.id` | `template_output.columns`、`checkin_record_item.item_code` |

一句话：**同库内指向一行用 `id`，跨库/跨副本/给人看指向一个概念用 `code`。**

`code` 不能当主键：按 §3.6 整模板复制后项 code 可在不同模板下重名（不全局唯一），工单引用项实例需要单列窄键，code 自带退役状态，且 `checkin_record_item` 是千万行级表（09 §5.2）。

`code` 必需的四个理由都在本期范围内：① Excel 批量录入的 upsert 键（§5、§9 —— 运营人员不可能填 uuid，重复导入必须是更新而非重建）；② 模板包导出/导入与跨环境搬运（§5 改动兜底与模板包）；③ `template_output.columns` 的可读性与可迁移性；④ 整模板复制后保留项身份（§3.6）。**若其中任一需求被砍，`code` 的必要性须重新评估。**

**必要配套（不是可选项）**：`check_template_item` 当前**没有** `DeletedAt`（对比 `check_template` 有），`DeleteItem`（`template_service.go:397`）是物理删除。由于记录事实存的是 `item_code` 而非 `item_id`，项被硬删后 §3.4.2 的装配对齐就取不到项名/标准。必须加 `retired_at` 改软删，唯一约束覆盖已退役行，退役 code 不可复用。

不建 `check_template_group`、不加 item.group_id；输出分组只在下面的 report 配置中。L1.sort 仅为录入顺序，不能暗中变成所有册子的列序。

```sql
-- owner: report；跨域 template_id 仅存ID，不建跨域FK
CREATE TABLE template_output (
  id uuid PRIMARY KEY,
  tenant_id uuid NOT NULL,
  doc_template_id uuid NOT NULL,
  template_id uuid NOT NULL,
  sort integer NOT NULL,
  columns jsonb,                      -- NULL/空 = 该模板全部未退役项按 sort 成列（默认规则，见下）
  header_groups jsonb NOT NULL,
  row_mode varchar(16) NOT NULL,
  row_axis jsonb NOT NULL,
  header_fields jsonb NOT NULL,
  standard_prefix varchar(32),
  issue_columns jsonb NOT NULL,
  photo_inline jsonb NOT NULL,
  UNIQUE (tenant_id, doc_template_id, template_id)
);
```

**`columns` 可以为空，空=该模板全部未退役项按 `sort` 成列**——这是 §4.9「改检查项 → 报告自动多一列、不用发版」能成立的前提。非空时只作**覆盖**：调整列序、隐藏某列、指定宽度策略；新增的 L1 项默认仍然出列，不因 `columns` 已有内容就被漏掉。要显式隐藏新项必须单独配 `hidden`，不能靠"没列进来"隐式排除。项名/值类型/标准一律从 L1 公共 API 读取，不再复制一份可编辑业务定义。`header_groups` 存标题与连续 item_codes，跨度从列推导。相同模板在不同 doc_template 下可有不同布局。绑定只允许同租户对象；平台内置输出作为复制源，先复制为租户 doc_template/绑定再选用，不能以 NULL tenant 绕过唯一性和隔离。

code 大小写/格式由服务统一规范化、非空且创建后不可改；模板 code 在租户内唯一，项 code 在租户+模板内唯一。删项保留退役身份占位（或只含身份的 tombstone），唯一约束覆盖退役项，**删除后不可复用 code**。含义变化建新 code，不把新项伪装成旧项；模板 code 同样不可删除后复用。复制为新模板获得新模板身份，可保留局部项 code，因为唯一范围不同；导入不能绕过退役占位或按同名重建 code。

### 3.3 值类型与 App 渲染
| `value_type` | App 控件 | 判定（唯一依据，见 §3.2.3） |
|---|---|---|
| `ok`（√×） | 「正常 / 有异常」等宽分段按钮（高 ≥48px）+ 异常观察点 tag；不用小圆点单选 | AI verdict + 人工确认/改判 |
| `number` | 数字输入 + 单位，`value_min`/`value_max` 前端即时提示（越界高亮），提交以实测值为准 | 服务端按 `value_min`/`value_max` 判 abnormal；AI 读数（`ai_prompt_kind=metric`）仅作交叉校验，不替代服务端判定 |
| `date` | 日期选择（生产日期由 AI 读标签预填） | **不判定，仅记录**；台账日期比对由 `builtin_kind=equipment_date_spot` 内置合成项负责 |
| `text` | 单行输入（水表读数/位置说明） | 不判定，仅记录 |
| `enum` | 选项按钮（对讲结果 正常/异常） | 按 `enum_options` 判 |

`standard`（单项标准原文）在项下以浅色小字展示——把甲方表尾的"检查标准"搬到每个检查项旁边，比按编号回查表尾好用。**录入侧永远同构**：App 里就是一张"检查项卡片"列表，差异只通过 `value_type`（换控件）、`standard`（换说明文字）、`photo_required`/`note_required`（换必填项）体现，**绝不按模板定制卡片布局**——否则 20 套模板就是 20 份页面。

### 3.4 两态、事实与历史口径
`status=draft|enabled`；published_at 仅是启用时间。模板修改/发布/导入写审计，但不建版本树、模板版本快照、历史重建或自动回滚接口；人工导出/导入仍受 code 身份规则约束。

#### 3.4.1 重出不等于重建
补印直接取旧归档文件。按最新 L1/L3 重新生成上月报告时创建新编号、新审核，旧报告不覆盖；新增项无旧值显示未采集，删项不出列但原事实保留，不能把空值当正常。当前标准不能重算并覆盖历史结论。待审件已冻结，模板变更不影响它；需要内容变化则作废后新建报告。

记录保留的 name/standard 是当次最小展示文本，可以回答该记录展示了什么；**不能由此恢复当时全部结构、判定区间、AI规则、输出布局或重新执行历史判定**。完整历史外观只在归档件中，不把审计日志、JSON导出或数据冻结批次包装成版本机制。

#### 3.4.2 记录项实例键与精简
- 定义项身份是 `(tenant_id, template_id, item_code)`，但它**不是**记录实例键。同点位两台设备、同日多轮不能相互覆盖。
- 主记录唯一键 `(tenant_id, task_id, point_id, round_seq)`；`round_seq` 由服务端确定（第几轮），补巡必须显式关联原记录。
- 记录项用独立 UUIDv7 `id` 作为异常/工单关联身份，业务唯一键为：

```
UNIQUE(tenant_id, record_id, template_id, item_code, equipment_id)
```

  `equipment_id` 非空=该项针对这台设备，**NULL=场所自身的项**（场所就是 `record_id → point_id`，不需要再编码成 `place:<point_id>`）。不使用 `subject_key`/`target_instance_id` 这类抽象键名。

  **Postgres 细节**：普通唯一索引里 `equipment_id IS NULL` 不去重。采用两个部分唯一索引（`WHERE equipment_id IS NULL` 与 `WHERE equipment_id IS NOT NULL`），不依赖 PG 15+ 的 `NULLS NOT DISTINCT`。若记录项将来改分区表，唯一约束及引用必须带其分区键（如 `record_created_at`）。

- **不设 `occurrence_id`**：`round_seq` 已把同日多轮拆成不同 `record_id`，该列只剩"同一记录内同一项重复测量"一个用途，而表单交互（一项一卡，03 §2）不支持该场景。将来确需多次测量再加列，本期不预建。
- **`source_item_instance_id` 不是本表的列**：项实例身份就是本表的 `id`。04 的 `work_order_issue.source_item_id` 存的就是这个 `id` 值，不要在记录项上再立一个号称"不可变项实例 ID"的字段（03 §5 原表述一并修正）。
- 草稿、AI job、照片绑定、提交校验、任务进度必须沿用相同的模板/对象身份（`template_id` + `item_code` + `equipment_id`），不再用 `item_name` 去重。模板变更致在途草稿项不一致时显式提示重载/重检，不把旧值套给新项。

`checkin_record_item` 目标字段：

| 分类 | 字段 | 说明 |
|---|---|---|
| 身份 | `id`、`tenant_id`、`record_id`、`template_id`、`item_code`、`equipment_id` | `tenant_id` 现有表**没有**，必须补（唯一键与 09 §4.1 子表策略都要求） |
| 最小展示快照 | `name`、`standard` | 只回答"该记录当时展示了什么" |
| 事实 | `result`（normal/abnormal/escaped）、`value_num`、`value_date`、`value_text`、`note`、`photos`、`abnormal_tags`、`exception_type` | `value_date` 为 08 原稿未列、本次新增：03 §2 的 date 项要与台账比对，存文本无法比对 |
| AI 留痕 | `ai_verdict`、`ai_reason`、`ai_reading` | 人工改判后仍保留 AI 原判 |
| 防作弊 | `shoot_lng`、`shoot_lat`、`shoot_at`、`suspicious`、`suspicious_reason` | |
| 其他 | `sort`、`created_at` | |

**删除的快照字段**：`requirement`（并入 `standard`）、`ai_hint`、`judge_type`、`judge_config`、`tags`（模板 tag 全集，只留 `abnormal_tags`）、`photo_required`。这些是"配方"不是"事实"——照片有没有本身就是事实，不需要再快照一份"当初必不必拍"。也不复制 `guide`、分组、列宽、行模式、整棵模板。

草稿按值类型保存完整输入，提交后删；正式事实不可因模板删除而级联删除（配套 §3.2.4 的 `retired_at` 软删）。

装配时由 `template_output.columns` 的 `item_code` 引用当前 L1 元数据，再按模板 + 项 + 对象对齐事实；缺项、类型不兼容、无历史值均有明确提示/校验，禁止按项名猜配。


### 3.5 本期计划明确选模板
候选＝同租户、同 point_type、用途相符且 enabled 的模板；计划编辑必须明确勾选 `template_ids`，即使仅一套也保存选择。任务生成保存所选模板集合及点位适用结果，不在执行时重新扫全部模板。控制室日常/功能本期即可分别选用；同选多套则独立模板段、独立项身份，不无条件合并。不同执行周期拆计划，不能套一个频次混跑。

point_template 仅表达例外候选，必须经计划授权才进入任务；跨类型例外校验对象及适用性，不因点位手工绑定就自动加查。选中模板被禁用/删除、用途/类型变化、集合为空时，计划生成/执行显式阻断并要求重新选择，不静默换模板。任务只固化身份选择，不承诺旧模板规则可重建。

freq_config 是带原件出处及确认状态的建议，执行仍以计划为准。**月度周期性抽查计划与巡检/报告计划一样可配置**：至少包括启用状态、月份周期与截止日、点位/设备范围、执行人、显式 `template_ids`、`ratio_percent` 抽查比例或 `fixed_count` 固定数量（二选一）、`random|longest_unseen` 策略、`no_repeat` 连中保护；任务生成时固化对象与模板集合。灭火器压力、生产日期/换粉日期的 2% 是已确认的专项比例；防火门、应急灯、安全出口指示牌、手报、喷淋头、烟感等按月抽查，具体比例由计划配置，未确认前不虚构默认值。月度全覆盖不自动选月末一天；`每栋每月至少1个`要表达数量/分层/必检对象，不能折成全局百分比。屋顶必检+室内抽样+室外轮换需不同规则，不支持的规则必须补能力再发布，不能假装现有 spot_ratio 全覆盖。维保半月规则属于设备维保计划，不生成零项巡检模板。其余未定频次见 §2.1，甲方确认前不得自动启用计划。

### 3.6 复制与复用
本期做整模板复制与批量录入；blueprint/词库/片段按需后置。可按机房环境、水泵、水表、器材外观、联动、主机功能、逐台对讲、综合区域复用编辑骨架，但复制后为独立完整实例。母版改动只提示人工勾选同步，运行时不继承，不自动传播。维保表不混入逐台检查母版；输出 StylePack 必须本期 L3 建立，不能以 blueprint 后置为由省略。

### 3.7 按业务语义分层，不按历史还原分层
| 定义 | owner / 载体 | 边界 |
|---|---|---|
| 巡检/专项检查项 | inspection / L1 patrol、spot | 逐项事实入 checkin_record_item |
| 查验矩阵检查项 | inspection提供 verify；acceptance选用 | 对象、记录与流程入 acceptance，不复用打卡 |
| 资料/钥匙/园林等对象行清单 | acceptance自有配置、稳定row_code | 不伪装设备类型、不塞设备L2 |
| 设备档案列/表单/导入导出 | equipment / L2 | 只管设备主字段与extra |
| 维保批次和确认流水 | equipment | confirmed后生效，不是L1模板；逐项作业另用spot |
| 输出分组/列序/装订 | report / L3 | 只引用定义身份，不持有可编辑业务标准副本 |

上述各类均不因“需要历史还原”而引入模板版本。共用渲染能力不意味着共用对象配置、记录表、审核流程。

### 4.2 `layout` 块白名单 + 示例 + 装配契约
`layout.blocks[]` 只允许这些块——**只描述顺序与数据绑定，不描述坐标**（坐标在渲染器）：

| 块 | 用途 | 数据源 |
|---|---|---|
| `cover` | 封面（项目名/台账编号/标题/月度/编制单位/日期 + logo） | 报告上下文变量 |
| `notice` | 说明整格段落（依据/责任/覆盖范围） | 变量插值 |
| `sign` | 签字栏：**按输出模板声明的签字位渲染**（位数、标签、位置来自甲方母版骨架），每个签字位绑定一个审批链人工环节 + 手写签名图 | 签字位声明 + 审核链快照 |
| `summary_table` | 检查汇总表 7 列 | 按**设备系统/设施类别**聚合 |
| `template_loop` | 模板循环：按 `system`（可选 `point_type` 过滤）遍历模板，每模板出「记录表 + 问题表」 | 模板表 + 记录快照 |
| `section_table` | 单个模板的检查记录表（**转置**：列=检查项，行按 `template_output.row_mode` 展开） | 当前模板的项 + 记录按 `item_code` 对齐 |
| `issue_table` | 问题照片表 5 列 | 该模板内异常项 + 工单/复核结论 |
| `photo_group` | 照片墙 | 模板级 / 逐项照片 |
| `footer_note` | 表尾合并行「检查标准：1.…2.…」 | `item.standard` 按 `item.standard_no` 归并（不存全文） |
| `page_break` | 分页 | — |

`template_loop` + `section_table` 是核心：前者决定"出哪几张表"，后者做**转置 + 行展开**（`row_mode`：`date` 按记录日期聚合、`point` 一行一点位、`grid` 按位置维度分组、`equipment` 一行一台设备）。

**签字位与审批链的对账（`sign` 块）**：签字栏的**位数、标签与位置属于版式**，来自甲方母版抽出的段落骨架；**谁签属于审批链**。两者在**配置时对账，不在渲染时伸缩**：

- 不按链的环节数动态增减签字栏——签字栏是固定表格骨架，栏数变会改表格结构与分页，使黄金样本基线（§4.9，SSIM 比对）失效，"报告莫名变样"将无法定位。
- 输出模板声明 N 个签字位，每位绑定一个审批链人工环节；**保存输出模板时校验**：有签字位未绑定环节即阻断，不生成空白签字格（正式归档件里的空签字格等同"未签完"）。
- 签字位对应环节在该小区无候选人时，走 14 §4.6 的挂起 + 告警，**不是渲染成空栏**。
- 甲方确有"按批次才定"的签字方（如承接查验见证方），该签字位显式标记**可留空**——是声明，不是意外。

**粒度口径（重要）**：文档（`doc_template`）只是**装订单位**，甲方 5 个 docx 各装订一个设备系统下的若干模板表；表本身的单位永远是**模板**。所以同一个模板既能被系统级台账装订（`template_loop` 按 `system`），也能单独出一份（按 `point_type` 过滤，或直接一个 `section_table`）——换粉台账、消火栓专项这种"单类型单文件"就是后者。**不要为单类型单据再复制一套文档模板。**

```jsonc
{
  "blocks": [
    {"type": "cover", "vars": {"title": "物业消防设施（器材类）月度巡检维保台账",
      "fields": ["community.name", "report.no", "period", "community.address"]}},
    {"type": "notice", "text": "一、依据…二、管理机制（三级责任+NFC打卡+AI识别）…三、覆盖范围…"},
    {"type": "sign", "roles": ["巡检执行人", "工程/安全负责人", "项目负责人"]},
    {"type": "summary_table", "filter": {"system": "消防设施（器材类）"},
     "columns": ["类别","总数","正常完好","存在问题","整改完毕","整改完成率","备注"]},
    {"type": "template_loop", "filter": {"system": "消防设施（器材类）"}, "order": "template.sort",
     "each": [
       {"type": "section_table", "title": "{{template.name}}检查结果记录",
        "row_axis": "template_output.row_axis", "row_mode": "template_output.row_mode",
        "columns": "template.items",   // 列 = 该模板的检查项，自动，不在 layout 里重复写
        "header_fields": "template_output.header_fields"},
       {"type": "footer_note", "prefix": "{{template_output.standard_prefix}}", "text": "{{section.standard_merged}}"},
       {"type": "issue_table", "columns": "template_output.issue_columns", "empty_rows": 3}]},
    {"type": "photo_group", "title": "检查过程照片", "source": "section_photos"}
  ]
}
```

三个要点：① **"输出需要哪些字段"不在 layout 里重复声明**——`section_table.columns = template.items` 即"按该模板的检查项自动成列"，**这是"改检查项 → 报告自动变"的关键**；只有甲方版式固定的表（汇总表、问题照片表）才把列写死。② **`template_loop` 决定出几张表**：按 `system` 装订 5 本册子，按 `point_type` 过滤就是单类型单文件；同一套 20 套 L1 模板，配 5 条 `doc_template` 就是 5 本，配 1 条就是合订本。③ **渲染器只管画**：拿到"块 + 已装配好的数据"，字体/边距/分页/合并单元格在代码里。

**数据装配契约 `ReportData`**（渲染器不查库）

```go
type ReportData struct {
    Context  map[string]string // community/period/report_no/编制单位/日期/签字人
    Summary  []SummaryRow      // 汇总表行（聚合轴 = 设备系统/设施类别，与 summary_table.filter 一致；二级口径待确认见 10 §2-2/#3）
    Sections []SectionData     // 一个模板一段
    Photos   []PhotoGroup
}
type SectionData struct {
    Title        string
    HeaderFields []KV     // 测试人/测试时间
    Columns      []Column // 来自当前模板的检查项（standard_no / value_type / 单位），与记录按 item_code 对齐
    Rows         []Row    // 按 row_mode 展开；Cell = √/×/数值/文字/逃生
    Issues       []IssueRow // 问题照片表行（位置/说明/照片/处理情况）
    FooterNote   string     // 表尾检查标准

```

变量沿用简单插值 `{{community.name}}`、`{{period}}`、`{{report_no}}`；表格列取值复用 `equipment/service/type_schema.go:ResolveSchemaColumn`（固定文本 > 装配字段 > extra 口袋），**不新写一套**。好处：渲染器可单测（喂 JSON 出图 diff），装配逻辑可单测（喂库出结构），两边不纠缠——这也是把 `monthly.go` 拆开的具体切法。

### 4.3 一次导出 5 个 PDF（分册 / 空册 / 审核链）
甲方交付习惯是"一册一签字一归档"：巡检月报 = **5 个 PDF**（供水 / 供电 / 消防器材 / 消防系统 / 特种设备），对应 5 本台账。20 套 L1 模板只是配置单位，导出时按设备系统装订成 5 份：

| 层 | 单位 | 数量 |
|---|---|---|
| L1 模板（配置） | 一张检查记录表 | **20**（另有 1 张电梯定期维保输出表不建 L1，见 §2.1） |
| `doc_template`（装订版式） | 一本台账 | **5** |
| 输出文件 | 一个 PDF | **5** |

- 每个 `doc_template` 的 `template_loop` 带 `system` 过滤，只装订该系统的模板表；`summary_table` 同样按 `system` 过滤。
- 生成动作：一次点击 → 按 `system` 循环 5 次 → 5 个 PDF 打包 zip 下载，也可单独下载。
- **报告记录仍是一条**（小区 × 期间），审核链走一次（同一批人签 5 本，签字图复用）；新建 `report_file` 子表按册别/阶段/格式/文件ID/摘要/批次登记 5 个产物，**不用 `file_ids` 数组**。
- **某系统本月无数据也出册**：封面 + 汇总表全 0 + 空明细表 + 注记"本月无巡检记录"。甲方台账按册归档，缺册比空册麻烦。
- 现有实现是"一个 PDF 装全部点位类型"，改成 5 个文件只需在装配层按 `system` 分组。
- **明细范围是三档展示策略，不改统计口径**：现有代码已有 `detail_mode=full/abnormal`；本期补第三档 `normal_first_abnormal`（正常代表样本 + 全部异常）。规则：汇总/统计永远用全量已审核事实；`abnormal` 只出异常明细；`normal_first_abnormal` 对每个点位/设备取本周期最早一条审核通过正常记录作代表样本，异常记录全量列出。报告快照必须记录所用策略，封面与明细页眉标注，重出/归档可溯源。

### 4.4 渲染路线（唯一一条）
```
甲方原始 DOCX 母版（页面/样式/表格/分节/签章/照片区全部保留）+ 真实业务事实与槽位映射
   → Go 母版渲染器（internal/pkg/ooxml，仅替换文字、克隆母版记录行、插入真实图片）
   → DOCX（可编辑，甲方能改）→ soffice --headless --convert-to pdf（盖章件）+ PNG（网页预览）
```

母版包保留完整 `document.xml/styles.xml/sectPr/tblPr/tblGrid/trPr/tcPr` 及全部静态内容，不再抽取后自行拼版。槽位只描述“哪个业务事实进入哪张母版表的哪个单元格”；记录增加时克隆母版标准行，禁止重建表格、表头或页面。动态文字可用 `noWrap` 与字号约束避免撑高母版行，但没有字符级占位符，也不执行模板命令。

**明确不采用的四条（不保留双轨）**

| 方案 | 为什么不 |
|---|---|
| 占位符填充（docx 里插 `{{...}}` 再替换） | 维护成本高；甲方改一个字模板就断；占位符表要单独维护。**占位符方案不采用** |
| 独立渲染服务（Python + LibreOffice，走 HTTP） | 多一个运行时依赖和一套契约；Go 自己吐 XML 更短，soffice 只做转换就够 |
| gofpdf 直出 PDF（现有 `pkg/pdf`） | 版式靠手写坐标，甲方改一个检查项就改 Go 发版；**整包删除**（附录 A） |
| HTML → PDF | 要装 Chromium，内存与稳定性成本高，版式仍要重画 |

**明确不做的另一件事：解析 PDF。** PDF 里只有绘制指令（"在 x=123 画一条线"），没有"表格/单元格/合并"的语义，任何自动识别都是猜；甲方只给 PDF 时我们连"这一列是什么检查项"都拿不到。**PDF 只做人工对照**（出图后并排看）。

**Word 的正确用法有两条，别混**：① **当母版（抽骨架）**——抽样式 + 表格骨架，供 `engine=ooxml` 渲染时套用，**这是选定路线**；② **当录入源（抽结构）**——把 docx 表格抽成结构化文本，人工确认后录进 `check_template`，已用 `python-docx` 验证（13 份文件抽成结构化结果，见 `backend/.tmp/template_dump.md`），**可行但必须人工复核**（合并单元格、多级表头、断行错位——甲方原文件里就有两处表头损坏——机器判断不了）。Python 只留作**一次性批量录入工具**，不进运行时。所以"要 Word 版本"是对的，价值不在"解析"，在**能精确拿到列清单和标准原文**，以及**能抽出母版骨架，让输出天生就是那个版式**。

### 4.5 保真度、风险护栏与部署
**先把"像"拆成三层，免得验收扯皮**

| 层级 | 例子 | 验收口径 |
|---|---|---|
| 结构一致 | 表头列、列顺序、两级合并、表尾标准、问题表列、5 本分册 | 必须逐册核对通过；这是本方案的结构验收目标，不写成脱离样本的百分比保证 |
| 视觉接近 | 字体字号、页边距、行高、边框粗细、单元格内边距 | 以甲方确认的黄金样本基线为准；不预设 95~99% 或"任意母版无损"承诺 |
| 像素级一致 | 与 Word 原件逐像素比对 | ❌ **不承诺**（那需要"原 XML 只替换文本节点"，等于回到占位符式的脆弱绑定） |

**风险护栏（第一天就上）**

| 风险 | 具体表现 | 护栏 |
|---|---|---|
| 字体不一致 | 服务器少字体 → 回退宋体/豆腐块，行高全变 | 渲染环境内置固定字体集（与抽 StylePack 时同一套），镜像锁版本；启动自检 |
| LibreOffice 版本漂移 | 升级后分页、字距变化，历史报告重出变样 | 锁 LO 版本；升级必须跑全量基线比对后才允许 |
| 表格跨页 | 表头不重复、行被切一半 | 表格骨架显式设"重复表头"（`tblHeader`）；每册先做"空数据出图"验证分页 |
| 字段/页码 | 目录、页码不更新 | 不用 Word 域生成目录（页数可算，自己生成）；页码走 OOXML 页脚域，转 PDF 前刷新 |
| 照片 | 旋转丢失、超大图撑爆页 | 统一 EXIF 转正、限 DPI（≤300）、长边压缩后再插 |
| 空数据 | 无数据的册子出半张表 | 空数据也出完整骨架（表格空行、汇总全 0、"本月无记录"注记） |
| 性能 | 5 本 × 几十页 × 几十张照片，一次导出很慢 | 单册独立任务 + 超时；照片并发预压缩；PDF 转换串行（LO 单进程） |

**回归基线（最重要一条）**：每册留一份"黄金样本"（固定 DocModel + 固定数据 → docx → PDF → PNG）。改渲染器、改 LO 版本、改 StylePack 都必须跑基线比对；候选图像相似度 **SSIM ≥0.98** 只作建议阈值，最终通过线以甲方确认基线为准，并辅以文字/分页/签字位置人工核对。**没有基线的渲染改动一律不许合**——否则"报告莫名变样"永远定位不到。

**部署（当前选择）**：后端镜像不安装 LibreOffice；开发与生产 Compose 默认启动独立 `report-renderer` 实例，镜像基于 Debian slim，包含 `libreoffice-writer`、固定字体、`pdfinfo` 和 Go worker。后端以原子目录任务调用共享卷中的转换器，worker 不开放 HTTP、完全断网、非特权运行，逐任务使用独立临时 profile，并限制 CPU/内存/PID/输入输出/超时。默认 `LIBREOFFICE_MODE=worker`，PDF 失败只标记对应 `report_file=failed` 并允许重试，**不把 DOCX 伪装成 PDF**；DOCX 输出链路保持不变。报告 PDF 预览与归档依赖真实转换结果，无可用 worker 的正式 PDF 部署不算验收通过。

**上线前必须先过的一关**：拿甲方器材类那份 docx 抽母版 → 用一份真实数据出 docx → 转 PDF → 和甲方原件并排看。过了方案才成立，没过就只是纸上设计。

### 4.6 Go 实现：godocx 实测结论 + 自建生成器
**试过 `github.com/gomutex/godocx v0.1.5`，公共 API 不够用（实测源码）**

| 我们需要 | godocx 公共 API | 结论 |
|---|---|---|
| 打开母版 `OpenDocument` | ✅ 有 | 可用 |
| 段落 / 标题 / 图片 / 分页 | ✅ 有 | 可用 |
| 建表、加行、加单元格 | ✅ 有 | 可用 |
| **两级表头的横向合并**（`w:gridSpan`） | ❌ 只在 ctypes 结构体里，`Cell.ct` 是私有字段 | **外部设不了** |
| **固定列宽**（`w:tblGrid` / `w:tcW`） | ❌ 无 API | 不了 |
| **跨页重复表头**（`w:tblHeader`） | ❌ 结构体里有，无公开方法 | 不了 |
| 垂直合并（`w:vMerge`，"〃"格） | ❌ 同上 | 不了 |

这四样恰好是甲方台账的硬需求，所以两条路：fork godocx 补 4 个方法（~200 行，但跟上游漂移），或**自建最小生成器（选定）**。选自建的理由：我们的需求不是"通用 docx 库"，而是"**把 StylePack + DocModel 写成一个 docx 文件**"。参数已固定，必须精确控制 `gridSpan` / `tblGrid` / `tblHeader`，自己吐 XML 反而最短——不是重造 OOXML，只实现一个窄子集（约 **1200~1500 行** + 单测，无外部依赖）。

**能力清单（写下来防止膨胀）**

```
读（母版抽取，zip + encoding/xml）：[Content_Types].xml / word/_rels/document.xml.rels / word/styles.xml
  / word/settings.xml / word/fontTable.xml / word/theme/theme1.xml / sectPr
写（正文）：paragraph(文字, 样式ID, 对齐, 缩进, 分页) / run(粗体, 字号, 字体)
  table(tblPr, tblGrid 列宽, tr, tc, gridSpan, vMerge, tblHeader, tcW, 垂直居中)
  drawing(内联图片：jpeg/png, 宽高) / pageBreak / sectionBreak
打包：document.xml + media/* + rels + content-types → zip → .docx
```

**包结构（不引框架）**

```
internal/pkg/ooxml/  reader.go(抽母版) writer.go(zip 打包) block.go(段落/表格/图片/分页 XML)
                    table.go(gridSpan/vMerge/tblHeader/tblGrid) image.go(图片 part+rel) style.go(StylePack)
internal/module/report/  model.go(DocModel) assemble.go(ReportData→DocModel) render_docx.go render_pdf.go(调 soffice)
```

母版抽取也用 Go 写，Python 的 `python-docx` 只留一次性批量录入。**PDF 只差一次转换**：`soffice --headless --convert-to pdf`，不需要任何额外服务。

### 4.7 xlsx 出口（不建独立系统 + 三件清理）
现状盘点（`excelize` 用了 5 处，各写一套列头）

| 位置 | 干什么 | 列头怎么来 |
|---|---|---|
| `pkg/excel/excel.go` | 用户导入模板、点位导入模板 | **硬编码数组**（`importHeaders`、`pointImportHeaders`） |
| `equipment/service/import_export.go` | 设备导入模板/导入/导出/按选导出 | 走 `equipment_type_schema`（数据驱动 ✅） |
| `inspection/service/point_service.go` | 点位导入模板/导入 | `pkg/excel` 硬编码表头 + **按列序号取值** |
| `inspection/service/checkin_export.go` | 打卡记录导出 | 硬编码列 |
| `stats/service/stats_service.go`、`system/service/user_service.go` | 统计导出、用户导入导出 | 硬编码列 |

**判断：不建独立 xlsx 模板系统。** 理由和 docx 不同——xlsx 的"版式"就是列 + 列宽 + 表头合并 + 单元格样式，excelize 完全能表达，不需要抽母版；真正会变的是**列定义**，那是字段方案已经管的东西。要统一的是这三件（都是清理，不是新系统）：

1. **列定义只有一个来源**：删掉 `pkg/excel` 里那几组硬编码表头，导入模板与导出列统一从字段方案取（`import_headers` / `export_columns` + `ResolveSchemaColumn`）。
2. **一个导入解析器**：`表头名 → 字段 key`（带别名、必填、类型/枚举校验、错误行号），替换现在"按列序号取值"（加一列就错位，这是最容易出的 bug）。各模块只声明"我用哪个 schema"。
3. **xlsx 作为 `doc_template` 的 `engine=xlsx_template`**，可选挂一个骨架文件：甲方 xlsx 的表头区 / 列宽 / 样式 / 合并保留，数据从 `layout.data_start_row` 开始填。换粉台账用这个（甲方版式 + 签字行）；普通导出不需要骨架，直接按列定义生成。

```jsonc
// engine=xlsx_template
{"sheet": "设备档案", "data_start_row": 3, "columns": "equipment_type_schema:extinguisher.export_columns"}
```

**明确不做**：单元格坐标级绑定（甲方插一行就崩，等于把占位符的坑再踩一遍）、甲方自上传导出模板（换粉台账骨架这一类除外）。一句话：**xlsx 是模板系统的出口之一，不是第二个系统。**

### 4.8 哪些输出进模板系统（判据表）
**判据：要交付、要归档、要签字的文档才进。** 不然模板条目会淹没在临时导出里。

| 输出 | 进吗 | engine | 装配器数据源 |
|---|---|---|---|
| 巡检月报（5 本） | ✅ | `ooxml` | 任务 + 打卡记录 + 逐项快照（按 `template_output.row_mode` 展开） |
| 承接查验报告（**六个类别**，册号未确认） | ✅ | `ooxml` | 接管批次 + 查验记录（矩阵/清单两种表型） |
| 物业分户查验台账（一户一档，册号留空未定） | ✅ | `ooxml` | 接管批次 + 房屋级分户查验记录 + 表计底数 |
| 灭火器换粉台账 | ✅ | `xlsx_template` | `equipment` 台账（不依赖巡检记录） |
| 单次维保记录单（要打印时） | ✅ 期2 按需 | `ooxml` | `equipment_maintenance` 一条流水 + 照片 |
| 打卡明细导出、统计导出、用户导入导出 | ❌ | — | 走 §4.7 的列定义 + excelize，一次性导出，不归档不签字 |
| 报告里的预览 PNG | ❌ | — | 由 PDF 转出，不是独立模板 |

**统一在"输出模板 + 渲染器"这一层，不统一在"装配器"**：装配器每模块一个（200~300 行），因为数据语义不同（打卡 / 查验批次 / 台账主数据）。装配器薄、模板与渲染器厚——这个分界决定了加模块便宜（写个装配器），改版式便宜（改母版/改 layout）。

### 4.9 甲方改东西改哪儿（三种路径，都不发版）
| 甲方改什么 | 改哪儿 | 改代码吗 | 验证 |
|---|---|---|---|
| **版式**：字体、列宽、行高、表头合并、加说明段、换标题、调页边距 | 母版 docx（Word 里直接改）→ 重抽 StylePack | 不用 | 跑基线比对，确认无连带漂移 |
| **结构**：哪几张表进哪本册子、表顺序、汇总表列、照片墙位置、签名栏角色 | `doc_template.layout`（块列表 JSON） | 不用 | 同上（PC 预览直接看） |
| **检查项**：加一列、改标准、改判定方式 | `check_template`（PC 模板编辑器） | 不用 | 报告自动多一列 |

**唯一例外**：甲方要"以前没有过的排版形态"（表内嵌子表、两表并排、图表），要新增一个 block 类型——这是块白名单的代价，换来版式不会乱、渲染可回归。甲方给 Word 的常规流程：甲方改完 Word 发回 → 我们重抽 StylePack + 跑基线 → 预览给对方确认 → 发布。录入检查项时先走"Excel 粘贴批量录入"，docx 表格解析只做辅助（人工复核），**不承诺全自动解析**，但要把一次录入压到半小时级。

## 6. 关键取舍
### 6.1 为什么不合并三张表
**共用机制；列式清单共表，字段方案与文档模板各自独立。**

| 层 | 消费方要什么 | 为什么不合并 |
|---|---|---|
| L1 检查项模板 | App 表单（离线、AI 排队、实时校验） | 有草稿/启用两态、被记录逐项引用，是"配方" |
| L2 台账字段方案 | 表格（列宽、导入列头、导出列） | **没有**两态管理、没有被记录引用，消费方是表格与导入导出 |
| L3 输出模板 | 渲染器（分页、字体、合并单元格） | 结构是"块"不是"字段" |

三者共用**机制**（两态管理、租户覆盖、JSON 校验），不共表。硬抽象会得到一个谁都不好用的 JSON：`equipment_type_schema` 并进来收益不成立——台账列随时可改，历史报告不依赖它，硬加"草稿/启用"只是空转。**什么时候才考虑把它并进来**（出现任一条件再说）：① 甲方要求台账列改动留审计/留痕；② 导入导出列要按租户独立配置且需审批；③ 出现第三种字段画像。**没有这些需求就不并**，两套并行不是罪，为统一而统一才是。

**判据（检验模板层有没有真的统一）**：新增一类设备 / 新接一个模块时，只加模板数据（1 个模板实例 + 若干项），**零代码改动、零发版**，也不需要新建一张模板表。哪天某个模块冒出一个"专属模板表"，就说明这里破例了。

### 6.2 为什么输出转置，而不是录入矩阵
甲方台账是"检查项做列、记录做行"的横向矩阵，**那是出报告时的展示形态，不是 App 录入形态**。矩阵录入（31 行 × 9 列、横向打 √×）在手机上不可用；表单式（一次巡检一屏卡片）才是巡检员能用的。系统内继续一项一条记录，转置放渲染层，代价只是四种行模式展开逻辑。

### 6.3 为什么块白名单，不做画布 DSL
**能配置到哪、到哪就停**：**录入侧永远同构**（App 里只有一张"检查项卡片"列表，差异只通过 `value_type`/`standard`/`photo_required`/`note_required` 体现，绝不按模板定制卡片布局，否则 20 套模板就是 20 份页面）；**输出侧异质**（列数、合并、表头格、照片区在渲染层按模板配置展开，这是唯一该"长得不一样"的地方）；**不可配置的**（分页、字体、页边距算法、合并单元格推导、照片格排版，留在渲染器代码里）。因此 `layout` 只给 10 个块（§4.2），不给任意画布 DSL。代价：遇到全新表结构（表里再嵌子表）要新增一个 block 类型；收益：版式不会乱、渲染可回归、甲方改结构不用发版。

## 7. 承接查验（期2 并行，随立项）
- **矩阵型**（房屋本体 / 器材统计 / 系统类 / 车库专项，约 35 张）：复用 `purpose=verify` 的 L1 检查项定义，检查项 √× 或数值/数量/状况；**选择、对象、记录与流程仍归 acceptance**。
- **清单核对型**（资料 / 钥匙 / 园林植物 / 固定资产，约 23 张）：由 acceptance 域自有的 `acceptance_list_schema` / `acceptance_list_row` 管理（稳定 `table_code` + 稳定行 `code`），**不塞进设备台账 L2 `equipment_type_schema`**，理由见 §3.7 与 05 §2。资料、钥匙、园林植物不是设备，不能为了复用一张表就把它们伪装成设备类型。
- 记录层**不复用打卡**：承接查验不是点位打卡，需要 `acceptance_batch`（接管批次）+ `acceptance_target`（查验对象）+ `acceptance_record`（缺项 + 照片 + 问题事实），见 05 文档。
- **AI 复用但不复用巡检业务**：现场查验走 `purpose=verify` + 09 §2.2 `image_inspection`；资料清单用 `doc_scan_extract/doc_page_check` 预登记，人工确认后才进审核。承接查验不建点位、不生成巡检任务、不写 `checkin_record`。
- 输出：`doc_kind=acceptance` 的 `doc_template`，块序列 = 封面 / 册目录 / 说明 / 签章 / `template_loop`（清单表 + 照片表）；两种表型在同一 PDF 里混排，渲染器按块类型取不同数据源。
- **接入成本不是"一个枚举值 + 一张表"**（05 §1 已明确否定该说法）：除 `purpose=verify` 外还要新建批次/对象/记录/问题/签署/交接日志六类表、独立清单 schema、审核与签署流程与 L3 六类输出。工作量按 05 与 06 的 2A 项估算并验收，不以枚举值个数衡量。

## 8. L2 台账字段方案（独立，三补一删）
`equipment_type_schema` **不并入模板系统**（没有两态管理、也没有被记录引用，消费方是表格与导入导出）。现有"平台默认 + 租户整体覆盖"形态是对的，本期三补一删：

1. **删掉 `table_mode` 这个计划**：原打算用 `matrix`/`list` 两种表型让 L2 兼容承接查验清单型，已按 §0.1/§3.7/§7 与 05 §2 取消——清单归 acceptance 自有 `acceptance_list_schema`。**L2 只服务设备台账一种形态**，不加 `table_mode` 列。
2. **类型口径统一**：主键一律用 `equipment_type` 字典 value（`extinguisher`/`hydrant`…），台账、模板、导出三处不出现第二套类型编码；与 `point_type` 的分工靠 `equipment_type.attrs.point_type` 一条映射（§3.1）。
3. **台账不许"所有设备一张表"**：列表按设备系统/类型分 Tab 或强筛选；导入模板按类型下发（灭火器 5 列、消火栓 4 列，互不兼容）；导出 xlsx 按类型一个文件/sheet。
4. **补默认方案**：`00052` 只给 `extinguisher`/`hydrant` 配了平台默认方案，其余类型取不到就退回"通用列"。补齐所有类型的默认方案（与模板同批录），并把"无方案"从静默回落改成**显式报错**，不留通用兜底。

**与模板系统的唯一共享点**：字段取值解析（`ResolveSchemaColumn`），报告渲染也用它。
