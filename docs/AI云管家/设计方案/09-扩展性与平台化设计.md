# 扩展性与平台化设计（IoT / AI / SaaS / 安全 / 性能）

> 版本：v1.1 2026-10-19
> 状态：设计补齐稿，待实施/验收（与 01~08 同级；已有与目标逐项区分）
> 定位：本系统不是一次性项目，要卖成 SaaS、接更多设备与 AI 能力。本文定义"哪里留缝、怎么留、留到什么程度"，**全部遵守一个前提：能配置的不写死，能晚建的不早建**。

## 0. 扩展原则

1. **平台底座 vs 业务**：01 文档已把账号/权限/审核链/消息/文件/AI/报告列为平台底座。本文再加三类扩展点：**设备接入（IoT）、AI 提供者、租户运营（SaaS）**。业务模块（巡检/工单/承接查验/收费）只消费底座，不感知底座怎么换。
2. **优先配置与显式注册**：已支持的类型/版式走字典与模板配置；新协议、新 AI 或新渲染能力仍须适配代码、契约回归和发布。允许按租户灰度，不承诺新增格式只加一行配置、不发版。
3. **按依赖落地而非一律留位**：IoT 期4、SaaS 运营期3不提前建表；AI Provider 期2收敛。期1/期2的租户隔离、文件授权、任务队列恢复、跨域联动原子性和安全渲染是上线必做项，不能以“只留接口字段”后置。

## 1. IoT 设备接入（期4 智控的缝）

### 1.1 模型：三层，不耦合

```
协议层（Adapter）            注册层                消费层
MQTT / GB28181 / ONVIF   →  iot_device（统一设备） →  事件 → 工单/消息
厂商 HTTP/Webhook           （租户 + 类型 + 状态）     读数 → 时序表（可挂检查项）
```

- **Adapter 按协议能力划分**，拟议连接/订阅/读取接口需携带 context、显式租户范围、取消/超时、错误与重连语义，具体签名待期4协议确认；不强迫所有协议实现同一能力集。只读先行（摄像头、水位、电梯状态），控制另行立项。
- **iot_device 表**（期4 建，期1/2 不建）：`tenant_id / community_id / point_id（可挂点位）/ type（字典 iot_type：camera/water_level/elevator/door_sensor...）/ vendor / protocol / endpoint / credential_ref（**不存明文**，引用密钥管理）/ status / attrs jsonb`。
- **凭证不直接落表**：`credential_ref` 指向密钥存储（`.env`/KMS 抽象），防止租户数据导出时泄出第三方账号。

### 1.2 事件与工单联动（这是 IoT 的全部业务价值）

```
设备事件（越限/离线/告警）
 → 规则（iot_rule：设备类型 + 指标 + 阈值 + 动作）
 → 动作：发消息 / 生成工单（复用 04 的工单池，source_type=iot）
 → 工单闭环（抢单/整改/主管审核），与巡检问题同源
```

规则引擎**不引框架**（Drools/Esper 这类一概不引）：`iot_rule` 一张表 + Go switch，规则数预计 < 100，够了。

### 1.3 读数与巡检的关系（远期，先留缝）

检查项 `value_source`（**二期按需字段，期1 不建**）：`manual（默认）| iot`。为 `iot` 时按 `iot_metric_key` 从读数表取最近一次值自动填表，巡检员只确认。水表读数、泵房温湿度将来都走这条路——**这也是为什么 `value_num`/`value_date` 必须存进 `checkin_record_item`**（08 §3.4.2）：以后可对比人工值与自动值，日期类读数同理。

### 1.4 明确不做
- 不做设备远程控制（只读先行）；
- 不做视频流存储（摄像头只接事件/截图，不存流，存储成本不可控）；
- 不做实时大屏（期4 再做，且必须基于已分区的时序表，不打线上库）。

## 2. AI 提供者与队列（已有基础，需改）

### 2.1 核实基线

`internal/pkg/ai` 为现有视觉客户端；`mp/service/ai_item_jobs.go` 已有 Redis List 待处理/processing、Hash 结果 TTL 2h、worker 默认 8（`ai.worker_count`），429 退避 2/4/8s 最多重试 3 次，单次超时按 `ai.timeout_seconds`（代码注释默认 180s）。代码以 BRPopLPush 搬到 processing，启动时回迁，不能照旧注释写成 BLPOP 即可靠完成。payload 已带 TenantID，但草稿回写等仍需显式 scope/任务代次约束；不是只换调用几行就完成平台化。

### 2.2 AI 能力服务与 Provider 目标

AI 不各业务各自接模型，收口为一个**能力服务**：业务域只声明任务类型、对象、证据、期望返回结构和审核策略，不直接写 OpenAI/Gemini/Claude 调用。

- 助手 Tab 走 **agent + 工具**形态：系统增删查改按业务域封装为工具（入参、权限、返回结构显式声明），agent 在调用者权限内取数与操作，不绕过接口鉴权；回答走 response 流（SSE）Markdown 流式渲染，思考过程与工具轨迹可展开；写操作先生成待确认计划，App 用居中确认弹窗写清对象、动作与条数，确认后执行并留痕。Go 侧选型倾向 [Eino（CloudWeGo）](https://github.com/cloudwego/eino)：类型化 Tool/ChatModel 组件 + ReAct 编排；轻量需求也可在现有 AI 客户端上自实现薄工具调用循环，不为此引入第二套运行时。**工具注册表同时服务外部 MCP 与 Skills，完整方案见 12 智能体化设计。**

- 任务类型先收敛：`image_inspection`（巡检照片）、`meter_reading`（表计读数）、`label_date_ocr`（设备标签/日期）、`doc_scan_extract`（承接查验资料扫描提取）、`doc_page_check`（缺页/签章/编号一致性辅助）。后续新深度学习模型或 OCR/文档模型接入，只新增 Provider 适配与任务模板，不改业务表结构。**能力服务与 12 的工具注册表是同一张能力目录**：识别类能力以 `async_job` 形态注册，业务主流程直调（不经 agent 环路），agent/MCP 作为目录的另一些消费者共享同一权限、配额与审计口径。
- 统一契约：`scene/tenant_scope/subject_type/subject_id/files/expected_schema/prompt_kind/request_id/retake_seq` 入队；返回 `pass/review/abnormal/error + fields + confidence + reason + raw_ref`。`error` 是终态，不是无限 pending。
- 业务侧规则仍归业务：巡检/维保/承接各自决定哪些场景 pending 禁提交、哪些允许人工先填、哪些必须强审。AI 只给建议，不替业务生效。
- 现有通义适配器作为第一个 Provider；新模型接入需实现适配、配置、配额与验收，不能保证无代码发布。

pending/running 未完成一律不准提交。不可用/超时/配额用尽须落明确失败状态，再按 03 的人工确认与审核规则处理，不把失败当合格；人工出口要留原因、确认人和审计。禁用 AI 的手动模式与 job 失败模式不得混淆。

### 2.3 公平性与恢复目标

AI 识别任务期1 从现有 Redis 队列迁到 `riverqueue/river` 的 `ai` 队列（01 §4.3）；Redis 继续承担会话/黑名单。补租户并发/速率配额 **加全局资源/厂商配额上限**，公平轮询，避免单租户独占和总并发失控；配置默认值需按现有 8 worker/180s 基线实测后决定，不宣称已有租户 2 并发/30s 超时。

迁到 River 后，入队与业务写入经 `InsertTx` 在**同一事务**提交，原"入库与入队非原子、需持久投递意图/补偿扫描"的问题随之消失；任务持久状态、租约/续约/超时接管、有限重试与 discarded 死信由库负责，不再自写。业务约束不变：草稿回写按 `(tenant, task, point, template_id, item_code, equipment_id)` 定位，并带 `request_id`/`retake_seq` 条件更新（08 §3.4.2、03 §3），**旧识别不得覆盖重拍结论**；重复入队用 `UniqueOpts` 去重。仍须补监控、过期提示、停写排空/取消流程与重启验收，并验证迁移期间旧 Redis 队列已排空、无在途 job 回写新草稿。

## 3. SaaS 平台化

### 3.1 已有与目标分开

已有 JWT/Redis 会话、四档角色（super_admin/tenant_admin/project_admin/field_staff）、租户/小区上下文与品牌功能。`equipment_type_schema` 已有 NULL 平台默认/租户覆盖；**不能推广为全表 tenant_id 完备，也不能把未建的 doc_template 当现有覆盖机制**。check_template 的目标范围按 08 实施和迁移。

### 3.2 未来期3目标（均须另行实现/验收）

- 平台默认模板/StylePack/字典授权复制为租户自有；copy 与覆盖明确，不允许租户改默认源。
- tenant_quota/tenant_usage：设备、点位、存储、AI、报告/工单用量及幂等计量；配额耗尽采用明确人工/排队/拒绝策略，不承诺所有动作无限放行。
- 运营后台、租户启停、健康度、退租导出（带文件清单/摘要且不带凭证）、白标域名与品牌；已有品牌能力先盘点再补。
- 不做公网自助开通。业主侧个人信息按最小采集、用途/留存/匿名化设计；删除与法定留存/归档证据冲突须逐类确认，不承诺直接删除全部事实。

### 3.3 岗位编制与审批链可靠性（期1 门禁）

> **模型定义与迁移顺序以 [14 权限与岗位模型](14-权限与岗位模型.md) 为准**，本节只保留与 SaaS 平台化相关的门禁要点，不重复模型正文。

甲方已确认**一人一岗、岗位数不膨胀、项目 = 小区**。据此 14 把原先的 岗位 / 角色 / 职责槽位 / 编制 / 数据范围 五层塌缩为两个：

```
角色（挂 sys_user，全局唯一，一人一个）  → 权限点 + 可抢工单类型 + 主管标志
任职（project_staff，一行一个小区）      → 数据范围 + 责任楼栋/生效期/代理
审批链节点 → 角色                        （duty_binding 与 Slot 枚举删除）
```

理由是原先有两处双写：岗位与角色表达同一件事（"没有权限的项目经理不该叫项目经理"）；`approval_flow` 与 `duty_binding` 都带 `ProjectID`、用相同的"租户默认 + 项目覆盖"机制回答同一个问题。角色的 `scope_level` 决定范围怎么算（platform=平台 / tenant=本租户全部小区 / project=任职行覆盖的小区），项目级即甲方说的"岗位"。以下四点作为期1/切换门禁：

1. **空名单不得跳过（三道防线）**。`community/service/flow_service.go:139` 的 `WalkFlowSkipEmpty` 是三链统一口径（空名单自动跳过 + 事后通知），与 03 §5"空流程/空审核名单不能自动通过"冲突。① **创建小区必带默认审批链**，不允许无链的小区存在；② **完整度未过不得启用**（每个审批节点至少 1 个候选人），未启用的小区不生成巡检任务；③ 运行期节点无人 = **挂起 + 告警 + 管理端待配置**，禁止自动通过，**并须同时提供断链修复入口**，否则等于把自动通过换成大面积卡死。前两道只减少触发、不取代第三道——名单会因离职/调岗/临时任职到期/角色变更/链被改绑而在运行期变空（14 §4.6.2）。此条与模型无关，合并前后危害一致，必须单独改。
2. **审批链断链可发现**。候选人解析为空、人员离职/禁用导致无人时，记录停留待处理并生成管理端告警；不能静默卡住。某小区无人持该角色时向上命中 `scope_level=tenant` 的任职（14 §1.5.2）。agent 预审节点同样适用：agent 不可用/超时 = 断链挂起 + 告警，不得跳过或默认通过。
3. **任职需要时效与代理**。任职行增加生效/失效时间与代理人规则（目标设计，不代表现有字段）：休假、调岗、夜班/周末由代理人承接；代理有范围、期限和审计，不靠禁用/借账号。临时与流动人员优先走"抢单即授权"（14 §2.4），不预配任职。
4. **角色必须有行业预置**。平台预置项目经理/品质主管/工程主管/巡检员/维保工/消控值班等标准项目级角色与默认审批链；新租户复制后只改差异。角色声明权限点、可抢工单类型与主管标志（14 §1.3）。**平台级默认审批链由预置包实例化成租户行提供**——`approval_flow` 只有项目/租户两级，不像原 `duty_binding` 有平台级那一层。

**范围只有一个来源**：可见小区 = 任职行覆盖的小区（`project_staff` 一行一个小区，不是用户表上的数组——责任楼栋/生效期/代理人天然按小区不同）；`sys_role.data_scope` 的范围语义按 14 §4.4 移除，"全项目/仅本人"由角色主管标志承载，单条记录的读权限由节点候选人身份赋予（"能审必能看"，14 §1.5.3）。现实现为"编制推导 + 角色 data_scope 作上限"双来源（`middleware/datascope.go:13`），属必改项。**责任楼栋 `building_ids` 是分派筛选、不参与鉴权**（现状即如此），精度到楼栋，楼层是点位属性不是组织实体（14 §1.7）。合并后 `post_dict.role_id`、`project_staff.posts`、`middleware/roleunion.go` 运行时并集、casbin `SyncAll` 第二份展开、`duty_binding` 整表、`Slot` 枚举、报告链 `fallbackInspector` 特例**一并删除**（14 §4.1）。

**审批授权不设独立权限点**：能否审某条记录的唯一判定是"是否为该记录当前节点的候选人"；菜单可见性由"角色是否被任一节点绑定"推导。因此不存在"角色权限点与节点绑定两处对不齐"的同步问题（14 §1.5.3）。

**一人一岗是结构约束**：角色挂用户且全局唯一，数据层面无法表示"同一账号在 A 是经理、在 B 是巡检员"。确需担任不同岗位时另建账号，因此账号须登记自然人标识（租户内唯一），审核候选人按自然人去重、绩效按自然人合并、离职关联账号一并停用（14 §2.1）。否则 03 §5 的防自审可被同一人的两个账号绕过。

概念边界：当前 `project_staff.project_id` 实际传的是 `communityID`，即 **project = community（一对一）**。甲方已确认不设片区、不把多个小区合成一个项目；分管多小区由任职的小区勾选表达，跨小区签字由候选人按业务对象范围解析表达（14 §1.5.2）。将来若"片区需独立报表或独立审批环节"，再单独评审加层，不提前虚构两层模型。

## 4. 安全设计（期1/期2上线门禁）

### 4.1 事实基线与表分类

已存在 JWT、Redis 会话/黑名单、RBAC、TenantScopeOrDefault/CheckTenantRow、围栏/NFC/EXIF/水印、上传归属校验。它们不是完整安全证明：当前租户 helper 在缺失 identity 时存在返回空/放行语义，不能给后台 worker 直接复用；file.checkRead 的 export/签章分支按权限提前返回，需要统一先租户后用途授权。

| 表类别 | 目标隔离规则 |
|---|---|
| 租户业务表（任务/正式记录/维保/工单/报告/report_file/租户文件/审计） | tenant_id 必填且服务端派生；所有增删查改/批量/导出显式租户和数据范围，小区归属必须一致；历史 NULL 先盘点转换，不能当公共行 |
| 子表/关联表/分区 | 自带租户或由受控父键严格继承，契约注明并核验父子同租户；唯一键/去重键包括租户，分区删除与历史回填检查范围；不是简单“全表加列” |
| 平台默认与租户覆盖配置（如 L2） | 显式 `platform_default` 与 tenant 范围，NULL 仅用于有声明的默认库；租户只读被授权默认、写自有，平台修改专门权限与审计；缓存键含 scope/tenant |
| 平台控制表（tenant/模块权限目录/迁移元信息） | 受权平台操作，平台扫描需显式 PlatformScope 与审计，不允许空租户触发全库查询 |
| 队列任务/投影/后台任务 | River 任务 args 必带 tenant、actor/system principal、数据范围、source/幂等键（`UniqueOpts`）；平台 job 先受权枚举租户，再逐租户执行，不能继承“默认租户” |

HTTP 身份缺失/租户未解析 fail closed；超管跨租户操作也须显式目标与审计。公开接口输入 `TenantScope`，不得以 `context.Background()` 或没有 Gin identity 推断全局权限。任务执行重新验证目标归属/租户启用与所需系统权限，不能信任客户端 payload。上述是需改目标，逐表 owner 清单与租户负例测试作为门禁。

### 4.2 文件与上传证据

- 统一授权顺序：验证身份→读取文件元数据并校验目标租户/允许的默认库范围→业务对象/小区数据范围→scene 与用途权限（预览/下载/导出/签章）→生成响应。拥有 report:download 或签章权限不能绕过租户；未识别 scene 默认拒绝。超管采用显式租户管理流程，不全局无痕放行。
- 所有本地/API/STS/云回调/报告产物适用同一规则；私有桶、短期签名地址与过期控制，业务引用用 file_id。存量 URL、静态目录与代理必须清查，不能 API 拦住但公共地址仍直读。签名公章单独受控，不因报告列表权限暴露原资产。
- 现有上传有场景扩展名/大小检查，公告支持 Office/ZIP；不能把“jpg/png/mp4/pdf ≤20MB”描述为现有白名单。目标按 scene 配置扩展名+魔数+解码一致性、实际流大小、图片像素与资源限制，STS 上传完成后服务端验证方可引用。回调验签、对象路径/归属、幂等登记与失败补偿核验。
- **证据与清洗副本分离**：接收原始字节即算 SHA-256、大小、上传人/租户/接收时间，保存在隔离证据区；受限解析先提取 EXIF/拍摄时间等防作弊事实并记录解析结果，失败标可疑；再生成去元数据/重编码/缩略图/水印副本供展示与 AI。记录父子关联、处理参数/时间与各自摘要，不能先去 EXIF 再声称已核对证据，也不能覆盖证据原件。原件默认不可直接预览，下载需独立权限与审计，恶意/隔离文件不可用于业务或渲染。
- MIME/nosniff、下载文件名与隔离预览域、存储路径不可由请求拼接；敏感数据脱敏与导出权限独立。密钥走现有环境管理/KMS引用，不入业务库、日志或模板/导出包。

### 4.3 模板包、OOXML 与 LibreOffice 隔离（期2必做）

1. ZIP/OOXML 入隔离区，限制压缩大小、解压总量、单项大小、文件数、压缩比与嵌套深度；拒绝路径穿越/绝对路径/符号链接。建议起始预算：包 ≤20MB、解压 ≤100MB、≤1000 项、压缩比 ≤100、不允许嵌套包；按合法甲方样本测试后定配置，不能无上限解压。
2. 只接受声明的 docx/xlsx 等结构与白名单内容；拒绝宏/vbaProject、ActiveX/OLE 嵌入、DDE、外链关系/外部图片/远程字体/链接工作簿及不支持字段。XML 禁 DTD/外部实体，layout/StylePack 只接受受控字段，不执行模板表达式或命令。xlsx 用户文本以文本写入，防公式注入。
3. LO worker 非特权、只读根、独立临时目录与 profile、最小挂载、无宿主文件和密钥、默认无网络/禁止外联；固定 LO/字体/locale/时区与镜像版本。限制 CPU/内存/进程/输出大小/时长，超时杀整个进程树并清理；不同租户任务不复用可污染的 profile，任务并发有全局与租户上限。
4. 产物验证格式/摘要/分页与册数后才登记 report_file；预览冻结待审件与最终签字归档件新增保存，不覆盖。冻结期间源事实/模板变化须重开报告而非悄悄重渲染；最终签字后归档不可改。
5. 当前 Dockerfile 未安装 LO，只有 ca-certificates/tzdata/curl/su-exec 等运行依赖；新增镜像/字体/隔离/就绪检查是实施目标。无 LO 时明确只出 docx，要求 PDF 的部署不算验收通过。恢复与切换门禁见 06。

### 4.4 审计、接口与负例验收

高危操作审计覆盖模板/默认库发布、模板包导入、报告冻结/签字/归档/作废、文件证据下载、权限变更、租户操作、死信重放与迁移清理；记录 actor/tenant/scope/target/time/correlation/前后摘要，不落 token/密钥/全量敏感附件。可复用现有 sys_operation_log 基础但要评估完整性，audit_log 是待建/待收口目标，不能说从无日志。

现有 token header 认证统一校验来源/CORS；若使用 cookie 则加 SameSite/CSRF token，不把“API 加签”与 CSRF 混为一谈。回调保留现有验签并按具体协议补时间戳/nonce 防重放。登录/验证码、上传、AI、报告/导出设置身份/租户/资源限流。**免登（微信授权/平台 SSO）**：免登令牌只能由授权渠道换取，绑定既有账号与租户，不换发超出原账号的权限；令牌可撤销、有过期与刷新，渠道回调验签+时间戳+nonce 防重放；免登失败回退账号密码登录，不因免登跳过权限校验。

验收至少覆盖：同权限不同租户读取/修改/批量/文件/签章被拒；NULL/未知 scene/缺 scope/job 伪造被拒；平台默认只读与租户自有覆盖正确；旧 job 不覆盖新草稿；恶意/超预算文档被隔离；LO 无外网且超时可清理；文件证据摘要、清洗链与归档不可覆盖可追踪。只测试正常路径不算安全验收。

## 5. 性能、容量与可靠性验收预算

### 5.1 基线与实施目标

已有 checkin_record/sys_operation_log 月分区、任务查重与模板批量加载；07 的统一批量口径是方案要求，不代表所有接口已覆盖。启动确保当月/下月分区存在，不等于所有查询自动带分区键。需验证大历史范围的索引/裁剪与分页，不按表规模臆断“足够”。

报告/导出走 River 的 `render` 队列（01 §4.3），持久 pending/running/done/failed 状态、超时/进度/取消/幂等由库承载，HTTP 不同步等待 LO；入队与报告主记录写入同事务（`InsertTx`），渲染队列全局并发受 §4.3 的 LO 隔离上限约束。字典/StylePack 缓存按 tenant/scope/key，失效以 TTL/水位兜底。图片只压缩派生副本，不覆盖原始证据。IoT 分区/保留期属于未来设计，实测后定，不预建。

### 5.2 建议负载与验收值（全部待压测，不是性能承诺）

以下是一期压测用**预算起点**，不是已达到值或销售 SLA；实施前确认部署硬件/磁盘/网络、真实模板照片密度与厂商配额，超预算先收敛负载或调设计再评审。

| 维度 | 建议起始场景/预算 |
|---|---|
| 部署基线 | 分别记录 app/PG/Redis/LO 的 CPU/RAM 限额与磁盘类型；可用合计 8 vCPU/16GiB、SSD 的隔离测试环境起测，不能据此保证生产容量 |
| 数据 | 10 租户/100 小区、10万点位/20万设备、1000万检查项事实、12个月历史；照片单独记录平均/P95尺寸和存储量，冷热分布接近试点 |
| 在线混合负载 | 200 登录在线、50 同时操作；持续 30min：读40RPS/业务写10RPS（不含上传字节与外部 AI）；再测2倍突发5min、热点单租户与跨租户公平性 |
| API 预算 | 列表/详情 P95 ≤500ms、提交 P95 ≤1s（不含上传/AI/异步渲染）；非预期错误率 <0.1%，无租户泄漏/丢事实/重复生效，读分页上限100 |
| AI | 8 worker 基线，模拟 180s 慢调用与429/超时，并测试租户配额/全局上限；队列等待 P95 建议≤60s只在约定输入速率/厂商可用场景验收，超预算要可见排队，不能承诺厂商延迟 |
| 报告 | 全局 LO 先限2并发、单租户1；同时投10份“五册、每册100页、含照片”任务，记录排队/渲染分段耗时与RSS；建议单任务执行 P95≤5min，另测空册与大图极值；以实际甲方样本修订 |
| 批量维保确认 | 07 §3 的 `pending → confirmed` 是全方案**最长的单事务**（同事务写整单确认 + 最多 500 台生效流水 + 500 行台账日期回写，按设备 ID 顺序加锁），此前本表遗漏。起始场景：500 台上限单 × 3 单不同小区并发，记录事务时长与锁等待 P50/P95/P99、死锁与重试次数、WAL 与长事务对 autovacuum 的影响；另测两人并发确认同一单（只一人胜出）、确认中途超时/断连（整单回滚、无半生效流水）、500 台中混入已报废或越权设备（整单保持 pending 并返回具体冲突）。**500 是 07 §1 的防呆上限，不是已验证容量**：事务时长或锁等待超预算时，先下调单批上限或按 07 §3 显式拆批关联原单，不得后台静默剔除成员 |
| 任务队列（River） | 混合 notify/ai/render 三队列：100 任务/s 持续 30min、1000/s 突发 1min；记录入队与业务同事务的提交耗时、各队列等待与执行 P95、重试次数与 discarded 比例。制造 1 万积压后在不停正常流量下建议 10min 内追平。崩溃用例：worker 执行中 kill -9、PG 短暂不可用、同一幂等键并发入队，验证任务不丢不重（`UniqueOpts` 去重生效、超限转 discarded 可在 River UI 定位） |
| 稳定性 | 2h混合耐久，内存/临时目录不持续增长；PG连接、锁等待、IO、Redis内存/持久化、LO资源与队列最老年龄全程记录 |
| 恢复 | 初始演练预算 RPO≤24h、RTO≤4h，须业务确认与实测；有计划破坏性切换要求停写后最终恢复点无事实丢失，不用24h RPO容忍迁移丢数据 |

每次报告记录版本/硬件限额/样本/随机种子/并发/吞吐/延迟分位/错误与积压曲线/资源峰值、故障点与恢复结果。未达值必须说明瓶颈与可接受降额，重新批准预算；不能以平均耗时或空库代替验收。

### 5.3 依赖边界

保留现有 Redis（go-redis、会话/黑名单、Compose 服务）；AI 队列期1 迁出到 River（§2.3），Redis 不再承担业务任务持久化。**不引入独立消息中间件**：新增依赖只有 `riverqueue/river`，它是 PG 原生任务队列，跑在同一个 PostgreSQL 实例上，**不新增基础设施组件**（无需额外容器与运维对象）。明确不引 Watermill（只给路由与中间件抽象，outbox 与消费端去重事务仍需自写）、不引 Kafka/RabbitMQ/NATS/新规则框架。跨域事实联动按 01 §4.1 在同事务内完成，不需要总线。暂不分库分表；真实瓶颈出现后再评估。
