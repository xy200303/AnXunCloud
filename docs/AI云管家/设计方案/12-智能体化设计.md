# 12 智能体化设计（Agent / MCP / Skills）

> 目标：把系统能力以**工具（Tool）**形式统一暴露——内部 agent（助手 Tab）进程内调用，外部 AI 客户端经 **MCP** 接入，预置 **Skills** 承载编排好的工作流。
> 核心原则：**一份工具注册表，三种暴露形态**；工具不绕过接口鉴权，写操作必须经人确认。

## 1. 总体结构

```
内部 agent（助手 Tab，Eino ReAct）──┐
                                  ├─→ 工具注册表（Tool Registry）──→ 各业务域既有服务/契约
外部 AI 客户端（MCP 协议）────────┤            ↑
Skills（预置工作流）= 提示词模板 + 工具调用序列 ──┘
业务主流程（巡检拍照/资料扫描）──→ AI 能力服务（识别）──┘ 识别能力作为异步任务型工具注册进同一张表
```

- 工具注册表是唯一事实来源：每个工具声明 `name`、`description`、入参 JSON Schema、返回结构、**读写属性**（readOnly）、**形态**（sync / async_job）、所需权限点、限流档。**注册表在代码（进程内注册、随版本发布），不落库**——工具是编译期能力，落库会出现"库里有、代码里没有"的漂移；落库的只限运行期数据：租户级开关、限流档覆盖、Skills、MCP token 与审计日志。
- 内部 agent 与外部 MCP **共用同一张注册表**，只是传输与认证不同；不允许出现"内部一套接口、外部另一套接口"。
- 工具实现直接复用业务域公开契约（01 §4.1），不在工具层重写业务逻辑，不跨域读表。
- **识别能力统一进目录（异步任务型工具）**：09 §2.2 的 AI 能力服务（`image_inspection`/`meter_reading`/`label_date_ocr`/`doc_scan_extract` 等）作为 `async_job` 形态的工具注册进同一张表——调用返回 job 句柄，结果经队列回调/轮询获取。agent 在对话中可直接使用识别能力（拍照片发给助手 → `ai.inspect_image` → 结果流式回对话）；但**巡检/查验主流程不经过 agent 环路**，照旧直调能力服务——识别是高频队列化调度，不需要语言模型参与决策，agent 只是目录的另一个消费者。统一的是注册与治理（权限、配额、审计、Provider 适配），不是调用路径。识别结果仍是"建议，人工确认才算事实"，与写操作确认弹窗遵循同一条人工确认规则。

## 2. 内部 agent（助手 Tab）

- 运行时：[Eino](https://github.com/cloudwego/eino)（CloudWeGo，类型化 Tool/ChatModel + ReAct 编排）；工具从注册表进程内装载，调用时注入**调用者身份**（user/tenant/ProjectIDs），权限判定走与接口相同的 datascope 链路（09 §4）。
- 回答走 response 流（SSE）Markdown 流式渲染；思考过程、工具调用轨迹（名称 + 摘要 + 耗时）可展开（02 §3）。
- **写操作确认弹窗**：agent 先产出待确认计划，App 以居中弹窗写清对象、动作和条数，用户确认后才真正执行；确认动作本身是一次带签名的工具回执，防重放。确认前不落库。选项类选择可先用底部上滑 sheet，但最终写操作确认不采用上滑弹层。
- 会话与上下文：会话按用户+租户隔离；agent 只能看到调用者权限内的数据；长期记忆只存用户显式保存的偏好，不把业务数据写进模型上下文外的存储。
- **PC 后台同样内嵌助手**（菜单"智能助手"）：面向管理员的数据导入（拖入 Excel → 解析/校验/预览 → 确认导入）、报表导出（生成 → 转换 → 下载链接）、批量编辑场景；工具、确认、留痕与 App 端同一套，区别只是宿主界面。

## 3. 外部 MCP 接入

- 形态：系统内置 **MCP Server**，传输用 Streamable HTTP（SSE 兼容）；端点按租户隔离：`/mcp/{tenant}`。
- 认证：Bearer token（绑定租户 + 用户 + 允许的工具范围），可在后台签发/撤销；**token 的数据范围在签发时固化为当时该用户范围的子集，不在运行时按岗位推导**——否则用户调岗会让 token 范围悄悄漂移（14 §7）；用户调岗只可能使 token 失效，不得扩大其范围。**撤销后 5 秒内调用返回 401**（缓存 TTL 与校验路径按此约束设计），并保留撤销前的全部调用以便回溯。调用日志进审计（09 §4.4）。
- 工具映射：MCP `tools/list`、`tools/call` 直接映射注册表；tool annotations 标 `readOnlyHint`，只读工具对写操作不可见；外部调用写工具同样要先返回"待确认"句柄，由人在 App 内确认后执行——**外部渠道不能代替人确认**。`async_job` 型工具（识别类）映射为"返回 job 句柄 + 结果通知"，不让客户端干等。
- 配额：按 token 限流（读/写分档），全局配额与内部 AI 共用 09 §2.3 的公平性约束。
- 明确不做：不开放任意 SQL/自由查询接口；不暴露文件原文下载工具（文件只给摘要与受控链接，09 §4）。

## 4. Skills（预置工作流）

Skill = 一个命名工作流：提示词模板 + 允许的工具子集 + 参数表单 + 输出形态。从助手 Tab 或外部 MCP 以 `skill_name` 触发。

| Skill 示例 | 工具子集 | 输出 |
|---|---|---|
| 生成本周品质周报 | inspection.get_stats、workorder.list_workorders、report.draft_text | 文字稿（非正式报告） |
| 到期设备派单 | equipment.query_due、staff.get_schedule、workorder.create_workorder（写） | 确认弹窗 → 工单回执 |
| 承接查验批次初始化 | acceptance.create_batch、staff.assign_staff（写） | 确认弹窗 → 批次回执 |
| 设备台账问答 | equipment.*、inspection.list_records（只读） | 表格/摘要 |
| **批量预审（审核助手）** | inspection.list_records、ai.inspect_image、inspection.review_record（写） | 预审摘要 → 确认弹窗 → 逐条审核留痕 |

- **审核可以走 agent，但有边界**：agent 先预审——对照 AI 识别结论、证据完整性、数值越界、逾期等规则，把记录分成"建议通过"与"须逐条人工审"。**只有低风险记录可批量过**：AI 预选正常、证据齐、无异常、无人工改判、非本人提交；AI 判异常、人工改判、无法检查、高风险项仍须逐条人工审核（03/04 口径不变，agent 不替代人对异常负责）。批量确认弹窗写明本次将审核通过的条数与逐条清单入口，审核人一次确认，**每条记录的审核人仍记本人**，审核链与留痕与手工逐条审核完全一致。本人提交的记录 agent 不给审（同 03 审核回避）。

- Skills 有草稿/启用两态，随租户覆盖；平台预置包带默认 Skills（08 §9 预置包机制复用）。
- Skill 内写工具同样要确认；Skills 不能把多个写操作串成"一次确认全执行"。

## 5. 工具命名、参数与提示词设计（以 agent 视角）

模型选工具只看 `name + description`，抽参数只看参数名与 Schema——这三者就是"给 agent 读的文档"，按写给模型看的标准写，不按写给程序员看的标准写。

### 5.1 命名与描述

- **name 用小写业务语言 `域.动作`**，动词开头、读出来就懂：`inspection.list_records`、`workorder.create`、`equipment.query_due`。禁止技术黑话与缩写（`query`、`getList`、`doXxxImpl`），禁止一义多名（同一件事只留一个名字）。
- **description 四要素**：做什么 / 什么时候用 / 什么时候别用 / 返回什么。关键词与用户在界面上看到的词一致——用户说"工单池"，描述里就要出现"工单池"；用户说"台账"，描述里不要只写 ledger。不写实现细节（不写表名、不写 SQL 语义）。
- 写工具的 description 必须含"需确认弹窗"；异步识别工具必须含预期耗时与超时行为。
- 示例（`workorder.create`）：

```yaml
name: workorder.create
description: 创建一张工单（维修/维保执行）。当用户要求"派单/安排人处理某个问题"时使用；
  不要用于巡检异常的自动入池（那是审核通过的副作用）。需要确认弹窗，确认后才真正成单。
  返回工单号与状态。
```

### 5.2 参数设计

- **必填最少化**：只有没有它就干不成活的参数才必填；其余给安全默认（`limit=20`、`period=本月`、`sort=风险优先`）。
- **参数名用业务词**：`community_name`（名称，支持模糊）、`building_no`、`status`（枚举值即业务词：pending/approved/rejected，description 里注中文含义）；时间用相对语义 `"本月"`/`"2026-10"` 都可，工具内部归一。
- **歧义不静默猜**：`"1栋3楼灭火器"` 匹配到多台时返回候选清单让 agent 反问用户（"您指哪一台？"），不随机选一台执行。
- **返回结构**：`items[] + total + has_more + next_cursor`，每项是紧凑摘要；需要完整字段再调 `xxx.detail`。错误分三类可行动化：`no_permission`（说缺什么权限）、`ambiguous`（给候选）、`not_found`（说清哪个对象不存在）——agent 拿这三类就能自己决定是反问、换参数还是如实回复。

### 5.3 系统提示词骨架

```
你是 AI云管家助手，以当前用户的身份工作，只能使用已注册的工具。
- 数字必须有口径：凡给出统计数字，说明周期与范围（如"本月 · 戎安华府"）。
- 数据不足、没有权限或对象不存在时直接说明，不允许编造数字或记录。
- 写操作（创建/修改/派单/审核）：先用一句话复述要点生成确认弹窗，用户确认后才调用执行。
- 审核类结论只给"建议通过/建议驳回/须人工"及依据，不直接代表审核通过。
- 列表用表格输出；用户的问题答不了就说答不了，并给出最接近的可用工具入口。
```

- 提示词里**不放业务数据**，只放角色、边界与输出规则；数据一律经工具取。权限边界靠工具层强制，不靠提示词自觉。

### 5.4 描述质量评测

工具 name/description/参数的任何变更，先过评测集再启用：意图→工具选择准确率、参数抽取正确率、无工具场景的拒答/反问正确率、数字幻觉率。评测样本来自真实用户问法（"帮我看看 1 栋灭火器""今天能派谁去 3 栋"），不过不启用。

## 7. 安全与验收口径

- 工具调用 = 接口调用：同样的租户/项目/操作权限校验（授权语义按 14）；越权调用返回明确拒绝并记审计。
- 写操作无人确认不落库；确认弹窗带过期（10 分钟）与一次性签名。
- 外部 MCP token 可撤销、按范围授权；泄露处置 = 撤销 + 审计回溯。
- 压测：agent 会话并发、工具调用 P95、MCP 长连接占用并入 09 §5 负载表。
- 验收场景：内部 agent 只读问答、写操作确认与反悔、越权工具调用被拒、外部 MCP 只读接入、token 撤销即失效、Skill 触发完整链路。

## 8. 分期

| 期 | 内容 |
|---|---|
| 期2 | 工具注册表 + 内部 agent（助手 Tab）+ 只读工具 + 写操作确认弹窗 |

## 9. 扩展性（未来加工具/能力的方式）

设计上加能力只动一处，注意点如下：

- **新增工具**：在业务域实现契约方法，注册表加一行声明（名称/Schema/权限点/读写属性/形态）。内部 agent 与外部 MCP 自动可见，不改传输层、不改 App。工具只加不删，废弃标 deprecated。
- **新增识别能力**：作为 `async_job` 工具注册（声明预期耗时与超时行为，agent 编排据此决定等待还是先回"识别中"）；识别调用占用租户同一份 AI 配额，权限校验与业务主流程同口径——能拍哪个对象的照片才能识别哪张。
- **新增业务域**（如收费、装修上线）：按 §5 的 `域.动作` 命名补一组工具即可；首页对应灰色入口同期点亮，两件事共用一份注册表，不会跑偏。
- **新增 Skill**：只写提示词模板 + 工具子集 + 参数表单，不写代码；工具子集必须是已注册工具，Skill 不能私藏未注册能力。
- **新增模型/Provider**：走 09 §2.2 能力服务加 Provider 适配，agent 编排层不变。
- **注意事项**：① 工具的 `description` 和入参 Schema 质量直接决定 agent 选工具的准确率，描述写清"什么时候用、入参含义、返回什么"，新增工具须过一遍评测集再启用；② 新工具默认只读上线，写工具必须接确认弹窗链路后才能启用；③ 权限点复用现有动作权限，不为工具单开平行权限；④ 限流档随工具声明，高成本工具（报表生成、批量操作）单独降档；⑤ 工具返回结构保持紧凑摘要，不把大对象塞进模型上下文。
