# 13 后台管理系统设计（PC 后台）

> 状态：改造评审设计。**不是已实现说明**——文内「现状」是对 `frontend/src` 与 `backend` 的实测盘点，「目标」是待实施/验收项，两者逐节分开。
> 定位：PC 后台的 **owner 文档**。菜单结构、App/PC 职责划分、后台可扩展配置架构、加载与状态细节在本文定义一次；业务规则仍以 03/04/05/07/08 为准，领域边界以 01 为准，AI 能力与安全以 09 为准，agent/工具以 12 为准。
> 沿用现有 Vue 3 + Element Plus 工程（`frontend/`），**不另起独立前端工程**，不重画成第二套产品架构（02 §7）。

## 0. 定位与分工原则

甲方新规划把系统推向两个方向：**向下接更多设备（IoT，09 §1）**、**向外连业主端（社区四板块，02 §3）**。App 侧已按五 Tab 展开（AI助手/主页/卷宗库/社区/我的），执行与轻管理已经足够。随之暴露的是 PC 后台的三个短板：复杂编排没地方做、新能力（AI 服务化、工具注册表、设备接入、业主端内容）没有配置入口、现有配置页按功能硬编码不具扩展性。

分工三条原则，后续所有页面归属按此判定：

1. **PC 是管理能力的超集。** App 能办的每一个管理动作，PC 必须有等价入口、同一套权限点与审计口径；反向不成立。出差在手机上能改的，回到电脑上一定也能改。
2. **按"参数复杂度与可逆性"分流，不按"谁是领导"分流。** 参数多、步骤多、改错后果不可逆（流程编排、模板版式、批量导入、能力与密钥配置）→ 只在 PC；看、判断、少量参数的决策（审核、签字、调岗、启停、内容审核）→ App 优先，PC 保留。
3. **同一能力只有一个目标页面与一套规则。** 不为了"手机也能用"复制第二套流程（02 §3）；App 侧做不了的，显示只读与"去电脑端办"的明确说明，不放"看得见点不动"的按钮（02 §3）。

**主要问题**

1. **模板分散**：检查项模板在巡检管理、输出模板在系统管理、承接查验内容配置在承接查验——三处都是"配置模板"，管理员找一次要翻三个菜单。
2. **报告缺的是多册与归档阶段，不是整页**：现有 `stats/reports` 已能生成、审核、签字、下载（见 §1），但只支持单文件 `file_id`、状态只有待审核/已通过/已作废；五册、冻结待审件与最终归档件分阶段、单册失败重试属期2 新增。
3. **工作台与统计分析分裂**：两个一级菜单都在"看数字"，职责重叠。
4. **承接查验配置三处散落**：批次管理、查验内容配置、签署主体（已并入小区设置），新建批次后还要跳回去配。
5. **筛选/批量不均**：记录/点位/设备已有批量，但批次、小区、模板、系统管理各页普遍只有名称+状态，缺负责人/时间/完整度等运营条件，批量动作不齐（§7）。
6. **危险操作无约束**：删除直接删，有业务数据的对象没有"只能停用"的保护。
7. **编制抽屉已有但藏在三级下钻里**：小区列表 → 点小区 → 岗位编制抽屉 → 再切 Tab；配置完整度（缺人/断链）在列表上看不出来。
8. **新能力无配置入口**：AI 能力服务（09 §2.2）、工具注册表/Skills/MCP token（12）、IoT 接入（09 §1）、社区与业主端内容（02 §3）在后台均无页面，且现有配置页按功能硬编码，加一个能力就要加一套页面（§4）。

## 4. 可扩展后台架构

### 4.1 为什么现在这版配置撑不住

现有配置页是**按功能硬编码**的：AI 一张表单、字典一张表、系统配置一张键值表。按这个做法，接入一个新能力（新 AI 任务类型、新 IoT 协议、新输出引擎、新业务域）就要新增一套页面与一套存储，且"平台默认/租户覆盖"每次都要重新实现一遍。

扩展性不靠"多留字段"，靠**把配置拆成三层**，每层的变更代价与审计要求不同。

### 4.2 三层配置模型

| 层 | 内容 | 载体 | 变更代价 | 后台形态 |
|---|---|---|---|---|
| **L0 能力目录** | 工具（12 §5）、AI 任务类型（09 §2.2）、IoT 协议适配器（09 §1.1）、输出引擎（08）、业务模块 | **代码显式注册**，启动装载；不入业务库 | 发版 + 契约回归 | **只读展示**：名称、说明、入参 Schema、读写属性、形态（sync/async_job）、所需权限点、版本、deprecated 标记 |
| **L1 启用与策略** | 能力对租户的启用/停用、Provider 绑定、模型与超时、并发与配额、限流档、权限点映射、Skills 启停 | 入库，**平台默认 + 租户覆盖**（与 `equipment_type_schema` 同构，09 §3.1） | 改配置不发版 | 可编辑；改动进高危审计（09 §4.4） |
| **L2 实例与密钥** | Provider 账号、IoT 端点与凭证、MCP token、签章资产 | 业务库只存**引用**（`credential_ref`），明文走 env/KMS（09 §1.1、§4.2） | 改配置不发版 | 只显示掩码 + 最近使用/最近校验结果；**不回显明文**；撤销即时生效 |

**为什么 L0 不入库**：Schema 与实现强绑定。若允许在后台凭空新增一条工具/任务类型声明，就会出现"配置里有、代码里没有"的幽灵能力——agent 会去选它、MCP 会列出它，然后在调用时失败。因此后台只能**在 L0 已声明的能力上做启停与调参**，不能创建能力。这与 09 §0.2「不承诺新增格式只加一行配置、不发版」一致。

**平台默认与租户覆盖的边界**（09 §3.2）：租户只读被授权的平台默认、写自有覆盖；租户改不了默认源；平台改默认需专门权限与审计；缓存键含 scope/tenant。

#### 4.2.1 分层配置的统一机制（scope 两列 + 稀疏覆盖 + 读时解析）

现状并存两套模式，**本期统一为一套**：

| 现状模式 | 用在 | 问题 |
|---|---|---|
| 一张表 + `tenant_id` 可空，NULL = 平台默认 | `post_dict`、`approval_flow`、`duty_binding`、`equipment_type_schema` | **Postgres 中 NULL ≠ NULL，唯一约束在平台默认行上失效**。现有实现靠在索引里裹 `COALESCE(tenant_id,'000…0')` 打补丁（`00001_init.sql:2298/2319/2347` 三处各写一遍）；且部分索引**撑不了 `ON CONFLICT` 推断**，upsert 会失败 |
| 基表 `sys_config` + 覆盖表 `tenant_config(UNIQUE(tenant_id,key))` | 键值型配置（含现在的 AI 配置） | 两张表形状不同（`sys_config` 带 `name`/`config_group`/`remark`，`tenant_config` 只有 key+value），导致两套读写路径。另有**三处各写一遍回落逻辑**：`ConfigService.Resolve`（`config_service.go:159`）、`TenantService.GetConfig`（`tenant_service.go:202-210`）、品牌页占位 |

**统一形态**：所有分层配置——**不分键值型与结构型**——各层级都**同表**，用**显式 scope 两列**区分，不用 NULL。`tenant_config` 并入 `sys_config`（更名 `config`）：

```sql
scope     TEXT NOT NULL,   -- platform | tenant | project
scope_id  UUID NOT NULL,   -- platform 层为保留哨兵；tenant 层为租户 ID；project 层为小区 ID
UNIQUE (scope, scope_id, <业务键>)
```

选显式两列而非"`tenant_id` 去空 + 哨兵"，是因为**将来要精确到小区**：`scope` 自带层级语义，不用靠"`project_id` 是否为空"去推断当前是哪一层；加层也不改索引形状。

**键值型配置的键级属性用 CHECK 约束锁在平台行**。`name`/`config_group`/`remark`/`allow_tenant_override`/`is_secret` 描述的是**键本身**，不是某一层的值——`allow_tenant_override` 写在租户行上是自相矛盾（"租户自己说租户不许覆盖"，谁赢？），这种歧义会直接造出错误的授权判断：

```sql
CREATE TABLE config (
  scope     TEXT NOT NULL,   -- platform | tenant | project
  scope_id  UUID NOT NULL,   -- platform 层为保留哨兵
  key       TEXT NOT NULL,
  value     TEXT NOT NULL,
  name TEXT, config_group TEXT, remark TEXT,        -- 键级，仅 platform 行
  allow_tenant_override BOOLEAN, is_secret BOOLEAN, -- 键级，仅 platform 行
  UNIQUE (scope, scope_id, key),
  CHECK (scope = 'platform' OR
         (name IS NULL AND allow_tenant_override IS NULL AND is_secret IS NULL))
);
```

此处 NULL 表示"本行不适用该列"，与上文反对的"NULL 当默认值"不是一回事——唯一键三列仍全 NOT NULL。

**"有没有覆盖"统一由行是否存在判定**。现状写路径已经是这个语义——`TenantService.SaveConfig` 存空值时**删除整行**而非存空串（`tenant_service.go:230-235`，注释写明"空值 = 清除覆盖"），`Resolve` 里的 `value != ""`（`config_service.go:164`）是冗余防御而非缺陷。改造要点不是"修 bug"，而是**收口**：三处回落实现（`Resolve`、`GetConfig`、品牌页占位）合并为一处。

> 收口时两端必须同改：若有人把 `SaveConfig` 改成存空串、却删掉了 `Resolve` 的空串判断，"清除覆盖"会静默变成"覆盖为空"——对 `ai.prompt` 这类"留空=用内置规则"的键，表现为内置规则失效。迁移测试须覆盖这一例。

**白名单与密钥标记从代码挪到列**：现"仅白名单 key 可写""密钥类 `ai.*` 永不下放租户"硬编码在 `TenantService` 里，后台看不见、改要发版；改为 `allow_tenant_override` / `is_secret` 两列后是数据，也正是下文「平台可对某项标记不允许下级覆盖」的落点。

四条配套规则：

1. **稀疏覆盖**：只有当值与继承值**不同**才落行。GitLab 的 cascading settings 踩过的坑就是"父级改了、子级留着陈旧覆盖"，修法正是这条。
2. **读时解析，顺序显式**：`project → tenant → platform`，逐层回落。不靠 NULL 推断，不做"取最宽"这类隐式合并。
3. **UI 必须显示有效值与来源**：每项标「继承自平台默认 / 本级已覆盖」，并提供「恢复默认」（= 删除本级覆盖行）。业界反复反馈"有效值/继承来源视图缺失"是高频痛点——这也是共用组件要接 `scope` prop 的原因（§4.2.2）。
4. **不用 JSONB 合并表达覆盖**：Postgres 的 `||` 是**浅合并**，嵌套对象整体替换，覆盖里没重述的默认字段会被**静默删掉**。要么拆成列，要么自写递归合并——本期选前者。

**密钥不进配置表**（业界共识，与 09 §1.1 的 IoT `credential_ref` 同口径）：配置表只存**引用**（secret path / key ARN），密钥材料走 env/KMS 并按 scope 隔离、每次访问记审计。`ai_provider` 表因此只存 `credential_ref`，不存 Key 本体。

**默认不级联时的锁定**：平台可对某项标记"不允许下级覆盖"（lock），用于必须全局一致的项（如安全开关）。标记后下级 UI 只读并说明原因。

#### 4.2.2 一能力一组件一张表两个壳（禁止平台/租户各写一套）

现有代码已有正确样板，**本期推广为硬规则**：

| 能力 | 共用组件 | 平台壳 | 租户壳 |
|---|---|---|---|
| 审批链 | `components/ReviewFlowEditor.vue`（796 行） | `platform/review-flow-template/index.vue`（55 行） | `system/review-flow/index.vue`（56 行） |
| 岗位 | `components/PostManager.vue` | `platform/post-templates/index.vue`（30 行） | `system/posts/index.vue`（35 行） |

两个壳页各 30~56 行，差异只有**传哪个 api、要哪个权限点**。规则：

- **一个能力 = 一个组件 + 一张表 + 每层一个壳页**；禁止为平台侧和租户侧各写一套 UI，或各建一张表。
- 组件统一接三个 prop：`api`（该层的接口）、`save-perm`（`platform:*:update` / `system:*:update`）、**`scope`**（用于显示"继承自上级"与"恢复默认"；`ReviewFlowEditor` 现缺此 prop，须补）。
- **同一能力在各层用同一菜单名**，作用域由上级菜单与面包屑体现——现状"岗位模板库 / 岗位管理"、"审批流程模板 / 审批流程"是同一组件两个名字，须统一。**不再往 `模板` 上堆词**：该词已被三层模板体系（检查项模板 L1 / 台账字段方案 L2 / 输出模板 L3）与承接查验内容模板占用（AGENTS.md §4.1 命名约定）。

适用清单：审批链（已做）、岗位（已做）、**AI 供应商与绑定**（待建，§4.3）、检查项模板 L1、输出模板 L3、字典、承接查验内容模板、工具注册表与 Skills。

### 4.3 AI 配置：供应商注册表 + 场景引用（平台 / 系统管理各一份）

现状是**平台级一张表单**（`AiConfigPanel.vue`）：一个协议、一个地址、一个 Key、一个模型，前提是"一个模型干一件事"。按任务类型拆成多行后，若每行各填一遍协议/地址/Key/模型，等于**把同一个服务商配 N 遍**——这是把 §4.2 的 L2（实例与密钥）压进了 L1（启用与策略）。

正确形态是两层。**AI 配置按 §4.2.2 的"一能力一组件两个壳"在平台管理与系统管理下各挂一份**（同一组件、同一批表，用 `scope` 区分层级：平台层维护默认供应商，租户层按需覆盖或新增），页内五个 Tab：

| Tab | 层 | 内容 |
|---|---|---|
| **模型供应商** | **L2** | 注册供应商（预设：百炼/混元/DeepSeek/Kimi/智谱/OpenAI/Gemini/Claude/models.dev/自定义）→ 名称、API 协议、API Key、Base URL；其下注册**模型**：模型 ID、显示名、上下文窗口、最大输出、**能力标记**（视觉 / 文本 / 工具调用）、单模型高级参数（温度、超时、并发、流式） |
| **能力绑定** | **L1** | 任务类型（代码注册，不可新建）**只选一个已注册模型** + 超时/重试 + 自定义判定规则；下拉**按能力过滤**——标「需视觉」的任务只列带视觉能力的模型 |
| **助手与 Agent** | L1 | 助手对话、agent 预审节点、Skills 各自选模型（要求**工具调用**能力）+ 工具子集 |
| **MCP 接入** | L1/L2 | token 签发撤销与范围；MCP 是把本系统能力暴露给外部客户端，**模型在对方那边** |
| **配额与用量** | L1 | 租户并发/速率 + 全局资源与厂商配额上限、队列积压与最老任务年龄、死信计数（09 §2.3、§5.2） |

**一处注册、处处引用**：供应商与模型注册一次，巡检识别、助手 Agent、Skills、agent 预审节点全部引用，不各自重配协议与密钥。换服务商只改绑定，不动业务配置。

**新建三张结构化表**（不塞进 `sys_config` 键值表——一个供应商挂多个模型、每个模型带上下文窗口与能力标记，键值表表达不了）：`ai_provider`（名称/协议/base_url/**`credential_ref`**，不存 Key 本体）、`ai_model`（模型 ID/显示名/上下文窗口/最大输出/**能力标记**）、`ai_task_binding`（任务类型 → 模型 + 超时/重试/自定义规则）。三张表均带 §4.2.1 的 `scope` 两列。

分三张表只因为它们是**一对多**（一个供应商挂多个模型），**不是因为分层**——每张表自身跨所有层级，平台行与租户行同表同形，不存在"平台一张、租户一张"。AI 的键值型设置（AI 总开关、全局并发与速率上限）仍进 §4.2.1 的 `config` 表，同一套 scope 解析。

这个选择逼出两个必须写死的细节，否则覆盖语义会在运行期出错：

1. **覆盖粒度按行，不按父实体**。`ai_model` 独立解析，键为 `(scope, scope_id, provider_code, model_id)`。租户为了换自己的 Key 而覆盖了 `bailian` 供应商行时，**平台那 4 个模型仍然继承得到**，不需要重新登记一遍；租户只在想改某个具体模型时才落那一行。否则"覆盖供应商"会连带清空模型列表，变成重配而不是覆盖。
2. **跨层引用用业务 code，不用行 id**。`ai_task_binding` 指向模型时存 `(provider_code, model_id)`，**不存 `ai_model.id`**——存行 id 的话，租户覆盖了该模型后，绑定仍指着平台那一行，覆盖对已有绑定不生效，且表现为"改了没反应"这种极难排查的症状。解析在读时按 project→tenant→platform 逐层命中。这与 AGENTS.md §4.1「`id` 指向一行、`code` 指向一个业务概念」同一条。

**能力标记是硬约束**：只有带**视觉**的模型能绑到 `image_inspection`／`meter_reading`／`label_date_ocr`／`doc_scan_extract`；只有带**工具调用**的能用于 Agent 与 Skills。可由「获取模型列表」自动带出，手动添加时需自行勾选并用「测试」验证——勾错会导致绑定后调用失败。

**从 AI 配置里挪走的项**：

- `重拍放行次数`、`同步判定开关`、`同步超时秒数` → **App 固定交互逻辑**（业务规则，不是模型参数）。识别中禁止提交，失败后直接转人工填写/确认，不另设巡检规则配置页。
- `prompt 种类` → **检查项模板 L1 的 `ai_prompt_kind`**（08 §3.2.3）。它是逐检查项的判定维度，共 11 种**跨设备通用**维度（general/presence/damage/metric/state/label/passage/leak/indicator/tidiness/baseline），不按设备分类，更不存在"消防专用 prompt"。
- `自定义判定规则` 保留在能力绑定的「高级」里，明确"整体替换内置规则后 `expected_schema` 不变"。

**失败处理不是可配开关**（03 §3）：`pending/running`（识别中）禁提交，防的是不等结果就交；`error` 是终态、**不阻塞提交**——巡检员可重试重拍，或填人工结论 + 故障说明后提交并强制人工审核，但不得以"默认正常"代填。两者都是固定规则。

### 4.4 工具注册表、Skills 与 MCP

**工具注册表落在 L0（代码注册）+ L1（租户启用与限流）**，不是"后台建一条工具记录"。后台页面：

- **AI 配置 → 助手与 Agent**（可编辑）：助手对话／agent 预审节点／Skills 各自引用已注册模型（须带**工具调用**能力），不与其他 AI 消费方或工具清单堆叠。
- **智能助手 → 助手设置**：统一管理工具与 Skills 的启停、限流和 MCP token。工具目录由代码注册，不另设能力中心页面；token 只在签发那一次显示明文，之后只显掩码。

**撤销的时效要写进验收**：12 §6 只说"可撤销"，本文补明确口径——**撤销后 5 秒内 HTTP 返回 401**（缓存 TTL 与校验路径按此约束设计），并记录撤销前的全部调用以便回溯。没有时限的"可撤销"等于留了一个窗口。

**工具表治理**（12 §8 的注意事项落到后台）：新增工具默认只读上线；写工具必须接人工确认链路后才能启用；工具只加不删，废弃标 deprecated 至少一个版本期。后台需显示"引用计数"（被哪些 Skill/MCP token 允许范围引用），否则没人敢停用。

## 6. 业务流程简化

1. **新建小区 = 一条向导**（替代"建空壳再跳四处配"）：基本信息 → 导入楼栋 → 导入点位（批量建点/二维码）→ 人员与流程（从租户默认带出）→ 模板与承接查验类型 → 完成。每步可暂存，最后给"配置完整度检查"。

   **创建即带默认审批链，不允许无链的小区存在**（14 §4.6.2 第一道防线）：第一步写入时即从租户默认带出三链（打卡/维保/报告签字），管理员可改不可清空。

   **小区分未启用 / 已启用两态，启用是门禁**：创建后为未启用，向导各步可暂存；**「开通完整度」全绿才能启用**——点位 / 人员 / **流程（每个审批节点至少 1 个候选人）** / 模板 / 签署。**未启用的小区不生成巡检任务**，因而不会产生待审记录（14 §4.6.2 第二道防线）。拦「启用」而不拦「创建」，否则必须先有小区才能导点位配人的向导会被卡死。
2. **新租户上线 = 预置包 + 小区向导 ×N**：预置包导入一次（点位类型/检查项模板/台账字段/审批流程/输出模板/默认 Skills），之后每个小区走向导，不再逐项配（09 §3.3 第 4 条）。
3. **报告链一页走完**：生成（选项目/期间/范围）→ 冻结 → 审核 → 签字 → 归档，同一页展示状态时间线与各册文件，不来回跳。
4. **审批链一处配，项目可覆盖**：租户默认在系统管理「审批流程」，项目覆盖在小区设置「流程与签字」；两页都显示"继承自哪里"，保存时提示影响范围（未送审任务/记录）。节点**直接绑角色**（14 §1.5），不再经职责槽位中转——原 `duty_binding` 与审批链双写已取消。**节点无人保存前阻断**：绑的角色在该小区无在职人员时，保存给出明确警告并标记该小区为断链，不默默存成"跳过"（14 §4.6）。节点名按职责（月报审批/打卡复核），不按角色（14 §1.5.1）。
5. **承接查验批次创建即快照**：建批次时自动带出当前内容/签署/审核链配置，送审前可改，不用建完再找配置页。
6. **批量能力前置**：列表勾选后直接出批量动作（启停、下发配置、生成二维码、导出），不要求先进详情。
7. **能力配置带连通性自检**：AI Provider、IoT 端点、MCP token 保存后提供"测试"动作，返回耗时与实际响应摘要；失败给具体原因（鉴权/网络/配额/模型名），不只报"失败"。

## 7. 筛选与批量能力补齐

## 8. 运营看板：按小区分行，不混成一个数

甲方口径：**各小区的收费率等经营数据各不相同**（14 §1.1）。因此分管多小区的人，看板不能只给合计值——一个 85% 的平均收费率会掩盖"A 小区 95%、B 小区 60%"，看了没法行动。

| 规则 | 说明 |
|---|---|
| **默认按小区分行** | 每个在管小区一行关键指标，合计行在底部。**现有工作台的「各小区今日执行情况」条形图本就按完成率升序、&lt;100% 标橙**，在它基础上扩展即可，不另起表格 |
| **合计必须标范围** | 写明"3 个小区合计"，不能让人误读成单个小区 |
| **垫底自动排前** | 完成率最低、整改最慢、逾期设备最多的小区排最上面（02 §9.1 已要求"管辖项目横向对比"，现原型未实现） |
| **单小区用户不显示对比区** | 只管一个小区的人不需要横向对比，不制造噪音 |
| **口径标注** | 现场已提交与审核通过分别统计，不把待审核写成合格完成（02 §2） |
| **断链与配置缺陷入告警区** | 空名单挂起、`blocked_by_config` 点位、缺签署配置集中呈现，可直达修复页（14 §3.2） |

看板详情页（原型 62，现为"项目概况/客户服务/财务经营/品质保障"四版块）需支持**按小区切换或并列对比**，不只给聚合视图。

**四个统计子页必须保留的现有指标与能力**（合并一级菜单时不得丢失）：

| 子页 | 现有指标与能力 |
|---|---|
| 覆盖率 | 点位覆盖率 / 实检应检 / 异常数 / **疑似作弊** 四卡 + 趋势图 + 各小区覆盖率图 + 明细表 + 导出（`stats:export`） |
| 及时率 | 三卡 + 两图 + 明细表 |
| 巡更达成率 | 应巡 / 实巡 / 达成率 / 逾期 / 单轮点位完成率 五卡 + 达标线 + 按天明细（达标·不达标标签） |
| 绩效 | 人均完成率 / 人均异常 / 疑似作弊 三卡 + 巡检员横向对比图 + 服务端排序表（点疑似作弊跳记录）+ 分页 |

图表统一走 `CHART_COLORS` + 异步 `Echart` 组件（echarts ~568KB 首屏后加载）+ `empty-text` 空态。

**数据来源提醒**：收费率、清欠率、报事关闭率来自收费与报事模块，而这两个模块当前是**灰色占位、未建设**（02 §1）。这些指标在看板上现为演示数据，必须标注，不得在甲方面前当作已有能力——已登记 10 §2 第 20 项。

## 9. 加载、状态与反馈细节

02 §7 的"加载"一行只写了"首屏加载、分页、空结果、请求失败分别表达"。PC 后台的列表与长任务更多，本节把它展开为可验收的口径。

### 9.1 加载态

| 场景 | 表现 | 禁止 |
|---|---|---|
| 列表首屏 | **骨架行**（表头先出，骨架行数=分页大小的可视部分），筛选区立即可用 | 整页 spinner 盖住筛选区；加载时筛选不可点 |
| 分页/排序/筛选切换 | 表格区局部 loading 遮罩（淡），表头与筛选保持可见可改 | 整页重载、滚动位置丢失 |
| 抽屉/弹窗详情 | 骨架块（字段标签先出），主操作按钮在数据到齐前禁用 | 空白抽屉、按钮先可点后报错 |
| 下拉选项（小区/模板/人员） | 首次展开才拉取，带 loading 文案；失败给"重试"而非空列表 | 空下拉伪装成"没有数据" |
| 看板卡片 | 每卡独立加载与重试，一卡失败不拖垮整屏 | 一个接口失败整页空白；**失败显示假零**（02 §2） |
| 大列表（>1000 行可视） | 虚拟滚动；仍保留分页上限 100 的服务端口径（09 §5.2） | 前端一次性渲染全量 |

### 9.2 空态与错误（三类分开，不混）

| 类型 | 文案要点 | 下一步 |
|---|---|---|
| 无数据 | "还没有 X" | 给创建入口（有权限时） |
| 无权限 | "没有查看 X 的权限" | 指向谁能开（不显示数据轮廓） |
| 配置缺陷 | 具体缺什么（缺坐标/围栏非法/断链/未配签署） | 直达修复页 + 已通知谁 |
| 请求失败 | 发生了什么 + 重试 | **行内/卡内重试**，不整页报错；表单失败保留已填数据 |

错误信息只讲发生了什么和下一步，**不混入制度说明**（02 §7）。`blocked_by_config` 在列表行标橙/红，并计入运营看板的告警区（03 §6）。

### 9.3 长任务（报告生成、批量导入、二维码生成、批量确认）

- 统一走 River（01 §4.3），HTTP 不同步等待；页面显示**持久状态**（pending/running/done/failed）与进度，刷新后状态不丢。
- 进度口径按 07：**已处理/成功/失败/跳过**四个数分开，提供失败明细、导出与**仅重试失败**；不因部分失败把成功项重做，不把"处理完成"写成"全部成功"。
- 轮询与推送：报告生成等用户在场的长任务用 SSE 或 2s 轮询并在 done/failed 后停止；后台批量任务降为 5~10s 轮询；**离开页面停止轮询**。
- 任务可取消的，取消是显式状态（不是静默丢弃）；不可取消的（已进 LO 渲染）明确说明。
- 队列积压与最老任务年龄在运营看板/平台管理可见（09 §5.2）。

### 9.4 保存与并发

- 抽屉/弹窗保存中：按钮进 loading 并禁用，前后端共同防重（02 §7）；失败保留数据与错误定位到字段。
- **审批、签字、归档、确认类操作不做乐观更新**：必须等服务端确认再改 UI，且按状态+revision 条件更新，防重复审核覆盖新修订（03 §5）。
- 列表行内启停可乐观更新，失败回滚并提示。
- 危险操作（停用/删除/撤销 token/改配额）二次确认，确认框写明**影响对象与范围**；有业务数据的对象删除改"停用"（§1 问题 6）。
- 配置类保存提示影响范围（如审批链改动影响多少未送审记录，§6.4）。

### 9.5 缓存与失效

字典、模板、StylePack、工具目录按 **tenant/scope/key** 缓存，发布或覆盖后失效（09 §5.1）；缓存键含 scope 防跨租户串读（09 §4.1）。前端列筛选记忆、分页大小记忆按用户+页面存本地，不影响数据权限。
