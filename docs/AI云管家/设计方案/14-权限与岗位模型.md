# 14 权限与岗位模型

> 状态：改造评审设计。**不是已实现说明**——文内「现状」是对 `backend/internal` 的实测核对（附 file:line），「目标」是待实施/验收项，两者逐节分开。
> 定位：**授权模型的 owner 文档**。组织与范围、角色与审批授权的边界在本文定义一次；它跨 App / PC / agent 工具 / 文件授权，不属于任何单一端。09 §3.3、§4.1 的租户与岗位条款以本文为准同步，12 的工具与 token 授权引用本文。
> 范围：不含业主端账号体系（仅定分流口子，见 §2.5），不含业务流程规则（03/04/05）。

## 0. 结论先行

**五个概念塌缩成两个：角色 + 任职。**

甲方已确认「一人一岗，需要不同岗位时另建账号」「岗位数不会膨胀」「项目 = 小区」。在此前提下，原先的 岗位 / 角色 / 职责槽位 / 编制 / 数据范围 五层里，有三层没有承载对象：

- **岗位与角色是同一件事。** 分离的本质问题是它隔离了两件本该一致的事：角色配错，项目经理就干不了活；而**没有权限的项目经理本来就不该叫项目经理**。两套东西各配一遍、各错一遍，是臃肿而非解耦。
- **职责槽位与审批链是同一件事。** `approval_flow` 与 `duty_binding` 都带 `ProjectID`（NULL = 租户默认、非空 = 项目覆盖），**用完全相同的机制回答同一个问题："这个项目里，这一步谁来办"**。配一件事动两处，还得想谁压谁。
- **数据范围不是独立配置项。** 它就是任职覆盖的小区。

合并后：

```
任职 = 人 × 角色 × 勾选的多个小区
审批链节点 → 角色（月报审批 → 项目经理；打卡复核 → 安全主管）
范围 = 任职勾选的小区
```

管理员只碰三个页面，每样只有一处：**审批流程 / 角色定义 / 人员任职**。

这不只是"少几个概念"——现有的多条严重缺陷**随合并消失而非被修复**：岗位→角色的运行时并集、casbin 的第二份并集实现、槽位回落查另一个槽位的特例、主管判定硬编码、"谁是管理员"两套算法，都失去了存在理由。

**明确不做**：Grant 三元组、主体类型多态、通用范围锚点、片区/项目层、业主塞进任职表。这些解决的是"范围形状不可预测"，而甲方已明确形状（§1.1）。

## 1. 模型定义

### 1.1 甲方已确认的业务口径（模型前提）

**以下任何一条变更，都须重新评审模型并登记 10 §2**：

- **组织两层：公司 → 项目，且项目 = 小区（一对一）。** 不设片区，不把多个小区合成一个项目。
- **一人一岗。** 同一个人在不同小区基本是同一个岗位；需要担任不同岗位时**另建账号**。
- **岗位数量不会膨胀**（物业工种通常 6~10 种，不超过 20）。这是岗位与角色能合并的前提：不会出现"大量岗位共用少数权限组合"导致的重复定义。
- **各小区的收费率等经营数据各不相同**，分管多小区的人必须按小区分别看，不能只给合计值（呈现规则见 13 §8）。

### 1.2 两个概念与唯一来源

| 概念 | 回答什么 | 唯一来源 |
|---|---|---|
| **角色** | 他是什么岗位、能干什么、审什么、抢什么单、看多深 | `sys_user` 上的角色（**全局唯一，一人一个角色**） |
| **任职** | 他在哪些小区工作 | `project_staff` 行（一行一个小区）；**数据范围即这些行覆盖的小区** |

```
公司 ──> 项目（= 小区，一对一）

用户 ──持有──> 一个角色
                ├─ 权限点集合（能点什么功能）
                ├─ 可抢工单类型
                ├─ 主管标志（项目级数据看全项目 / 仅本人）
                └─ scope_level（决定范围怎么算，§1.4）

任职行（人 × 小区，一行一个小区）
  ├─ 数据范围：这些行覆盖的小区
  ├─ building_ids  责任楼栋（分派筛选，**不是权限边界**，§1.6）
  ├─ 生效期        effective_from / effective_to（本期新增）
  └─ 代理          delegate_user_id / delegate_until（本期新增）

审批链节点 ──绑定──> 角色 ──解析──> 在对象范围内有任职、且持该角色的在职人员
```

**"他是什么角色"只有一个答案。** 甲方口径是「物业经理在 A 是物业经理，换到 B 也是物业经理」，角色因此挂在用户上，不按小区分别配；确需在不同小区担任不同岗位时**另建账号**（§1.1）。这让"一人一岗"成为**结构约束而非约定**——数据层面无法表示"同一账号在 A 是经理、在 B 是巡检员"。

鉴权是一句话：**他的角色给权限点，他的任职行给范围**；某条记录能不能审，看他是不是该记录当前节点的候选人（§1.5）。

#### 1.2.1 范围为什么是独立的表，不是用户表上的数组

`project_staff` 保持**一行一个小区**（现状结构，唯一键 `(project_id, user_id)`），不改成 `sys_user` 上的小区 ID 数组。三条理由：

1. **有三个属性天然按小区不同**：责任楼栋（楼管员在 A、B 两小区负责的栋号不一样）、生效期（临时增派某一个小区到某日）、代理人（休假时不同小区可能托给不同的人）。用数组就得往数组里塞对象，等于在 jsonb 里手搓一张表。
2. **范围变更频繁，账号主数据不该跟着抖**。`sys_user` 是登录与账号主数据；调岗、增派、到期是常态操作。
3. **查询与完整性**：最热的判定是"这个人对这个小区有没有范围"，一行一小区就是索引命中；数组要 GIN + `@>`。小区删除时行结构可级联清理，数组会留悬挂 ID。现有 `StaffProjectIDs`（`middleware/datascope.go:19`）的 `Pluck("project_id")` → `ApplyCommunityFilter` 的 `IN (?)` 本就是按行设计，不用改。

"勾选多个小区"是**界面写法**，不是存储结构——勾 3 个小区 = 一个事务写 3 行，UI 合并成一张卡。管理员操作体验不变。

### 1.3 角色（甲方口径的"岗位"）

角色是配置对象，**项目级角色就是甲方说的岗位**。一个角色声明三件事：

| 声明项 | 项目经理 | 安全主管 | 巡检员 | 维保工 |
|---|---|---|---|---|
| 权限点集合 | 项目管理全集 | 巡检与审核 | 任务执行 | 维保登记与工单执行 |
| 可抢工单类型 | 全部 | 巡检整改 | 巡检整改 | 换粉、水压试验 |
| 主管标志（可见深度） | 全项目 | 全项目 | 仅本人 | 仅本人 |

平台预置一套行业标准角色（项目经理 / 品质主管 / 工程主管 / 巡检员 / 维保工 / 消控值班），新租户复制后只改差异（09 §3.3 第 4 条）。

**权限点与角色属性的分界线**：

| 问题形态 | 用什么表达 | 理由 |
|---|---|---|
| 能不能做这件事 | **权限点** | 一刀切，无子类型 |
| 能做这件事的**哪几类** | **角色属性** | 有类型维度，权限点要表达就得炸成 `workorder:grab:refill`、`workorder:grab:elevator`…（权限维度上的 role explosion） |

据此：**"谁能被派巡检任务" = 该小区任职 ∩ 角色含巡检执行权限点**，推导得出，不单独配——巡检没有子类型维度，查哪些点位由计划决定、哪几栋楼由责任楼栋决定。而"可抢工单类型"必须是角色属性，因为换粉/水压/电梯/土建是真实类型，电梯还要资质。将来若甲方提出"这个人只做消防不做供水"，那时才给巡检加类型属性，现在不建。

**合并要求把现有的"大杂烩角色"拆明白**：现 seed 只有四个角色（`seed.go:86-91`），其中两个是按"用哪个端"划分的桶，不是按工种——

- `project_admin`（项目管理员，`ScopeProject`）：注释"**项目经理/主管等**项目级后台使用人员：业务菜单全开"
- `field_staff`（一线人员，`ScopeSelf`）：注释"**巡检员/维修工/楼管员/前台等**移动端使用人员"

同时 `post_dict` 里 `project_manager` 与 `safety_supervisor` **共用 `project_admin`**（`seed.go:555-556`），但二者职责分别是"月报终审，全员管理"与"管理巡检员，巡查打卡审核，月报主管审批"——显然不是同一套权限，共用只是图省事。

合并后这两个桶拆成具体工种角色，**角色即岗位**。

#### 1.3.1 内置角色（平台预置）

| scope_level | code | 名称 | 主管标志 | 由什么合并而来 |
|---|---|---|---|---|
| `platform` | `super_admin` | 超级管理员 | — | 保留 |
| `tenant` | `tenant_admin` | 租户管理员 | — | 保留 |
| `project` | `project_manager` | 项目经理 | 全项目 | `project_admin` + 岗位 `project_manager` |
| `project` | `quality_supervisor` | 品质主管 | 全项目 | `project_admin` + 岗位 `safety_supervisor` |
| `project` | `engineer_supervisor` | 工程主管 | 全项目 | 新增（维保生效确认的默认承办） |
| `project` | `inspector` | 巡检员 | 仅本人 | `field_staff` + 岗位 `inspector` |
| `project` | `maintainer` | 维保工 | 仅本人 | `field_staff`（原注释的"维修工"） |
| `project` | `building_manager` | 楼管员 | 仅本人 | `field_staff`；用任职行的 `building_ids` 限定责任楼栋 |
| `project` | `fire_duty` | 消控值班 | 仅本人 | 新增 |

**`project_admin` / `field_staff` 两个 code 随合并删除**——它们按"用哪个端"分类，而端由权限点与主管标志自然决定，不需要一个角色来表达。

租户可在预置基础上改差异或新增（如"客服主管""前台"），但**不鼓励按人新建角色**；岗位数预期 6~10，不超过 20（§1.1）。

### 1.4 角色的作用域：`scope_level` 决定范围怎么算

角色统一挂在用户上，`scope_level` **不决定"挂哪儿"，决定"范围怎么算"**：

| scope_level | 例 | 范围 |
|---|---|---|
| `platform` | 平台超管 | 平台；**执行具体操作必须指定目标租户**（09 §4.1） |
| `tenant` | 租户管理员、集团职能 | 本租户全部小区；不需要任职行 |
| `project` | 项目经理、巡检员…（= 甲方说的岗位） | **他的任职行覆盖的小区**；无任职行 = 无范围（fail closed） |

一个公式：

```
可见范围 = scope_level=platform ? 平台（须显式指定租户）
         : scope_level=tenant   ? 本租户全部小区
         : 任职行覆盖的小区集合

可见深度 = 角色主管标志（全项目 / 仅本人）
单条记录 = 若为该记录当前审批节点的候选人，则可读（"能审必能看"，§1.5.3）
```

**项目级角色的安全性靠任职行兜底**：持"项目经理"角色的人，只在有任职行的小区里是项目经理，没有任职行的小区什么都看不到。这是角色挂用户之后仍然安全的原因——权限点是全局的，但**范围不是**。

**术语对齐**：代码统一 `sys_role` + `scope_level`，**UI 在项目上下文中显示为"岗位"**（对齐甲方与现有「岗位管理」菜单）。文档与接口须写明二者是同一个对象，不制造第二套名词（AGENTS.md §4.1 命名约定）。

### 1.5 审批链节点（取代职责槽位）

审批链节点**直接绑角色**，不再经由槽位中转。`duty_binding` 整表、`Slot` 枚举与 `resolveSlotPosts` 三级回落一并删除（§4.1）。

```
审批链 approval_flow（project_id NULL = 租户默认，非空 = 项目覆盖）
  └─ 节点 = { 职责名, 角色code, mode: any|all, kind: ''|ai, on_pass/on_abnormal/on_review }
                    └─> 候选人 = 持该角色、且在对象范围内有任职的在职人员
```

#### 1.5.1 节点按职责命名（硬规则）

**节点名说"要办什么事"，绑的角色说"谁来办"。** 节点名不得按角色命名——项目覆盖换了角色之后，按角色起的名字就是谎话，而这一层的价值恰恰在于可重绑。

| 现状节点名（按角色，必改） | 目标节点名（按职责） | 代码位置 |
|---|---|---|
| 巡检员确认 | **报告现场确认** | `flow_service.go:31` |
| 项目复核 | **打卡复核** | `flow_service.go:33` |
| 经理确认 | **月报审批** | `flow_service.go:91` |

#### 1.5.2 候选人按业务对象范围解析

**不是按单个小区查。** 这决定了跨小区场景能否自然表达：

- *单小区记录*（一条打卡记录）：对象范围 = 该小区 → 解析出该小区持该角色的人，与现行为一致。
- *跨小区报告*（覆盖 A、B 两小区，需两地项目经理各自签字）：对象范围 = {A, B} → 节点绑"项目经理"，解析出 A 的与 B 的项目经理，**两人都进候选**。不需要"跨小区节点"，也不需要片区层。
- *公司级职能*（集团品质总监审所有项目月报）：该小区无人持该角色时，**向上命中 `scope_level=tenant` 的任职**。

现 `SlotUserIDs(db, communityID, slot)` 只按单个 communityID 查，属必改项（§5 第 2 步）。多人候选时的**会签 / 任一人通过**由节点的 `mode` 决定（03 §5），本文只保证候选人解析正确。

#### 1.5.3 节点绑定即授权（三道闸降成一道）

**唯一判定：你是不是这条记录当前节点的候选人。**

| 问题 | 判定依据 |
|---|---|
| 能不能审**这条记录** | 是否为该记录当前节点的候选人 —— **唯一判定** |
| 能不能读**这条记录** | 同上。**"能审必能看"**：候选人身份即赋予该条记录的读权限，与角色主管标志无关 |
| 能不能看到审核菜单/入口 | **推导**：我的角色是否被任一审批节点绑定。不单独配权限点 |
| 页面内的附加操作（批量通过、导出） | 权限点 —— 这些是独立能力，与审批资格无关 |

**不设"审批类权限点"**，因此不存在"角色权限点与节点绑定两处对不齐"的问题，也不需要"保存审批链时校验该角色有无对应权限点"这类同步校验——没有可同步的东西。那种校验虽然比现状好，但本质是维持双写再加一道对齐，还会引入一张"节点类型 → 必需权限点"的隐含映射表需要有人维护。

**回落层级的变化**：`duty_binding` 原有三级（项目→租户→平台），`approval_flow` 只有两级（项目→租户，`project_id IS NULL` 即租户默认）。平台级默认流程由**预置包实例化成租户行**提供（09 §3.3 第 4 条已有此机制），平台默认能力不丢。

**断链规则不变**：节点绑的角色在该对象范围内无人 → 挂起 + 告警 + 修复入口，不得跳过或自动通过（§4.6）。

### 1.6 为什么不引入片区/项目层

组织树（公司→片区→项目→小区）在甲方口径下没有承载对象：项目即小区，分管多小区由任职的小区勾选表达，跨小区签字由 §1.5.2 的对象范围解析表达，区域层面不出独立报表、不设独立审批环节。**多一层就多一处范围推导歧义**，收益为零。

若将来出现"片区要出独立报表或有独立审批环节"，再评审加层；届时现有任职行的小区集合即可固化为片区，不需重写授权链路。

### 1.7 授权范围 vs 责任范围（`building_ids` 的定位）

两件事必须分开，混在一起会把频繁变动的排班塞进权限模型：

| | 授权范围 | 责任范围 |
|---|---|---|
| 回答 | 能不能访问这个小区的数据 | 该他巡哪些点 |
| 粒度 | **小区** | **点位集**（按楼栋/单元筛出） |
| 存哪 | 任职行覆盖的小区 | 巡检计划 / 任务 |
| 变更频率 | 低（调岗） | 高（换班、顶班、临时调整） |

**`building_ids`（责任楼栋）属于责任范围，是生成计划/派任务时的默认筛选条件，不是权限边界。** 三条依据：

1. **现状即如此**。该字段只用于展示楼栋名（`community/service/staff_service.go:190-201`）、保存（`:273`）与校验楼栋归属该小区（`:371`）；`middleware/datascope.go` **一处都没引用**。
2. **隐私已由主管标志覆盖**。楼管员是"仅本人"档，本来就只看得到自己提交的记录；再按楼栋切，保护的东西有限。
3. **顶班是常态**。强制为权限边界意味着每次顶班都要先改配置，而物业换班很频繁。

甲方已确认**精度到楼栋即可，不需要楼层**，因此 `building_ids` 保持扁平数组，`building` 表（楼栋/区域，`inspection/model/models.go:196`）无需加层。楼层本就不是组织实体，而是点位属性（`inspection_point.floor`，负数=地下层），需要时在筛点位那一步用。

现有注释"责任楼栋（仅楼管员用，空=全部楼栋）"容易被下一个人当成权限去实现，须改为明确标注"分派筛选，不参与鉴权"。

将来若甲方明确要求"楼管员不得看别栋的记录"，正确做法是**按点位集授权**（计划/任务派给他的点位），不在组织树上加层；且须先确认那是隐私需求还是界面噪音——后者用默认筛选即可。

## 2. 边界规则

### 2.1 同一自然人（"另建账号"的配套硬规则）

甲方口径允许一个人持有多个账号（担任不同岗位时）。这会绕开防自审：**03 §5 的"非提交人""不得自审"按账号判定，同一个人用 A 账号提交、B 账号审核即可通过。**

因此：

- 账号须登记**自然人标识**（手机号或身份证，租户内唯一），多个账号指向同一自然人
- **审核候选人按自然人去重**：提交人的任一关联账号都不得出现在该记录的候选名单中
- **绩效与工作量按自然人合并**，不把一个人统计成两份
- **离职时关联账号一并停用**，不漏掉另一个

这条不落地，"另建账号"就是在安全规则上开口子。

### 2.2 一人一岗是结构约束

角色挂在用户上、一人一个角色，因此"同一账号在 A 是经理、在 B 是巡检员"**在数据层面无法表示**——一人一岗不再是靠人自觉的约定。确需担任不同岗位的，按甲方口径**另建账号**（配套的自然人去重见 §2.1）。

**不设个人级权限覆盖**：既不能给单个人追加权限点，也不能删减。需要别的权限就换岗位，或新建一个岗位。理由是排障成本——一旦允许个人覆盖，"他为什么能/不能做这件事"就有两个来源，每次都要先判断是岗位给的还是手动加的；而岗位数本就不多（§1.1），新建一个岗位比维护一批个人例外更清楚。同一小区内确实身兼两职（小项目里项目经理也排消控班），按实际职责建一个合并岗位，不靠叠加权限表达。

### 2.3 角色变更跟随持有者（合并后从"最好有"升为"必须有"）

合并后权限点、可抢工单类型、主管标志**全挂在角色上**，改一个角色影响所有持该角色的人——以前至少还隔着岗位一层。因此：

- 改角色定义，所有持有者**跟着变**
- **保存前必须列出受影响人数与审批节点**（与审批链改动同一个提示口径，13 §6.4）
- 高危变更（收窄权限点、改主管标志）进审计

### 2.4 临时与流动人员：抢单即授权

只来抢一两单的机动人员**不预配任职**：

```
工单池按公司级范围开放 → 他看得见
抢到单 → 生成临时任职（范围 = 该小区，角色 = 对应执行角色，有效期 = 工单生命周期）
工单关闭 → 自动回收
```

管理员零操作。能抢什么由角色的"可抢工单类型"决定。临时任职与正式任职同一张表、同一套范围推导，不是特例分支。

**跨租户（跨物业公司）抢单不在本期**：它触及租户隔离这条最硬的边界（09 §4 fail closed），且涉及临时工可见信息范围、责任归属、证据归属、结算与黑名单等业务决策，登记 10 §2 待确认，确认前不实现。

### 2.5 业主端的口子

业主**不进**任职表、不给角色。预留方式：

- 独立身份表：租户 + **小区（单个）** + 房屋/户 + 账号 + 状态
- **独立登录入口与中间件分流**：业主令牌与员工令牌不互通；业主请求命中员工接口按"身份不属于本端"拒绝，不是"权限不足"
- 范围锚点是房屋/小区，不参与任何审批节点

硬塞进任职表的后果是具体的：节点候选人解析会把业主算进去。开放期次与个人信息口径登记 10 §2。

## 3. 管理流程（目标）

### 3.1 一个页面办完

现状入口只有"小区 → 人员"，一人多小区要跑多个小区页。**增加反向入口：人员档案页**，一页管该人全部任职；App 对应 `65 岗位设置与人员分配`，与 PC 人员档案共用授权规则。

| 场景 | 管理员操作 | 系统行为 |
|---|---|---|
| 入职 | 加人 → 选角色 → 勾小区 → 保存 | 角色写入 `sys_user`；每个勾选小区写一条任职行；自动成为相应节点的候选人 |
| 换岗 | 在人员档案中修改该账号的角色 | 旧权限撤销、新的生效；审批候选自动跟换，不能误改任职行 |
| 增减小区 | 改该人员的小区勾选 | 范围即时变更；每个小区仍是一行任职 |
| 临时增派 | 该人员加勾小区 + 设到期日 | 到期自动失效 |
| 离职 | 停用账号或任职行 | 权限随之失效；**停用前提示他是否为某节点唯一候选人**，要求指定接替 |
| 休假 | 任职行设代理人 + 期限 | 代理有范围与到期，不靠借账号（09 §3.3 第 3 条） |
| 批量调岗 | 人员列表勾选批量改角色 | 13 §7 |

### 3.2 配置页必须当场回答"配完会怎样"

现状繁琐感的根源不是菜单层级，是**配置页不回答结果**：配完要去别处验证，而断链看不见。人员与小区配置页必须满足以下要求：

- 项目人员页**实时显示**本项目每个审批节点的当前候选人数，断链标红并可就地修复
- 顶部「开通完整度」：点位 / 人员 / 流程 / 模板 / 签署，缺哪项点进哪项
- 保存角色或审批链时，提示受影响的人数与节点（§2.3）
- 合并后"审了也看不到数据"不再可能发生（§1.5.3 候选即可读），`middleware/datascope.go:118` 现有的标红提示随之失去用途

## 4. 现状与差距（实测，含代码证据）

以下 file:line 均已逐条核对。

### 4.1 三层中转与双写（随合并消失，不是修复）

**（a）岗位→角色的运行时并集。** `middleware/roleunion.go:16` `EffectiveRoleIDs`：有效角色 = `sys_user.role_ids` ∪ 在职任职岗位绑定的角色（`post_dict.role_id`）。文件头注释：

> 《管理后台信息架构与菜单归位方案》第三章，最终决策……**实时计算、不落库：配岗即得权限、离岗即失权限**

问题有三：不落地因而管理员在编制页勾岗位时看不见"这同时授予了哪些能力"；实时算出的集合无法在个别人身上追加（§2.2 要求"能加"）；**casbin 接口鉴权走 `authz.SyncAll` 用同一套并集逻辑另行展开写入**，两份实现一旦漂移，HTTP 与 casbin 鉴权结论不一致。

**（b）槽位与审批链双写。** `approval_flow`（`models.go:354`，带 `ProjectID`）与 `duty_binding`（带 `ProjectID`）用相同的"租户默认 + 项目覆盖"机制回答同一问题。

**（c）槽位回落查另一个槽位。** `patrol_execute` 的真实用途不是任务派发，而是给报告链的"巡检员确认"节点当名册兜底：

```go
// report_service.go:136-141（:957-961 同）
if slot == sysmodel.SlotReportInspector {
    defaults = SlotUserIDs(db, communityID, sysmodel.SlotPatrolExecute)
}
```

`flow_preview.go:34-37` 的 `fallbackInspector` 同理。

**合并后全部消失**：角色即岗位、全局唯一挂在 `sys_user`；任职行只管小区范围与小区级属性，审批链节点直接绑角色。删除 `post_dict.role_id`、`roleunion.go` 并集、casbin 第二份展开、`duty_binding` 整表、`Slot` 枚举、`fallbackInspector` 特例。**这些是删除，不是改写。**

### 4.2 审核类动作三道闸，一线角色被同时挡住

一个巡检员被放进审核候选时，**三层独立阻挡**：

| 层 | 代码 | 后果 |
|---|---|---|
| 权限点 | `seed.go:370` 未给 field_staff 审核权限点（同文件 `:368` 写明"审核权限由动态审核链和候选人名单控制"） | 接口拒绝 |
| 数据范围 | `middleware/datascope.go:28` `ManagedProjectIDs`：只有一线岗位 = self 档 → `:110` `ApplyCommunityFilter` 返回 `1 = 0` | **读不到那条记录** |
| 前端显隐 | App/PC 只按权限点显隐入口 | 连入口都看不见 |

`datascope.go:118` 的注释写明原设计意图是「能审必能看」，但现状只做到"把审了也看不到的名单成员标红"，没有真正放行。

**目标**：按 §1.5.3，**节点候选人身份是唯一判定**——不设审批类权限点、候选即赋予该条记录的读权限、菜单可见性由"角色是否被任一节点绑定"推导。前端显隐同步改，不能只看权限点。

### 4.3 "名单即授权"自己带例外

`community/service/staff_service.go:106` `SlotAuthorized`：超管（`:110`）与持 `tenant_admin` 角色者（`:113-117`）**直接放行，绕过名单**；而同文件 `:52` `SlotUserIDs` 的注释写着"名单即授权"。

**一个叫"名单即授权"的函数内部藏着绕过名单的例外**，读注释的人不会知道。

**目标**：去掉短路放行。超管与租户管理员若需代办，走**显式授权 + 审计**（与 09 §4.1"超管也须指定目标范围"同口径），不默认具备全部节点资格。

### 4.4 范围双来源

`middleware/datascope.go:13` 注释即承认："可见项目集合由 `project_staff` 岗位编制推导，**角色 data_scope 作上限**"。于是改一个人的可见范围，可能要改角色、也可能要改任职，**页面上看不出改哪个才生效**。

**目标**：范围只认任职覆盖的小区；`data_scope` 的范围语义移除。"全项目 / 仅本人"的可见深度由**角色主管标志**承载（它本就在干这件事）；租户级全量属 `scope_level=tenant` 的角色（§1.4）；单条记录的读权限由节点候选人身份赋予（§1.5.3）。

### 4.5 主管判定硬编码（随合并简化）

`middleware/datascope.go:55`：`post == model.PostProjectManager || supervisorPosts[post]`——硬编码岗位 code 与字典 `is_supervisor` 标志并存，而 seed 里 `project_manager` 的 `is_supervisor` 为 `false`（`seed.go:555`），**靠硬编码兜底**。违反 AGENTS.md §4.6「不按名称前缀判业务」。

**合并后**：主管标志是角色自带属性，直接读，硬编码与字典查表一并删除；修正 seed 数据（项目经理应为主管级）。

### 4.6 空名单自动跳过（最高危，与模型无关，必须单独改）

`community/service/flow_service.go:139` `WalkFlowSkipEmpty`，注释：

> 空名单自动跳过版走链（**三链统一口径，替代裸 WalkFlow**）：落定的人工环节名单为空（voters 返回空）时自动跳过该环节继续走

跳过后由 `:170` `NotifySkippedFlowSteps` 事后通知管理员。**这与 03 §5「空流程/空审核名单不能自动通过」直接冲突**，且是三链（打卡 / 维保 / 报告签字）的统一口径，不是个别分支。

实际后果有两层：

1. **直接后果**：新项目配了审批链但忘了配人 → 所有记录**自动通过、无人审核**，界面一切正常。
2. **与 AI 故障叠加（更隐蔽）**：`mp/service/checkin_ai_gate.go:94-100` 在 AI 超时/失败时把记录路由到 `AIGateReview`（转人工），这一步是对的——`FlowStep.OnReview` 的可选值也只有 `next/reject/goto:N`、**不含 `finish`**，闸门本身不会直接放行。但接下来若该人工环节名单为空，`WalkFlowSkipEmpty` 会跳过它，走到链尾即 `walk.Finish` → `AuditAutoPass`。**于是「AI 失败 + 空名单」= 静默自动通过**：单看任一处都正常，合起来就放行了。这使本条的优先级高于"只是没人审"——它同时是 AI 故障兜底路径的终点。

> 另：`seed.go:508` 对 `ai.timeout_seconds` 的注释写"超时/失败**默认通过**"、`:514` 对 `ai.sync_timeout_seconds` 写"超时按失败**放行**"，与上述代码实际行为（转人工）不符，属**陈旧注释**，迁移时一并订正，避免下一个人照注释实现成 fail-open。

#### 4.6.1 两种"空"要分开

| | 空链（没配审批链） | 空名单（链在，节点绑的角色在该小区无人） |
|---|---|---|
| 何时发生 | 只在创建小区时 | **运行期随时** |
| 能否前置拦截 | 能，根治 | 只能减少，不能根治 |

**创建时拦不住空名单**：创建小区的那一刻人还没配（向导第 4 步才配人，13 §6.1），此时只能校验"链存在"。且名单会在运行期变空，至少五种来源：

1. 持该角色的人离职 / 停用
2. 调岗（换了角色）
3. **临时任职到期**（`effective_to` 过期自动失效，§2.4 引入）
4. 角色定义被改或角色被停用
5. 审批链事后被编辑，换绑了一个本小区没人的角色

#### 4.6.2 三道防线

| 防线 | 挡什么 | 落点 |
|---|---|---|
| **① 创建小区必带默认审批链** | 空链 | 从租户默认带出，**不允许无链的小区存在**（13 §6.1 向导第一步即写入） |
| **② 启用前完整度检查** | 启用时刻的空名单 | 「开通完整度」的"流程"项 = **每个审批节点至少 1 个候选人**；未启用的小区不生成巡检任务，因而不产生待审记录（13 §6.1） |
| **③ 运行期挂起 + 告警 + 修复入口** | 运行期漂移成空 | **删不掉**，见下 |

**拦「启用」而不是拦「创建」**：拦创建会把向导卡死——必须先有小区才能导点位、配人员。小区创建后处于未启用态，向导各步可暂存，完整度全绿才能启用。

前两道让第三道很少触发，但**不能取代它**：现状是"每个新项目都可能静默自动通过"，加完前两道后变成"只有人员变动才可能断链，且立刻告警"。

**目标（第三道）**：`WalkFlowSkipEmpty` 改为**挂起 + 告警 + 管理端待办**，并**同时提供断链修复入口**（§3.2）。只改挂起而不给修复路径，等于把"自动通过"换成"大面积卡死"，会被要求改回去。

**源头减少漂移**：停用某人或改其角色前，若他是某节点唯一候选人，要求先指定接替（§3.1），不直接放行。

### 4.7 "谁是管理员"两套算法（随合并消失）

登录鉴权用 §4.1(a) 的角色并集；而管理面通知收件人（`flow_service.go:184` `adminUserIDs`）按手动分配的 `role_ids` 查。**仅靠岗位获得 project_admin 的人收不到空名单跳过、设备到期等通知。** 合并后角色只有 `sys_user` 一个来源，分歧自然消失。

## 5. 迁移与门禁

合并是**破坏性改造，不双写、不建兼容层**（06）。**1–3 不可乱序**，4–6 可并行。

| 步 | 动作 | 说明 |
|---|---|---|
| 0 | **完整影响面扫描**：`post_dict` / `duty_binding` / `Slot` 枚举 / `data_scope` 的全部引用（含 frontend、App、接口契约）；**仅靠岗位获得管理权限的账号清单** | §4 的删除清单基于抽样 grep，不等于完整影响面；此数决定切换是否需要停写窗口 |
| 1 | **`post_dict` + 四档角色 → 内置角色表（§1.3.1）**：`project_admin`/`field_staff` 两个桶拆成具体工种角色，`project_admin`/`field_staff` 两个 code 删除 | 保守口径：拆出的各角色**先继承原桶的完整权限点**（行为等价、无人失权），再由甲方逐项裁剪。**此中间态可用于切换，但不是最终形态**（品质主管暂时拥有项目经理全部权限、维保工暂时拥有巡检员全部权限），不得当成验收结果发布。差异登记 10 §2 |
| 2 | **`project_staff.posts` 删除**（角色改挂 `sys_user`，§1.2）；`sys_user.role_ids` 退化为单个角色；`FlowStep.Slot` → 角色 code；**候选人解析改为按业务对象范围**（现只按单个 communityID，§1.5.2）；**删 `duty_binding`、`Slot` 枚举、`fallbackInspector` 特例** | 任职行只剩范围与小区级属性（`building_ids`/生效期/代理）。跨小区报告的多地签字依赖解析改动 |
| 3 | **删除** `post_dict.role_id`、`roleunion.go` 并集、casbin 第二份展开 | 此时角色只有 `sys_user` 一个来源、范围只有任职行一个来源，切换无感；**无需停写窗口** |
| 4 | 节点候选人成为审批的唯一判定；候选即赋予该记录读权限；**同步**改 App/PC 显隐为"角色是否被任一节点绑定" | 前端仍按权限点显隐的话，有资格的人看不到入口 |
| 5 | 取消审批类权限点；去掉 `SlotAuthorized` 短路放行 | **必须在 4 之后**——先取消权限点而候选判定尚未接管，那一刻是真实越权窗口 |
| 6 | 范围只认任职；`data_scope` 去范围语义；主管标志归角色、删硬编码、修 seed；管理员判定统一；**空名单改挂起 + 告警 + 修复入口**；节点改职责名 | 独立于 4–5 |

**发布门禁**（与 09 §4.4 负例验收合并执行）：

1. 第 1~2 步完成后，**逐账号对拍**：新模型算出的权限点集合与 `EffectiveRoleIDs` 实时计算结果一致，方可进入第 3 步
2. 租户越权负例：同权限不同租户/不同小区读取、修改、批量、文件、签章被拒
3. 自然人去重负例：A 账号提交、B 账号（同自然人）不得出现在候选名单
4. 空名单负例：未绑角色的节点**不得产生 approved**，须挂起并生成告警与待办；**无审批链的小区不得创建**，完整度未过的小区**不得启用、不生成巡检任务**（§4.6.2 三道防线）
