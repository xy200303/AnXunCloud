# 专项巡检与专项检查报告设计方案

> 版本：v3（2026-08-20，报告通用化：月度报告按巡查类型生成，不分两套报告）｜状态：待评审
> 关联文档：《汇报线与审批链扩展设计方案》《数据库设计文档》《物业巡检管理系统方案》

## 1. 业务模型

安全检查分两大类：

### 1.1 日常巡逻（保安巡更）

保安员按**固定路线**巡逻，频次来自物业合同（如「白天巡逻不少于 3 次」）。系统需要：

- 路线 = 一串**有序点位**（门岗 → 各楼栋 → 车库 → 周界 → ……）；
- 频次 = 每天若干**轮次**（如 08:00-20:00 每 3 小时一轮，白天 4 轮；夜间另配）；
- 考核 = **巡更达成率**：应巡 N 轮 / 实巡几轮 / 每轮是否走完全部点位 / 是否超时——这是合同履约证据，也是物业被甲方考核的口径。

### 1.2 专项检查

以消防设施月度专项检查为典型：保安员每月对小区公共区域**所有消防箱/灭火器**逐一检查。每个楼层都有消防箱，老办法是带笔在箱上打 √/×，内容如：

- 消防枪头在不在；
- 手动报警按钮（手报）是否正常；
- 水带有没有、是否完好；
- 灭火器是否在有效期内。

新做法：逐项**拍照**，由 **AI 图像识别辅助判定**器材是否完好/在位，检查完成后生成**整个小区的消防器材专项检查报告**（签字 + PDF 归档，作为消防迎检/维保凭证）。

### 1.3 两大类差异对系统的要求

| 维度 | 日常巡逻（巡更） | 专项检查 |
|---|---|---|
| 周期 | 每天多轮次（间隔/班次） | 每月一次（或季度） |
| 点位 | 位置型（门岗、楼栋、车库…） | 器材型（消防箱、灭火器…） |
| 检查深度 | 到点打卡为主，异常上报 | 逐项检查 + 必拍照片 + AI 识别 |
| 产出 | 巡更达成率（履约考核） | 专项检查报告（签字归档） |
| 汇报线 | 保安队长/安全主管 | 专业主管（消防→工程主管） |

## 2. 现状盘点（代码事实）

| 机制 | 现状 | 差距 |
|---|---|---|
| 巡查类型 `patrol_type` | 硬编码 4 值（safety/equipment/environment/building）+ 字典 | 无「日常巡逻/专项检查」大类分组；加消防等类型要改代码 |
| 周期 `cycle_type` | daily(隔N天)/weekly(星期)/monthly(日期)，**每天每人一个任务、单一 time_window** | 表达不了「每天多轮次」；任务无轮次概念，无法考核单轮超时/漏巡 |
| 点位 | 位置粒度，有序进任务（App 已按序号展示路线） | 消防器材点位需批量建；计划选点是显式名单，器材点位多了手选不现实 |
| 检查项模板 | 逐项：标准要求、必填、照片要求(none/optional/required) | 无 AI 识别要点字段 |
| AI 审核 | `pkg/ai.ReviewCheckin` 多模态审核打卡照片；**检查项级结论字段已预留**（`checkin_record_item.ai_verdict/ai_reason`），按项照片送模型的消息构造已有 | 模板项没有「识别要点」输入；结论未落到逐项 UI；无消防器材专项提示词 |
| 汇报线槽位 | 维度槽位 `patrol_report_line.<type>`（switch 硬编码），设备专项默认绑工程主管 | 新增类型要改代码 |
| 报告 | 月度综合报告（小区+月份，三级签字 + PDF） | 无专项维度报告；无巡更达成率口径 |

## 3. 方案设计

### 3.1 巡查类型字典化 + 大类分组

- `patrol_type` 改**字典驱动**：`ValidPatrolType` 查字典启用项即合法；存量 4 值落成字典种子。
- 字典表 `sys_dict_data` 加通用扩展列 `attrs`（jsonb），`patrol_type` 每项用 `attrs.category` 标记大类：`daily_patrol`（日常巡逻）/ `special`（专项检查）。归组建议：safety→日常巡逻；equipment/environment/building→专项检查；新增 `fire`（消防设施专项）→专项检查。
- 前端所有选类型的入口（计划表单、任务/记录筛选、统计）按大类分组显示：「日常巡逻」「专项检查」。
- 维度槽位约定化：每个类型自动衍生 `patrol_report_line.<type>` 槽位（去掉硬编码 switch）；`fire` 平台默认绑 `engineering_supervisor`（工程主管）。
- **以后加专项（电梯、防汛、消杀…）= 字典加一项 + 绑一个默认岗位，零代码。**

### 3.2 日常巡逻：轮次化巡更

**计划周期扩展**（`cycle_config` 内扩展，不加新 cycle_type）：

```jsonc
// cycle_type = "daily" 时支持：
{
  "interval": 1,                 // 现有：隔几天
  "rounds": [                    // 新增：每天轮次（巡更类必填）
    { "name": "早班-1", "window": "08:00-10:00" },
    { "name": "早班-2", "window": "11:00-13:00" },
    { "name": "午班",   "window": "14:00-16:00" },
    { "name": "晚班",   "window": "17:00-19:00" }
  ]
}
```

轮次是完全自由配置的列表：轮次数、名称、时间窗都任意——两班倒（07:00-19:00 / 19:00-07:00）、三班倒（8 小时一轮）、每 3 小时一轮都只是同一结构的不同填法，表单提供模板一键填充。**`window` 可留空 = 自由时段轮次**：只考核「每天巡够 N 轮」（配合 `daily_min_rounds` 达标线），不限定每轮几点到几点；自由时段轮次逾期判定回落任务日终，App 归到「全天」组并显示「不限时段」。注意：自由时段只考核次数、不考核间隔；合同要求「每 3 小时一次」这类间隔约束时必须配固定窗口。

- 前端提供便捷生成：填「开始/结束时刻 + 每隔 N 小时 + 每轮时长」自动展开成 rounds，可再手工微调；内置常用班次模板（两班倒：白班 07:00-19:00、夜班 19:00-07:00；三班倒 8 小时制）。
- **跨零点轮次**：window 允许跨零点（如 19:00-07:00）；任务日期归属**开始时刻所在日**（夜班 19:00 开始 → 任务日期为当天，执行到次日 07:00）；逾期翻转/动态逾期判定一律以「快照窗口的结束时刻已过」为准（结束时刻早于开始时刻时归次日）——**夜班任务不得在次日 00:10 的例行翻转中被误判逾期**。
- **任务生成**：每轮 × 每人 生成一个任务；`inspection_task` 加 `round_name`（轮次名快照）与 `time_window`（本论时间窗快照）两列——超时判定、漏巡统计都以轮次任务为最小单元，现有「任务超时翻转」逻辑直接适用。
- **巡更达成率**：统计模块加巡更口径——按 小区/计划/日期段 输出：应巡轮次、实巡轮次、达成率、单轮点位完成率、超时轮次清单；支持按合同频次（如「白天≥3 轮」）设达标线，不达标标红。这份统计就是给甲方/公司考核的履约表。
- App：巡更任务按轮次列出（「早班-1 08:00-10:00」），点位顺序即巡逻路线，逐点扫码/NFC 打卡，现有流程不变。

**时间场景判定规则表**（实现与测试的统一依据；`RoundWindowEnd(task_date, window)` = 窗口结束绝对时刻，结束 ≤ 开始则归次日；一律服务器本地时区）：

| # | 场景 | 示例 | 判定规则 |
|---|---|---|---|
| 1 | 普通轮次，窗口内 | 08:00-10:00，现在 09:00 | 正常可执行（pending/doing） |
| 2 | 普通轮次，窗口已过未完成 | 08:00-10:00，现在 10:01 | 实质逾期：翻转 overdue / 统计动态判逾期 |
| 3 | 跨零点轮次，窗口内 | 19:00-07:00（D 日任务），现在 D+1 日 02:00 | 正常执行中；**00:10 例行翻转不得误伤** |
| 4 | 跨零点轮次，窗口已过 | 19:00-07:00（D 日任务），现在 D+1 日 07:01 | 实质逾期 |
| 5 | 未来任务（提前 N 天生成） | 明天的轮次 | 一律 pending，不参与任何逾期判定 |
| 6 | 非轮次任务（无 rounds） | 计划级 time_window 或为空 | 有窗口按窗口结束判定；无窗口回落「task_date 日终（次日 00:00）」——与存量行为一致 |
| 7 | 计划顶层 time_window 跨零点 | 19:00-07:00 | 与轮次同规则（结束归次日） |
| 8 | 窗口起止相等 | 07:00-07:00 | 非法，保存校验拒绝（全天就配 00:00-23:59） |
| 9 | 统计日期段含今天 | 今天的白班未结束 | 窗口未过不计逾期、不计未巡；计入「待开始/进行中」 |
| 10 | 夜班任务的按天归属 | 19:00-07:00 | 计入任务日期（开始日）那天；daily_min_rounds 达标按任务日期天判定 |
| 11 | 翻转任务可配时刻 | overdue_check_time 00:10 | 翻转条件从「昨日未完成」改为「窗口结束时刻 < now 且未完成」，对全部任务类型统一适用 |
| 12 | 时区 | 容器/服务器 | 全部本地时区；部署 TZ=Asia/Shanghai（compose 已带，回归确认） |
| 13 | 自由时段轮次（window 留空） | 「第 1 轮」无窗口 | 只考核次数不考核时段；逾期回落任务日终（次日 00:00）；App 归「全天」组显示「不限时段」 |

逾期翻转统一实现为一个纯函数：`ShouldOverdue(task, now) bool`——有快照 time_window 按规则表算窗口结束；无则 `task_date+1天 <= now`；scheduler 每日翻转与统计动态判定共用，杜绝两套口径。

### 3.3 专项检查：消防器材点位 + 逐项标准 + AI 识别

**点位建模**（沿用 v1 结论：位置点位承载器材检查，不建设备台账）：

- `point_type` 字典新增：`fire_cabinet`（消防箱）、`fire_extinguisher`（灭火器）等；
- 粒度：一处器材一个码——「1栋1层电梯厅消防箱」「2栋3层灭火器点」，每层楼每个消防箱一个点位（与现状"每个楼层都有消防箱"一一对应）；
- **批量建点助手**：按 楼栋×楼层×每层数量 批量生成点位并套用模板，二维码批量打印沿用现有版式（编号+点位信息）；
- **计划按类型圈选**：`inspection_plan` 加 `selection_mode`（explicit 默认 / by_point_types）+ `point_types`，任务生成时动态展开命中点位——新装消防箱建好码自动进下期专项任务。

**消防箱检查模板**（示例，按点位类型绑定）：

| 检查项 | 标准要求 | 照片 | AI 识别要点 |
|---|---|---|---|
| 消防枪头在位 | 枪头齐全无缺失 | 必拍箱内全景 | 画面中应可见消防枪头 |
| 水带齐全完好 | 水带在位、无霉烂破损 | 必拍 | 画面中应可见卷盘/水带 |
| 手报按钮正常 | 外观完好、玻璃无破碎 | 必拍 | 手报外观无破损 |
| 灭火器压力正常 | 指针在绿区 | 必拍压力表特写 | 指针位于绿色区域 |
| 灭火器在有效期内 | 铭牌日期未过期 | 必拍铭牌 | 读取铭牌日期并判断是否过期 |
| 箱体与通道 | 箱门完好、前方无遮挡 | 选拍 | —— |

**AI 识别链路**（复用现有，不新建管线）：

- `check_template_item` 加 `ai_hint`（识别要点文本，可空；空=该项不送 AI）；
- 打卡上传后，`ReviewCheckin` 把「项名 + 标准要求 + ai_hint + 该项照片」送多模态大模型，逐项结论落 `checkin_record_item.ai_verdict/ai_reason`（字段已预留）；
- **定位：辅助初判 + 人工兜底**。AI 判「存疑/不通过」的项自动标黄进主管审核队列（审核页按项展示 AI 结论与照片对照），最终以人工审核为准；AI 结论不作为自动判异常的唯一依据。灭火器有效期这类需要读文字的项，AI 读出日期后由检查人确认；
- AI 未配置/不可用时流程完全不受影响（现有降级逻辑）。

### 3.4 报告：月度报告按「巡查类型」通用生成（不分两套报告）

不引入独立的「专项报告」概念，而是把**报告生成器通用化**：生成月度报告时可选择一个巡查类型——

- **不选（全部类型）** = 现有综合月报，行为完全不变；
- **选定类型（如消防设施专项）** = 该专项的月度检查报告。

`inspection_report` 扩展（无 `kind` 列，`patrol_type` 空即综合月报）：

| 新列 | 说明 |
|---|---|
| `patrol_type` | 可空；空=综合月报，非空=按该巡查类型生成（如 `fire`） |
| `plan_id` | 可空，溯源生成它的计划（综合月报为空） |

- **唯一性**：按 (community_id, period, patrol_type) 唯一——同一项目同一月，综合月报一份、每个专项类型各一份，互不冲突；存量数据 `patrol_type` 为空，天然兼容；
- **专项口径**（patrol_type 非空时）：只统计该类型期间内的任务完成、点位覆盖（应检/实检/漏检清单）、逐项不合格分布（哪些楼栋哪些消防箱缺枪头/水带/过期——这张表就是整改清单）、异常工单闭环状态；附 AI 初判与人工复核的一致率（运营参考）。取数层 `report_pdf_data.go` 只加一个 patrol_type 过滤条件，综合口径代码路径不变；
- **专项类型与点位的对应**：专项类型 = 把同类点位圈成一组去查的标签——计划按点位类型圈选（§3.3）把这些点位的任务打上同一个 `patrol_type`，报告再按它收拢取数。「圈点 → 干活 → 出报告」靠这一个标签串起来；
- **生成**：通用入口「生成月度报告」对话框加类型下拉（默认全部）；专项类型建议等该类型期间内任务全部完成后生成（前端给出完成度提示，不强制卡死）；
- **签字链**：综合月报与专项报告共用现有三级签字机制，名单槽位按类型取（专项报告主管级 = `patrol_report_line.<type>` 槽位，如消防→工程主管；综合月报维持现状）；PDF、公章、驳回交互完全复用；
- **标题**：类型为空「{项目}月度巡检报告（{期间}）」（现状），非空「{项目}{类型名}专项检查报告（{期间}）」；
- **前端**：报告列表加「类型」列与筛选（全部/综合/各专项类型），不分新页面。

**签字名单怎么定（关键，复用现有快照机制，零新发明）**：

现有月报生成时（`report_service.go:486-490`）：主管级/经理级名单由 `resolveSigners` 按槽位推导——**槽位绑定岗位 → 该项目编制内在职成员**（项目→租户→平台三级回落），生成请求可显式传名单手工调整，最终名单**快照**进报告（`supervisor_ids`/`manager_ids`）；某级为空自动跳过，三级全空直接归档签字栏留空；快照制保证后续人事变动不影响已生成报告。

专项报告唯一变化：**主管级槽位从固定的「月报主管级签字」换成该类型的汇报线槽位**。以消防专项为例：

```
patrol_type = fire
  → 槽位 patrol_report_line.fire
  → 绑定岗位：工程主管（平台默认；项目可在「岗位编制 → 环节分工」覆盖）
  → 该项目编制内在职的工程主管（如周建国）
  → 即主管级签字人，报告进入其待办
```

即：谁签字由「岗位编制 + 环节分工」的事先配置决定，生成报告时预填可微调；经理级继续走现有「月报经理级终审」槽位。项目想把消防专项改由安全主管签，只需在环节分工里改绑该槽位，报告逻辑不动。

### 3.5 汇报与归属（复用槽位，零新流程）

- 巡更类：汇报线走 `patrol_report_line.safety`（默认安全主管/保安队长）；
- 消防专项：走 `patrol_report_line.fire`（默认工程主管）；需要「工程主管→项目经理」两级时，在项目「打卡审批流程」加环节即可；
- 消防箱异常（缺枪头、灭火器过期）→ 异常工单 → 派单槽位默认工程主管 → 维修工处理 → 验收闭环，现有机制零改动；
- 超时/漏巡/异常通知全部走对应维度槽位，现有通知逻辑自动生效。

### 3.6 App 端

- 巡更：任务列表按轮次分组显示；打卡流程不变；
- 专项：逐项检查 + 必拍照片 + AI 结论回显（「AI 初判：未见枪头，请复核」样式提示）；提交后异常项自动转工单；
- 均无需新页面骨架，类型标签字典化后自动出现。

## 5. 实施拆解（建议顺序）

1. **类型字典化**（后端）：patrol_type 校验/槽位目录改字典驱动，迁移补种子与默认绑定；

6. **报告按类型生成**：report 增列、生成入口加类型选择、专项口径取数、签字与 PDF、前端类型列与筛选；

## 6. 明确不做（边界）

- 不做设备/器材全生命周期台账（采购/维保/报废/到期预警），需要时单独立项，点位模型不挡路；
- AI 识别定位辅助初判，不做无人值守全自动判定（误判风险，责任链要求人工兜底）；
- 不做 GPS 实时轨迹记录（当前为点位打卡制巡更；连续轨迹对手机耗电与隐私代价大，且点位打卡已满足「到没到点」的合同举证）；
- 综合月报与各专项报告各自独立签字归档（同一报告生成器按类型产出，互不混入）；不发明自动派单。
