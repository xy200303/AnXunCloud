# AI云管家 PC 后台静态 UI 原型评审索引

> 本目录是 **PC 后台（管理端）静态评审图，不是已实现功能或业务验收证明**。数据、身份与状态均为演示；按钮主要用于表达规则。
> 业务规则以方案 03/04/05/07/08 为准，后台摆放与配置架构以 [13 后台管理系统设计](../13-后台管理系统设计.md) 为准，授权语义以 [14 权限与岗位模型](../14-权限与岗位模型.md) 为准。
> **App（移动端）原型在 [`../原型图/`](../原型图/README.md)**，本目录不收录手机页面。

## 统一口径

- 沿用现有 Vue 3 + Element Plus 工程（`frontend/`）：深色侧栏 220px + 白色顶栏 + tags-view 标签条 + 灰底内容区。**不另起独立前端工程**，不重画成第二套产品架构（02 §7）。
- 侧栏菜单按 13 §3 目标菜单：运营看板 / 小区管理 / 巡检管理 / 工单管理 / 承接查验 / 模板中心 / 报告中心 / 智能助手 / 系统管理 / 平台管理（超管专属）。**一级菜单图标互不重复**（02 §7）。
- **审批流程沿用现有设计器**（`frontend/src/components/ReviewFlowEditor.vue`，796 行）：钉钉/飞书式**约束结构布局**——纯 DOM 垂直链、连线「⊕」插入环节、AI 环节三分支泳道、goto 只能向后跳到人工环节、环节增删后序号自动重映射。**不换成自由画布（VueFlow）**：约束结构已是直观与可校验的平衡点，自由图会引入不可达环节/环/死胡同，而"异常·存疑·改判·AI失败·无法检查必须经人工环节"这类硬不变量在任意图上难以静态保证。真出现按金额/风险分流的条件分支需求时再评估（原型 82）。
- **AI 失败不阻塞提交**（03 §3）：只有 `pending/running`（识别中）禁提交，防的是不等结果就交；`error` 是终态、**可以提交**——巡检员重试重拍，或填人工结论 + 故障说明后提交并强制走人工审核，但不得以"默认正常"代填。两者都是固定规则，不是 Provider 级可配项。
- **AI 配置在平台管理与系统管理下各一份，供应商注册一次、处处引用**（13 §4.3）：按 §4.2.2「一能力一组件两个壳」，同一组件、同一批表，用 `scope` 区分层级。**模型供应商** Tab 注册协议/地址/`credential_ref`/模型（L2），**能力绑定** Tab 里任务类型只选一个已注册模型（L1），助手 Agent／Skills／agent 预审节点同样引用——**不各自重配协议与密钥**。模型的**能力标记**（视觉/文本/工具调用）是硬约束：绑定下拉只列能力匹配的模型。
- **AI 的三件事分三处配，不混在一页**（08 §3.2.3，原 `judge_type` 一列承载三个正交维度已拆开）：① **连哪个模型**在 AI 配置 → 能力绑定（79c）；② **逐项判定维度** `ai_prompt_kind` 在检查项模板 L1（41）——11 种通用维度（general/presence/damage/metric/state/label/passage/leak/indicator/tidiness/baseline）**跨设备类型通用**，供水供电消防特种设备都用同一套，不存在"消防专用 prompt"；③ **本项是否调 AI** `ai_enabled` 同在 L1。业务规则（重拍放行、失败出口、强制人工审核情形）在巡检管理 → 巡检规则（90）。
- **签字栏位数属版式、不按环节数伸缩**（08 §4.2）：位数与位置来自甲方母版骨架，每位绑定一个审批环节，**未绑定在保存输出模板时阻断**；环节无候选人走挂起告警而非渲染空栏；确需按批次才定的签字方显式标记"可留空"。栏数动态变动会改表格结构与分页，使黄金样本基线失效。
- **角色即岗位，系统管理下只有「岗位」一个菜单**（14 §1.4）：原「角色管理」与「岗位管理」合并，不留两套名词。岗位带作用域（platform/tenant/project），项目级岗位的范围由人员任职决定。
- **App 能办的管理动作，PC 必须有等价入口；反向不成立。** 参数多、步骤多、改错不可逆的（流程编排、模板版式、批量导入、能力与密钥配置）只在 PC；看与判断类（审核、签字、调岗、内容审核）App 优先、PC 保留。职责划分表见 13 §2。
- **建改一律弹窗或抽屉**，列表页只读 + 行内操作，不跳页创建。抽屉遮罩要淡（抽屉式编辑的价值就是保留上下文）。只有多列表格 + 批量错误预览这类复杂编辑器才用整页。
- **配置页必须当场回答「配完了会怎样」**（14 §3.2）：小区设置抽屉右侧实时显示每个审批环节的当前候选人数、断链标红并可就地修复；顶部「开通完整度」缺哪项点进哪项。这是消除"配完去别处验证"的关键，不是装饰。
- **分层配置统一用显式 `scope` 两列**（13 §4.2.1）：同一能力各层级**同表**，`scope`（platform/tenant/project）+ `scope_id` 均 NOT NULL，**不用 NULL 表达"平台默认"**（Postgres 中 NULL≠NULL 会让唯一约束失效，现有三处索引靠 `COALESCE` 打补丁）。选两列而非单列去空，是为了**将来精确到小区**时不改索引形状。**键值型与结构型统一为同一形态**（`tenant_config` 并入 `sys_config`）；键级属性（name/分组/备注/能否被下级覆盖/是否密钥）用 CHECK 锁在 platform 行。配套：稀疏覆盖（与继承值相同不落行）、读时解析 project→tenant→platform、**UI 必须显示有效值与来源**（继承自上级 / 本级已覆盖 / 恢复默认）、不用 JSONB `||` 合并、密钥只存引用。
- **一能力一组件一张表两个壳**（13 §4.2.2）：`ReviewFlowEditor`（796 行）与 `PostManager` 已是样板——平台壳与租户壳各 30~56 行，差异只有传哪个 `api`、要哪个 `save-perm`。**禁止为平台侧和租户侧各写一套 UI 或各建一张表**；组件统一接 `api`/`save-perm`/`scope` 三个 prop。**同一能力在各层用同一菜单名**（原"岗位模板库/岗位管理"、"审批流程模板/审批流程"须统一），不再往 `模板` 上堆词。
- **能力配置分三层**（13 §4.2）：L0 能力目录由**代码注册、后台只读**（不能在后台凭空新增一条工具/任务类型，否则会出现"配置里有、代码里没有"的幽灵能力）；L1 启用与策略可编辑（平台默认 + 租户覆盖）；L2 密钥与凭证只显掩码、不回显明文。
- **危险操作**：有业务数据的对象删除改为"停用"并提示影响；停用/删除需二次确认与原因。停用账号前检查是否为某审批环节唯一候选人。
- **三类空态分开**（13 §9.2）：无数据 / 无权限 / 配置缺陷，文案与下一步都不同，不显示假零、不静默失败。
- **列表加载用骨架行**，筛选区立即可用；分页/筛选切换只局部遮罩表格，不整页重载、不丢滚动位置。长任务（报告生成、批量导入、二维码生成）走 River 持久状态，刷新不丢，进度按"已处理/成功/失败/跳过"四个数分列。
- **审批、签字、归档、确认类操作不做乐观更新**：等服务端确认再改 UI，按状态+revision 条件更新防重复审核。
- 看板**按小区分行、不取平均**（13 §8）：各小区收费率等数据各不相同，合计行必须标明范围，垫底项自动排前；只管一个小区的账号不显示对比表。收费/报事指标当前为演示数据——模块尚未建设。

## 画后台原型前必须先读现有实现（硬规则）

**后台不是从零设计，现有 PC 后台已经成型且设计得不错。** 原型的作用是在现有实现基础上标注"哪里要改、为什么改"，不是另画一套——凭想象另画会比现版更差，还会误导开发者按原型重做。

动笔前按页对照：

| 原型 | 必读的真实实现 |
|---|---|
| 小区列表 / 小区设置抽屉 | `frontend/src/views/community/` |
| 用户 / 岗位 / 审批流程 | `frontend/src/views/system/users|roles|posts|review-flow/` |
| **审批链配置** | `frontend/src/components/ReviewFlowEditor.vue`（796 行设计器，复用它，不要另画表格） |
| 运营看板 | `frontend/src/views/dashboard/` + `frontend/src/views/stats/` |
| AI 与平台配置 | `frontend/src/views/platform/configs/`（含 `AiConfigPanel.vue`） |
| 巡检执行侧各页 | `frontend/src/views/inspection/` |

- **权限配置是侧滑抽屉 + `el-tree` 权限树**（目录/菜单/按钮三级、父子联动半选、按钮为叶子），不是扁平 chip 分组。
- **审批链是「约束结构布局」设计器**（垂直链 + 连线「⊕」插入 + AI 环节三分支泳道 + goto 向后跳 + 序号自动重映射），不是一张节点表格。
- **一张原型 = 一个屏幕状态，禁止纵向堆叠多个页面/Tab/弹窗**。列表与详情分开（详情走弹窗或抽屉，02 §7）；不同 Tab 各一张；弹窗要画成浮在遮罩之上的真弹窗，不是页内嵌入块。堆在一起会让开发者以为那就是布局。
- **原型里不放文档说明表**：规则与取舍写进方案文档，原型只画界面。
- **不要删掉现有列与操作**：真实列表已有的筛选、批量、导入导出、空态、`v-perms` 权限控制要保留，新增的才标注。
- 新模型（14）带来的有意改动要**显式标注**（如"数据范围三档 → 只剩全项目/仅本人，范围由任职决定"），与"原型漏画"区分开。
