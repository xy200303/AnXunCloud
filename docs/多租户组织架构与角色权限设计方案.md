# 多租户组织架构与角色权限设计方案

> 版本：v1.0（评审稿）
> 适用范围：安巡云物业巡检平台的组织、角色、权限、业务流程重构
> 前置文档：《物业巡检管理系统方案》《需求规格说明书》《数据库设计文档》

---

## 一、为什么重构

现系统的权限模型是"单租户 + 4 个内置角色（超级管理员/管理员/巡检员/维修员）+ 权限点 + community_ids 数据范围"，与实际物业公司的组织运作方式不匹配，已经暴露的问题：

1. **业务身份靠推导**。月报"安全主管/物业经理"签字人是按"权限点 + 数据范围"反推出来的，出现过巡检员被推导为主管的数据错配。
2. **角色语义僵化**。现实中"谁是安全主管"是项目上的人事安排，同一人可以兼任多岗（巡检员兼维修工、主管兼经理），角色表无法表达。
3. **组织模型缺失**。一个小区就是一个项目服务中心，有完整的岗位编制（项目经理 + 四条业务线主管 + 一线人员），系统里只有扁平的"用户属于小区"。
4. **单租户**。系统要服务多家物业公司，目前所有数据混在一起，无法隔离。
5. **工单流过于简单**。现实中问题来源有两类：计划性巡检（被动执行）和一线人员日常主动发现（楼管员、前台、维修工都可能报单），工单需要"报单→派单→接单→维修→验收"的完整闭环。

## 二、业务组织模型

### 2.1 三层结构

```
平台（安巡云运营方）
 └── 租户 = 物业公司（tenant）
      └── 项目 = 小区 / 项目服务中心（community，现有表演进）
           └── 岗位编制（project_staff）
```

- **平台**：系统的运营方，超级管理员属于平台，可以管理所有租户。
- **租户（物业公司）**：数据隔离的基本单位。每家物业公司是一个租户，租户之间数据完全不可见。
- **项目（小区）**：一个小区对应一个项目服务中心，是业务发生的场所。现有 community 表演进为项目语义，表名不变。

### 2.2 项目服务中心岗位编制

按实际物业项目服务中心的标配编制（**这是系统内置的默认模板，租户可增删改，见 3.2**）：

| 岗位 | 岗位代码 | 职责 | 常见兼任 |
|---|---|---|---|
| 项目经理 | `project_manager` | 项目第一负责人，月报终审，全员管理 | 可兼任某线主管 |
| 安全主管 | `safety_supervisor` | 管理巡检员，安全/秩序巡查，月报主管审批 | — |
| 工程主管 | `engineering_supervisor` | 管理维修工，设备设施专项巡查，工单派单 | 可兼维修工 |
| 环境主管 | `environment_supervisor` | 环境卫生/绿化巡查管理 | — |
| 客服主管 | `service_supervisor` | 管理前台接待和楼管员，报单分诊 | — |
| 巡检员 | `inspector` | 按计划执行巡查打卡 | 可兼维修工 |
| 维修工 | `repairman` | 设备设施专项巡查 + 接工单维修 | 可兼巡检员 |
| 楼管员 | `building_manager` | 负责若干楼栋，日常巡查、主动报单 | — |
| 前台接待 | `receptionist` | 前台接报、录入报单 | — |
| 保洁员 | `cleaner`（预留） | 环境线一线人员 | 本期不进系统，预留 |

编制规则：

- **一人多岗**：同一个人在一个项目里可以有多个岗位（巡检员兼维修工是最常见组合；小项目里项目经理兼安全主管也允许）。
- **一人多项目**：同一个人可以在多个项目任职（例如一个工程主管管两个相邻小区）。
- **岗位是项目上的配置，不是用户属性**。用户管理只管"这个人是谁、账号状态如何"；"他在哪个项目干什么"全部在项目（小区）管理里配置。这与已确认的"小区配置主管/经理"方案一致，只是从两个岗位扩展为完整编制。

### 2.3 权限层级

```
超级管理员（平台）
 └── 物业公司负责人（租户管理员，租户内全部数据）
      └── 项目经理（本项目全部业务线）
           └── 各线主管（本项目 + 本业务线）
                └── 一线人员（仅本人相关数据）
```

## 三、核心设计：角色与岗位分离

这是本次重构最关键的一个决策，把两个被混在一起的概念拆开：

| 概念 | 回答的问题 | 在哪里配置 | 决定什么 |
|---|---|---|---|
| **角色（role）** | 这个人能用系统的哪些功能 | 用户管理 | 功能权限（菜单、按钮、接口） |
| **岗位（project_staff）** | 这个人在哪个项目承担什么职责 | 项目（小区）管理 | 数据范围、审批/签字/派单身份 |

- **角色 = 权限模板**。系统内置少量模板，租户可以自建角色、自由勾选权限点（现有角色管理 + casbin 权限点的机制保留，不动）。
- **岗位 = 业务身份**。月报该谁签、工单该谁派、谁算这个项目的巡检员，全部从 `project_staff` 查，**不再从角色推导**。
- 业务身份授权规则：**名单即授权**。只要某人在报告签字名单 / 项目岗位名单里，对应操作就放行，不再额外要求持有某个权限点（之前已确认：任何人都可以被配置为主管/经理，同一人可兼任多级）。

### 3.1 哪些是角色，哪些是岗位

判定标准：**"用什么端、管多宽"是角色；"干什么业务、担什么责"是岗位**。

- 巡检员、维修工、楼管员、前台接待、项目经理、各线主管——这些回答的是"干什么业务"，**全部是岗位**，只出现在项目岗位编制（project_staff）里，不占角色名额；
- 角色只按"使用端 + 管理幅度"抽象成少数几个权限模板。

内置角色（权限模板）精简为 4 个：

| 角色 | code | 使用端 | 功能范围 |
|---|---|---|---|
| 超级管理员 | `super_admin` | Web | 平台方，全部权限 + 跨租户 |
| 租户管理员 | `tenant_admin` | Web | 物业公司负责人：租户内全部业务功能 + 用户/角色/项目等租户级系统管理 |
| 项目管理员 | `project_admin` | Web | 项目经理、主管、客服等后台使用人员：业务菜单全开，不含租户级系统管理 |
| 一线人员 | `field_staff` | 移动端 | 打卡、任务、问题上报、工单处理、月报签字等移动端功能 |

角色只是初始模板：

- 给某人"项目管理员"角色，他到底是项目经理还是安全主管，由项目岗位编制决定；两人功能权限可以完全一样，业务身份完全不同；
- 一线人员的移动端入口显隐由岗位驱动：没有 `repairman` 岗位的人看不到"接单"入口，没有 `inspector` 岗位的人不会被派巡查任务——功能权限给的是"能力"，岗位决定"用不用得上"；
- 租户可自建角色微调（例如只允许前台用 PC 报单、看不到统计报表），不影响业务流；
- 派单、签字这类业务动作的授权按 5.3 走岗位名单，与角色无关。

### 3.2 岗位可自定义与职责槽位

不同物业公司的管理关系不一样：有的公司工程主管管巡检员，有的公司安全主管管巡检员；有的公司客服主管负责分诊，有的公司前台直接派单。**系统不能把"哪个岗位干什么"写死**，分两层处理：

**岗位本身：租户级字典，可自定义。** 2.2 的 10 个岗位只是开通租户时预置的默认模板，租户可以改名、停用、新增（如"秩序班长""绿化工""电梯专员"）。新增 `post_dict` 表（tenant_id + code + name + status），`project_staff.posts` 引用本租户岗位字典的 code。内置模板岗位的 code 固定保留，用于默认绑定和数据迁移。

**业务职责：系统定义"槽位"，租户决定槽位绑哪个岗位。** 业务流程是系统实现的，所以职责种类（槽位）是系统固定的；但"哪个岗位承担这个职责"是配置：

| 职责槽位 | 默认绑定（内置模板） | 决定什么 |
|---|---|---|
| 巡查任务执行 | `inspector` | 巡检计划默认派给哪个岗位的人 |
| 设备专项巡查执行 | `repairman` | 设备类巡查计划默认执行人 |
| 工单分诊 | `service_supervisor` | 上报工单先进谁的待办 |
| 工单派单 | `engineering_supervisor` | 谁有权把工单指派给维修工 |
| 工单接单 | `repairman` | 工单池对谁可见、可被派给谁 |
| 月报主管级签字 | `safety_supervisor` | 生成月报时主管级默认签字人 |
| 月报经理级终审 | `project_manager` | 生成月报时终审默认签字人 |
| 巡查汇报关系 | `safety_supervisor` 管 `inspector` | 任务派发、漏巡统计的管理口径 |

- 绑定关系**租户级配默认值，项目级可覆盖**（例如 A 小区由工程主管审月报、B 小区由安全主管审）；
- 系统代码只认槽位、不认具体岗位 code：月报生成时查"本项目'月报主管级签字'槽位绑的岗位上有哪些人"，换绑岗位只改配置，代码不动；
- 槽位允许绑多个岗位，也允许绑"无"（该环节按规则跳过或降级，如月报该级无人则跳过）；
- 签字名单等业务授权仍可在单次业务里临时调整（生成月报时手工增删签字人），槽位绑定只决定**默认值**。

这样 A 公司"工程主管管巡检员"和 B 公司"安全主管管巡检员"只是配置差异，系统行为各自正确。

## 四、数据模型变更

### 4.1 新增表

**tenant（租户）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| name | varchar | 物业公司名称 |
| contact_name / contact_phone | varchar | 联系人 |
| status | smallint | 启用/停用（停用则该租户全部账号无法登录） |
| remark | varchar | 备注 |
| created_at / updated_at | timestamptz | |

**project_staff（项目岗位编制）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| tenant_id | uuid | 租户（冗余，加速隔离查询） |
| project_id | uuid | 项目（→ community.id） |
| user_id | uuid | 用户（→ sys_user.id） |
| posts | jsonb | 岗位数组，如 `["inspector","repairman"]`，一人多岗 |
| building_ids | jsonb | 责任楼栋（仅楼管员用，空=全部楼栋） |
| status | smallint | 在职/停用 |
| created_at / updated_at | timestamptz | |

约束：`UNIQUE(project_id, user_id)`；每个项目 `project_manager` 至多一人（保存时校验）。

**post_dict（岗位字典，租户级）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| tenant_id | uuid | 租户；为空 = 平台内置模板岗位 |
| code | varchar | 岗位代码（租户内唯一） |
| name | varchar | 岗位名称 |
| is_supervisor | boolean | 是否主管级（数据范围推导用：主管级 → project 档） |
| status / remark | | |

开通租户时从平台模板复制一份；租户此后可自由增删改。`UNIQUE(tenant_id, code)`。

**duty_binding（职责槽位绑定）**

| 字段 | 类型 | 说明 |
|---|---|---|
| id | uuid | 主键 |
| tenant_id | uuid | 租户 |
| project_id | uuid / null | 为空 = 租户级默认；非空 = 项目级覆盖 |
| slot | varchar | 槽位代码（系统固定枚举，见 3.2：如 `report_sign_supervisor`、`order_dispatch`） |
| post_codes | jsonb | 绑定的岗位 code 数组，空 = 该环节跳过/降级 |

查询规则：项目级覆盖优先，缺省回落租户级默认，再缺省回落平台内置默认绑定。

### 4.2 存量表调整

| 表 | 变更 |
|---|---|
| `sys_user` | 加 `tenant_id`；**去掉 `community_ids` 字段**（数据归属改由 project_staff 表达，避免两处配置互相冲突——这是之前确认过的原则） |
| `sys_role` | 加 `tenant_id`（内置角色 tenant_id 为空，全平台共享；租户自建角色归属租户）；`data_scope` 枚举扩展为 `all / project / self`（去掉 custom，见 5.2） |
| `community` | 加 `tenant_id`；保留 name/address/status；负责人字段由 project_staff 的项目经理岗位替代 |
| 其余业务表（点位/计划/任务/打卡/工单/报告/通知等） | 全部加 `tenant_id`，查询统一走租户隔离 |

### 4.3 数据隔离方案

采用**行级隔离**（所有租户同库同表，`tenant_id` 区分），不采用分库/分 schema：

- 物业公司数据量小（单项目月打卡数据千级），行级隔离性能完全足够；
- 运维一套库，备份升级简单，符合 Docker Compose 私有化交付的定位；
- 实现：JWT 中携带 tenant_id，中间件注入上下文，GORM 加全局查询条件；`super_admin` 可指定租户或跨租户。所有跨表唯一约束（如账号、项目名）改为 `UNIQUE(tenant_id, ...)`。

## 五、权限模型

### 5.1 功能权限（不变）

沿用现有机制：菜单挂权限点 → 角色绑菜单 → 用户绑角色 → casbin 校验接口和按钮。租户管理员只能在自己租户内建角色、勾权限点，看不到平台级菜单（租户管理、套餐等）。

### 5.2 数据权限（重构）

现有 `data_scope = all / custom + community_ids` 改为三档，由岗位自动推导、角色可收窄：

| data_scope | 含义 | 适用 |
|---|---|---|
| `all` | 租户内全部项目 | 物业公司负责人 |
| `project` | 所在项目的全部数据（多项目则并集） | 项目经理、各线主管 |
| `self` | 仅本人相关：我的任务、我上报的、派给我的工单、待我签的报告 | 一线人员 |

业务线隔离靠功能权限天然完成：客服主管没有巡检计划的菜单权限，自然看不到巡检数据；不需要额外的"业务线数据范围"。

推导规则（用户登录时计算，缓存到 Redis）：

1. 查 `project_staff` 得到该用户全部任职（项目 × 岗位）；
2. 任一岗位是项目经理 → 这些项目全量可见；任一岗位在岗位字典中标记为主管级（`is_supervisor`）→ 这些项目可见；只有一线岗位 → `self`；
3. 角色 data_scope 作为上限约束（角色给 `self`，即使是主管也只看本人——用于外包人员等场景）。

### 5.3 业务身份权限（改为名单制）

所有"哪个岗位承担哪个职责"按 3.2 的槽位绑定（duty_binding）解析，下表是平台默认绑定：

| 业务动作 | 现在的判定 | 改为 |
|---|---|---|
| 月报主管/经理签字 | 权限点 + 数据范围推导候选池 | 槽位 `report_sign_supervisor` / `report_sign_manager` 绑定的岗位人员（默认 安全主管 → 项目经理），生成报告时可调整；名单成员即可签，允许同一人兼签两级 |
| 工单派单 | 无派单概念 | 槽位 `order_dispatch` 绑定岗位（默认工程主管，或项目经理） |
| 工单接单 | 维修员角色 | 槽位 `order_accept` 绑定岗位（默认 `repairman`）的本项目人员 |
| 月报巡检员确认 | 当月有任务的巡检员 | 不变（按任务事实），执行人身份取自岗位编制 |

保留的唯一硬约束：**同一份报告同一签字级别，一人只签一次**；不再做"主管不能是巡检员"之类的职责分离校验（名单本身就是管理员的显式授权，小项目一人多岗是常态）。

## 六、业务流程映射

### 6.1 巡检：被动任务 + 主动发现双轨

- **被动（计划性）**：现有"点位 → 计划 → 任务 → 打卡"不变。任务增加"巡查类型"维度（安全巡查 / 设备设施专项巡查 / 环境巡查 / 楼栋巡查），不同类型派给对应岗位人员：设备设施专项巡查派给维修工，楼栋巡查派给楼管员。
- **主动（发现上报）**：所有移动端用户（楼管员、前台、维修工、巡检员、主管）都有"问题上报"入口：拍照 + 定位 + 描述，一键提交，自动生成工单进入待分诊池。

### 6.2 工单闭环（扩展现有工单模块）

```
上报（任何人，含业主电话由前台代录）
  → 分诊（客服主管：确认有效性、分类、定优先级；无效可驳回）
  → 派单（工程主管：指定维修工；也支持维修工从工单池抢单，由项目配置开关）
  → 接单处理（维修工：到场、维修、完工拍照）
  → 验收（报单人或客服主管：确认解决；不通过则退回重修）
  → 闭环归档
```

- 超时规则：分诊/接单/维修各环节可配 SLA（系统配置），超时站内通知主管升级。
- 维修工的日常工作 = 设备设施专项巡查任务（6.1 被动轨）+ 工单接单（本流程），两个入口在他移动端首页并列。

### 6.3 月报签字流（吸收已确认的小区签字人方案）

```
巡检员确认（当月有任务的全部巡检员）
  → 主管审批（默认安全主管，生成时可从项目岗位名单调整）
  → 项目经理终审（默认项目经理，可调整）
  → 归档 + 盖章 PDF
```

- 签字人默认值取自 project_staff 岗位配置；项目没配对应岗位时该级自动跳过；
- 允许同一人兼任多级（名单去重后逐级签）；
- 现有 `inspection_report.supervisor_ids / manager_ids` 字段沿用，语义变为"主管级名单 / 经理级名单"。

## 七、后台页面调整

## 九、部署模式与配置分层

安巡云同时支持两种交付模式，**共用同一套代码、同一套多租户架构**，不维护两条产品线：

- **SaaS 模式**：平台部署一套，多家物业公司作为租户接入；
- **私有化模式**：整套 Docker Compose 装到客户自己的服务器上。私有化 = 只开通了一个租户的同一套系统，没有任何特殊分支。

### 9.1 配置分三层，就近优先

```
平台默认（.env / 平台配置，部署级）
  └── 租户覆盖（tenant_config 表，白名单 key）
        └── 项目覆盖（仅少数业务参数，如分诊/抢单开关）
```

读取时"项目 → 租户 → 平台"逐级回落。

### 9.2 各层管什么

| 层级 | 内容 | 说明 |
|---|---|---|
| 平台默认 | 数据库、Redis、JWT 密钥、默认 COS、默认大模型 Key、平台名称 | 只在 `.env`，永不下放给租户 |
| 租户覆盖（白名单） | **品牌类**：系统 LOGO、系统名称、主题色、登录页；**业务参数**：SLA 时长、默认围栏半径、职责槽位绑定（3.2） | SaaS 刚需：物业公司的员工/业主必须看到自家品牌（白标）；私有化客户同样可用 |
| 租户覆盖（预留，本期不做功能） | COS 配置、大模型 Key | 大客户"数据存自家 COS / 用自家模型 Key"的低频需求。**架构留挂点**：文件模块已有统一抽象（md5 file_id），加"按租户路由存储后端"；大模型调用处封装"取租户配置、缺省回落平台"取值函数。真要做时密钥加密存储，或仅平台代配置不开放自助 |

约束：可覆盖的 key 用**白名单**控制，密钥类配置加密落盘；私有化模式下租户覆盖照常可用（该客户改自家品牌），基础设施仍以 `.env` 为准。
