# 红色物业 AI 智能巡检增强方案

> 版本：v1.0（讨论稿） 日期：2026-08-25
> 配套文档：《物业巡检管理系统方案》《数据库设计文档》《接口文档》

## 一、背景与定位

甲方规划建设「红色物业 AI 智能体」，包含三大板块：AI 公文会务、AI 智能巡检、AI 数智宣传。
其中 **AI 公文会务与 AI 数智宣传为独立系统，不在本系统建设范围内**。

本系统（安巡云）的定位：**巡检主线的 AI 化增强**——在现有「计划 → 打卡 → 照片 → 报告」
闭环之上叠加 AI 自动化能力，核心目标是巡检的**智能化**与**简约化**：

- 智能化：拍照后由 AI 判定设施状态，巡检员不做专业判断
- 简约化：一线操作极简，任何文化程度的人都能零培训上手

甲方的关键判断：工单系统几乎每个物业都有成熟产品，再做一套没有意义。
本系统**整体移除工单模块**，不做派单、不做维修闭环；巡检异常以
「问题清单 + 巡检报告 + 推送通知」留痕即结束，维修处置由物业线下自行安排。

## 二、现状盘点

以下能力已具备，本方案只在其上叠加，不推翻重做：

- 点位管理：二维码 / NFC / GPS 围栏，点位类型字典化（字典管理可自助新增类型）
- 计划与任务：计划支持**按点位类型圈选点位并批量建点**（"一类设施一个任务"的数据模型已具备）
- 打卡：照片水印、逐检查项填报
- AI 逐项识别：`ai_hint` 检查项提示 + 多模态识别客户端（`backend/internal/pkg/ai`）
- 报告：按巡查类型生成巡检报告
- 触达：公告 + uniPush 推送链路

## 三、核心设计

### 3.1 类任务连续巡检

任务按"类"组织而非按"点"组织：一个小区一栋楼几百个消防设施，
一个任务 = 一类设施（如"消防设施"），巡检员顺着一个任务连续作业。

- 任务详情为点位清单，按楼栋 → 楼层排序，顶部进度条（如"已完成 47/300"）
- 打卡动作：扫码 / NFC 或从清单点入 → 拍照 → 提交 → **自动跳转下一个未打卡点位**
- 未打卡点位始终置顶可见，走完即知漏检（甲方核心痛点"易漏检"的直接解法）
- 点位顺序仅作引导，**允许乱序打卡**（几百个点位强制按序不可行）

### 3.2 连续巡检向导（极简交互，已定稿）

操作链条压缩到最短：任务列表 → 点位概览 → 拍照向导。
向导内**一次只呈现一个动作**，顶部三级进度「点位 3/47 · 本项 2/8」。

**标准项两种形态**：

1. **拍照项**（视觉判定类型）：项名 + 大白话提示（"拍压力表，要看得清指针"）+ 大拍照按钮。
   拍完**立即后台上传并进入 AI 识别队列（并发处理），立即推进下一项，不等待**。
2. **感官项**（判定类型 `manual`：噪音/气味等 AI 不可判项）：大白话提问 +
   「正常」绿色大按钮 /「有异常」红色按钮。**点「正常」一次即过**（默认正常，减少点击）；
   异常时描述可选填。

**点位收尾（每个点位唯一阻塞点）**：本点位全部项过完点「提交本点位」，
等待剩余识别结果（通常只剩 1~2 项、几秒）：

- 全部通过 → 绿勾 + 语音 → 自动进入下一点位
- 有"没拍好"（质量不合格）→ 只列出这些项逐项补拍
- 有异常 → 红屏列出 AI 描述 → 确认后去下一处（描述可否编辑走配置项 `ai.result_editable`）

**导航**：返回键（物理/导航栏统一拦截）与页内「上一项」按钮 = 回退一步
（上一项 → 上一点位 → 任务第一步时退出向导），不单独设退出按钮。

**断点续传**：向导状态（点位/项索引、照片 file_id、识别 job_id、各项状态）
每步持久化本地；App 退出后从任务页「继续巡检」恢复，识别中的项凭 job_id 重查结果。

**已提交点位修改**：报告未归档前，已打卡点位可进入"修改模式"重新提交覆盖
（原记录留痕标记 superseded，审核页可见修改历史）；报告生成时覆盖记录锁定，锁定后只读。

**技术要点**：逐项识别走 Redis 队列 + 并发 worker（`ai.worker_concurrency`）；
照片质量与内容判定合并为每项一次小模型调用（1~2 秒）；巡检员体感全程只在点位收尾等一次。
重拍发生在打卡落库前，不产生脏数据。AI 未配置时自动回退手动模式（完整表单）。

### 3.3 判定标准（检查项「判定类型」枚举）

甲方确认的三类基础标准，扩展为九类 + 一项对比能力。
每个检查项配置判定类型与阈值，AI 按类型走不同 prompt 策略：


| #  | 判定类型        | 示例                           | AI 判定方式         | AI 可判性            |
| -- | --------------- | ------------------------------ | ------------------- | -------------------- |
| 1  | 有无            | 灭火器是否缺失                 | 视觉判定            | 可判                 |
| 2  | 是否损坏        | 外观破损、锈蚀、变形           | 视觉判定            | 可判                 |
| 3  | 指标区间        | 温度 / 湿度 / 电压 / 水压      | 表计读数 + 阈值比对 | 可判（精度见 §3.5） |
| 4  | 状态/位置正确   | 阀门开闭、开关状态、防火门关闭 | 视觉判定            | 可判                 |
| 5  | 有效期/标识合规 | 检验日期过期、合格证、铅封     | OCR 识别            | 可判                 |
| 6  | 通道/遮挡       | 消防通道占用、栓箱堆物         | 视觉判定            | 可判                 |
| 7  | 渗漏/异常痕迹   | 漏水渗油、积水、水渍           | 视觉判定            | 可判                 |
| 8  | 指示灯/运行状态 | 运行灯、故障灯亮灭             | 视觉判定            | 可判                 |
| 9  | 环境整洁        | 设备房杂物堆放                 | 视觉判定            | 可判                 |
| 10 | 基线对比        | 锈蚀加重、渗漏扩大             | 与上次照片对比      | 辅助判定             |
| 11 | 手动确认（manual） | 有无异常噪音、有无异味      | 不调 AI，巡检员手选（默认正常一键过） | 仅人工           |

**边界（写进合同附件，验收依据）**：异响、异味、温度手感、震动等
**照片不可判**项走 `manual` 手动确认项，不纳入 AI 判定范围。

### 3.4 识别引擎抽象（大模型一期 / 传统视觉二期）

识别层设计为**可插拔引擎接口**，两种实现并存、按检查项类型路由：

- **一期：多模态大模型引擎**（Qwen-VL / GPT-4o 级别）
  零训练、设施类型随意扩展（改 prompt 即适配）、质量校验与内容判定合并一次调用。
  扩展现有 `pkg/ai` 客户端，密钥与开关放系统配置页，按租户启用。
- **二期：传统视觉引擎**（目标检测 / 语义分割 / 专项读表模型）
  适用于甲方对特定表计数值精度有硬要求的场景（如消防水压必须精确记录），
  指针表读数采用"检测表盘 → 定位指针 → 角度换算"方案，精度高于大模型。
  不依赖、不排期，作为可选优化路线。

### 3.5 读数精度的诚实声明

大模型读压力表 / 温度计数值**精度不稳定**：一期允许大模型读数但带置信度，
低置信自动进人工复核；对精度有硬要求的表计类型，二期切换专项读表引擎。

### 3.6 极简 UX 设计（适老化标准）

巡检员画像为低文化程度、低操作能力人群，移动端按以下标准执行：

- 大字体、大按钮、强颜色对比（绿=正常 / 红=异常 / 黄=待复核）
- 语音播报辅助（"正常，下一处"/"照片不清晰，请重拍"）
- 正常情况零输入；异常情况 AI 预填描述，仅点确认
- 主流程不超过两级页面，禁止隐藏手势操作

### 3.7 管理操作手机化的边界

一线巡检、打卡、异常确认、报告查看、点位建档、计划配置——全部 App 端完成
（点位 / 计划管理 App 端已有基础，本方案补齐）。
字典、权限、系统参数等**一次性低频配置保留在 PC 后台**，不搬上手机。

## 四、工单系统移除方案

工单模块（含分派、验收、维修闭环）整体移除：

- 管理后台：工单菜单、路由、页面移除
- App：工单 tab 与相关页面移除
- 权限点：工单相关权限点从菜单种子中清除
- 后端：工单接口下线；代码与数据表**封存保留一个版本周期**，
  确认甲方验收无反复后再物理清理（防止返工风险，对用户完全不可见）
- 巡检异常的归宿：自动汇入问题清单 → 写入巡检报告 → 推送通知管理员，留痕即止

## 五、与独立系统的数据出口

AI 公文会务 / AI 数智宣传系统的素材（问题清单、整改情况、巡检台账）由本系统产出，
提供只读出口，不做主动集成：

- 标准化导出：问题清单 / 巡检报告 Excel、PDF 下载
- 预留只读 API：按小区、时段、设施类型查询巡检结果与问题数据

## 六、技术架构

- 识别引擎接口：`backend/internal/pkg/ai` 扩展为引擎抽象（多模态大模型 / 传统视觉可插拔）
- 判定协议：统一结构化 JSON 返回 `{quality_pass, quality_issue, status, confidence, description}`
- 异步与追溯：报告合成等长文本任务走 Redis 异步队列；AI 判定结果随打卡记录落库，全程可追溯
- 无新增基础设施组件（不引入向量库 / 消息队列等新依赖）

### 6.1 模型接入（公有云 API，已确认）

模型统一走**公有云 API 调用**，不考虑私有化部署。接入层分「协议适配」与「平台预设」两层：

**协议适配层**：抽象 4 种协议适配器，覆盖国内外全部主流平台

| 协议 | 覆盖平台 | 说明 |
|------|---------|------|
| OpenAI Chat Completions（`/v1/chat/completions`，多模态走 image_url） | OpenAI 官方 + 阿里云百炼 / 腾讯混元 / 百度千帆 / Kimi / DeepSeek / 智谱等国内平台的 OpenAI 兼容端点 | **主力协议**，事实行业标准，新增平台大概率零适配 |
| OpenAI Responses（`/v1/responses`） | OpenAI 官方新接口（o 系列 / GPT-5 系主推） | 第三方支持尚少，适配成本低，提前预留 |
| Gemini（generateContent） | Google Gemini 系列 | 专用适配器，仅接 Gemini 时启用 |
| Claude（Messages API） | Anthropic Claude 系列 | 专用适配器，仅接 Claude 时启用 |

国内平台官方均提供 OpenAI 兼容端点（如百炼 `compatible-mode/v1`），功能与原生协议等价；
DashScope / 混元 / 千帆的**原生协议不做**——其独有特性（新特性首发、异步批处理等）本场景用不到。

**平台预设层**：后台「模型配置」页内置常用平台预设——选定平台（阿里云百炼 /
腾讯混元 / Kimi 等）后自动填充协议类型与接口地址，管理员只需填 API Key 和模型名；
另保留「自定义」项，允许手动指定协议 + 接口地址接入任意兼容平台。

**配置项**：平台预设、协议类型、接口地址、API Key、模型名、超时、重拍放行次数、
AI 总开关；均在系统配置页维护，按租户生效（可按租户配置不同平台与额度）。

## 七、成本估算（对甲方口径）

以一个 300 点位的小区消防专项巡检为例：每点位一次多模态调用，
单轮巡检 API 成本约数元至十几元，月成本数十元量级。
远低于一名巡检员一次返工的人工成本。

## 八、AI 误判免责与人工复核

- AI 判定做不到 100% 准确，误判必然存在
- AI 结论定位为**记录与初筛**：管理员在后台查看问题清单时顺带复核，
  不给一线增加任何流程
- 强制提交的"待复核"照片、低置信读数，统一进后台复核队列
- 本节作为方案附件与甲方书面确认，避免验收争议
