## 一、通用约定

### 1.1 接口分组

| 分组 | 前缀 | 使用方 | 认证通道 |
|---|---|---|---|
| 管理后台 | `/api/admin` | PC 管理端（Vue SPA，托管于 `/admin`） | `admin` |
| App 端 | `/api/app` | Android / iOS / 鸿蒙 App | `app` |
| 小程序端 | `/api/mp` | 微信小程序（v21 起与 App 共用 `app` 通道会话） | `app` |
| 统一文件层 | `/api/files` | 三端共用（跨通道认证 AuthAny） | `admin`/`app`/`mp` 任一 |
| 公开接口 | `/api/public`、站点页面 | 官网访客、短链接扫码、一次性 ticket | 免登录 |

App 端与小程序端的业务接口**同形同逻辑**（同一批 Service/Controller），差异仅在登录方式与 App 端额外挂载的管理功能（见第三章）。

### 1.2 认证方式

- 登录/刷新接口签发**双令牌**：`access_token`（访问令牌）+ `refresh_token`（刷新令牌），响应含 `token_type`、`expires_in`。
- 业务请求携带访问令牌，两种头等价：
  - `Authorization: Bearer <access_token>`
  - `X-Token: <access_token>`
- 会话按通道隔离（admin / app 各自独立会话存储），登出/改密/停用账号会清除对应会话。
- 令牌过期返回 `40102`，用 `refresh_token` 调各端 `/refresh` 换新；`refresh_token` 失效返回 `40103`，需重新登录。

### 1.3 多租户与租户上下文

- 系统是**多租户**架构（租户=物业公司）。登录时用户名在多个租户下存在时，必须携带 `tenant_code`（公司代码）消歧，否则返回 `40109`。
- 系统管理（租户级）接口按**租户上下文**过滤数据：
  - 非超管：固定为本人租户，请求参数一律忽略；
  - 超管：可用 `?tenant_id=` 查询参数或 `X-Tenant-Id` 请求头指定目标租户，缺省为默认租户（`default`）；指定的租户必须存在。
- 业务数据（点位/任务/工单/报告等）经 `community`（小区/项目）链路天然按租户隔离，无需显式传租户参数。
- 租户被停用后，该租户全部账号无法登录（`40108`）。

### 1.4 统一响应结构

所有 JSON 接口（含错误）统一包装：

```json
{ "code": 0, "message": "success", "data": {} }
```

- `code=0` 成功；非 0 为业务错误码（见 1.6），`message` 为可读提示，`data` 为 `null`。
- 文件下载、SSR 页面、二维码图片等二进制响应不适用该包装。

### 1.5 分页约定

- 请求：`page`（默认 1）、`page_size`（默认 20，上限 100），query 参数。
- 响应 `data` 结构：

```json
{ "list": [], "total": 0, "page": 1, "page_size": 20 }
```

### 1.7 文件上传与下载约定

- **统一文件层 `/api/files`**（三端登录即可）：`POST /api/files` 直传（multipart，字段 `scene`、`file`）、`POST /api/files/sts` 取 OSS/COS 直传凭证、`GET /api/files/*key` 鉴权下载（`?download=1` 强制附件下载；图片/PDF 默认可内联预览）。
- **scene（场景）**决定存储前缀与读权限：`checkin`（打卡）、`workorder`（工单）、`avatar`（头像）、`signature`（手写签名）、`seal`（公章）、`notice`（公告附件）、`app`（发布物）、`export`（导出包）等。`signature`/`seal`/`export` 为保护前缀，不暴露于 `/uploads` 静态路由，只能经 `/api/files` 鉴权访问。
- 内容图（checkin/workorder/avatar/notice）在本地存储模式下也可经 `GET /uploads/*key` 免登录访问（仅非敏感场景）。
- 打卡/工单照片上传后得到 `file_key`，业务接口提交时只传 `file_key`。

### 1.8 权限模型速览

- 权限点形如 `模块:对象:动作`（如 `inspection:point:list`），由 Casbin（`casbin_rule`）按角色判定；用户**有效角色 = 用户直挂角色 ∪ 在职岗位绑定角色**（实时并集）。
- `RequirePerm("a","b")` 表示任一权限点命中即放行。
- 「登录即可」= 只需有效令牌，不校验权限点；「免登录」= 公开接口。
- 数据范围 `data_scope`：`all`（全部）/ `project`（所辖项目，主管级岗位自动推导为该档）/ `self`（仅本人）。
- 平台管理菜单（`is_platform=true`，租户管理、岗位模板库等）仅超管可见、可授权，`tenant:*`、`platform:*` 权限点只授 `super_admin`。

### 2.24 月度报告（三级电子确认签字）

报告状态机：`pending_inspector`（巡检员确认，名单制可多签/代签）→ `pending_supervisor`（主管级签字）→ `pending_manager`（经理级终审）→ `approved`（归档）；任一级驳回回到 `pending_inspector`。主管/经理签字授权以**报告生成时圈定的名单成员身份**为准（supervisor_ids/manager_ids），不挂权限点；名单为空该级自动跳过。

报告按巡查类型通用生成（§3.4）：`patrol_type` 空=综合月报（全类型口径），非空=该类型专项检查报告（只统计该类型任务/点位/逐项不合格分布）；同一小区同一月按 (community_id, period, patrol_type) 唯一，综合月报与各专项各一份。专项报告主管级签字槽位取该类型汇报线（`patrol_report_line.<type>`，如消防→工程主管）。标题：综合「{项目}YYYY年M月月度巡检工作报告」；专项「{项目}YYYY年M月{类型名}专项检查报告」（类型 label 尾部「专项巡查/专项/巡查」自动裁掉，避免叠字）。
