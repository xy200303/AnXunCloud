## 二、总体约定

### 2.1 主键与 ID 策略

- 主键统一 `id uuid`，应用层 UUIDv7（时间有序，利于索引局部性与客户端幂等）。例外：`casbin_rule.id` 为 bigint 自增（序列 casbin_rule_id_seq）。
- `checkin_record` / `sys_operation_log` 为按月分区表，主键为 `(id, created_at)` 复合（分区键必须进主键）。
- `app_release.id` / `checkin_item_draft.id` 带 DB 默认值 `gen_random_uuid()`（双保险），其余表无 DB 默认值。
- 跨表引用以应用层关联为主，物理外键仅 14 条（见 §7.4）；`tenant_id` 一律不建外键。

### 2.2 通用列与软删除

- 业务表普遍含 `created_at` / `updated_at timestamptz NOT NULL DEFAULT now()`；主数据表另含 `deleted_at`（gorm 软删除），相关唯一索引普遍带 `WHERE deleted_at IS NULL` 部分条件。
- 无 `deleted_at` 的表（只增不改或硬删）：check_template_item、checkin_record、checkin_record_item、checkin_item_draft、sys_login_log、sys_operation_log、sys_message、sys_role_menu、casbin_rule、post_dict、project_staff、duty_binding、approval_flow、sign_asset、upload_file、user_push_device、app_release、tenant、tenant_config。
- 例外中的例外：post_dict / project_staff / duty_binding / approval_flow / sign_asset 有 `updated_at` 但无 `deleted_at`（移出=硬删或状态翻转）。

### 2.3 jsonb 自定义类型

系统大量使用 `jsonb` 存储数组/对象，对应 `backend/internal/pkg/types/jsonb.go` 的自定义类型，落库统一非 NULL（空为 `[]` / `{}`）：

| 类型 | 形态 | 用途示例 |
|---|---|---|
| `IDArray` | uuid 字符串数组 | sys_user.role_ids、inspection_plan.point_ids / inspector_ids、inspection_task.point_ids、project_staff.building_ids、inspection_report.inspector_ids / supervisor_ids / manager_ids |
| `StringArray` | 字符串数组 | project_staff.posts（岗位代码）、duty_binding.post_codes、inspection_plan.point_types、checkin_record_item.photos / checkin_item_draft.file_keys（file_key 数组） |
| `JSONMap` | 对象 | inspection_plan.cycle_config、check_template_item.judge_config、inspection_report.stats、sys_dict_data.attrs |
| `SignArray` | `[{user_id,name,signed_at,signature_file_key,asset_id,proxy_by,proxy_name,proxy_reason}]` | inspection_report.inspector_signed 签字留痕（含代签三字段） |
| `AttachmentArray` | `[{name,url}]` | sys_notice.attachments |
| `FlowStepArray` | `[{slot,name}]` | approval_flow.steps 审批链环节 |

### 2.4 多租户行级隔离

租户（`tenant`）= 物业公司，是数据隔离基本单位。隔离策略分三档：

1. **入口表租户必填**：`sys_user.tenant_id`、`community.tenant_id` 非空；登录账号租户内唯一，业务数据经 community 归属租户。
2. **租户可空 = 平台共享**：`sys_role`（空=内置角色，全平台只读共享）、`post_dict`（空=平台内置模板岗位）；唯一索引用 `COALESCE(tenant_id, 零UUID)` 处理。
3. **冗余列便于过滤**：业务表（building / inspection_point / inspection_plan / inspection_task / checkin_record / checkin_item_draft / inspection_report / check_template / sign_asset / sys_notice / sys_message / upload_file / sys_login_log / sys_operation_log）带 `tenant_id` 冗余列（=所属小区租户或操作者租户）；查询主路径仍按 community / 接收人链路隔离，冗余列用于日志过滤与统计。

### 2.5 状态字段约定

- 启停用统一 `status varchar(16)`，取值 `enabled` / `disabled`（CHECK 约束兜底）；接口层以 `1` / `0` 交互（`model.StatusInt` / `StatusStr` 互转）。
- 例外：`sys_notice.status` 为 int（0 草稿 / 1 已发布 / 2 已下线，CHECK 0/1/2）。
- 业务流程状态（任务、打卡审核、报告等）为字符串枚举，见各表说明与 §4.2 汇总。

### 2.6 分区表（运行期滚动建分区）

`checkin_record` 与 `sys_operation_log` 为**按月 RANGE 分区表**（分区键 `created_at`，主键 `(id, created_at)` 复合），各挂一个 DEFAULT 分区兜底（`*_default`，保留在基线内）。应用启动时与巡检调度器每日执行 `database.EnsurePartitions`，自动创建**当月与下月**分区（`CREATE TABLE IF NOT EXISTS ... PARTITION OF ... FOR VALUES FROM ... TO ...`），无需人工干预。因主键含分区键，外键无法仅引用分区表的 `id`（checkin_record_item 因此刻意不加 FK，见 §3.2.9）。分区表上的索引以 `ON ONLY` 建在父表，新分区自动继承。

## 五、关键设计说明

### 5.1 计划周期细则（inspection_plan.cycle_config）

`cycle_config` 为 JSONB 对象，结构随 cycle_type 变化：

| cycle_type | 键 | 说明 |
|---|---|---|
| daily | （无需执行日配置） | 每个自然日均为执行日 |
| weekly | `weekdays: [1..7]` | 执行日星期序列（周日=7），升序去重 |
| monthly | `days: [1..31, -1]` | 执行日日号序列，-1 解析为当月最后一日，超出当月天数的剔除 |

通用键（与 cycle_type 无关）：

| 键 | 类型 | 说明 |
|---|---|---|
| `rounds` | `[{name, window}]` | 巡更轮次：每个执行日按轮次各生成一条任务，任务快照 round_name/time_window；window 允许跨零点（如 22:00-02:00），任务日期归属开始时刻所在日 |
| `daily_min_rounds` | 非负整数 | 每日达标轮次线（未配置=不设线） |

点位分配（assign_mode）：

- `all`（默认）：每个执行日巡全部点位。
- `split`：点位按「执行日数 × 巡检员数」连续切块均分（点位名单已按路线优化排序，连续块=地理聚集，每人每天跑的距离最小），取 (执行日下标, 巡检员下标) 对应的一块；仅 weekly/monthly 合法（大点位月检按日摊派场景）。

任务生成幂等性由 uk_task_plan_date_inspector（plan_id + task_date + inspector_id + COALESCE(round_name,'')）保证；调度器每日 00:05 起生成未来 N 天任务（`inspection.task_generate_days`），00:10 将昨日未完成任务置 overdue（`inspection.overdue_check_time`）。

### 5.2 坐标系

经纬度统一 **GCJ-02**（火星坐标系），与腾讯地图/微信小程序坐标一致；`numeric(10,7)` 精度约 1cm 级。点位坐标必填且带范围 CHECK（chk_point_lng / chk_point_lat）。

### 5.3 快照语义与「识别即审核」

**写时快照**（历史数据不随源表变更）：

- 任务快照：inspection_task.point_ids / time_window / round_name / patrol_type（生成时展开或复制，计划变更不溯及已生成任务）。
- 逐项快照：checkin_record_item 的 name / requirement / photo_required / ai_hint / judge_type / judge_config（打卡当时从模板项复制）。
- 报告快照：inspection_report.stats（统计口径固化）、signature_key / seal_file_key / inspector_signed（签章资产版本快照）。

**识别即审核**（AI 识别与审核统一，无独立审核结果字段冗余）：

- 逐项层：拍照即入 checkin_item_draft 异步识别，结论 ai_verdict=pass/abnormal，附 ai_reason / ai_reading / quality_*；正式提交时快照进 checkin_record_item 并同事务删除草稿。
- 记录层：checkin_record.ai_verdict=pass 自动放行（audit_status=auto_pass）；review/error/force_submit 转人工（audit_status=pending，走 approval_flow 审批链，audit_step 记录进度）。
- 质量第一层：ai_quality_pass/ai_quality_issue 不达标拒绝打卡并提示重拍，重拍次数（`ai.max_photo_attempts`）用尽后可 force_submit 强制提交转人工复核。

**覆盖修改与归档锁定**：已提交点位允许重拍覆盖（`ai.result_editable` 控制）——旧记录置 superseded_by 指向新记录，列表/统计/报告统一过滤失效记录；报告归档后 locked_at 非空，该点位打卡不可再覆盖修改。

### 5.4 编号规则

- 主键 UUIDv7：应用层生成（时间有序，利于索引局部性），checkin_record 支持客户端自带 ID 实现离线幂等写入。
- 点位二维码编号：`P` + 6 位序列（如 `P000018`，无分隔符，肉眼报号与扫码解析都最简单）；序号源为 PG 序列 **qrcode_no_seq**，业务编号与 UUID 主键解耦。
- casbin_rule.id：PG 序列 casbin_rule_id_seq 自增。

### 5.5 权限模型（RBAC + 数据权限 + 名单制槽位）

- **功能权限**：casbin RBAC with domains（dom 当前统一 default），p 策略=角色→权限点，g 策略=用户→角色；策略由 `authz.SyncAll` 全量重建。有效角色 = sys_user.role_ids ∪ 在职编制岗位绑定角色（project_staff → post_dict.role_id），**实时并集**，不物化。
- **数据权限**：角色 data_scope 定上限（all/project/self），主管级岗位（post_dict.is_supervisor）自动推导 project 档；小区级过滤走 `ApplyCommunityFilter` / `CheckCommunity`（按在职编制推导可见小区集合）。
- **名单制授权**：月报签字、打卡审核、巡查执行等业务身份一律走 duty_binding 槽位 → 岗位 → 在职编制人员名单（项目级 → 租户级 → 平台默认三级回落），不再从「权限点 + 数据范围」反推。

### 5.6 分区与大表策略

- `checkin_record`、`sys_operation_log` 按月 RANGE 分区 + DEFAULT 分区兜底；应用启动与每日调度自动预建当月/下月分区（`EnsurePartitions`）。
- 分区表主键必须含分区键（id + created_at），因此跨表 FK 无法仅引用其 `id`：checkin_record_item 刻意不加 FK，走应用层事务一致性；checkin_record 的出站 FK（→inspection_task / inspection_point）不受影响。
- 归档清理可按分区整表 DROP，成本远低于 DELETE。
