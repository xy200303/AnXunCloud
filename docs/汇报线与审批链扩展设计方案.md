# 汇报线与审批链扩展设计方案

> 状态：**P1（槽位维度化）与 P2（审批链）均已落地**（2026-08-19）。前置文档：《多租户组织架构与角色权限设计方案》《管理后台信息架构与菜单归位方案》。
> 背景：巡查汇报关系（patrol_report_line）已接入打卡审核/抽查/催办授权与异常/逾期通知。当前只有**一条**汇报线（默认绑安全主管），无法表达"设备巡查归工程主管、楼栋巡查归客服主管"；且后续会出现"项目经理审核主管"等**更深审批层级**。本方案目标：横向（业务线）与纵向（审批深度）都可扩展，且不再靠堆槽位枚举硬撑。

## 1. 问题分解：两个正交的扩展方向

| 方向 | 例子 | 本质 |
|---|---|---|
| 横向：同一职责按业务线分人 | 安全巡查→安全主管审，设备巡查→工程主管审，楼栋巡查→客服主管审 | 槽位的**维度（dimension）** |
| 纵向：同一业务要过几级审批 | 主管审 → 项目经理复核；以后可能更多级 | **审批链（chain）** |

错误做法（要避免）：每加一个维度组合就加一个槽位枚举（`patrol_report_line_safety`、`patrol_report_line_equipment`…平铺枚举），以及每加深一级就改一次状态机。这会让槽位列表爆炸、代码里全是特判。

正确做法：**槽位负责"谁"（单点职责），审批链负责"几步"（流程深度）**，两个概念分开建模。

## 2. 槽位维度化（横向扩展，本次实施）

### 2.1 命名规范：`<family>.<dimension>`

槽位 code 仍是字符串（表结构不动），引入层级命名：

```
patrol_report_line              # 通用槽位（兜底，现有数据即此）
patrol_report_line.safety       # 安全巡查汇报线
patrol_report_line.equipment    # 设备专项巡查汇报线
patrol_report_line.environment  # 环境巡查汇报线
patrol_report_line.building     # 楼栋巡查汇报线
```

- `family` = 职责种类（系统定义，如 patrol_report_line）
- `dimension` = 业务线维度值（与巡查类型 patrol_type 同枚举：safety/equipment/environment/building）
- 以后出现新维度（如按楼栋、按班次）沿用同一规范 `<family>.<dimension>`，**不改表结构、不改解析框架**

### 2.2 解析回落链（在现有三级回落前加"维度回落"）

现有：项目级 → 租户级 → 平台级。维度化后按序解析：

```
patrol_report_line.<line>：项目级 → 租户级 → 平台级
        ↓ 全部未配置
patrol_report_line（通用）：项目级 → 租户级 → 平台级
```

- 已配置维度槽位 → 精确命中（如设备巡查 → 工程主管）
- 未配置 → 回落通用槽位（现有"绑安全主管"的配置继续有效，**老数据零迁移**）
- 通用槽位也未配置 → 该环节按规则跳过（现有语义）

`communitysvc.ResolveSlotPosts` 改为接受完整槽位 code，新增 `ResolveReportLine(db, projectID, patrolType)` 封装上述六级查找。`SlotUserIDs`/`SlotAuthorized` 不变（拿到 code 后逻辑一致）。

### 2.3 消费点按巡查类型路由

| 消费点 | 路由依据 | 说明 |
|---|---|---|
| 打卡审核/抽查/催办授权 | 记录所属任务的 `patrol_type` | 设备巡查的打卡只有工程主管（或管理员）能审 |
| 异常打卡通知 | 同上 | 设备异常通知工程主管，不再惊动安全主管 |
| 逾期未巡通知 | 同上（按任务 patrol_type 分组） | 分线提醒对应主管 |

注意：checkin_record 本身无 patrol_type，经 `task_id → inspection_task.patrol_type` 取（打卡必属任务，离线补传也挂任务）。

### 2.4 seed 默认绑定

| 槽位 | 默认绑定岗位 |
|---|---|
| `patrol_report_line`（通用兜底） | `safety_supervisor`（保持现状） |
| `patrol_report_line.safety` | 不设默认（回落通用即可，避免冗余） |
| `patrol_report_line.equipment` | `engineering_supervisor` |
| `patrol_report_line.environment` | `environment_supervisor` |
| `patrol_report_line.building` | `service_supervisor` |

前端职责绑定页按 family 分组展示（`DutySlots` 注册维度槽位即自动出现，通用槽位居上作兜底说明）。

## 3. 审批链（纵向扩展，本次只定模型+接口，引擎按需实施）

### 3.1 模型（P2 已实现）

审批流 = 有序环节列表，**每个环节引用一个槽位**（名单解析复用第 2 章，不发明新"人"的概念）：

```jsonc
// approval_flow 表（tenant_id/project_id 可空：平台默认 / 租户级 / 项目级，同一套回落）
{
  "flow_code": "checkin_review",          // 业务流程 code（系统定义）
  "steps": [
    { "slot": "patrol_report_line", "name": "汇报线审核" },
    { "slot": "project_review", "name": "项目经理复核" }  // 可选第二环节（默认绑 project_manager 岗位）
  ]
}
```

- **流程种类（flow_code）系统定义**：打卡审核流（checkin_review）已落地；后续请假/采购等审批流按同一模型扩展，代码只认 flow_code，不认步骤数
- **步骤内容（几步、每步绑哪个槽位）是配置**：`approval_flow` 表按 项目级 → 租户级 → 平台默认 回落（与 duty_binding 同一作用域模型），未配置时代码内置单步默认链兜底（行为与链化前一致）
- 存储：独立表 `approval_flow`（迁移 00002；比 tenant_config JSON 多了作用域回落与唯一约束，与 duty_binding 镜像）
- 执行：`checkin_record.audit_step` 记录审批进度；通过当前环节 → 进度 +1 并通知下一环节名单；末环节通过 → `audit_status=pass`；驳回 → rejected；撤销审核 → 进度回 0 重走整链
- 配置入口：系统管理 → 岗位管理 → 职责槽位默认绑定页「打卡审核链」（租户级）；小区管理 → 编制 → 职责槽位绑定页（项目级覆盖）；平台管理 → 岗位模板库（平台默认）

### 3.2 与现有两条"链"的关系（重要：不强行统一）

- **打卡审核**：现在是单步（汇报线审一次）。审批链引擎落地后改为按链执行：当前步名单成员可审，通过后进下一步，全部通过才 `pass`；驳回回到 pending。`audit_status` 增加 `step_no` 或 `current_step` 记录走到第几步
- **月报三级签字**：保持现状（名单快照制，签字留痕/代签/公章快照有法律语义，且已稳定运行）。语义上它就是一条预置三步链，但**不迁移进通用引擎**，避免为抽象而抽象
- **"项目经理审核主管"**：= 打卡审核流配两步 `[汇报线, project_review]`。`project_review` 作为新槽位注册（默认绑 project_manager），届时零代码新增概念

### 3.3 授权判定统一入口不变

所有名单制授权继续走 `communitysvc.SlotAuthorized`（超管/租户管理员默认放行，名单约束项目内分工）。审批链引擎只回答"当前步是哪个槽位"，授权判定不引入第二套规则。

## 4. 明确不做的（防过度设计）

- **不建通用组织树/汇报关系表**（parent_id 式的"谁是谁的上级"）：主管管谁由"槽位→岗位→编制"表达已足够，组织树会带来冗余真相源和同步难题
- **不引入 BPMN/工作流引擎**：流程种类少且固定，链模型已覆盖"加深层级"的需求
- **月报签字不迁入通用链引擎**（见 3.2）
- **维度不做多级嵌套**（`family.a.b` 只允许一层 dimension，出现真实需求再评估）

## 5. 实施步骤

**P1（本次，槽位维度化）**

1. `duty_binding` 槽位枚举注册维度槽位（`DutySlots` 加 4 条，带 line 标签；文档同步）
2. `ResolveReportLine(db, projectID, patrolType)`：维度槽位 → 通用槽位六级回落
3. 审核/抽查/催办/异常通知/逾期通知按任务 patrol_type 路由（checkin 经 task_id 取类型）
4. seed：维度槽位默认绑定（2.4）；演示数据同步（设备周检的打卡审核归工程主管）
5. 前端职责绑定页按 family 分组展示
6. 文档：本方案落地后更新《多租户组织架构与角色权限设计方案》§3.2 槽位表

**P2（审批链，已落地）**

1. ~~flow 配置存储（tenant_config JSON 起步）~~ → 独立 `approval_flow` 表 + 三级配置界面（平台/租户/项目）
2. 打卡审核按链执行（audit_step 进度、非末环节通知下一环节名单、驳回即打回、撤销回 0）
3. 注册 `project_review` 槽位（默认 project_manager）；演示租户华安配置「汇报线审核 → 项目经理复核」两级流

## 6. 验收标准（P1）

- 设备专项巡查的打卡，安全主管审核被拒（40304），工程主管可审
- 楼栋巡查异常打卡 → 客服主管收到通知，安全主管不收
- 未配置维度槽位的项目 → 行为与现状完全一致（通用槽位兜底）
- 超管/租户管理员在各条汇报线上均默认放行
