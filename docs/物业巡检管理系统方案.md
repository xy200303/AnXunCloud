# 物业巡检管理系统建设方案

> 版本：v1.1
> 定位：生产级方案，可直接据此立项开发并投入公司日常使用，非演示原型。
> 技术栈：Go（Gin + GORM + PostgreSQL + Redis）+ Vue3 企业级管理后台 + 微信小程序

---

## 一、现状与痛点

| 现状 | 痛点 |
|---|---|
| 巡检员到小区手动纸笔记录 | 记录易丢失、难追溯、无法汇总统计 |
| 手动拍照，照片存在个人手机 | 照片与点位、时间对不上，事后补拍无法识别 |
| 管理员无法确认巡检员是否真到点位 | 存在"没去现场、事后补记录"的管理漏洞 |
| 异常情况靠口头/微信上报 | 问题无闭环，维修跟进无记录 |

**建设目标**：巡检员用微信小程序完成"到点打卡 + 现场拍照 + 异常上报"；管理后台（侧边栏式 Web 系统）实时掌握每个小区、每个点位、每个巡检员的巡检执行情况，形成"任务 → 执行 → 异常 → 整改 → 复核"的完整闭环。

## 二、系统组成与角色

### 2.1 系统组成

```
┌─────────────────────┐     ┌──────────────────────────┐
│  微信小程序（巡检端） │     │  Web 管理后台（管理端）    │
│  · 巡检员打卡拍照    │     │  · 物业公司管理员/主管     │
└────────┬────────────┘     └───────────┬──────────────┘
         │ HTTPS                        │ HTTPS
         └──────────────┬───────────────┘
                        ▼
              ┌──────────────────┐
              │  Go API 服务(Gin) │
              ├──────────────────┤
              │ PostgreSQL+Redis │
              │ 对象存储（照片）    │
              └──────────────────┘
```

### 2.2 角色与权限

| 角色 | 端 | 主要能力 |
|---|---|---|
| 超级管理员 | Web 后台 | 全部功能 + 系统管理（用户/角色/权限/配置） |
| 物业主管 | Web 后台 | 制定巡检计划、查看所辖小区执行情况、处理异常、审批整改 |
| 巡检员 | 小程序 | 接收任务、到点打卡、拍照上传、上报异常、整改后复拍 |
| 维修人员（可选） | 小程序 | 接收派单、处理异常工单、上传维修结果 |

权限模型采用 **RBAC**：用户 → 角色 → 菜单权限 + 按钮级权限 + 数据权限（按小区隔离，主管只能看所辖小区数据）。

## 三、功能设计

### 3.1 小程序端（巡检员）

1. **登录**：微信授权 + 手机号绑定，首次由后台开通账号，无需注册。
2. **今日任务**：按日期展示分配的巡检任务（小区 → 巡检路线 → 点位列表），显示进度（已检 3/12 点）。
3. **点位打卡（二维码 + GPS 围栏双支持）**：
   - 每个点位**同时**配置二维码和 GPS 围栏，打卡方式按点位可配：`扫码`、`围栏`、`扫码或围栏`（默认，满足其一即可）、`扫码且围栏`（高安保点位，如配电房）；
   - 扫码打卡：扫描点位张贴的二维码（后台批量生成打印）；
   - 围栏打卡：进入点位围栏范围（半径可配，默认 100m）后点击打卡，无信号地下室等 GPS 弱场景自动降级提示扫码；
   - 打卡时强制现场拍照（调用相机，**禁止从相册选择**），照片自动叠加水印：点位名称、时间、GPS 坐标、巡检员姓名；
   - 每个点位可配置"必拍项"（如：配电箱、消防栓、电梯机房），少拍不能提交。
4. **异常上报**：对点位选择"异常"，填写描述 + 拍照，自动生成异常工单。
5. **离线支持**：无信号场景打卡数据本地暂存，恢复网络后自动补传（服务端记录原始打卡时间，防止改时间造假）。
6. **历史记录**：查看自己过往的巡检记录和工单处理状态。
7. **消息通知**：任务提醒、工单指派、整改驳回，通过微信订阅消息推送。

### 3.2 Web 管理后台（侧边栏结构）

```
侧边栏
├── 工作台（Dashboard）
│     · 今日巡检完成率、进行中任务、待处理异常数、逾期任务
│     · 各小区执行排行、近 7 天趋势图
├── 巡检管理
│     ├── 点位管理（小区 → 楼栋/区域 → 点位，配置二维码 + GPS 围栏 + 打卡方式 + 必拍项）
│     ├── 巡检计划（周期计划：每天/每周/每月，按路线指派巡检员）
│     ├── 任务监控（实时看每个任务：点位 x/x、每个点的打卡时间/照片/距点位距离）
│     └── 巡检记录（按人/小区/时间筛选，查看明细与照片原图）
├── 异常工单
│     ├── 工单列表（待派单/处理中/待复核/已关闭）
│     └── 工单详情（异常照片 → 派单 → 维修反馈 → 复核关闭，全程留痕）
├── 统计分析
│     ├── 巡检覆盖率/及时率/异常率报表
│     ├── 巡检员绩效（完成率、平均耗时、异常发现数）
│     └── 数据导出（Excel/PDF 月报，可直接给业委会/甲方）
├── 小区管理（多小区/多项目，楼栋与区域维护）
├── 系统管理
│     ├── 用户管理（后台账号 + 巡检员/维修工账号，所属小区，启停用、重置密码，
│     │              支持 Excel 批量导入（模板下载/逐行校验/失败明细）与按筛选导出）
│     ├── 角色管理（角色定义、菜单权限分配、数据权限范围）
│     ├── 菜单管理（菜单/按钮权限点维护，前端路由与按钮显隐联动）
│     ├── 字典管理（工单状态、点位类型、异常类型等可配枚举）
│     ├── 参数配置（围栏默认半径、拍照水印开关、疑似作弊阈值、消息开关）
│     ├── 通知公告（面向巡检员的公告推送）
│     └── 日志管理（操作日志、登录日志，可按人/模块/时间检索）
└── 个人中心（修改密码、个人信息）
```

**后台核心查看场景（对应管理诉求）**：
- "有没有每个点位都去到" → 任务监控页以路线形式展示点位状态：✅已打卡 / ⚠️跳过 / ❌未打卡，缺卡一目了然；
- "有没有打卡记录" → 每次打卡含：打卡时间、GPS 坐标与点位距离（如"距点位 8m"）、打卡方式（扫码/围栏）；
- "看到他们的照片数据" → 打卡记录里直接查看带水印照片，支持原图放大、按点位/时间检索，照片存对象存储不可篡改删除。

### 3.3 防作弊机制（生产系统关键）

- 拍照强制走相机，禁用相册选择；
- 照片服务端打水印（时间 + 坐标 + 人 + 点位），并校验照片 EXIF 拍摄时间与打卡时间偏差；
- 打卡坐标与点位围栏距离超阈值（按点位配置，默认 100m）标记"疑似作弊"，计入报表；
- 服务端记录打卡时间，不信任客户端时间；
- 补传数据标记"离线补传"并保留原始时间戳。

### 3.4 后台 UI 设计规范（专业企业级，杜绝"AI 味"）

- 采用 **Element Plus** 经典企业后台布局：固定深色侧边栏 + 顶部面包屑/标签页（Tags View）+ 内容区，参照若依（RuoYi）/ vue-element-admin 的成熟交互范式，物业行业用户上手零成本；
- 配色：主色 `#409EFF` 系或深青蓝 `#1F2D3D` 侧边栏，中性灰阶内容区，不使用渐变大紫大蓝等"AI 风"配色；
- 交互规范：列表页统一"搜索栏 + 工具栏 + 表格 + 分页"，表单统一抽屉/对话框，操作前二次确认，删除走软删除；
- 图表：ECharts，克制的单/双色系列；
- 字体：系统默认中文字体栈，不引入花哨 Web 字体。

## 四、技术架构

### 4.1 技术选型

| 层 | 选型 | 说明 |
|---|---|---|
| 小程序 | 微信原生小程序（WXML/WXSS/JS） | 微信生态内体验最好，打卡/扫码/相机 API 稳定 |
| 管理后台 | Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts | 企业级后台事实标准，侧边栏/权限指令/标签页开箱可用 |
| 后端 | **Go + Gin + GORM** | 高性能、单二进制部署、并发处理打卡/照片回调无压力 |
| 数据库 | **PostgreSQL 15+**（JSONB 存配置类字段；如需复杂地理查询可启用 PostGIS 扩展，非必需） | |
| 缓存 | **Redis** | 登录会话/JWT 黑名单、任务进度缓存、计划生成分布式锁 |
| 鉴权 | JWT（access + refresh）+ Redis 会话 | 后台与小程序两套登录入口，统一 RBAC 中间件鉴权 |
| 照片存储 | 阿里云 OSS / 腾讯云 COS | 小程序直传（STS 临时凭证），后端只存 URL |
| 水印/图片处理 | Go 端 `disintegration/imaging` 或 OSS 图片处理服务（推荐后者，零服务器开销） | |
| 定位 | 小程序 `wx.getLocation` + 服务端 Haversine 距离计算 | 坐标系统一 GCJ-02 |
| 消息 | 微信订阅消息 + 企业微信 Webhook（工单实时推送给主管，可选） | |
| 部署 | Docker Compose（app / postgres / redis / nginx），单台云服务器起步 | |

### 4.2 后端工程结构（Go）

```
server/
├── cmd/server/main.go        # 入口
├── internal/
│   ├── config/               # 配置加载（viper，yaml + 环境变量）
│   ├── middleware/           # JWT、RBAC 鉴权、操作日志、限流、CORS
│   ├── module/
│   │   ├── system/           # 用户/角色/菜单/字典/参数/日志（系统管理）
│   │   ├── community/        # 小区/楼栋
│   │   ├── inspection/       # 点位/计划/任务/打卡记录
│   │   ├── workorder/        # 异常工单
│   │   ├── stats/            # 统计报表/导出
│   │   └── mp/               # 小程序端接口（登录、任务、打卡、补传）
│   ├── pkg/                  # jwt、oss、watermark、geo、excel、response
│   └── router/               # 路由注册（/api/admin、/api/mp 分组）
└── go.mod
```

每个 module 内按 `handler → service → repository(GORM)` 分层，职责清晰。

### 4.3 照片上传链路

```
小程序 ──① 申请上传凭证──▶ 后端 ──▶ OSS STS 临时凭证
小程序 ──② 直传照片─────▶ OSS（带回调）
OSS  ───③ 上传回调─────▶ 后端（打水印、写库、更新任务进度）
```

照片不走应用服务器，几万张照片/月服务器带宽也不受影响。

## 五、数据库核心表设计（PostgreSQL）

```sql
-- ========== 系统管理 ==========
sys_user(id, username, password, name, phone, openid, avatar,
         role_ids JSONB, community_ids JSONB,  -- 数据权限：所辖小区
         status, last_login_at, created_at, updated_at, deleted_at)

sys_role(id, code, name, data_scope,          -- all / custom(按小区)
         remark, status, created_at)

sys_menu(id, parent_id, title, path, icon, type,  -- dir/menu/button
         perms, sort, visible, status)

sys_role_menu(role_id, menu_id)               -- 角色-菜单关联

sys_dict_type(id, code, name)
sys_dict_data(id, type_code, label, value, sort, status)

sys_config(id, key, name, value, remark)      -- 系统参数（围栏半径、水印开关等）

sys_login_log(id, user_id, ip, ua, status, msg, created_at)
sys_operation_log(id, user_id, module, action, method, path, params,
                  ip, status, cost_ms, created_at)

-- ========== 业务 ==========
community(id, name, address, manager_id, status, created_at)

building(id, community_id, name, type)        -- 楼栋/区域

-- 巡检点位：二维码 + GPS 围栏双支持
inspection_point(id, community_id, building_id, name, type,
                 qrcode_no,                   -- 二维码编号（唯一）
                 longitude, latitude,         -- GCJ-02
                 fence_radius,                -- 围栏半径（米）
                 credential,                  -- 点位凭证：qrcode / nfc / none
                 require_fence,               -- 是否要求 GPS 在围栏内
                 required_photo_items JSONB,  -- 必拍项
                 sort, status)

inspection_plan(id, community_id, name, point_ids JSONB,  -- 点位路线（有序）
                cycle_type,                   -- daily/weekly/monthly
                cycle_config JSONB, inspector_ids JSONB,
                start_date, end_date, time_window,        -- 要求执行时段
                status)

inspection_task(id, plan_id, community_id, inspector_id,
                task_date, status,            -- pending/doing/done/overdue
                total_points, done_points, started_at, finished_at)

-- 打卡记录（核心表）
checkin_record(id, task_id, point_id, inspector_id,
               checkin_time,                  -- 服务端时间
               client_time,                   -- 客户端原始时间
               longitude, latitude, distance_to_point,
               checkin_type,                  -- qrcode / fence / offline
               photos JSONB,                  -- [{item, url, watermarked_url}]
               result,                        -- normal / abnormal
               remark, is_suspect, suspect_reason)

work_order(id, order_no, checkin_id, community_id, point_id,
           title, description, photos JSONB,
           reporter_id, assignee_id, priority,
           status,      -- pending/assigned/processing/review/closed/rejected
           fix_photos JSONB, fix_remark,
           finished_at, reviewed_by, review_remark, created_at)

work_order_log(id, order_id, action, operator_id, detail, created_at)  -- 流转留痕
```

关键索引：`checkin_record(task_id)`、`checkin_record(inspector_id, checkin_time)`、`inspection_task(task_date, status)`、`work_order(status)`；`sys_operation_log` 按月分区或定期归档。

## 八、部署与运维

- **起步配置**：1 台 4C8G 云服务器（Go 应用 + PostgreSQL + Redis + Nginx，Docker Compose 编排）+ OSS/COS 对象存储，日活几十人规模足够；后续可平滑拆分。
- **备份**：PostgreSQL 每日 `pg_dump` 全量备份到 OSS，保留 30 天；OSS 照片开启版本控制防误删。
- **安全**：全站 HTTPS；JWT + Redis 会话，密码 bcrypt；接口按 RBAC 中间件鉴权；操作日志全量留痕；小程序照片 URL 私有读 + 签名防盗链；SQL 全部走 GORM 参数化防注入。
- **监控**：服务健康检查 + 日志（zap 结构化日志，按天滚动），接口异常告警到企业微信。
- **成本估算**（按 10 个小区、30 名巡检员、日均 500 张参考）：云服务器约 ¥200–400/月，OSS 存储+流量约 ¥50–100/月——整体年运维成本在 ¥5000 以内。

## 九、验收标准（上线即按此验收）

1. 点位同时支持二维码与 GPS 围栏，打卡方式按点位可配且校验生效；
2. 打卡照片为现场拍摄且带水印（时间、坐标、点位、姓名），无法使用相册照片；
3. 后台任务监控可实时看到每个任务点位覆盖情况，缺卡点位明确标识；
4. 打卡记录可按人/小区/时间检索并查看照片原图；
5. 异常上报自动生成工单，派单→处理→复核→关闭全程留痕；
6. 无网络环境打卡可在恢复网络后自动补传，且保留原始时间；
7. 月度巡检报表可一键导出 Excel/PDF；
8. RBAC 权限生效：不同角色登录后台仅看到权限范围内的菜单与按钮，数据权限按小区隔离；
9. 系统管理五件套（用户/角色/菜单/字典/参数）全部可用，操作日志完整记录。
