# 管理后台信息架构与菜单归位方案

> 版本：v1.0（已确认）
> 关联文档：《多租户组织架构与角色权限设计方案》
> 背景：多租户改造（P3）完成后，后台出现"平台级/租户级功能混放、岗位写死、公章全局共用、兼容代码堆积"四类问题。本方案定信息架构与命名，并给出清理与归位清单。

---

## 一、总规则：谁用，就放谁那

整个后台只有三个层级，判断任何功能归属只问一句：**这是平台的事、公司的事、还是项目的事**。拿不准往下一级放（能租户自管的绝不收到平台）。

| 层级 | 谁用 | 放什么 |
|---|---|---|
| **平台管理** | 超管（平台运营方） | 整个平台级：租户管理、菜单管理、字典管理、系统配置、品牌官网、岗位模板库 |
| **系统管理** | 租户管理员（物业公司） | 本公司内部：用户管理、角色管理、岗位管理、签章管理、日志管理、通知公告、企业品牌 |
| **业务模块** | 项目人员 | 项目内：小区（含编制）、点位、计划、任务、工单、统计、月报 |

- 命名原则：**菜单名起给天天用的人看**。租户管理员日常看到的"系统管理"就是他公司的系统管理（与通用后台一致，零迷惑）；超管看到的"平台管理"即平台级全局视角。真正平台级的配置（菜单/字典/系统配置/官网）全部在平台管理目录，租户可见的"系统管理"里没有语义冲突。
- 技术上设"平台级菜单"标记（is_platform）：平台管理目录仅超管可见可授权；tenant_admin 只有系统管理 + 业务模块。
- 私有化部署 = 单租户，超管两组都可见，体验与无租户一致。

## 二、租户上下文：超管进入系统管理的语义

**平台管理是站在平台上看全局，系统管理与业务模块是站在某家公司里看内部。**

- 租户上下文对超管**全局生效**：除"平台管理"目录是平台全局视角外，超管在后台的一切页面（系统管理 + 小区管理 + 巡检/工单/统计等业务模块）都处于同一租户上下文中——默认默认租户，Layout 头部全局切换器；切到哪家公司，整个后台看到和操作的就是哪家公司的数据；
- 租户管理员上下文锁死本租户，不显示切换器；私有化（仅默认租户）不显示切换器；
- 实现：前端 store 持久化当前上下文，超管请求统一携带 `X-Tenant-Id` 头（或 `?tenant_id=`）；后端非超管强制覆盖为本人租户，超管取上下文值（缺省默认租户）；列表查询与 CheckCommunity/ApplyCommunityFilter 均按上下文租户过滤（超管不再是"全平台不过滤"）。
- 不做"全平台混合列表 + 每页各自筛选"（归属歧义、创建类操作无法落租户）。

## 三、岗位管理（核心新功能）

岗位定义与岗位使用分离：

| 概念 | 位置 | 内容 |
|---|---|---|
| 岗位模板库 | 平台管理 | 平台维护的模板岗位 + 平台默认槽位绑定，**只读于开通租户那一刻**，仅作初始拷贝源，不参与任何租户的实际业务 |
| **岗位管理** | 系统管理 | 本租户岗位（扁平结构 + `line` 业务线字段：安全/工程/环境/客服/综合，页面按业务线分组展示，**不做 parent_id 树**）、是否主管级、**岗位绑角色**、本租户**职责槽位默认绑定** |
| 项目编制 | 小区管理（不动） | "某人在某项目任某岗"，项目语境的人事安排；项目级槽位覆盖照旧 |

规则（最终决策）：

- `post_dict` 租户化：**开通租户时从模板库整份复制**（含 code/业务线/is_supervisor/role_id 绑定/平台默认槽位绑定），此后租户自管，模板后续修改不影响老租户；
- **岗位绑角色 = 有效角色实时并集，不落库**：用户实际持有角色 = 用户管理手动分配的角色 ∪ 其全部在职岗位绑定的角色（buildIdentity 登录态构建时实时计算）。配岗即得权限、离岗即失权限，无残留无回收难题；功能权限仍只由角色定义，岗位只是角色的一个来源；数据范围上限按并集"取最宽"走现有规则。管理员标准动作简化为：建账号 → 配岗位，权限自动正确，手工角色仅是特殊微调；
- 职责槽位仍是系统固定枚举；默认值三级回落：项目级覆盖 → 租户默认 → 平台默认；
- is_supervisor 语义不变（数据范围推导用）。

## 四、签章管理：租户隔离（修复）

- 现状：sign_asset.tenant_id 列已有（v20），但查询全部忽略它——**公章实际全局共用一枚，是 bug**；
- 修复：签章所有查询按当前租户上下文过滤；公章 active 按租户取；个人签名仍按人（owner_id）不变；
- 页面留在系统管理（各公司管自己的章）；历史报告快照（seal_file_key）不受影响。

## 五、菜单归位明细

| 菜单 | 归位 | 说明 |
|---|---|---|
| 租户管理 | **平台管理** | 超管专属 |
| 品牌官网 | **平台管理** | 安巡云产品门户，平台级 |
| 菜单管理 | **平台管理** | 菜单树全平台共享，tenant_admin 不可见 |
| 字典管理 | **平台管理** | 平台字典（租户字典后续按需） |
| 系统配置 | **平台管理** | 平台级参数 |
| 岗位模板库 | **平台管理（新增）** | 模板岗位 + 平台默认槽位绑定 |
| 用户/角色管理 | **系统管理** | 按租户隔离 |
| 岗位管理 | **系统管理（新增）** | 见第三章 |
| 签章管理 | **系统管理** | 补租户过滤 |
| 日志管理 | **系统管理** | 补租户过滤（sys_login_log/operation_log 需 tenant_id） |
| 通知公告 | **系统管理** | 补租户过滤（sys_notice 已有列） |
| 企业品牌 | **系统管理** | 原"租户品牌"改名 |

## 六、兼容性清理清单

原则：开发阶段不留代码级兼容兜底；实体标签（已打印的张贴物）的物理兼容保留。

**删除**：

- 工单旧端点 `/assign`、`/review`、`/accept`（PC + App 管理端双份）及 AssignReq/ReviewReq DTO、ActionAccept 常量；
- 工单 detail 响应 fix_*/review_* 别名键（含 mp_service review_remark 兼容键）、前端时间线旧动作别名映射；
- `community_ids` 兼容输出（system/auth/mp DTO 与填充点、StaffProjectIDs）+ 数据库列（00018 误加回，新迁移彻底 DROP）；App/小程序同步改用 projects 语义字段；
- `report:sign:supervisor` / `report:sign:manager` 权限点（菜单 seed、角色绑定、authz 测试用例）；
- sys_user.user_type 半退役字段收敛（保留则收敛取值，优先删列）；
- 计划周期 days/monthdays 双键兼容（保留一种）；
- 字典 user_type 旧值（inspector/repair）。

**保留**：NFC 小写兼容、扫码内容归一（已张贴实体标签的物理兼容，删除会导致现场标签失效）。

**迁移史**：择机将 00001–0002x squash 为单一基线迁移（开发期一次性操作，prod 基线化一次）。
