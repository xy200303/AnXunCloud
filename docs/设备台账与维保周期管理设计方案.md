## 1. 背景与需求

甲方（武汉一品行物业）提出灭火器维保管理需求，原始诉求：

1. 干粉灭火器出厂满 5 年首次维修充粉，之后每 2 年换药充粉一次。
2. 每次完成换药维修，要做好检查登记，把维修换药时间录入管理系统。
3. 录入之后 2 年内该灭火器视为维修合格，日常月度巡检不需要每次都核对换药日期。
4. 系统设置时间阈值，到期自动弹窗提醒，督促再次充粉维修。

经讨论，需求泛化为**通用设备台账 + 维保周期管理**：灭火器是第一个设备类型，消火栓、水泵、电梯、配电柜、烟感等后续可零代码接入。

**首要设计约束（甲方明确）**：日常巡检零新增动作——不要求巡检员每天/每次例行拍标签；只有在换粉登记、台账数据缺失、到期核验、随机抽查命中时才需要特别拍一下。

分工原则（与甲方确认）：

- **巡检员**（小张）：执行换粉后的维保登记（一键+一拍）、抽查时拍日期标签并确认日期——现场干活的人
- **物业经理/安全主管**（严勇）：确认维保登记（AI 预筛后批量秒批）、接收逾期升级提醒、处理比对异常、台账管理——督促的人，不做数据录入

**核心信任设计**：登记人（巡检员）与登记受益人（此后 2 年免检）是同一人，因此**维保登记必须经经理确认才生效**——防止"自己登记、自己受益、低概率被查"的闭环漏洞（评审结论，一期必做）。

## 3. 总体设计

### 3.1 核心抽象：设备类型驱动

设备类型走字典 `equipment_type`，每种类型携带规则参数：

- **首次维保月数**（可空）：出厂/启用后首次维保的期限
- **维保周期月数**：首次之后的固定维保周期
- **启用催办**（开关）：灭火器=true；电梯等外包合同驱动型设备=false（只记录不催办，避免无意义提醒）

示例：

| 类型 | 首次维保 | 周期 | 催办 | 说明 |
|---|---|---|---|---|
| 干粉灭火器 | 60 个月 | 24 个月 | 是 | 5 年首保 + 之后 2 年（甲方规则） |
| 消火栓 | （空） | 12 个月 | 是 | 年度检测 |
| 电梯 | （空） | 1 个月 | 否 | 维保公司按月上门，只记录 |

单个设备允许**人工覆盖下次到期日**（二手设备、维保合同差异等），规则只负责计算默认值。

**一点两具聚合规则**：一个灭火器点位常放 2 具（消防标配），台账按具登记、点位可关联多具；检查项自动判定取**最差**（任一关联设备逾期则该项异常），抽查按系统指定设备编号逐具采集。

规则参数存放方式：**字典扩展**（约定值），一期不做单独配置界面——见「确认事项」第 3 条。

### 3.3 设备与点位的关联逻辑

**关联模型**：`equipment.point_id` 多对一（一具设备某一时刻只在一个物理位置；一个点位挂多具），"点位有哪些设备"按 point_id 反查，不设中间表。设备关联是打卡时实时反查的（任务只快照点位名单），**改绑后下一次打卡立即按新关联生效**，无历史快照污染。

**建立关联的四种方式**：

1. **后台设备表单**：小区 → 楼栋 → 点位级联选择器
2. **Excel 导入**：点位列填二维码编号（如 P053202）或"楼栋+点位名"，导入时自动绑定；找不到留空并在结果中提示——初始批量建台账主路径。**日期列允许为空**：初始数据不全时先导入骨架，首轮巡检通过「台账补录」触发器自动补齐日期（冷启动双腿路径）。v1.8 起另支持**自动推理绑定**（见下）

**导入自动推理绑定**（v1.8，戎安台账实测驱动：864 行消防设备中约 102 行唯一匹配）

- 归一化（两侧共用）：全角数字/字母转半角、去空白
- 楼栋键：`(数字)+栋/号楼/#楼/#` → "b{n}"（"11栋"整体捕获为 11，不被"1栋"误匹配；前导零归一）；含「车库」关键词 → "b车库"（仅当小区存在同名楼栋才可能命中）
- 楼层键：架空层→0；负n/Bn 楼/层→-n；n 楼/层/F→n（F 后紧跟英文字母视为型号跳过）
- 设备文本优先级：安装位置 → 管控区域 → 设备名称 → 机房名称，取第一个同时解析出楼栋+楼层的；多段范围（"1-5栋楼道"）保守跳过
- 点位键：楼栋取点位所属楼栋名称归一化（无楼栋信息时从点位名解析），楼层从点位名解析
- **安全规则：恰好 1 个候选点位才绑**（0=无对应、>1=歧义，都跳过）；只填 NULL 的 point_id（绝不动人工已绑）；building_id 为 NULL 时顺带填上；幂等重导的更新路径同样只补 NULL
- 结果带 auto_bound 计数（歧义/无对应不逐条报）
3. **App 扫码绑定**（现场零星补录）：扫点位二维码 → 该点位已关联设备列表 →「添加设备」自动带出点位绑定，可顺手拍钢印由 AI 读出生产日期回填——显著降低初始台账建设成本
4. **改绑**：设备挪位置时编辑重新关联，操作日志留痕（谁、何时、从原点位解绑）

**边界规则**：

- **类型软校验**：点位类型与设备类型有映射（fire_extinguisher↔灭火器、fire_cabinet↔消火栓等），不匹配时警告不拦截（现实混挂常见）
- **点位删除**：存在关联设备时提示并自动解绑（point_id 置 NULL），设备台账保留；点位停用不影响关联
- **未关联点位的设备**：台账/到期判定/提醒照常工作（按自身 next_due_date），只是不参与打卡检查项判定与抽查比对

**展示面**：

- 后台：点位详情新增「关联设备」tab（编号 + 状态灯 + 到期日）；台账列表点位列可点击互跳
- App：扫码结果/点位详情展示关联设备完整列表（编号 + 红黄绿状态灯）

### 3.4 到期判定（统一纯函数）

台账落库后，判定只看 `next_due_date` 一个字段：

- **正常**：next_due_date - today > warn_days
- **临期**：0 ≤ next_due_date - today ≤ warn_days
- **已逾期**：next_due_date < today

阈值优先级：设备 warn_days > 类型配置 > 全局 `equipment.expire_warn_days`（默认 30 天）。

### 3.5 台账有效期自动判定（绑定即启用 + 逐台独立）

> v1.6 重构：**废弃「模板内置项触发」与「一点多具取最差聚合」**。新模型：点位绑了台账设备就自动生效（绑定即启用），每台设备独立一条判定（逐台独立）。模板侧的「台账有效期」选项已撤下，保存模板项时后端拒绝 equipment_validity / equipment_date_spot 两种类型（打卡记录历史快照仍可能带这两个类型，判定类型白名单保留识别）。

**`equipment_validity` 台账有效期（系统内置判定类型）**

- **触发：绑定即启用**。任务详情组装时按点位查询绑定的在用设备（一次 IN 批量查，无 N+1），有设备的点位在检查项末尾**逐台注入合成检查项**，无设备则不出现——与模板是否配置完全无关
- **参与范围：仅启用催办的设备类型**（与 equipment_expire job 同口径，类型规则 `Remind` 标志）。零值规则类型（导入自动扩充的 custom_N，如公告栏/门禁等纯台账设备）即使绑定了点位也**不注入合成项**——不产生「台账补录」噪音，守住日常巡检零新增动作原则；甲方在字典里给该类型配上周期规则后自动开始参与
- **合成项结构**：`name` 带设备名称/编号（如「设备维保·1栋1楼灭火器（MFZ-001)」），`judge_type=equipment_validity`，`judge_config` 携设备快照 `{equipment_id, equipment_no}`（逐台去重键控与后续抽查比对用），`photo_required=none`，`auto_judge` 挂**该设备自己**的判定 `{status, next_due_date, warn_days, overdue_days, has_pending_register, show_register, equipment_id/code/name}`
- **逐台状态**（每台独立计算）：
  - 正常（normal）→ 绿色「台账有效（至 xxx）」
  - 临期（warning）→ 黄色「将于 N 天内到期」，带登记入口
  - 逾期（overdue）→ 红色「已逾期 N 天」，带登记入口
  - 无数据（no_data：next_due_date 为空无法判定）→ 灰色「台账数据缺失，请补录」，带补录入口（台账补录走 §3.6 同一确认链）
  - 有待确认登记（has_pending_register）→ 叠加「已登记待确认」标记
- **打卡提交**：客户端不为合成项提交结果（App 只读展示、提交时跳过）；服务端按点位实时逐台判定，自动往打卡记录**逐台追加快照项**（每台一条 checkin_record_item）。任何一台首次逾期 → 该项 pass=false 且**记录级强制 abnormal 转人工审核**（不被 AI 结论放行）；合成项不走 AI 识别、不要求照片
- **逾期重复异常逐台去重**（按 equipment_id 键控，互不影响）：设备首次逾期打卡产异常并进审核队列；同一设备持续逾期的后续打卡只标「维保逾期·催办中」（pass=true，不再产新异常，防审核队列刷屏）；pending 登记中的设备标「已登记维保待确认」；确认后恢复全绿
- **登记入口逐台内嵌**：临期/逾期设备各自的合成项带「已完成维保？登记」按钮（跳登记页带该设备上下文），无数据设备带「台账补录」入口——工作流内闭环
- 月报中该项统计需**标注判定来源**（系统判定/人工判定），过渡期两种口径并存时报告说得清

**`equipment_date_spot` 日期标签抽查（事中抽查，v1.7 已实现）**

- 触发配置放**设备类型规则/全局配置**（已实现：类型字典 attrs 加 `spot_ratio`（%，>0 覆盖全局），全局 `equipment.spotcheck_enabled`（总开关）/`equipment.spotcheck_ratio`（默认 10）/`equipment.spotcheck_salt`（部署随机，00046 补 seed））；不进模板、不占模板项
- 触发后注入合成项（每台一条，紧跟该设备的有效期项）：`name`=「标签抽查·名称(编号)」、`judge_type=equipment_date_spot`、`photo_required=required`（必拍 1 张）、两个日期字段（生产日期/维修日期，可选「无贴纸」）+「标签缺失」选项；触发即必交（服务端按任务上下文重算触发，缺交阻断打卡）
- 台账长期未验证（超 6 个月无 confirmed 维保且无通过抽查快照）概率翻倍（cap 100）；label_missing 设备不参与抽查（已走异常通道）
- 触发机制（双触发器，服务端在任务详情组装时判定）：
  - **到期核验**：设备临期/逾期的点位打卡时必触发（实物证据核验，防"台账说换了粉但瓶上还是旧贴纸"）
  - **随机抽查**：按比例按**确定性哈希**判定——`hash(任务ID + 点位ID + 日期) % 100 < 比例`；同任务同点位同日结果固定，刷新躲不掉；哈希盐值存 sys_config 防推算；台账长期未验证（超 N 个月）的设备概率自动上调
- 触发后该项为**必拍 + 必填日期**：采集两个字段——生产日期（瓶体钢印）+ 维修日期（贴纸，无贴纸选"无"）
- **AI 辅助 + 巡检员确认**（复用 metric 类成熟链路）：AI 读标签建议日期回填，巡检员现场目视核对——读对点确认、读错手改；提交值为巡检员确认值，责任在巡检员
- 未触发时该项不出现（打卡表单与平常无异）
- 隐藏收益：抽查项是天然的**防补拍机制**——补拍的人无法站在灭火器跟前读标签

**「拍标签」统一动作模型**：台账补录 / 换粉登记 / 到期核验 / 随机抽查四种触发对巡检员呈现为**同一个动作形态**（拍照 + AI 读数回填 + 现场确认，约 10 秒），他无需区分触发原因；差异只在服务端后续动作（回写台账 / 追加维保流水 / 只比对）。

### 3.6 维保登记：一键 + 一拍 + AI 预检 + 经理确认

**巡检员侧（打卡现场，约 15 秒）**：

1. 触发触点（两处）：打卡时"台账有效期"项逾期/临期显示「已完成维保？登记」按钮；或今日任务页「维保待办」卡片
2. 点一下 → 日期自动填当天（可改）→ **拍一张新维修标签照片**（必传）→ 提交
3. 维保单位/备注全部选填；提交后状态 `pending`，该设备提醒暂停催办但台账暂不更新

**AI 预检（提交时自动执行，输出 pass/review 结论）**：

1. **读日期回填**：读标签日期自动填登记日期（巡检员确认/修改）；日期格式按**年月粒度**归一化（钢印格式五花八门，按日比对会误报）
2. **照片有效性预检**：判断"像不像维修标签"（拍天花板/旧标签/翻拍屏幕/全黑模糊 → review）；**只标记不拦截**——AI 看错常见，照片糊了允许手填日期照常提交进存疑队列
3. **交叉核对**：标签日期 vs 登记日期不一致 → review；钢印生产日期 vs 台账 manufacture_date 不一致 → review（登记环节顺带防换设备）；EXIF 拍摄时间偏差超阈值 → review（复用 suspectCheck 口径）

**经理侧（确认页，约 3 秒/条）**：

- 确认列表按 AI 结论排序：**review 置顶标红重点看，pass 可批量秒批**
- 确认 → 台账生效；驳回（填理由）→ 巡检员收通知重新登记
- 信任链：巡检员登记（人证）→ AI 预检（机审）→ 经理确认（人裁）→ 10% 抽查（兜底），造假需连过四关

### 3.7 抽查比对规则（v1.7 已实现，提交时后端一次性动作）

抽查项确认的两个日期与台账交叉核验，外加实物独立判定：

| # | 比对 | 不符说明 |
|---|---|---|
| 1 | 瓶体生产日期 vs 台账 `manufacture_date`（年月容差） | 设备被私自更换，台账未跟上 |
| 2 | 维修贴纸日期 vs 台账 `last_maintenance_date`（年月容差） | 换粉漏登记，或假登记 |
| 3 | 瓶上无贴纸 vs 台账存在维修记录 | 假登记实锤 |
| 4 | 实物日期独立推有效期：贴纸日期+2年（无贴纸则生产日期+5年）≥ 今天？ | 实物已超期——即使台账被做假也骗不过瓶体钢印，终极兜底 |

任一不符 → 打卡记录标异常 → 进经理审核队列（v1.7 实现：该项 pass=false + 记录级强制 abnormal 转人工，不被 AI 放行；勾选「标签缺失」→ 直接强制异常进审核等经理处置）。

**关键原则：抽查只核对、不写台账。** 比对不符有两种性质（巡检员填错 / 台账漏登），须经理人工裁决：填错 → 打回纠正打卡记录；漏登 → 督促补走维保登记。

实现口径（v1.7）：日期一律**年月粒度**容差（钢印格式五花八门）；规则 4 的周期取类型规则 cycle_months（无贴纸取 first_months，缺省 24）；点位未挂台账设备时天然不出现抽查项（绑定即启用模型）；比对快照（现场提交值+结论）存 checkin_record_item.judge_config 留证。

### 3.7.1 标签缺失逃生通道（v1.7 新增）

现场钢印磨损/铭牌缺失、什么日期都读不到时，补录/抽查流程不能卡死巡检员：

- **登记/补录加「标签缺失」标志**：勾选后日期免填，**照片仍必传**（拍设备本体作证），提交照常进确认链（equipment_maintenance.label_missing 随单暂存）
- **确认通过** → 设备打 `label_missing=true`：退出自动到期判定与抽查（打卡合成项/到期提醒/抽查触发均跳过），台账列表可筛选「标签缺失」（灰色虚线状态灯）
- **经理处置两出口**（现有能力组合，无新流程）：① 更换设备——旧设备停用/报废 + 新建设备建档；② 后台代登记——经理凭纸质记录用 admin 维保登记接口补日期（确认链留痕），确认后**清除标记**恢复正常判定
- 正常登记/补录（非标签缺失）确认后同样清除标记（覆盖设备换过标签的场景）
- 标签缺失登记的 AI 预检只跑照片有效性（无标签可读日期）

### 3.8 到期提醒与升级链（v1.7 含报废催办）

报废催办链（v1.7 已实现）：设备 `scrap_date <= today` 且在用户 → 报废提醒（巡检员+项目管理员）+ 升级 tenant_admin（督促口径），消息类型 `equipment_scrap`，重复节奏复用 `equipment.overdue_remind_interval_days`；应报废设备在打卡逐台判定中**视同逾期**（每次强制异常，不去重——用报废设备本身即违规）；更换设备后提醒自然消失。标签缺失设备不参与任何自动提醒。



**Scheduler 新 job `equipment_expire`**：每日 08:00（可配）扫描启用催办类型的临期/已逾期设备。

| 阶段 | 通知谁 | 方式 |
|---|---|---|
| 临期（warn_days 内） | 巡检员 | 推送 + 站内消息 + 今日任务页"维保待办"卡片，只提醒一次 |
| 到期 ~ 逾期 N 天（默认 7） | 巡检员 | 待办卡片持续挂红，每周推送一次 |
| 逾期 N 天以上 | 巡检员 + **物业经理（升级）** | 双方都推；经理侧文案为"督促" |

补充规则：设备存在 `pending` 维保登记时暂停催办（已登记待确认，不该再催）；被驳回后恢复催办。

防打扰：临期每台设备每周期只提醒一次（`last_notified_at`）；App 启动弹窗每天最多一次（本地记日期）。

### 3.9 App 端交互

**巡检员（执行人）**

- 今日任务页顶部「维保待办」红色卡片（逾期/临期台数 + 最早逾期天数），混在日常工作流
- 维保登记主入口在**打卡现场**（§3.6）；待办卡片 → 台账页（自动筛待维保）为备用入口
- 登记被驳回时收通知，附理由，可重新登记
- 启动弹窗（自绘 UI，每天一次）：待维保台数 + [去处理]/[知道了]
- 权限：授 `equipment:list` + `equipment:maintenance`；新增/删除/报废等管理操作不可见

**物业经理/安全主管（督促人）**

- 入口：「我的 → 管理功能 → 设备台账」（按权限显隐，挂逾期数角标）
- 台账页：类型 tab（字典驱动）+ 状态筛选 + 红黄绿状态灯 + 到期日/逾期天数/报废日期
- 设备详情：出厂日期、最近维保、到期日、维保历史时间线（含照片凭证、确认状态、AI 结论）
- **维保确认页**：pending 列表（review 置顶），批量确认/驳回
- 接收逾期升级推送与弹窗；处理抽查比对异常（审核队列）
- 临期不打扰经理，逾期未处理才升级

**扫码联动（一期顺手做）**：扫点位二维码后，点位信息展示关联设备的有效期状态（纯展示不阻断）。

**边界**：App 只做查看 + 维保登记/确认 + 接收提醒；批量导入、新增、删除、报废留后台 PC 端。

## 4. 分期实施

**一期（本方案主体，约 2.5–3 天）**

- 后端：equipment 模块（模型 + 迁移 + CRUD + 导入导出）、维保登记 + **确认链**（含 AI 预检）、equipment_expire 定时 job、提醒与升级链
- 检查项：`equipment_validity` 内置类型（台账自动判定 + 内嵌登记入口）
- 后台：设备台账页 + 维保确认列表（v1.6 起模板编辑器无新增类型，绑定即启用）
- App：台账查看 + 打卡现场一键登记 + 维保确认 + 维保待办卡片 + 提醒弹窗

**二期（按需启动）**

- `equipment_date_spot` 抽查类型（确定性哈希触发 + AI 读日期 + 三重比对）——依赖台账积累数据后更有价值
- 打卡页设备临期提示增强、月报纳入设备到期统计、报废催办链

## 5. 不做的事（防止过度设计）

- 多级维保计划模板、维保工单流转审批、备件库存管理——属 EAM 范畴，有付费需求再议
- 设备类型规则的独立配置界面（一期走字典扩展）
- 台账侧记录"被抽查次数"统计（一期比对结果只记在打卡记录快照上）
- 报废自动催办（一期仅展示报废日期）

## 6. 确认事项（开发前需拍板）

1. **台账粒度**：按「具/台」登记（每具灭火器一个编号）——甲方现有台账是按具还是按点位？
2. **初始数据**：甲方是否有现成设备台账 Excel？是否含生产日期（决定防换设备比对一期是否可用）？是否含点位对应关系（决定导入自动绑定的可行性）？
3. **类型规则存放**：字典扩展（约定填法，一期推荐）vs 独立配置表带界面？
4. **提醒提前量与升级天数**：临期默认 30 天、逾期 7 天升级经理，是否合适？
5. **抽查未触发时的体感**：抽查项完全不出现（推荐）vs 显示"本次未抽中"？
6. **提醒接收人范围**：巡检员按当前任务执行人确定，是否需要支持按小区指定维保责任人？
7. **经理确认是否愿意承担**：登记确认环节每天约几秒批量操作——需向甲方说明这是防造假的关键一环

## 7. 风险与备注

- 不触碰现有打卡主流程，新模块独立挂载；两个内置判定类型走 judge_type 扩展体系，风险低
- 租户隔离沿用 `TenantScopeOrDefault` / `CheckTenantRow` 既有口径
- 设备编号租户内唯一约束，导入时同编号按更新处理（幂等可重导）
- **登记-免检闭环风险已通过确认链封堵**（评审结论）：登记人=受益人的场景下，无确认的登记等于开 2 年免检后门
- AI 预检只做标记不做闸门：照片质量差不应卡死正常登记，存疑交人裁
- 日期比对一律按年月粒度（钢印格式不统一），防止误报淹没真实异常
