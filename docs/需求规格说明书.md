# 物业巡检管理系统 需求规格说明书

> 版本：v1.0
> 状态：已评审基线（依据《物业巡检管理系统方案 v1.1》《UI-UX 设计方案 v1.0》编写，功能范围以方案文档为准）
> 技术栈：微信小程序（原生）+ Vue3/Element Plus 管理后台 + Go（Gin + GORM + PostgreSQL + Redis）
> 读者：产品、开发、测试、运维及物业公司验收人员

---

## 1. 引言

### 1.1 目的

本文档定义物业巡检管理系统的全部功能性需求与非功能性需求，作为开发实现、测试用例编写、上线验收的唯一依据。每条需求均含可测试的验收标准，测试人员可直接将其转化为测试用例。

### 1.2 项目背景

物业公司巡检员目前采用纸笔记录 + 手机手动拍照的方式完成小区点位巡检，存在记录易丢失、照片与点位时间对不上、无法确认巡检员是否真实到场、异常问题无闭环等问题。本系统通过"微信小程序打卡拍照 + Web 管理后台监控管理"，形成"任务 → 执行 → 异常 → 整改 → 复核"的完整闭环。

### 1.3 范围

**本期范围内**：

- 微信小程序巡检端：登录、今日任务、二维码 + GPS 围栏双模式打卡、强制现场拍照与水印、必拍项校验、异常上报、离线补传、历史记录、消息通知、我的工单。
- Web 管理后台（侧边栏式）：工作台、巡检管理（点位/计划/任务监控/巡检记录）、异常工单、统计分析、小区管理、系统管理（用户/角色/菜单/字典/参数/通知公告/日志）、个人中心。
- Go 后端：RESTful API、RBAC 鉴权、照片对象存储链路、计划任务生成引擎、防作弊校验、报表导出。

**本期范围外（方案明确预留、不实现）**：

- 智能巡检硬件（蓝牙信标、AI 图像识别）接入；
- 业主端小程序；
- 巡检轨迹全程记录与电子巡更报表；
- 企业微信/钉钉组织架构打通；
- PostGIS 复杂地理分析（PostgreSQL 可预留扩展）。

### 1.4 术语表

| 术语 | 定义 |
|---|---|
| 点位 | 小区内需要巡检的具体位置（如配电房、消防栓），配置二维码 + GPS 围栏 + 打卡方式 + 必拍项 |
| 巡检路线 | 一次巡检中点位组成的有序列表（`inspection_plan.point_ids`） |
| 巡检计划 | 按周期（每天/每周/每月）自动生成巡检任务的规则定义 |
| 巡检任务 | 计划在某具体日期为某巡检员生成的一次执行实例，状态：pending/doing/done/overdue |
| 打卡 | 巡检员在点位通过扫码或 GPS 围栏方式确认到场并提交现场照片的动作 |
| credential / require_fence | 点位打卡校验的两个独立维度：`credential` 点位凭证 `qrcode`（扫码）/ `nfc`（NFC 卡）/ `any`（任一，扫码或 NFC 匹配其一即可）/ `none`（免凭证）；`require_fence` 是否要求 GPS 在围栏内。两者至少启用一项，同时启用则都须通过 |
| 围栏 | 以点位坐标为圆心、`fence_radius` 为半径（默认 100m，可配 50–500m）的圆形地理范围，坐标系 GCJ-02 |
| 必拍项 | 点位配置的必须拍摄对象清单（如配电箱、消防栓），少拍不得提交 |
| 疑似作弊 | 打卡坐标与点位距离超出围栏阈值等触发服务端标记（`is_suspect`）的记录 |
| 离线补传 | 无网络时本地暂存、恢复网络后自动上传的打卡数据，保留客户端原始时间戳 |
| 异常工单 | 巡检员上报异常后自动生成的处理单据，状态机：pending → assigned → processing → review → closed（可 rejected 驳回） |
| RBAC | 基于角色的访问控制：用户 → 角色 → 菜单权限 + 按钮权限 + 数据权限（按小区隔离） |
| 数据权限 | 角色级数据范围：`all`（全部小区）或 `custom`（指定小区集合） |
| 系统管理五件套 | 用户管理、角色管理、菜单管理、字典管理、参数配置 |
| STS | 对象存储临时安全凭证，用于小程序照片直传 OSS/COS |
| 水印 | 服务端叠加在打卡照片上的防篡改信息：点位名称、时间、GPS 坐标、巡检员姓名 |

### 1.5 需求编号与优先级约定

- 编号格式：`REQ-<模块>-<序号>`，模块前缀：`MP` 小程序端、`DB` 后台-工作台、`INS` 后台-巡检管理、`WO` 后台-异常工单、`STA` 后台-统计分析、`COM` 后台-小区管理、`SYS` 后台-系统管理、`NF` 通用/非功能。
- 优先级：**P0** 上线必须（缺则不可验收上线）；**P1** 重要（上线后首个迭代内补齐）；**P2** 可后置（不影响主流程，后续版本实现）。

## 2. 角色定义

| 角色 | 使用端 | 职责与能力 | 开通方式 |
|---|---|---|---|
| 超级管理员 | Web 后台 | 全部功能 + 系统管理（用户/角色/权限/参数/日志）；数据权限为全部小区 | 系统初始化内置 |
| 物业主管 | Web 后台 | 制定巡检计划、查看所辖小区执行情况、派单、审批复核整改；数据权限按小区隔离 | 后台开通账号 |
| 巡检员 | 微信小程序 | 接收任务、到点打卡、强制拍照、上报异常、整改后复拍、查看个人历史 | 后台开通账号并绑定微信 |
| 维修人员（可选角色） | 微信小程序 | 接收派单、处理异常工单、上传维修结果照片 | 后台开通账号并绑定微信 |

权限约束：巡检员与维修人员**无** Web 后台访问权；后台用户与小程序用户共用 `sys_user` 表，通过 `openid` 是否绑定及登录入口区分。

## 3. 整体业务流程

### 3.1 主流程：日常巡检闭环

1. 物业主管在后台维护小区/楼栋/点位（生成并张贴二维码），创建巡检计划（周期 + 路线 + 巡检员 + 执行时段）。
2. 系统按计划周期每日自动生成巡检任务（定时任务，Redis 分布式锁防重复生成）。
3. 巡检员打开小程序"今日任务"，按路线顺序执行：到点 → 扫码或围栏校验 → 强制现场拍照（含必拍项）→ 提交打卡。
4. 服务端记录打卡（服务端时间 + 客户端原始时间 + 坐标 + 距点位距离 + 照片），实时更新任务进度；若结果选择"异常"，自动创建异常工单。
5. 主管在后台任务监控实时查看各任务点位覆盖（已打卡/跳过/未打卡）与疑似作弊标记；在异常工单模块派单给维修人员。
6. 维修人员处理并上传维修结果照片 → 主管复核：通过则关闭工单，驳回（必填原因）则退回处理中。
7. 统计分析模块按周期生成覆盖率/及时率/异常率与绩效报表，支持导出 Excel/PDF 供业委会/甲方存档。

### 3.2 离线场景流程

巡检员在无信号区域（如地下车库）执行打卡 → 数据（含照片）本地暂存并显示离线横幅 → 网络恢复后自动批量补传 → 服务端标记 `checkin_type=offline` 并保留 `client_time` 原始时间，防作弊规则照常生效。

### 3.3 任务状态流转

```
任务：pending(待开始) → doing(进行中，首次打卡触发) → done(全部点位完成)
      pending/doing 超过 task_date 结束且未完成 → overdue(已逾期)

工单：pending(待派单) → assigned(已派单) → processing(处理中) → review(待复核)
      review --复核通过--> closed(已关闭)
      review --复核驳回(必填原因)--> processing
```

## 4. 功能需求 — 小程序端（REQ-MP）

### 4.1 登录与账号

**REQ-MP-001 微信授权登录（P0）**

- 描述：巡检员/维修人员通过微信 code 换登录态（`POST /api/mp/login`），无需注册；账号须由后台预先开通并完成微信绑定。
- 业务规则：
  - 首次使用：微信授权获取 openid 后，若该 openid 未绑定任何账号，进入手机号绑定页，输入手机号 + 验证码/后台预置校验完成绑定；
  - 账号被停用（`sys_user.status` 禁用）时登录拒绝并提示"账号已停用，请联系管理员"；
  - 登录态采用 JWT（access + refresh），access 过期后静默刷新，refresh 过期需重新授权。
- 验收标准：
  1. 已绑定账号的微信进入小程序，可自动完成登录并进入今日任务页；
  2. 未绑定的微信登录时进入手机号绑定流程，绑定成功后自动登录；
  3. 使用未在后台开通的手机号绑定时，提示账号不存在且无法进入系统；
  4. 后台停用某账号后，该账号再次进入小程序被拒绝并显示停用提示；
  5. 模拟 access token 过期，接口请求可自动续期，用户无感知。

### 4.2 今日任务

**REQ-MP-002 今日任务列表（P0）**

- 描述：首页按日期展示当前用户当日全部巡检任务（`GET /api/mp/tasks/today`），卡片含小区名、点位进度（已检 x/y）、要求执行时段、状态标签（待开始/进行中/已完成/已逾期）。
- 业务规则：
  - 页面顶部展示日期与今日总进度环（已检点数/总点数）；
  - 进行中的任务排在列表最前，并显示主按钮"继续巡检"；
  - 任务点位按巡检计划定义的路线顺序排列，不允许乱序展示。
- 验收标准：
  1. 当天有 2 个任务时，列表正确展示 2 张卡片，进度数字与后台任务数据一致；
  2. 完成 3/12 个点位后刷新，进度环与卡片均显示 3/12；
  3. 超过执行时段未完成时任务卡片显示"已逾期"标签；
  4. 当日无任务时显示空状态（图标 + 说明文案），不出现报错或白屏。

**REQ-MP-003 任务执行页（点位路线）（P0）**

- 描述：从任务卡片进入点位路线页（`GET /api/mp/tasks/{id}`），按路线顺序展示每个点位的状态：已打卡（含时间与结果）、当前待打卡（高亮放大、显示"去打卡"）、未打卡。
- 业务规则：
  - 当前待打卡点位卡片为页面视觉焦点，已完成的折叠为一行；
  - 从打卡流程返回列表时，保持原滚动位置与最新进度；
  - 每个点位展示其打卡方式要求（扫码/围栏/扫码或围栏/扫码且围栏）。
- 验收标准：
  1. 9/12 进度下进入页面，前 9 个点位显示打卡时间与结果，第 10 个高亮显示"去打卡"，其余显示待打卡；
  2. 完成一次打卡返回后，列表进度即时 +1 且滚动位置不变；
  3. `both` 模式点位在页面明确提示需同时扫码且在围栏内。

### 4.3 点位打卡（核心）

**REQ-MP-004 扫码打卡（P0）**

- 描述：点击"扫码打卡"调起 `wx.scanCode` 扫描点位张贴的二维码，码值（`qrcode_no`）与当前点位匹配方可继续。
- 业务规则：
  - 码值与当前点位不匹配：震动 + 红色错误提示，不允许提交；
  - 二维码由后台批量生成，码值全局唯一，与点位一一对应；
  - 二维码仅作为点位身份凭证，扫码成功后仍需完成拍照等其余校验。
- 验收标准：
  1. 扫描当前点位的二维码，校验通过进入拍照环节；
  2. 扫描其他点位的二维码，页面震动并提示码值不匹配，提交按钮不可用；
  3. 扫描非本系统二维码，提示"无效二维码"；
  4. 服务端日志记录该次打卡 `checkin_type=qrcode`。

**REQ-MP-005 GPS 围栏打卡（P0）**

- 描述：通过 `wx.getLocation` 获取当前坐标（GCJ-02），与点位坐标做 Haversine 距离计算，进入围栏范围（`fence_radius`，默认 100m）方可打卡。
- 业务规则：
  - 打卡页实时显示与点位距离：围栏内显示绿色"距点位 xm（围栏内 ✓）"；超范围显示红色提示并注明还差多少米，按点位配置禁止提交；
  - 距离计算在服务端复核，客户端距离仅作展示；
  - GPS 弱信号场景（如地下室）定位失败/精度不足时，自动降级提示改用扫码打卡（该点位须支持扫码）。
- 验收标准：
  1. 距点位 8m（围栏半径 100m）时显示围栏内标识，提交可用；
  2. 距点位 126m 时显示红色超范围提示与差值，提交按钮禁用；
  3. 模拟定位超时/失败，页面出现降级引导提示扫码打卡；
  4. 篡改客户端上送的坐标（调试工具注入），服务端复核距离仍以服务端计算为准并在记录中保存 `distance_to_point`。

**REQ-MP-006 凭证 + 围栏双维度打卡校验（P0）**

- 描述：点位打卡校验由两个独立维度组成——点位凭证 `credential`（`qrcode` 扫码 / `nfc` NFC 卡 / `any` 任一（扫码或 NFC）/ `none` 免凭证）解决「到的是不是这个点位」；围栏校验 `require_fence` 解决「人在不在现场」。两者至少启用一项，同时启用则都须通过，打卡页按点位配置渲染对应校验流程。
- 业务规则：
  - `credential=qrcode`：出现扫码入口，码值须与点位一致；`credential=nfc`：读取 NFC 卡号须与点位登记卡号一致；`credential=any`：扫码与 NFC 入口并列，任一方式核验通过即可；`credential=none`：免凭证（须开启围栏）；
  - `require_fence=true`：实时定位距点位 ≤ 围栏半径才允许提交；
  - 凭证与围栏同时启用时，任一不满足均提示缺失项并拒绝提交。
- 验收标准：
  1. 各组合点位分别执行打卡，校验逻辑与上述一致；
  2. 凭证+围栏同时启用的点位只满足其一时，提交被拒绝并提示未满足的校验项；
  3. 后台修改点位凭证或围栏配置后，小程序端再次进入该点位打卡流程即按新规则校验，无需发版。

**REQ-MP-007 强制现场拍照（禁止相册）（P0）**

- 描述：打卡拍照调用 `wx.chooseMedia` 且限定 `sourceType: ['camera']`，用户无法从相册选择任何图片。
- 业务规则：
  - 所有打卡照片、必拍项照片、异常照片、维修结果照片均只能现场拍摄；
  - 拍摄后立即本地预览，后台压缩并直传对象存储，弱网先存本地队列；
  - 服务端校验照片 EXIF 拍摄时间与打卡时间偏差，超出疑似作弊阈值（系统参数可配）时标记疑似作弊。
- 验收标准：
  1. 点击拍摄按钮，系统相机直接唤起，全程无相册入口（iOS/Android 各验证一款机型）；
  2. 通过开发者工具构造相册图片上送，服务端 EXIF 校验识别并标记 `is_suspect` 及原因；
  3. 拍摄完成后 1 秒内出现本地预览。

**REQ-MP-008 照片水印（P0）**

- 描述：服务端在打卡照片上叠加水印：点位名称、打卡时间、GPS 坐标、巡检员姓名。
- 业务规则：
  - 水印在服务端（OSS 图片处理或 Go 端）生成，原始图与水印图分别保存（`photos` 记录 `url` 与 `watermarked_url`）；
  - 水印内容取自服务端数据（服务端时间、点位档案、打卡人），不接受客户端传入的水印文案；
  - 水印功能有系统级开关（参数配置），默认开启。
- 验收标准：
  1. 完成一次打卡后，后台查看该记录照片，可见包含点位名/时间/坐标/姓名的水印；
  2. 水印时间与服务端打卡时间一致，与客户端时间无关；
  3. 关闭水印参数后新打卡照片无水印，历史照片水印不受影响；
  4. 原始图与水印图均可通过后台查看原图。

**REQ-MP-009 必拍项校验（P0）**

- 描述：点位可配置必拍项列表（`required_photo_items`，如配电箱、消防栓、电梯机房），打卡页逐项展示，全部拍摄完成才能提交。
- 业务规则：
  - 每个必拍项一张对应照片，已拍项显示"已拍 ✓"，未拍项显示"点击拍摄"；
  - 未拍齐时提交按钮点击给出明确提示（还差哪几项）；
  - 无必拍项的点位至少拍摄 1 张现场照片方可提交。
- 验收标准：
  1. 配置 2 个必拍项的点位，只拍 1 项提交被拦截并提示缺失项名称；
  2. 全部必拍项拍摄完成后提交成功，后台照片中可按必拍项名称区分查看；
  3. 无必拍项点位不拍照直接提交，被拦截提示需拍照。

**REQ-MP-010 打卡提交与结果记录（P0）**

- 描述：提交打卡（`POST /api/mp/checkin`）上送坐标、二维码码值（如扫码）、照片 key、巡检结果（正常/异常）、备注；服务端落库打卡记录并更新任务进度。
- 业务规则：
  - 打卡时间以服务端接收时间为准（`checkin_time`），客户端时间仅存档（`client_time`），不信任客户端时间；
  - 同一点位同一任务重复打卡：默认不允许，已打卡点位再次进入显示已完成状态；
  - 打卡成功后：打勾动画（≤300ms）+ 震动反馈 + 自动跳到下一点位，目标"两步操作完成一次打卡"；
  - 提交按钮异步 loading + 禁用，防重复提交。
- 验收标准：
  1. 提交成功后任务进度即时更新（小程序与后台任务监控一致）；
  2. 修改手机系统时间后打卡，记录中 `checkin_time` 为服务端时间；
  3. 连续快速点击提交按钮，仅生成一条打卡记录；
  4. 已打卡点位不可再次提交打卡。

**REQ-MP-011 疑似作弊标记（P0）**

- 描述：服务端对打卡坐标与点位距离超出该点位围栏半径的记录自动标记"疑似作弊"（`is_suspect=true` 并写 `suspect_reason`），计入统计报表。
- 业务规则：
  - 触发条件（满足其一）：坐标距点位超围栏半径（经人工确认放行的围栏模式除外）、EXIF 拍摄时间与打卡时间偏差超阈值、客户端与服务端时间差超阈值（阈值均为系统参数）；
  - 疑似作弊记录不阻止打卡提交（避免现场误判阻塞工作），但在任务监控与巡检记录中醒目标识。
- 验收标准：
  1. 模拟超围栏距离提交（如配置允许超范围提交的 either 模式），记录被标记疑似作弊且原因正确；
  2. 后台任务监控中该点位行显示"疑似作弊"标识；
  3. 修改阈值参数后，新产生的打卡按新阈值判定。

### 4.4 异常上报

**REQ-MP-012 异常上报自动生成工单（P0）**

- 描述：打卡页巡检结果选择"异常"时内联展开异常表单：描述、照片（最多 6 张）、紧急程度；提交后系统自动创建异常工单并返回工单号（格式如 `WX20260805-003`）。
- 业务规则：
  - 选"异常"时描述必填、照片至少 1 张；
  - 工单与打卡记录关联（`work_order.checkin_id`），初始状态 `pending`，上报人为当前巡检员，所属小区/点位取自打卡上下文；
  - 提交成功 toast 展示工单号，可在"我的工单"中查看后续状态。
- 验收标准：
  1. 选择异常、填写描述、拍 1 张照片提交后，后台工单列表出现对应工单（状态待派单，信息完整）；
  2. 描述为空时提交被拦截并提示；
  3. 照片超过 6 张时无法继续添加；
  4. 工单号全局唯一且按日期递增。

### 4.5 离线补传

**REQ-MP-013 离线打卡本地暂存与自动补传（P0）**

- 描述：无网络时打卡数据（含照片、坐标、客户端原始时间）本地暂存，恢复网络后自动批量补传（`POST /api/mp/checkin/offline-sync`）。
- 业务规则：
  - 离线时首页顶部显示黄色横幅："当前离线，打卡将在恢复网络后自动上传（已暂存 N 条）"，N 实时更新；
  - 网络恢复后自动触发补传，补传期间不阻塞继续打卡；
  - 服务端对补传记录标记 `checkin_type=offline`，`client_time` 保留原始打卡时间，`checkin_time` 为服务端接收时间；防作弊校验照常执行；
  - 本地暂存数据补传成功前不可被清除，补传失败的条目保留并支持重试。
- 验收标准：
  1. 断网完成 2 次打卡，横幅显示已暂存 2 条；恢复网络后 2 条自动补传成功，后台记录可见且标记"离线补传"；
  2. 补传记录中 `client_time` 与断网时实际打卡时间一致；
  3. 补传中途再次断网，已传条目不重复提交（幂等），未传条目下次继续；
  4. 杀掉小程序进程后重开，未补传数据仍在且恢复网络后可补传。

### 4.6 历史记录与我的工单

**REQ-MP-014 历史巡检记录（P1）**

- 描述：巡检员可查看自己过往的巡检记录（日期、小区、点位、结果）与工单处理状态。
- 业务规则：仅展示本人数据；超过 50 项分页加载；照片缩略图加载小图，点击查看原图。
- 验收标准：
  1. 本人完成的历史打卡按时间倒序完整展示，与后台数据一致；
  2. 无法查看其他巡检员的记录（接口层校验，伪造他人 ID 返回无数据/403）；
  3. 记录超过 50 条时分页加载且有"没有更多了"终态。

**REQ-MP-015 我的工单（维修处理）（P0）**

- 描述：被派单的维修人员（或巡检员查看自己上报的工单）在"我的工单"中查看工单详情时间线，维修人员处理后上传维修结果照片与说明，工单进入待复核。
- 业务规则：
  - 维修结果照片同样强制现场拍摄（禁相册）；
  - 提交处理结果后工单状态 `processing → review`，全程写入流转日志；
  - 被驳回的工单在列表中标识驳回原因，可重新提交处理结果。
- 验收标准：
  1. 派单给维修人员后，其小程序"我的工单"出现该工单；
  2. 上传维修照片与说明提交后，后台工单状态变为待复核，时间线新增处理记录（操作人/时间/照片）；
  3. 驳回后的工单维修人员可见驳回原因并可再次提交。

### 4.7 消息通知

**REQ-MP-016 微信订阅消息推送（P1）**

- 描述：任务提醒、工单指派、整改驳回三类事件通过微信订阅消息推送；小程序内"消息"页展示消息列表并引导用户完成订阅授权。
- 业务规则：
  - 推送前校验用户订阅状态，未订阅不强弹，仅在消息页提供授权引导；
  - 消息有点开落地页（任务详情/工单详情）；
  - 消息开关为系统参数，可整体关闭。
- 验收标准：
  1. 主管派单后，被派单人微信收到订阅消息，点击进入对应工单详情；
  2. 复核驳回后，处理人收到驳回通知；
  3. 未授权订阅的用户不收到推送但消息页内可见消息记录；
  4. 关闭消息开关参数后不再发起推送。

### 4.8 小程序体验要求

**REQ-MP-017 小程序端可用性规范（P1）**

- 描述：小程序遵循 UI/UX 设计方案的专项要求，保障一线巡检员（多为中年员工、户外/戴手套操作）可用。
- 业务规则：
  - 触控目标 ≥ 44×44pt（约 88rpx），相邻目标间距 ≥ 8px；拍照按钮高度 ≥ 56px，整个卡片区域可点；
  - 所有点击 100ms 内有按压反馈；状态动画 150–300ms 且仅 transform/opacity；
  - 适配刘海屏与底部安全区，主按钮不压手势条；正文 ≥ 15px(30rpx)，户外强光可读；
  - 底部 TabBar 三项：任务 | 消息 | 我的，图标 + 文字。
- 验收标准：
  1. 按 UI 走查清单在 375px 小屏、刘海屏机型走查通过；
  2. 打卡主按钮与拍照按钮尺寸满足上述数值要求（走查工具实测）；
  3. 任意可点元素点击均有即时按压态反馈。

## 5. 功能需求 — 后台·工作台（REQ-DB）

**REQ-DB-001 核心指标统计卡（P0）**

- 描述：工作台首行展示 4 个统计卡：今日任务完成率（环形进度）、进行中任务数、待处理异常数（有值时红色高亮）、逾期任务数；卡片可点击下钻到对应列表页。
- 业务规则：统计口径受当前用户数据权限约束（按小区隔离）；数据每进入页面实时查询，不展示缓存过夜数据。
- 验收标准：
  1. 构造当日 12 点任务完成 9 点，完成率卡显示 75% 环形进度；
  2. 存在 2 条待派单工单时，待处理异常卡显示 2 且红色高亮，点击跳转工单列表待派单 Tab；
  3. 主管账号登录仅统计其所辖小区数据，与超管全量数据不一致（以权限范围为准）。

**REQ-DB-002 趋势与小区排行图表（P0）**

- 描述：第二行展示近 7 天巡检完成率折线图（单系列主色，面积填充 10% 透明度）与各小区今日执行情况横向条形图（按完成率排序，未完成标橙）。
- 业务规则：遵循 ECharts 图表规范：图例常显可点击、tooltip 精确值、网格线 `#EBEEF5`、每张图配一句文字结论；无数据显示空状态而非空白坐标轴；图表加载骨架屏、失败给重试按钮。
- 验收标准：
  1. 近 7 天有数据时折线图正确渲染，tooltip 显示当日精确完成率；
  2. 某小区今日完成率 <100% 时对应条形标橙；
  3. 全部无数据时显示空状态文案，不渲染空坐标轴；
  4. 超管与主管看到的小区集合不同（数据权限生效）。

**REQ-DB-003 最新异常与执行动态（P1）**

- 描述：第三行展示最新异常工单列表（前 5 条，可点击进详情）与今日任务执行动态时间线。
- 验收标准：
  1. 新产生工单后刷新工作台，最新异常列表首条为该工单；
  2. 点击工单条目跳转工单详情页；
  3. 今日有打卡行为时，动态时间线按时间倒序展示打卡事件（人/点位/时间）。

**REQ-DB-004 工作台框架交互（P1）**

- 描述：后台整体框架：固定深色侧边栏（`#1F2D3D`，220px 可折叠至 64px）+ 顶栏（面包屑、全屏、消息通知未读角标、用户下拉）+ Tags View 标签页；菜单由后端按角色权限动态下发（`GET /auth/routes`）。
- 业务规则：Tags View 切换不丢筛选条件，右键支持关闭其他/关闭全部；最小适配宽度 1280px，页面整体不允许横向滚动；退出登录项与其他项分隔线隔开。
- 验收标准：
  1. 不同角色登录后侧边栏菜单不同，与角色权限配置一致；
  2. 在列表页设置筛选后切换标签页再切回，筛选条件保留；
  3. 1280/1440/1920 三档宽度走查，页面无横向滚动条。

## 6. 功能需求 — 后台·巡检管理（REQ-INS）

### 6.1 点位管理

**REQ-INS-001 点位档案维护（P0）**

- 描述：左侧小区/楼栋树 + 右侧点位表格，支持点位的新增/编辑/启停用/删除（软删除）。点位字段：所属小区、楼栋/区域、名称、类型（字典）、二维码编号、GPS 坐标（GCJ-02）、围栏半径、打卡方式（四种）、必拍项列表、排序、状态。
- 业务规则：
  - 二维码编号全局唯一，系统自动生成，不允许手工重复；
  - 删除点位前校验：若点位被进行中计划引用，提示先调整计划，不物理删除任何数据；
  - 表单使用抽屉（字段 ≤6）或对话框，必填项前置校验。
- 验收标准：
  1. 新增点位保存后列表可见，字段完整入库；
  2. 停用点位后，新生成的任务不再包含该点位（历史任务不受影响）；
  3. 删除被进行中计划引用的点位被拦截并给出提示；
  4. 删除操作二次确认，删除后数据库中记录为软删除（`deleted_at` 非空）。

**REQ-INS-002 地图选点与围栏配置（P0）**

- 描述：点位表单内嵌腾讯地图组件拾取坐标，围栏半径滑块 50–500m（默认 100m），地图实时画圈预览；打卡方式单选（扫码/围栏/任一/两者）；必拍项为动态列表（可增删项）。
- 验收标准：
  1. 地图点击选点后坐标回填表单；
  2. 拖动滑块至 200m，地图圆形围栏实时更新且保存后字段为 200；
  3. 新增/删除必拍项保存后，小程序打卡页必拍项同步变化。

**REQ-INS-003 批量生成二维码（P0）**

- 描述：支持按小区/楼栋批量选择点位生成二维码，导出 A4 排版 PDF（含点位名称、编号）直接打印张贴；支持批量导入点位。
- 验收标准：
  1. 勾选 10 个点位导出 PDF，含 10 个二维码且每个可扫出正确 `qrcode_no`；
  2. PDF 按 A4 排版不裁切、可直接打印；
  3. 批量导入模板填写的点位数据校验通过后批量入库，错误行给出明确行号与原因。

### 6.2 巡检计划与任务生成

**REQ-INS-004 巡检计划管理（P0）**

- 描述：计划的 CRUD，字段：小区、名称、点位路线（有序列表）、周期类型（daily/weekly/monthly）、周期配置（每周几/每月几号）、巡检员（多人）、起止日期、要求执行时段（time_window）、状态。
- 业务规则：
  - 计划停用后不再生成新任务，已生成任务不受影响；
  - 路线点位、巡查类型和执行时段调整会同步 pending/doing/overdue 未完成任务，已完成任务保留历史快照；
  - 同一计划对同一巡检员同一日期只生成一个任务。
- 验收标准：
  1. 创建 daily 计划后，次日自动为指定巡检员生成任务；
  2. weekly 计划配置周一/周四，仅在该两日生成任务；
  3. 停用计划后次日不再生成任务；
  4. 手动触发两次生成逻辑，不产生重复任务（幂等）。

**REQ-INS-005 任务自动生成与状态机（P0）**

- 描述：系统每日定时（Redis 分布式锁防并发重复）按生效计划生成当日任务，状态流转 pending → doing → done / overdue。
- 业务规则：
  - 首次打卡将任务置为 doing 并记录 `started_at`，全部点位完成置 done 并记录 `finished_at`；
  - `task_date` 结束（或超过执行时段，按参数口径）仍未完成的任务标记 overdue；
  - 任务表冗余 `total_points` / `done_points` 实时维护，与打卡记录一致。
- 验收标准：
  1. 完成首次打卡后任务状态变 doing，完成全部点位变 done，进度 12/12；
  2. 跨天后未完成任务自动标记 overdue；
  3. 分布式部署/重复触发下任务不重复生成。

### 6.3 任务监控

**REQ-INS-006 任务监控实时视图（P0）**

- 描述：以任务卡片 + 点位时间线形式展示每个任务的实时执行情况：每点位一行，含状态图标（✅已打卡 / ⚠️跳过或疑似作弊 / ❌未打卡）、打卡时间、打卡方式（扫码/围栏/离线）、距点位距离、照片入口；顶部任务进度条。
- 业务规则：
  - 状态用图标 + 颜色双重编码（图标为主、颜色为辅）；
  - 疑似作弊记录行内标识"疑似作弊"及距离（如"距126m"）；
  - 数据实时刷新（进入页面拉取最新），不受页面缓存影响。
- 验收标准：
  1. 巡检员现场打卡后，刷新任务监控对应点位行即时显示时间/方式/距离；
  2. 缺卡点位明确显示 ❌未打卡；
  3. 构造超距打卡，该行显示疑似作弊标识与距离值。

**REQ-INS-007 任务监控筛选 Tab（P0）**

- 描述：列表页提供状态筛选 Tab：全部 / 进行中 / 已完成 / 有缺卡 / 有异常 / 疑似作弊。
- 验收标准：每个 Tab 筛选结果与定义一致（如"有缺卡"仅显示存在未打卡点位的任务），Tab 切换后分页重置。

**REQ-INS-008 打卡照片查看（P0）**

- 描述：任务监控与巡检记录中点击"照片"弹出照片墙（带水印缩略图），进入查看器支持放大、左右切换，并展示 EXIF 校验结果与打卡元数据（时间/坐标/距离/方式）。
- 业务规则：照片 URL 私有读 + 签名防盗链；照片存对象存储不可篡改删除（OSS 版本控制）。
- 验收标准：
  1. 照片墙加载带水印缩略图，点击可放大查看原图并左右切换；
  2. 查看器显示该照片 EXIF 校验结论与打卡元数据；
  3. 未登录或越权直接访问照片 URL 被拒绝。

### 6.4 巡检记录

**REQ-INS-009 巡检记录检索（P0）**

- 描述：打卡记录列表（`GET /api/admin/inspection/checkins`），支持按巡检员、小区、点位、时间范围、结果（正常/异常）、打卡方式、是否疑似作弊组合筛选；行点击展开打卡明细（照片、坐标地图小窗、水印信息）。
- 业务规则：列表遵循通用范式（搜索栏 + 工具栏 + 表格 + 分页）；记录只读，不提供编辑/删除入口；数据权限按小区隔离。
- 验收标准：
  1. 按"巡检员=张三 + 本周 + 异常"筛选，结果集与数据库吻合；
  2. 行展开可看到照片与坐标地图小窗；
  3. 界面无任何修改/删除打卡记录的入口；
  4. 主管账号仅能检索所辖小区的记录。

## 7. 功能需求 — 后台·异常工单（REQ-WO）

**REQ-WO-001 工单列表与状态 Tab（P0）**

- 描述：工单列表顶部状态 Tab：待派单 / 处理中 / 待复核 / 已关闭，各 Tab 带数量角标；支持按小区、点位、紧急程度、上报人、时间筛选；主管登录默认落在"待派单"。
- 业务规则：Tab 口径映射状态机——待派单 = pending；处理中 = assigned + processing；待复核 = review；已关闭 = closed（含已驳回历史可查）。
- 验收标准：
  1. 新上报异常后，待派单角标 +1 且列表首条可见；
  2. 各 Tab 数量与对应状态工单总数一致；
  3. 主管登录工单模块默认激活待派单 Tab。

**REQ-WO-002 工单详情与流转时间线（P0）**

- 描述：详情页左右结构：左侧异常信息（照片、点位、上报人、描述、紧急程度），右侧流转时间线（上报 → 派单 → 处理反馈 → 复核关闭），每步含操作人、时间、照片；所有流转写入 `work_order_log`。
- 验收标准：
  1. 完成一次"派单→处理→复核通过"全流程后，时间线完整展示 4 个节点及操作人/时间；
  2. `work_order_log` 表中每一步均有对应留痕记录；
  3. 工单导出/打印件保留完整时间线，可直接归档。

**REQ-WO-003 派单（P0）**

- 描述：待派单工单可派单：对话框选择处理人（维修人员/巡检员），可填写要求说明；派单后状态 pending → assigned，并通过订阅消息通知处理人。
- 业务规则：只能选择启用状态且数据权限覆盖该工单小区的账号；派单操作记录操作日志。
- 验收标准：
  1. 派单成功后工单状态变为已派单，处理人小程序收到通知；
  2. 停用账号不出现在可选处理人列表；
  3. 派单动作在操作日志中可查。

**REQ-WO-004 复核与驳回（P0）**

- 描述：处理人提交维修结果后工单进入待复核；主管复核：通过 → closed（记录复核人/时间/意见）；驳回 → 退回 processing，**驳回原因必填**，处理人收到驳回通知。
- 验收标准：
  1. 复核通过后工单状态 closed，时间线含复核意见；
  2. 驳回时不填原因无法提交；
  3. 驳回后处理人小程序收到通知且可重新处理，再次提交后状态回到 review；
  4. 已关闭工单不可再执行派单/处理/复核操作（按钮禁用且接口拦截）。

**REQ-WO-005 工单号与权限（P1）**

- 描述：工单号自动生成（`WX + 日期 + 序号`），全局唯一；工单查询与操作均受数据权限约束（按小区隔离）。
- 验收标准：
  1. 同日创建 3 个工单，工单号按序递增且无重复；
  2. 主管 A 无法通过接口访问非所辖小区的工单详情（返回 403/无数据）。

## 8. 功能需求 — 后台·统计分析（REQ-STA）

**REQ-STA-001 巡检覆盖/及时/异常率报表（P0）**

- 描述：报表页统一"筛选条 + 指标卡 + 图表 + 明细表 + 导出"五段式；核心指标：巡检覆盖率（已打卡点位/应检点位）、及时率（要求时段内完成的任务占比）、异常率（异常打卡/总打卡），三指标并列展示；支持按小区、时间范围（7 天/30 天/自定义）筛选。
- 验收标准：
  1. 用已知数据集验证三指标计算口径与手工核算一致；
  2. 切换时间范围后指标卡、图表、明细表同步刷新；
  3. 无数据区间显示空状态而非报错。

**REQ-STA-002 巡检员绩效报表（P0）**

- 描述：按巡检员统计完成率、平均耗时、异常发现数、疑似作弊次数；表格支持按列排序。
- 业务规则：平均耗时 = 任务 `finished_at - started_at` 的平均（仅已完成任务参与）；绩效数据受数据权限约束。
- 验收标准：
  1. 已知数据下各列数值与手工核算一致；
  2. 点击列头排序升降序正确；
  3. 疑似作弊次数与打卡记录中 `is_suspect=true` 数量一致。

**REQ-STA-003 数据导出（Excel/PDF）（P0）**

- 描述：报表与巡检记录支持导出 Excel；月度巡检报告支持导出 PDF（可直接提交业委会/甲方）；导出按钮 loading 防抖，大文件异步生成后消息中心通知下载。
- 业务规则：导出内容受数据权限约束；导出动作记录操作日志；异步导出任务完成后在消息中心生成下载链接（带时效）。
- 验收标准：
  1. 导出 Excel 打开后字段与页面明细表一致；
  2. 月报 PDF 含覆盖率/及时率/异常率与小区明细，排版完整；
  3. 连续点击导出按钮只生成一个导出任务；
  4. 大数据量导出走异步，完成后消息中心出现下载通知且链接可下载；
  5. 主管导出的文件仅含所辖小区数据。

## 10. 功能需求 — 后台·系统管理（REQ-SYS）

### 10.1 认证与 RBAC

**REQ-SYS-001 后台登录与会话（P0）**

- 描述：后台账号密码登录（`POST /auth/login`），密码 bcrypt 存储；JWT（access + refresh）+ Redis 会话；支持退出登录、Token 失效跳转登录页。
- 业务规则：连续登录失败锁定策略（参数可配，默认 5 次锁 10 分钟）；登录成功/失败均写登录日志（IP、UA、结果、原因）。
- 验收标准：
  1. 正确账号密码登录成功进入工作台；
  2. 连续 5 次错误密码后账号锁定 10 分钟，期间正确密码也拒绝；
  3. 退出登录后旧 Token 访问接口返回 401；
  4. 登录日志记录每次登录的 IP/UA/结果。

**REQ-SYS-002 菜单与按钮级权限（P0）**

- 描述：RBAC 模型：用户 → 角色 → 菜单（dir/menu/button 三类，`perms` 权限标识）；登录后 `GET /auth/routes` 按权限动态下发路由，前端菜单与按钮按权限显隐（按钮级用权限指令控制）；后端接口按 RBAC 中间件逐一鉴权。
- 业务规则：前端隐藏仅为体验手段，所有接口必须在服务端做权限校验；无权限访问接口返回 403。
- 验收标准：
  1. 为角色去掉"点位管理"菜单权限后，该角色登录侧边栏无此菜单，直接访问路由与 API 均被拒（403）；
  2. 去掉某按钮权限（如"删除点位"），界面按钮不渲染，直接调用删除接口返回 403；
  3. 权限调整保存后，重新登录即生效。

**REQ-SYS-003 数据权限（按小区隔离）（P0）**

- 描述：角色配置数据范围：`all`（全部小区）或 `custom`（勾选小区集合）；所有业务查询（任务、记录、工单、报表、工作台）按该范围过滤。
- 业务规则：用户多角色时数据权限取并集；数据权限在服务层查询条件强制注入，不依赖前端传参。
- 验收标准：
  1. 配置主管仅管辖小区 A/B 后，其工作台、任务监控、工单、报表均只出现 A/B 数据；
  2. 通过 API 传参指定小区 C 的数据进行查询，返回为空（服务端强制过滤）；
  3. 用户同时属于"小区 A 角色"与"小区 B 角色"时可见 A+B 数据。

### 10.2 系统管理五件套

**REQ-SYS-004 用户管理（P0）**

- 描述：后台账号与巡检员/维修工账号统一管理：用户名、姓名、手机号、角色（多选）、所辖小区（多选）、状态（启停用）；支持重置密码、账号启停用；巡检员账号展示微信绑定状态。
- 业务规则：用户名唯一；初始密码/重置密码需符合复杂度（≥8 位含字母数字）并在首次登录强制改密；不可停用/删除超管账号；删除为软删除。
- 验收标准：
  1. 创建巡检员账号并配置小区后，该账号可绑定微信登录小程序；
  2. 停用账号后其后台与小程序登录均被拒；
  3. 重置密码后旧密码失效，新密码首次登录强制修改；
  4. 尝试停用/删除超管被拦截。

**REQ-SYS-005 角色管理（P0）**

- 描述：角色 CRUD + 权限分配界面：左侧角色列表，右侧菜单权限树（父子联动勾选）+ 数据范围单选（全部 / 按小区多选）；角色可启停用。
- 业务规则：角色编码唯一；被用户引用的角色不可删除；内置超管角色不可编辑权限。
- 验收标准：
  1. 新建角色、勾选部分菜单与小区 A，分配给测试账号后，该账号菜单与数据范围与配置一致；
  2. 权限树勾选父节点自动联动子节点，取消子节点父节点变半选；
  3. 删除已分配用户的角色被拦截。

**REQ-SYS-006 菜单管理（P0）**

- 描述：菜单/按钮权限点维护：标题、路由 path、图标、类型（目录/菜单/按钮）、权限标识 perms、排序、显隐、状态；前端路由与按钮显隐与其联动。
- 业务规则：菜单树形结构（parent_id）；停用菜单后所有角色均不可见；perms 标识全局唯一。
- 验收标准：
  1. 新增一个菜单并授权给角色后，该角色登录可见且路由可访问；
  2. 停用菜单后所有角色菜单中消失；
  3. 按钮类型权限点配置 perms 后，前端按钮权限指令按此控制显隐。

**REQ-SYS-007 字典管理（P1）**

- 描述：字典类型 + 字典数据两级维护（如工单状态、点位类型、异常类型、紧急程度），业务页面下拉项从字典取值；字典数据可启停用、排序。
- 验收标准：
  1. 在字典中新增一种异常类型后，小程序异常上报与后台筛选项中出现该类型（无需发版）；
  2. 停用某字典项后新单据不可再选，历史数据展示不受影响。

**REQ-SYS-008 参数配置（P0）**

- 描述：系统参数键值维护，至少含：围栏默认半径（默认 100m）、拍照水印开关（默认开）、疑似作弊判定阈值（距离/EXIF 时间偏差）、登录失败锁定策略、消息推送开关；参数修改即时生效并记录操作日志。
- 验收标准：
  1. 修改围栏默认半径为 150m 后，新建点位默认围栏半径为 150m（已有点位不变）；
  2. 关闭水印开关后新打卡照片无水印；
  3. 每次参数修改在操作日志中可查（操作人/旧值/新值）。

### 10.3 通知公告与日志

**REQ-SYS-009 通知公告（P2）**

- 描述：面向巡检员的公告发布（标题、内容、发布时间），小程序"消息"页展示；支持撤销。
- 验收标准：发布公告后巡检员小程序消息页可见；撤销后不再展示。

**REQ-SYS-010 日志管理（P0）**

- 描述：操作日志（用户、模块、动作、请求方法/路径、参数、IP、结果、耗时）与登录日志（用户、IP、UA、结果、失败原因）只读列表，支持按人/模块/时间检索与导出；不提供任何编辑/删除入口；`sys_operation_log` 按月分区或定期归档。
- 业务规则：敏感字段（密码等）不入日志；所有增删改操作必须留痕。
- 验收标准：
  1. 执行一次点位删除后，操作日志可按模块/操作人检索到该记录且含耗时与结果；
  2. 登录失败记录在登录日志中且原因正确；
  3. 列表无编辑/删除按钮，直连 API 亦无对应写接口；
  4. 日志中不出现明文密码；
  5. 日志支持导出。

### 10.4 个人中心

**REQ-SYS-011 个人中心（P1）**

- 描述：后台用户可修改个人信息（姓名、头像、手机号）与密码（需验证旧密码）；修改密码后强制重新登录。
- 验收标准：
  1. 旧密码错误时修改被拒；
  2. 修改密码成功后旧会话失效，需用新密码重新登录；
  3. 个人信息修改即时生效并写操作日志。

### 10.5 用户批量导入导出

**REQ-SYS-012 用户导入模板下载（P0）**

- 描述：用户管理页提供"下载导入模板"入口，下载标准 Excel 模板（.xlsx），供批量开通巡检员/维修工等账号使用。
- 业务规则：
  - 模板列依次为：姓名*、手机号*、角色*（可多选，填角色名称，多个用逗号分隔）、所属小区*（填小区名称，多个用逗号分隔，巡检员用于数据权限）、初始密码（选填，留空则默认手机号后 6 位，首登强制改密）、状态（选填，启用/停用，默认启用）、备注（选填）；
  - 模板首行为表头且锁定，必填列以 * 标识；模板附 1 行填写示例与填写说明（角色/小区名称须与系统内现有名称完全一致）；
  - 模板内容随系统数据动态可校验：示例中引用的角色与小区名称使用当前系统真实存在的数据。
- 验收标准：
  1. 点击"下载导入模板"可获得 .xlsx 文件，列名、顺序、必填标识与上述规则一致；
  2. 模板内含示例行与填写说明，示例中的角色/小区名称在系统中真实存在；
  3. 无"用户导入"按钮权限的角色看不到该入口，直接调用模板下载接口返回 403。

**REQ-SYS-013 用户批量导入与逐行校验（P0）**

- 描述：用户管理页支持上传按模板填写的 Excel 文件，服务端逐行校验并创建账号，实现批量开通巡检员账号。
- 业务规则：
  - 仅接受 .xlsx 格式且列结构与模板一致的文件，文件大小与行数设上限（行数 ≤ 500，超限整体拒绝并提示）；
  - 服务端逐行校验（不信任前端校验）：必填项非空（姓名、手机号、角色、所属小区）；手机号符合大陆手机号格式且全局唯一（与库中已有用户及本文件内其他行均不重复）；角色名称必须存在（多个角色逐一校验）；小区名称必须存在（多个小区逐一校验）；状态仅允许"启用/停用"（留空视为启用）；初始密码如填写须符合复杂度（≥8 位含字母数字）；
  - 用户名默认取手机号（若用户名与手机号分离实现，则自动生成的用户名同样需保证唯一）；
  - 密码 bcrypt 哈希入库；留空的初始密码按"手机号后 6 位"生成并标记首次登录强制改密；
  - 导入创建的用户字段映射与手工新增一致（角色写入 `role_ids`、小区写入 `community_ids`），导入来源可在备注/日志中追溯。
- 验收标准：
  1. 上传 10 行全部合法的 Excel，10 个账号全部创建成功，角色与小区关联正确，可用手机号 + 初始密码登录；
  2. 构造含以下缺陷的文件各行分别失败且原因明确：缺姓名、手机号格式错误（如 12 位）、手机号与已有用户重复、同一文件内两行手机号重复、角色名称不存在、小区名称不存在、状态填"正常"（非法值）、初始密码仅 6 位纯数字；
  3. 上传非 .xlsx 文件或列结构与模板不符的文件，整体拒绝并提示；
  4. 上传 501 行文件被整体拒绝并提示行数超限；
  5. 前端绕过直接调接口提交非法数据，服务端校验同样拦截。

**REQ-SYS-014 导入结果反馈与失败明细（P0）**

- 描述：导入完成后页面展示结果汇总：成功条数、失败条数；失败行附行号与失败原因，并可下载失败明细 Excel（原始行数据 + 失败原因列）。
- 业务规则：
  - 导入策略为"跳过失败行、导入成功行"（非全有或全无）：校验失败的行不影响合法行入库；
  - 结果汇总即时展示（失败原因逐行可查看），失败明细 Excel 含原行号、原始填写内容、具体失败原因，可直接修正后重新导入；
  - 重新导入修正后的文件时，已成功导入的手机号行会按唯一性规则失败并提示"已存在"，不产生重复账号（幂等）；
  - 导入过程中网络中断/页面关闭不影响服务端已开始的导入事务，再次进入可通过操作日志与失败明细核对结果。
- 验收标准：
  1. 上传 8 行合法 + 4 行非法的文件，结果显示成功 8、失败 4，库中新增且仅新增 8 个账号；
  2. 下载失败明细 Excel，含 4 个失败行，每行行号与原因准确（如"第 5 行：角色名称'巡检主管'不存在"）；
  3. 修正失败明细后重新导入，修正行成功，与首批重复的行提示已存在，账号总数不重复增加；
  4. 全部行非法时成功 0、失败 N，库中不产生任何新账号。

**REQ-SYS-015 用户列表导出（P0）**

- 描述：用户管理列表支持按当前筛选条件（角色、小区、状态、关键字等）导出 Excel。
- 业务规则：
  - 导出内容与列表当前筛选结果一致，字段与列表列一致（用户名、姓名、手机号、角色、所属小区、状态、微信绑定状态、最后登录时间、创建时间），不含密码字段；
  - 导出受数据权限约束：主管仅能导出其所辖小区相关用户；
  - 导出按钮 loading 防抖；数据量大时异步生成并消息中心通知下载（复用 REQ-STA-003 机制）；
  - 导出动作记录操作日志。
- 验收标准：
  1. 设置筛选"角色=巡检员 + 状态=启用"后导出，Excel 行数与列表总数一致且均满足筛选条件；
  2. 导出文件中无密码列；
  3. 主管账号导出的文件不含非所辖小区用户；
  4. 连续点击导出按钮只生成一个导出任务，操作日志中有本次导出记录。

**REQ-SYS-016 导入导出安全规则（P0）**

- 描述：用户批量导入导出的全局安全约束。
- 业务规则：
  - 任何导出文件（用户列表、失败明细）均不得包含密码字段（含哈希值），初始密码只在创建时按规则生成，不以明文形式持久化或下发；
  - 导入与导出操作均记入操作日志（操作人、文件名、成功/失败条数、IP、时间）；日志中不出现明文密码；
  - 通过导入创建、且使用默认/初始密码的账号，首次登录（后台或小程序绑定流程）强制修改密码后方可正常使用；
  - 导入/导出接口需"用户导入""用户导出"按钮级权限点控制，服务端逐一鉴权；
  - 导入文件解析做安全校验：限制文件大小、拒绝宏/可执行内容伪装、防止公式注入（导出单元格以 `=`、`+`、`-`、`@` 开头的文本做转义处理）。
- 验收标准：
  1. 检查用户导出与失败明细 Excel，无任何密码相关列；
  2. 执行一次导入后，操作日志可按模块"用户管理"检索到该记录，含成功/失败条数；
  3. 用导入创建且未改密的账号登录，被强制跳转修改密码页，改密前无法访问其他功能；
  4. 无对应按钮权限的角色调用导入/导出接口返回 403；
  5. 在备注列填入 `=1+1` 类公式后导出，打开 Excel 该单元格按文本显示而非执行公式。

**REQ-SYS-018 内置超管账号保护（P0）**

- 描述：`admin` 为系统唯一内置超级管理员账号（`sys_user.is_builtin=true`，迁移自动标记存量 admin/持超管角色账号），服务端强制保护，防止误操作导致系统失去管理入口。
- 业务规则：
  - 内置账号不可删除（含软删除）、不可停用，违反返回 41014；
  - 编辑内置账号时不可移除其 super_admin 角色绑定（41014），姓名/手机号等资料可正常修改；
  - 既有保护保留：任何人不能停用/删除当前登录账号（41006）；super_admin 内置角色不可删除（41007）；
  - 用户列表/详情接口返回 `is_builtin`，前端据此禁用删除/停用按钮。
- 验收标准：
  1. 以另一超管账号删除/停用 admin，返回 41014 且数据不变；
  2. 编辑 admin 去掉 super_admin 角色返回 41014；仅改姓名保存成功；
  3. 普通用户的停用/删除不受影响；
  4. 列表接口 admin 行 `is_builtin=true`。

### 10.6 开放注册

**REQ-SYS-017 开放注册开关与自助注册（P1）**

- 描述：系统参数 `auth.register_enabled`（默认关闭）控制是否开放自助注册；开启后登录页提供注册入口，访客通过 `POST /api/admin/auth/register` 提交用户名/密码/姓名/手机号完成注册，无需管理员逐个开通后台账号。
- 业务规则：
  - 开关由管理员在"参数配置"页维护，修改即时生效（配置缓存失效）；关闭时注册接口返回 40303；
  - 用户名 4–20 位字母数字下划线且全局唯一（41001），手机号格式校验且全局唯一（41008），密码 8–32 位且含字母与数字；
  - 注册成功的账号不绑定任何角色：可登录但无菜单与按钮权限（`/auth/routes` 返回空），仅可访问个人中心等"登录即可"接口，由管理员分配角色后方可使用业务功能；
  - 注册失败计入登录同口径 IP 限流，连续失败达阈值锁定 10 分钟（42900）；注册行为写入操作日志。
- 验收标准：
  1. 开关关闭时调用注册接口返回 40303，登录页不显示注册入口；
  2. 开启后提交合法参数注册成功，可立即登录；
  3. 重复用户名/手机号分别返回 41001/41008，弱密码返回 40001；
  4. 新注册账号登录后菜单为空、访问用户管理返回 40301，分配角色后菜单即时出现；
  5. 连续失败注册触发限流返回 42900。

## 11. 通用 / 非功能需求（REQ-NF）

### 11.1 性能

**REQ-NF-001 响应性能（P0）**

- 描述：在方案约定规模（10 个小区、30 名巡检员、日均 500 张照片）下：后台列表/详情接口 P95 响应 ≤ 500ms；工作台统计接口 P95 ≤ 1s；小程序任务列表/打卡提交接口 P95 ≤ 1s（不含照片上传耗时）；照片上传走 OSS 直传不经过应用服务器。
- 验收标准：用 JMeter/压测脚本模拟约定规模 2 倍并发，上述接口 P95 达标；抓包验证照片流量直连 OSS 域名。

**REQ-NF-002 容量与存储（P1）**

- 描述：单台 4C8G 云服务器（Docker Compose：app/postgres/redis/nginx）+ 对象存储可支撑约定规模稳定运行；PostgreSQL 每日 `pg_dump` 全量备份至 OSS，保留 30 天；OSS 照片开启版本控制防误删。
- 验收标准：
  1. 按日均 500 张照片 × 90 天造数后，核心查询性能仍满足 REQ-NF-001；
  2. 备份任务连续 3 天成功生成备份文件且可恢复验证；
  3. OSS 中误删照片可通过版本控制找回。

### 11.2 安全

**REQ-NF-003 传输与存储安全（P0）**

- 描述：全站 HTTPS；密码 bcrypt 哈希存储；SQL 全部走 GORM 参数化防注入；照片 URL 私有读 + 签名防盗链；敏感配置（密钥、数据库口令）走环境变量/配置文件，不入代码库。
- 验收标准：
  1. HTTP 访问被重定向/拒绝，仅 HTTPS 可用；
  2. 数据库中无明文密码；
  3. 对登录、打卡、搜索接口做常见 SQL 注入渗透测试，全部被拦截；
  4. 未带签名直接访问照片 URL 返回 403。

**REQ-NF-004 接口鉴权与限流（P0）**

- 描述：除登录等白名单接口外，全部接口经 JWT + RBAC 中间件鉴权；后台 `/api/admin` 与小程序 `/api/mp` 两组路由入口分离、互不越权；登录、打卡提交等关键接口限流防刷。
- 验收标准：
  1. 无 Token / 过期 Token 访问业务接口返回 401；
  2. 小程序 Token 访问 `/api/admin` 接口返回 403（反之亦然）；
  3. 对登录接口高频请求触发限流（返回 429 或锁定提示）。

**REQ-NF-005 审计留痕（P0）**

- 描述：所有增删改操作写操作日志；工单流转全程写 `work_order_log`；打卡记录只增不改删；日志按月分区/定期归档。
- 验收标准：抽查 10 个写操作，操作日志 100% 留痕；数据库层面验证打卡记录表无更新/删除入口（应用不提供接口）。

### 11.3 兼容性

**REQ-NF-006 浏览器与终端兼容（P0）**

- 描述：管理后台兼容 Chrome / Edge 最近两个大版本，分辨率 1280/1440/1920 三档走查通过；小程序兼容 iOS / Android 主流机型（微信最新两个版本），覆盖 375px 小屏与刘海屏。
- 验收标准：按 UI 走查清单在上述环境执行，布局、交互、图表渲染无阻断性缺陷；页面整体无横向滚动。

### 11.4 可用性与交互一致性

**REQ-NF-007 通用交互规范（P1）**

- 描述：两端遵循 UI/UX 设计方案的交互规范：异步按钮 loading + 禁用防重复提交；危险操作红色 + 二次确认（按钮文案写动作本身）；表单 label 必现、失焦校验、错误就近提示并说明修正方法；空状态"图标 + 说明 + 主操作"三件套；加载 >300ms 骨架屏、>10s 给取消/重试；返回列表保留筛选与滚动位置；术语全系统统一（点位/任务/打卡/工单）。
- 验收标准：按设计方案 §六、§七 质量验收清单逐项走查全部通过。

**REQ-NF-008 可访问性与可读性（P2）**

- 描述：正文文字与背景对比度 ≥ 4.5:1（WCAG AA），大字号/图标 ≥ 3:1；功能色均配图标或文字，禁止红绿单独配对；组件内禁止写死裸色值，全部走设计令牌。
- 验收标准：用对比度检测工具抽查 10 处文本全部达标；走查确认无仅靠颜色传达含义的状态；代码扫描无组件内裸色值（令牌豁免）。

### 11.5 可靠性与运维

**REQ-NF-009 监控与告警（P1）**

- 描述：服务提供健康检查接口；应用日志采用 zap 结构化日志按天滚动；接口异常告警推送企业微信 Webhook。
- 验收标准：kill 应用进程健康检查失败；制造接口 500 错误后企业微信收到告警；日志文件按天滚动生成。

**REQ-NF-010 优雅降级（P1）**

- 描述：Redis 不可用时核心打卡链路不阻断（会话校验降级策略明确并记录日志）；OSS 回调失败时照片补传/重试机制保证最终入库；消息推送失败不影响业务流程。
- 验收标准：
  1. 停掉 Redis 后打卡提交仍可完成或返回明确错误文案（按实现的降级策略），不出现 500 裸错误；
  2. 模拟 OSS 回调失败，重试后照片与打卡记录关联正确；
  3. 关闭消息服务，打卡与工单流转不受影响。

## 12. 约束与依赖

### 12.1 技术约束

- 后端：Go + Gin + GORM，单二进制部署；数据库 PostgreSQL 15+（JSONB 存配置类字段）；缓存 Redis（会话/JWT 黑名单、任务进度缓存、计划生成分布式锁）。
- 管理后台：Vue 3 + Vite + Element Plus + Pinia + Vue Router + ECharts，UI 遵循《UI-UX 设计方案》令牌与规范。
- 小程序：微信原生（WXML/WXSS/JS），不使用跨端框架。
- 照片存储：阿里云 OSS / 腾讯云 COS，小程序 STS 直传 + 服务端回调写库；坐标系统一 GCJ-02，距离计算采用 Haversine。
- 部署：Docker Compose（app/postgres/redis/nginx），单台云服务器起步。

### 12.2 外部依赖（上线前置条件）

| 依赖项 | 责任方 | 说明 |
|---|---|---|
| 微信小程序注册（企业主体） | 物业公司 | 用于正式环境与订阅消息模板申请 |
| 对象存储账号（OSS/COS）开通与配置 | 物业公司/开发方 | 含 STS、回调、版本控制、防盗链配置 |
| 腾讯地图 Key | 开发方 | 后台点位地图选点 |
| 各小区点位清单 | 物业公司 | 位置、名称、必拍项、打卡方式 |
| 点位二维码制作张贴 | 物业公司 | 后台批量生成 PDF 打印 |
| 巡检员微信收集与账号开通 | 物业公司 | 后台批量开通 |
| 微信订阅消息模板审核 | 开发方 | 任务提醒/工单指派/整改驳回三类 |

### 12.3 业务约束

- 打卡记录、工单流转日志、操作日志为审计数据，系统不提供任何修改/删除入口；
- 客户端时间不可信，一切时间判定以服务端为准；
- 数据权限按小区隔离为全局硬性约束，新增业务查询必须接入数据权限过滤；
- 删除操作一律软删除；
- 计划任务生成、补传等接口必须幂等，重试不产生重复数据。

### 12.4 与方案的对应关系

本文档全部需求条目均可追溯至《物业巡检管理系统方案 v1.1》§三（功能设计）、§八（部署与运维）、§九（验收标准）及《UI-UX 设计方案 v1.0》的对应章节；方案§十"后续可扩展方向"所列内容不在本期需求范围内。
